# План расширения UI E2E

План включает реализованный набор и очередь новых кейсов. Волна планирования
содержит **10 Jira-кейсов**, рабочий блок — **1–2 теста**. Последняя волна
содержит один оставшийся кейс; число не добирается дублями.

Исходное состояние на 06.11.2026: коммит `5a2525b7`, **10 автотестов** —
9 Jira-кейсов и пилот без Jira-key. Далее запланирован 161 новый кандидат:
**16 волн по 10 и последняя из одного**. После их реализации — 170 связанных
Jira-кейсов плюс пилот; параметризация может изменить число исполняемых тестов.

## Как отмечать выполнение

Первая новая волна оформлена Change
[add-ui-e2e-data-integrity](../../../../openspec/changes/archive/2026-11-09-add-ui-e2e-data-integrity/proposal.md).
Её статусы ведутся только в [tasks.md](../../../../openspec/changes/archive/2026-11-09-add-ui-e2e-data-integrity/tasks.md). Все 10 кейсов реализованы и проверены. Для следующих волн Change создаётся перед началом работы.

- Открытый флажок — задача не завершена; выполненный — подтверждены её критерии.
- Блокер записывается под открытой задачей с причиной и требуемым решением.
- Кейс готов после всех согласованных assertions, целевых прогонов, очистки
  и относящегося к нему review. Волна готова после итоговых проверок.
- Реализованный этап 0 отмечен по фактическому коду/приёмке; подготовка документов
  будущей волны не считается автоматизацией кейса.

## Классификация и размер блоков

Раздел указан в имени кейса: PROJ-UI, PAL, CT, VER-UI, TYP-UI, COL-GRA или RSS.
Цель проверки: целостность данных, права, жизненный цикл, функции редактора,
восстановление после ошибки, конкурентность, журнал/версии или клавиатура/UI.

Smoke, критический и полный регресс — наборы запуска, а не волны внедрения.
Сейчас есть `@smoke`; новые метки не считаются внедрёнными этим планом.

Волна из 10 кейсов выполняется блоками по 1–2 теста. На знакомой странице с
готовой подготовкой допустимы 3. Новая роль, страница или тип сетевой гонки —
отдельный небольшой блок. Сценарии независимы и не используют результат
предыдущего теста. При блокере сначала разбирается причина.

## Правила реализации и проверки

- Перед авторингом исследовать актуальный UI через Playwright, задать точные
  исходные данные, маршруты, локаторы и признаки завершения сохранения.
- Проверяемые действия выполняются UI; публичный API готовит и очищает данные.
  Owner подготавливает ресурсы, браузер работает именно проверяемой ролью.
- Каждый тест получает свою ДС и известные ID. Общий E2E Automation и исходные
  системы сохраняются; очистка проектов/стенда — после набора по согласованной политике.
- Перед DELETE подтверждаются все начатые записи. Неизвестный исход запрещает
  повтор мутации и удаление по имени. Лимит кейса не увеличивается ради прохождения.
- Основной запуск — собранный UI на 4173, `workers=1`, `retries=0`.
  Страницы и fixtures добавляются под реальные сценарии.
- На малый блок: types/format, новые и затронутые сценарии, 3–5 успешных
  выполнений новых кейсов без retries с корректной очисткой. При изменении
  общего helper проверяются все его потребители.
- На завершение волны: один общий Product E2E-прогон, независимое review и
  Strictacode compare с неизменными policy/baseline. FAST/FULL — отдельный
  согласованный этап; отсутствующий обязательный gate остаётся открытым.
- Изменение смысла кейса сначала согласуется; задача планирования не меняет
  продукт, Jira, зависимости или существующие тесты.
