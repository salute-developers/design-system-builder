# Product UI E2E

## Запуск

Все команды выполняются из `js/apps/client`. На Windows PowerShell используйте
`npm.cmd`, на macOS — `npm`.

```sh
npm run test:e2e
npm run test:e2e:headed
npm run test:e2e:debug
npm run test:e2e -- version-journal.spec.ts
```

Эти команды один раз собирают Client обычной `npm run build` и обслуживают
готовый `dist` через локальный `vite preview` на `http://localhost:4173/`.
Playwright ожидает HTTP-готовности и завершает свой сервер после набора.
Порт4173 должен быть свободен: чужой сервер не переиспользуется, другой порт
автоматически не выбирается. Запуск сервера ограничен120s; UI-лимиты не меняются.
Docker Client на3002 и backend не останавливаются.

Повторить текущие 20 сценариев пять раз, всего 100 выполнений:

```sh
npm run test:e2e -- --repeat-each=5 --workers=1 --retries=0 --max-failures=0
```

`test:e2e:built` сохранён как совместимый алиас `test:e2e`. Внутренний флаг
`--built-ui` больше не используется. Для готового локального или удалённого UI:

```sh
npm run test:e2e:external
npm run test:e2e:external -- --headed
```

External-режим не собирает UI и не запускает сервер. Он использует
`DSB_E2E_CLIENT_BASE_URL`, по умолчанию `http://localhost:3002/`.
Для удалённого стенда задайте согласованные адреса Client/Gateway и clientId.

## Предусловия и настройки

Нужны Node.js22.16.0+, готовые Gateway/Keycloak и обычная тестовая учётная запись
без `system_admin`, которой разрешено создавать проекты. Для external-режима
должен работать и Client. Тесты не запускают Docker, миграции, seed и не создают
пользователя.

Установите зависимости и Chromium:

```sh
npm ci
npm run test:e2e:install-browser
```

После обновления ветки повторите `npm ci`, если изменился `package-lock.json`.
Ошибка сборки Client останавливает запуск до начала тестов; она также
показывается при отдельном `npm run build`.

Скопируйте `e2e.env.example` в `.env.e2e.local` рядом с package.json, заполните
`DSB_E2E_USERNAME`, `DSB_E2E_PASSWORD` и разрешите `DSB_E2E_ALLOW_MUTATIONS=true`.
Не перезаписывайте уже настроенный приватный файл. На macOS ограничьте его права
через `chmod 600 .env.e2e.local`. Файл исключён из Git; пример содержит пустые
credentials. Токены между запусками не сохраняются.

| Настройка | Поведение |
| --- | --- |
| `DSB_E2E_GATEWAY_BASE_URL` | Общий API для обоих режимов; default `http://localhost:8080/`. |
| `DSB_E2E_CLIENT_ID` | Общий OAuth clientId; default `dsbuilder-api`. |
| `DSB_E2E_CLIENT_BASE_URL` | Только external; default3002. Основной режим задаёт4173. |
| `DSB_E2E_CREDENTIALS_FILE` | Другой dotenv-профиль вместо стандартного файла. |
| `DSB_E2E_PROJECT_NAME` | Имя собственного выделенного проекта; default `E2E Automation`. |

Process env имеет приоритет над dotenv. Файл читается через `parseEnv`, без
source/eval. Ручной projectId не нужен. Remote требует HTTPS, loopback допускает
HTTP; отключение проверки TLS запрещено.

Для локального прогона через IPv4 в отдельном окне PowerShell:

```powershell
$env:DSB_E2E_GATEWAY_BASE_URL = 'http://127.0.0.1:8080/'
npm.cmd run test:e2e -- --workers=1 --retries=0
```

Эта переменная передаёт один адрес gateway браузеру и API-подготовке.

Сборка получает только публичные API URL/clientId и флаги. Палитра использует
реальный API, редактор компонентов по умолчанию включён, как на dev-стенде.
Явный process env `VITE_COMPONENT_EDITOR_ENABLED` может изменить флаг;
`VITE_COMPOSE_PREVIEW_PLUGIN_URL`/`VITE_WEB_PREVIEW_PLUGIN_URL` — адреса плагинов.
При отсутствии явных адресов плагины выбирает backend. Пароли/токены не
передаются в `VITE_*`. Браузерная сессия создаётся для origin выбранного Client;
Gateway должен разрешать этот origin через настоящий CORS.

Состав набора и типы доступны без credentials, сети, браузера, сборки и серверов:

```sh
npm run test:e2e -- --list
npm run test:e2e:external -- --list
npm run test:e2e:check
```

Compose Preview smoke и модульные тесты запускаются отдельно от Product E2E.

## Первая волна

В наборе 20 сценариев. Пользователь подтвердил 15 последовательных успешных
выполнений T560 после изменения ожидания редактора. Отчёт от 09.11.2026
подтверждает последующий общий прогон первых 16 сценариев без падений и retries.
Статус итоговой проверки волны ведётся в OpenSpec tasks.md.

Для цветов fixture готовит CT-BASE публичным API в своей ДС и Theme A:
точные определения text.default.accent/text.default.promo-minor, Light/Dark,
связанные OnDark/OnLight/Inverse и состояния active/hover на трёх платформах.
Подготовка использует текущие editRevision каждой пары и один PUT без повторов.
Для T791/T647 сначала публикуется0.1.0, затем отдельно меняется Web/Light textAccent;
поэтому целевая запись журнала однозначна и не смешана с подготовкой.

Подтверждённые локаторы индикатора: role=status с «Ожидает сохранения» или
«Сохраняется…» во время записи; «Последнее сохранение — …» после подтверждения.
В T78410s отсчитываются от подтверждения HEX до реального PUT200 и конечного
индикатора. Ожидание прекращается сразу при успехе. Лимит15s существующего
T768 сохраняется. Reload в новых кейсах — проверка сохранённых данных,
а не восстановление после ошибки загрузки.

T560 получает отдельные Theme A и Theme B с собственным CT-BASE. Переключение
тем выполняется через карточки ДС в UI; обе записи подтверждаются отдельно
по точным tenantId. После reload значения A/B сверяются в редакторе.
Только T560 использует `fixtures/theme-isolation.ts`: создание и заполнение обеих
тем выполняются в одном ограниченном API-бюджете120s, отдельно от UI90s.
Общие fixtures остальных сценариев, лимит сохранения10s и очистка не меняются.
120s — предел подготовки, а не фиксированная задержка. Целевой прогон пользователя
из `js/apps/client` (остановится на первом падении):

```powershell
npm.cmd run test:e2e -- --grep "PLASMABLDR-T560" --repeat-each=5 --workers=1 --retries=0 --max-failures=1
```

## Данные и очистка

После входа helper выбирает только собственный active-проект с точным именем,
`ownerUserId=sub` и `effectiveRole=owner`. При отсутствии создаёт один проект
публичным API. Неоднозначность, admin, чужой или архивный проект дают отказ.
Проект сохраняется между тестами и запусками.

Каждый тест, которому нужна ДС, получает отдельную систему. Общая fixture
`createdSystem` удаляет её после успешного сценария и предусмотренных кейсом
проверок сохранения. После ошибки, таймаута или пропуска ДС сохраняется,
а известный ID попадает в аннотацию `retained-design-system`. Перед DELETE
проверяются актуальный Owner, зарегистрированный новый ID, свой проект,
обычный тип и отсутствие ID в исходном baseline. После одного DELETE
проверяются GET404 и сохранность исходных систем. Переименование не мешает
очистке по ID. Темы и публикации очищаются вместе со своей ДС.

Неизвестный результат POST запрещает автоматическое удаление по имени.
Имя попытки и подтверждённые ID доступны в annotations. После принудительного
убийства процесса finally не гарантирован; остатки разбираются по известным ID.
Постоянного журнала/lock/recovery и отдельного bootstrap нет.

Один worker и retries0 — настройки текущего набора. Общий E2E-проект используйте
последовательно между процессами/машинами: workers1 не является глобальным mutex.
Для проверки новой роли Owner готовит/очищает данные, браузер должен войти
пользователем проверяемой роли.

## Ожидания и диагностика

Успех подтверждают реальные ответы и конечное состояние UI. Подмены CORS,
произвольных sleeps, networkidle или автоматического reload для восстановления
нет. Fixtures/Steps/PageObjects/Api helpers добавляются под конкретную потребность;
BasePage и дублирующих уровней-обёрток нет.

UI-тест ограничен90s, действие15s, навигация20s, обычный expect10s. Готовность
редактора T768 после создания/reload проверяется до30s. ColorEditorPage также
ждёт готовность редактора до30s в open/switchTheme/reload через отдельную константу
colorEditorReadyTimeoutMs; лимит действия15s и сохранения новых кейсов10s прежние.
При появлении элемента ожидание сразу заканчивается. Fixture ресурсов имеет
общий бюджет250s на setup+teardown, сессии30s на вход+logout. Это верхние пределы,
а не обязательные задержки.

Ответ UI-мутации по-прежнему должен прийти за15s. При ошибке действия/ответа
дожидаемся обоих Promise и сохраняем обе ошибки. `PendingMutation` отдельно
учитывает сетевые события Playwright и записи API-подготовки. Перед DELETE он
дожидается их полных ответов, закрывает тестовый контекст браузера и проверяет
записи, начавшиеся во время закрытия. Для всех этих шагов действует общий
бюджет 60 секунд. При позднем ответе тест остаётся failed. Если исход наблюдаемой
записи или закрытие контекста не подтверждены, очистка сохраняет ДС и сообщает её ID.
POST/PATCH/DELETE не повторяются автоматически.

Технические API-операции используют Node fetch без redirect. Только GET при
таймауте/сбросе соединения имеет до двух попыток по10s в общем бюджете20s,
включая тело. HTTP-ошибки, JSON/assertions, DNS/TLS и неизвестные сетевые ошибки
не повторяются. Эта политика не добавляет retries браузерным GET. Собственный
logout выполняется после каждого теста, его ошибка сохраняется.

При падении загрузки attachment `page-readiness` показывает этап, pathname,
status/alert и pending/failed API GET с длительностями. `[e2e:http]` сообщает
безопасный код/попытку технического GET. Credentials, query, headers и тела
ответов в эту диагностику не пишутся.

Отчёты обоих режимов: `playwright-report/product/` и
`test-results/product-report.json`; failure screenshot/trace —
`test-results/product/`. Сохраните их перед следующим запуском, включая `--list`.

```sh
npx playwright show-report playwright-report/product
```

Сбой assertions, предусловий или cleanup даёт ненулевой exit. Trace может
содержать сессию/заголовки: это приватный локальный материал вне Git, он
автоматически не публикуется.
