## Why

Документацию дизайна SDDS (описание компонентов, токенов, правил для дизайнеров) нужно публиковать в сервис
документации так же, как документацию Compose и SwiftUI: тогда портал, DS Builder и агенты находят её рядом с кодовой
документацией по тем же `subjects`. Сейчас `dsbuilder docs generate --platform design` только упаковывает уже готовое
дерево: инструмента платформы, который собрал бы это дерево из общей документации и отличий вертикали, для `design`
нет. Документация вертикалей различается незначительно, поэтому её нужно собирать тем же слиянием Core и
пользовательского слоя, что на iOS и Android, а не копировать целиком в каждую вертикаль.

## What Changes

- `dsbuilder docs generate --platform design` сам собирает дерево `.sdds/temp/docs` перед упаковкой: общая документация
  дизайна становится Core-слоем, документация вертикали — пользовательским слоем.
- Источники ищутся по положению рабочей директории в репозитории документации дизайна `sdds-design-docs`: общий слой —
  каталог `core/` ближайшего предка, слой вертикали — каталог `docs/` текущей вертикали. Оба пути можно задать явно
  опциями `--design-core` и `--design-layer`.
- Новая обязательная для `design` опция `--artifact-version`: версия репозитория документации, обычно его git-тег. Она
  записывается в `meta/platform-context.json` и становится версией публикации, как версия `plasma-ios` на iOS.
- Слияние слоёв выполняет существующий `MergeEngine`: `append`, `prepend`, `replace` и `hidden` поддерживаются без
  ограничений iOS.
- Картинки слоёв попадают в `assets/core/` и `assets/user/`, а относительные ссылки на них в markdown переписываются
  под расположение страниц в архиве, чтобы сервис их разрешил.
- Сборка останавливается с понятной ошибкой, если страница из `structure.json` не найдена, ссылка в markdown ведёт на
  отсутствующий файл или за пределы своего слоя, либо не задана версия.
- `docs publish` не меняется: архив `design` уже принимается сервисом.
- В `frontend-kt/cli/USAGE.md` описывается раскладка репозитория документации дизайна и запуск сборки для вертикали.

## Capabilities

### New Capabilities
- `design-docs-aggregation`: сборка дерева документации дизайна из общего слоя и слоя вертикали в `dsbuilder docs
  generate --platform design`: поиск источников, раскладка `content`, `assets` и структур, версия публикации и проверки.

### Modified Capabilities
- `cli-platform-delegates`: требование «Documentation platform step» — для платформы `design` шаг агрегации выполняет
  сам CLI, а не пропускается; `--docs-dir` и `--no-aggregate` по-прежнему отключают шаг.

## Impact

- `frontend-kt`: модуль `feature-docs` (новый агрегатор дизайна в `application` и `data`, выбор дерева в
  `DocsGenerationSource`, модель команды `DocsGenerateCommand`), модуль `cli` (опции `--design-core`, `--design-layer`,
  `--artifact-version` в `DocsGenerateCliCommand`, справка и `frontend-kt/cli/USAGE.md`). Новых зависимостей нет: используется
  `WorkspaceFileSystem`.
- `backend-kt`: без изменений. Сервис документации уже принимает платформу `design` и версию из манифеста.
- `js`: без изменений.
- Внешний репозиторий `salute-developers/sdds-design-docs`: стартовая раскладка `core/`, `verticals/<вертикаль>/` и CI
  публикации создаются отдельной задачей после реализации CLI.
- Конфигурация: у каждой вертикали свой `.sdds/config.json` с проектом и дизайн-системой, ключ API передаётся в CI как
  секрет, как для остальных платформ.
