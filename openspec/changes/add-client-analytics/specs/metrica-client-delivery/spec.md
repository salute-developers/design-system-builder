## ADDED Requirements

### Requirement: Отдельный адаптер Метрики

`frontend-kt/analytics-metrica` SHALL реализовывать `Analytics` из `core-analytics` и скрывать преобразование событий, визиты и Measurement Protocol. HTTP и локальное хранение SHALL предоставляться через интерфейсы. Отправка SHALL происходить напрямую в `https://mc.yandex.ru/collect` без backend DS Builder и без credentials DS Builder.

#### Scenario: Прямая отправка

- **WHEN** CLI или MCP регистрирует разрешённую операцию
- **THEN** адаптер MUST формировать POST Measurement Protocol для выбранного счётчика и токена
- **AND** запрос MUST NOT содержать `Authorization` DS Builder или OAuth-токен
- **AND** транспорт MUST NOT следовать перенаправлению на сторонний хост

### Requirement: Единая постоянная идентификация установки

Адаптер SHALL сохранять один постоянный числовой `cid` установки `dsbuilder`, общий для CLI и встроенного MCP, в пользовательском каталоге вне проекта и `.sdds`. Значение SHALL быть положительным случайным 63-битным целым, передаваемым десятичной строкой без преобразования через floating-point. Хранилище SHALL обеспечивать атомарное создание при параллельных процессах. ID SHALL NOT меняться при обновлении CLI, смене режима/проекта, входе/выходе из аккаунта или по истечении 21 дня.

#### Scenario: Повторный запуск в другом проекте

- **WHEN** пользователь повторно запускает CLI из другого рабочего каталога
- **THEN** CLI MUST использовать ранее сохранённый `cid`
- **AND** встроенный MCP MUST использовать тот же `cid`, несмотря на другой токен отправки

#### Scenario: Параллельное создание

- **WHEN** процессы CLI и встроенного MCP одновременно впервые запрашивают идентификатор установки
- **THEN** оба MUST получить одно сохранённое значение
- **AND** файл состояния MUST остаться корректным

#### Scenario: Недоступное состояние

- **WHEN** хранилище недоступно или повреждено
- **THEN** аналитика запуска MUST отключиться без ошибки основной команды
- **AND** MUST NOT генерировать новый временный `cid` для каждого события

### Requirement: Начальный просмотр и цели операций

Перед первым событием процесса и после 30 минут без операций в MCP адаптер SHALL отправлять технический `pageview`, затем цель `event` с `ea=<channel>_<operation>_<outcome>`. Имена SHALL строиться только из закрытого каталога с проверкой коллизий. Цели SHALL быть заранее созданы в счётчике.

#### Scenario: Первое событие без веб-визита

- **WHEN** адаптер отправляет первое событие нового самостоятельно созданного `cid`
- **THEN** транспорт MUST сначала получить `pageview` с `dl`, затем `event` с нужным `ea`
- **AND** при неуспешной отправке просмотра цель MUST NOT отправляться
- **AND** один `HTTP 200` MUST NOT считаться доказательством корректной записи в отчёты

#### Scenario: Длительный простой MCP

- **WHEN** зарегистрированный инструмент вызван после 30 минут отсутствия операций
- **THEN** перед его итоговой целью MUST быть отправлен новый технический просмотр
- **AND** процесс MUST NOT создавать просмотры по таймеру во время простоя

### Requirement: Разрешённый набор передаваемых данных

Адаптер SHALL передавать только счётчик, токен выбранного канала, числовой идентификатор, время, технический URL, фиксированное имя цели и параметры `client_type`, `client_version`, `os_family`, `schema_version`. Передача SHALL NOT включать аргументы, поисковые строки, содержимое проектов, реальные пути, backend URL, пользовательские идентификаторы, тексты ошибок или credentials. Первая версия SHALL NOT передавать `duration_ms` и `error_category` как параметры визита и SHALL NOT обещать отчёт по средней длительности.

#### Scenario: Команда содержит конфиденциальные аргументы

- **WHEN** разрешённая команда получает пути, секреты или название проекта
- **THEN** перехваченный тестовым транспортом запрос MUST содержать только разрешённые поля
- **AND** данные исходных аргументов MUST отсутствовать в URL, теле и диагностике

### Requirement: Доставка с ограниченными затратами

Очередь SHALL хранить не более 128 событий в памяти и отбрасывать новое событие при переполнении. Один запрос SHALL иметь тайм-аут не более 1 секунды, завершение CLI SHALL ждать не более 1500 мс. События старше 12 часов SHALL отбрасываться. Автоматические повторы неоднозначно завершившихся запросов, дисковая очередь и процесс доставки после выхода SHALL отсутствовать в первой версии.

#### Scenario: Переполнение и отсутствие сети

- **WHEN** сеть недоступна и очередь заполнена
- **THEN** новая регистрация MUST вернуться без ожидания сети
- **AND** размер очереди MUST NOT превысить 128 событий
- **AND** основная команда или MCP-вызов MUST сохранить свой результат

#### Scenario: Неясный результат отправки

- **WHEN** запрос завершается по тайм-ауту после возможной передачи данных
- **THEN** адаптер MUST NOT автоматически повторять его и обещать доставку ровно один раз

### Requirement: Встраивание конфигурации в CI

Сборка выпуска SHALL получать отдельный от веба счётчик через `DSBUILDER_METRICA_COUNTER_ID`, разные токены через `DSBUILDER_METRICA_CLI_TOKEN` и `DSBUILDER_METRICA_MCP_TOKEN`, технический адрес через `DSBUILDER_METRICA_BASE_URL`. Токены SHALL считаться извлекаемыми из артефакта. Реальные значения SHALL NOT попадать в Git, журналы и дочерние процессы. Изменение конфигурации SHALL обновлять генерируемый артефакт сборки.

#### Scenario: Неполная конфигурация выпуска

- **WHEN** выпуск с включённой аналитикой собирается без одного обязательного значения или с одинаковыми токенами каналов
- **THEN** сборка MUST завершиться понятной ошибкой без печати токенов

#### Scenario: Раздельные токены

- **WHEN** один бинарник выполняет обычную команду и отдельно запускается в режиме MCP
- **THEN** обычная команда MUST выбирать токен CLI, а вызов инструмента MUST выбирать токен MCP
- **AND** оба MUST использовать счётчик CLI/MCP
- **AND** оба MUST использовать один ID установки; разные токены MUST NOT порождать разные локальные идентичности

### Requirement: Подтверждение реальной идентификации

До признания реализации готовой к выпуску SHALL быть получены доказательства приёма нового самостоятельно созданного `cid` без веб-визита, общей идентичности CLI/MCP одной установки, повторного визита с тем же ID и отдельного посетителя для другого ID. Отсутствие доступа к тестовому счётчику SHALL NOT считаться успешной технической проверкой. Наблюдение возврата после перерыва более 21 дня SHALL быть отложено и SHALL NOT блокировать реализацию или архивирование; долгосрочная возвращаемость до его результата не гарантируется.

#### Scenario: Переключение на встроенный MCP

- **WHEN** тестовая установка отправляет CLI-цель и MCP-цель с разными токенами и одним `cid`
- **THEN** отчёт или Logs API MUST подтвердить одного посетителя и обе цели
- **AND** режимы MUST различаться именами целей, а не ID посетителя

#### Scenario: Повторный визит

- **WHEN** на тестовом счётчике после его тайм-аута повторно переданы просмотр и цель с тем же `cid`
- **THEN** отчёт или Logs API MUST подтвердить нового визита того же посетителя
- **AND** результат MUST быть сохранён без токенов

#### Scenario: Нет необходимых доказательств

- **WHEN** нет доступа к тестовому счётчику или не подтверждена техническая идентификация посетителей
- **THEN** внешняя проверка MUST оставаться невыполненной
- **AND** реализация MUST NOT объявляться готовой к выпуску

### Requirement: Известный риск распространения токена

Документация SHALL фиксировать неоднозначность условий распространения извлекаемого `ms` как принятый риск, а не как полученное разрешение поставщика. Ответ поддержки Яндекса SHALL NOT быть обязательным условием реализации, архивирования или выпуска.

#### Scenario: Поддержка не ответила

- **WHEN** обязательные технические проверки пройдены, но ответа поддержки о распространении `ms` нет
- **THEN** отсутствие ответа MUST NOT блокировать готовность к выпуску
- **AND** принятый риск MUST оставаться описанным в проектном решении
