## 7. Клиентская очередь первичного чтения

- [ ] 7.1 Исправить общий ограничитель `readEditor`: убрать обязательный интервал 125 мс между стартами независимых чтений, согласовать ограничение параллелизма и приоритет данных открытого раздела с gateway rate limit; сохранить дедупликацию, отмену и обработку 429/503. Проверить повторное чтение темы и обязательные зависимости оболочки. Узко проверить корректность очереди и повторить браузерный HAR-прогон на той же теме.

Основание: ручной парный прогон Chrome от 12.11.2026, Test Theme, 7 407 адресов значений и 1 335 токенов. При двух общих CPU → всех 18 CPU медианы HTTP `token-values` 87 → 74 мс, `palette` 69 → 47 мс, но навигация до последнего API-ответа 2,192 → 2,187 с. Первые четыре чтения отправляются вместе, остальные десять — с шагом около 125 мс; отправка всех запросов растянута на 1,24 с. Это время API-загрузки, не завершения отрисовки. Первая секунда до API требует полной записи ресурсов/Performance: имеющиеся HAR содержат только XHR. CPU-статистика не сохранилась; влияние VPS steal time этим экспериментом не доказано.

Пункт 5.1 остаётся открытым: парный CPU-прогон не заменяет итоговое сравнение сохранения, адресного отката с клиентским обновлением, связей и остальных целевых чтений с dev при одинаковых данных и ресурсах. FAST/FULL/review отложены до достижения результата оптимизаций; отдельные дублирующие задачи на них не добавляются.
