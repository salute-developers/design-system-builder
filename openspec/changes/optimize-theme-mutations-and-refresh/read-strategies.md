# Сравнение стратегий чтения

## Выбор актуальной ревизии

Изолированный PostgreSQL 17, реальная схема из `/tmp/theme-opt-fixture.dump`, 153 105 значений всего,
10 407 устойчивых адресов выбранной темы. Для каждой границы сравнивались LATERAL с LIMIT 1,
DISTINCT ON и max(version_sequence_number) с последующим соединением. Во всех вариантах сначала
ограничивались устойчивые адреса дизайн-системой и темой; deleted проверялся после выбора последней
ревизии. Для пакетных вариантов использовался материализованный набор адресов.

По 3 прогрева и 20 измерений EXPLAIN ANALYZE, порядок вариантов чередовался. Это время выполнения
PostgreSQL без HTTP и преобразования JSON. Эксперимент выполнялся административным соединением;
права и исторические HTTP-контракты проверены отдельно PostgreSQL-тестом приложения.

| Граница | Возвращено значений | LATERAL, мс | DISTINCT ON, мс | Группировка, мс |
| --- | ---: | ---: | ---: | ---: |
| 0 | 0 | 11,84 | 2,48 | 2,45 |
| 1 | 7 407 | 13,77 | 16,16 | 30,54 |
| 2 | 10 407 | 15,32 | 23,57 | 38,02 |
| 3 | 10 407 | 15,48 | 23,62 | 37,44 |

Число строк и контрольная сумма полного содержимого ревизий совпали для каждой границы.
Пакетные варианты медленнее на заполненных границах; production LATERAL не заменён.
Это сравнение конкретных форм запросов на данном наборе, а не доказательство превосходства LATERAL
для любой глубины истории. Исходные планы и повторы: `/tmp/theme-read-strategy-results.json`.

## Технические редакции

Отдельный JDBC-эксперимент включает подготовку SQL, параметры, выполнение, получение строк и создание
Map. Сравниваются исходный IN с полной строкой, IN с двумя колонками, UUID-массив и соединение
entity_edit_states с устойчивыми адресами темы. На каждой из четырёх границ проверено равенство Map;
для IN/массива дополнительно проверялись наборы из 1 и 36 адресов. По 3 прогрева и 20 измерений,
с чередованием порядка. Сценарий воспроизводится задачей queryPerformance с
`-PperformanceScenario=edit-revisions`; результат — CSV, а не обычный HTTP-отчёт.

Массив выигрыша не дал. На 10 407 адресах JOIN занимает около 0,42–0,43 мс при пустом наборе редакций
против 3,32–4,48 мс исходного IN; на заполненных границах результаты неоднозначны:
8,54 против 9,92 мс и 9,45 против 7,85 мс. Поэтому универсальная замена общего helper на массив или
JOIN не выполнена. В helper оставлена узкая проекция; для чтения всего раздела темы подключён JOIN
без передачи уже прочитанных UUID. Адресные чтения используют точный набор. Дополнительные редакции
удалённых или отфильтрованных значений не расширяют ответ: номера применяются только к уже
выбранным предметным строкам. Итог оценивается по HTTP, а не только по этому частному эксперименту.

Исходный CSV: `/tmp/theme-edit-revision-strategies-join.csv`. В первоначальном эксперименте JOIN
также включал создание неиспользуемой строки IN; в воспроизводящем helper эта лишняя работа убрана.

## Изменения транзакции и палитры

Данные значений и снимка читаются в одной транзакции. Индекс resolver и раскрытие ссылок выполняются
после её завершения. Unit-тест проверяет чтение внутри транзакции, раскрытие снаружи и сохранение
readContext, readPage и mutationMetadata. Второй тест проверяет отсутствие чтения палитры для
литеральных значений и сохранение платформенной формы градиента. PostgreSQL-тест
EditorSectionReads подтверждает равенство полных/адресных чтений, права и исторические границы.

FAST/FULL/review не выполнялись. Итоговое сравнение всего Change остаётся отдельным незакрытым пунктом.

## Узкое HTTP-сравнение после изменений

Одинаковый снимок, изолированный Netty на loopback, пул 4, по 3 запроса перед серией и 20 измерений.
Исходный код dev f09a229e находится в `/tmp/ds-theme-optimization-baseline`; бизнес-код там не менялся.
Серверная медиана берётся из существующего http_request; клиентская включает получение и разбор JSON.
Это последовательные локальные чтения без нагрузки, а не прогноз задержек dev и не проверка поведения пула
при конкуренции. Отдельные экспериментальные PostgreSQL остановлены перед HTTP-сравнением.
