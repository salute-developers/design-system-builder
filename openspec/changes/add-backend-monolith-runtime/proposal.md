# Монолитная сборка backend

## Зачем

Для запуска DS Builder сейчас требуются отдельные прикладные процессы и nginx. Единственным поддерживаемым вариантом развёртывания становится монолит: одно JVM-приложение и один прикладной Docker-сервис, сохраняющие публичный API и правила доступа существующего микросервисного варианта.

## Что меняется

- Добавляется отдельный Gradle-проект `backend-kt/app` — единая точка сборки и запуска модульного монолита без nginx.
- Из приложений auth-helper, projects, ds и documentation выделяются повторно используемые модули `runtime`; границы проектов, их бизнес-модули и исходные точки запуска сохраняются для будущего выделения сервисов, без обязательства поддерживать отдельный Docker-запуск каждого сервиса.
- Монолит воспроизводит публичные маршруты, проверку личности и прав, защиту доверенного контекста, ограничения запросов, CORS и проксирование Keycloak. Текущие конфигурации nginx сохраняются без изменений как справочный контракт и задел для будущей инфраструктуры, но в действующем Docker-контуре не используются.
- Межмодульные вызовы проходят через минимальные публичные прикладные интерфейсы: проверку доступа пользователя к проекту, проверку ключа проекта и проверку принадлежности/доступности дизайн-системы. Публичными становятся только необходимые интерфейсы и типы их входов/результатов; реализации и остальные классы остаются закрытыми. DI подключает адаптеры внутри процесса; существующие HTTP-адаптеры сохраняются как задел для будущего разделения, без отдельного поддерживаемого Docker-контура.
- Миграции, начальные данные, политика доступа и OpenAPI переиспользуются из единственного источника. При упаковке ресурсы получают уникальные пути.
- App получает настройки через env независимо от Compose. Общая политика доступа загружается один раз, зависимости подсистем изолируются в DI, повторные регистрации запрещены. Фоновая обработка документации имеет ограниченный параллелизм и использует существующую очередь в БД.
- Dockerfile монолита, локальный и production Compose, команды запуска и матрица сборки образов переводятся на единственный прикладной сервис. Переход с прежнего контура описывается однократно с сохранением данных; переключатель режимов не вводится.

## Возможности

### Новые возможности

- `backend-monolith-runtime`: единый процесс, публичная точка входа без nginx, выбор адаптеров, изоляция БД, безопасное переиспользование ресурсов и жизненный цикл модулей.

### Изменяемые возможности

- `container-image-delivery`: сборка и развёртывание монолита вместо отдельных прикладных образов и nginx, с сохранением правил публикации и внешней инфраструктуры.
- `design-system-service-runtime`: выделение повторно используемого `runtime`, подключаемого как отдельным приложением ds-service, так и монолитом, с сохранением слоёв и независимости бизнес-фич.

## Влияние

Затрагиваются Gradle-сборки и приложения `backend-kt/identity-gateway`, `projects-service`, `ds-service`, `documentation-service`, новый `backend-kt/app`, конфигурация запуска и документация. Существующий composite build сохраняется; зависимости между сборками получают однозначные координаты. Публичные DTO, бизнес-правила, SQL-схемы, содержимое и версии миграций не меняются. PostgreSQL-базы остаются раздельными; PostgreSQL, MinIO и Keycloak остаются отдельной инфраструктурой. Монолит не содержит `project-publisher` и не требует Docker socket.

`frontend-kt` и `js` не требуют изменений клиентского API: используется тот же публичный адрес и набор маршрутов. Клиенты участвуют во внешней проверке совместимости. Микросервисный Compose больше не поддерживается. CI подготавливается к сборке монолитного образа вместо отдельных прикладных образов и nginx; правила веток, тегов, авторизации и публикации сохраняются. Фактическая публикация и переключение production требуют отдельного запроса.

На текущем этапе создаются только OpenSpec-артефакты. Реализация начинается после явного согласования.
