## Зачем

Опубликованная ДС фиксирует настройки, но редактор и экспорт продолжают читать общий аддитивный каталог, а preview использует активную сборку платформы. Последующие импорты меты поэтому способны менять поведение исторической версии. Нужно закрепить API и preview за Core-релизом, сохранив существующие идентификаторы и историю настроек.

## Что изменится

- Добавляется неизменяемый Core-релиз `{libraryId, platform, version}` со снимком используемых редактором и экспортом описаний компонентов, свойств, состояний и платформенных параметров.
- Общий каталог остаётся аддитивным реестром устойчивых ID. Данные API в контексте ДС разрешаются через её Core, а не через текущие изменяемые поля каталога.
- Черновик автоматически переходит на новый Core с сохранением всех настроек и проверкой совместимости. Удаление сущностей, включая давно deprecated, не блокирует Core-релиз.
- Публикация фиксирует Core и preview-сборки в существующей границе версии. Поздняя сборка допускается только для того же Core и не заменяет уже закреплённую.
- Блокирующие конфликты запрещают публикацию и экспорт для генерации только затронутой ДС; предупреждения deprecated не блокируют. Проверка повторяется на сервере при публикации.
- В разделе публикации появляется сводка проблем с переходами к компонентам. В редакторе рядом со «Стилизацией» и «Структурой» появляется секция «Проблемы»: причины, оформление, вариации/сочетания, состояния и сохранённые значения, действия удаления и допустимого переноса.
- **BREAKING**: системные чтения больше не используют общий актуальный API или глобально активный preview; релизный импорт требует координаты и полный состав нормализованных сущностей. Контекст ДС остаётся селектором обычных запросов; обязательный coreReleaseId клиент не передаёт.

## Возможности

### Новые возможности

- `core-release-catalog`: неизменяемые описания релизов поверх аддитивного каталога.
- `core-compatibility-report`: единая проверка конфигурации, актуальность отчёта и блокирующие конфликты.
- `core-preview-binding`: привязка существующих preview-сборок к Core и границе ДС.
- `component-problems-ui`: сводка перед публикацией и секция «Проблемы» с исправлениями.

### Изменяемые возможности

- `component-api-meta-import`: транзакционный релизный импорт при сохранении устойчивых ID и административной политики.
- `design-system-version-history`: фиксация Core/preview, проверка перед публикацией и автоматический Core черновика.
- `component-editor-bundle-api`: согласованная релизная модель и доступ к несовместимым сохранённым настройкам.
- `component-editor-operations`: удаление недоступных в новом Core настроек и атомарный перенос.
- `design-system-request-scope`: разделение глобального каталога и релизных системных чтений.
- `cli-components`: экспорт и происхождение данных для генерации в выбранном Core.
- `web-preview-plugin-selection`: выбор и кеш плагина по контексту ДС.
- `compose-preview-plugin-loading`: выбор Compose-плагина по контексту ДС при сохранении локального режима разработки.
- `web-preview-plugin-publication`: регистрация сборки в Core-релизе и выдача адреса в системном контексте.

## Влияние

- `backend-kt/ds-service`: feature-components, feature-design-systems и core — релизы, связи, проверка, исправления, репозитории, миграции Flyway, OpenAPI и route manifest. Переиспользуются предметные редакции, согласование правок и существующий реестр preview с libraryVersion/metaSha256/buildId; второго реестра нет.
- `identity-gateway`: системные маршруты отчёта и preview с существующими правами. Новые микросервисы, инфраструктура или отдельная активация Core не вводятся.
- `frontend-kt`: общий контекст чтения, fetch/export, проверка перед генерацией, импорт меты и публикация preview; CLI/MCP используют те же общие сценарии без зависимостей между feature-модулями.
- `js/apps/client`: системные API, ключи кеша, выбор preview, сводка публикации и секция «Проблемы». `js/cli`: передача координат релиза при импорте/публикации с сохранением формата массива React-меты и конфигурации генератора. Согласуется активный `host-compose-preview-plugin`: доступ к редактору не зависит от наличия preview.
- `plasma-android`: отдельный Change производителя меты/manifest с теми же координатами и контрольными суммами; Compose — первая реальная проверка. Файлы другого репозитория этим Change не изменяются.
- `separate-core-documentation-sources` зависит от этого Change и использует готовые Core-контекст, исходную мету и правила фиксации. Markdown, code binding и вкладка документации здесь не реализуются. Полное отражение всех методов платформенного API не является целью.

## Проверка и границы

Реализация начинается только после утверждения артефактов. Нужны проверки изоляции исторического чтения/экспорта/preview, удаления и deprecated, сложных сочетаний, конкурентной смены Core и исправлений. Реальная проверка Compose/PostgreSQL/S3 обязательна до архивирования. Исторический Core при миграции назначается только по доказуемым артефактам; недоказуемая история не объявляется восстановленной.
