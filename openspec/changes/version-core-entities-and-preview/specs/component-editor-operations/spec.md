## ADDED Requirements

### Requirement: Удаление несовместимого назначения

Операция MUST удалять сохранённое назначение по valueKind/valueId с проверкой прав, принадлежности, ожидаемой редакции и существующим согласованием правок. Отсутствие свойства/состояния в новом Core MUST NOT запрещать удаление. Общие сущности и опубликованные настройки MUST сохраняться.

#### Scenario: Удалённое свойство

- **WHEN** редактор удаляет конфликтное значение
- **THEN** сервер MUST удалить значение с его ссылками/поправками через существующие редакции и журнал

#### Scenario: Старая редакция

- **WHEN** значение уже изменено другим участником
- **THEN** операция MUST вернуть конфликт без удаления новой записи

### Requirement: Атомарный перенос несовместимого назначения

Перенос MUST явно выбирать целевое свойство текущего Core и проверять тип, токен, состояния, область и вложенную ссылку. Создание назначения и удаление источника MUST быть атомарными; занятое назначение MUST NOT перезаписываться молча. В первой реализации отдельные платформенные поправки источника MUST запрещать перенос с объяснением: ни смещения/шаблоны, ни их старые platformParamId MUST NOT теряться или копироваться в другое свойство. Наличие поправок MUST проверяться атомарно с операцией.

#### Scenario: Допустимая замена

- **WHEN** цель совместима и свободна, источник не содержит отдельных платформенных поправок
- **THEN** сервер MUST сохранить область/состояния/значение в цели и удалить источник одной операцией

#### Scenario: Цель занята

- **WHEN** в целевой ячейке есть значение
- **THEN** сервер MUST вернуть конфликт, сохранив обе исходные настройки

#### Scenario: Нельзя перенести

- **WHEN** тип или состояние цели не поддерживает значение
- **THEN** сервер MUST отклонить перенос без изменений и вернуть объяснение

#### Scenario: Назначение с платформенными поправками

- **WHEN** источник содержит отдельное платформенное смещение или template
- **THEN** сервер MUST отклонить перенос с понятной причиной, сохранив значение, все поправки, их ревизии и цель без изменений
- **THEN** UI MUST объяснить необходимость ручного исправления

### Requirement: Обычная запись по текущему Core

Создание и изменение значения MUST проверять тип, токен, компонентные состояния, платформенные параметры и известные ограничения вложенных ссылок по текущему Core черновика, а общие состояния — по системному набору. Сохранённый тип общего каталога MUST NOT подменять тип Core. Проверка и запись MUST использовать согласованный контекст при конкурентной смене выбора Core данной ДС с проверкой coreSelectionRevision. Посторонние конфликты ДС MUST NOT запрещать допустимое исправление отдельного назначения.

#### Scenario: Новый тип после выбора версии

- **WHEN** пользователь выбрал Core B, который изменил тип свойства с color на typography, а общий каталог сохранил color
- **THEN** обычная запись совместимого typography-значения MUST проходить; новое несовместимое color-значение MUST отклоняться без изменения данных

#### Scenario: Core сменился после открытия редактора

- **WHEN** редактор прочитал A, а другая сессия выбрала B и изменила coreSelectionRevision
- **THEN** сервер MUST вернуть 409 CORE_SELECTION_STALE без изменений; после обновления контекста новая явная запись MUST проверяться по B

#### Scenario: Исправление при других конфликтах

- **WHEN** пользователь сохраняет допустимое значение, а другая настройка ДС всё ещё конфликтует
- **THEN** запись MUST разрешаться при соблюдении прав и revision

### Requirement: Восстановление незавершённой правки после смены Core
Клиент SHALL останавливать автоматическую отправку сохранённой правки с прежней
или неизвестной ревизией Core. Он SHALL предоставлять сохранение полной локальной
копии и продолжение с перечитанной серверной моделью. Скопированная правка SHALL
NOT становиться predecessor следующей новой операции.

#### Scenario: Старая или неизвестная ревизия
- **WHEN** при открытии компонента найдена правка с несовпадающей или отсутствующей ревизией Core
- **THEN** пользователь видит правку и действие продолжения с серверной версией
- **AND** после сохранения копии новые изменения используют текущую ревизию Core

#### Scenario: Core изменился на сервере
- **WHEN** команда получает CORE_SELECTION_STALE
- **THEN** редактор предлагает то же явное восстановление, сохраняя полную незавершённую цепочку

#### Scenario: Копию нельзя записать
- **WHEN** браузер не смог сохранить копию
- **THEN** редактор остаётся в восстановлении и исходная правка остаётся доступной для повтора

#### Scenario: Смена пользователя
- **WHEN** пользователь меняется во время незавершённой отправки
- **THEN** старая очередь отменяется до следующей команды без изменения хранения токенов
