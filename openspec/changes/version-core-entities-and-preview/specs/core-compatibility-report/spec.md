## ADDED Requirements

### Requirement: Единая проверка сохранённых настроек

Сервер MUST проверять сохранённые настройки активных компонентов выбранной границы до фильтрации по Core: компоненты, свойства, состояния, платформенные параметры, доказуемую совместимость типов/токенов и вложенных ссылок. Общие состояния MUST проверяться по предустановленному системному набору независимо от меты Core; состояния конкретного компонента MUST проверяться по выбранному релизу. Отсутствие используемой сущности в соответствующем источнике MUST быть конфликтом; deprecated само по себе MUST быть предупреждением. Этот отчёт MUST NOT обещать диагностику удалённых иконок или закрепление загрузок внешнего каталога иконок: они вне области проверки Core.

#### Scenario: Удалённое свойство

- **WHEN** черновик явно выбрал B, где нет свойства с сохранённым значением
- **THEN** отчёт MUST содержать блокирующую проблему с этим значением, не удаляя его

#### Scenario: Предупреждение

- **WHEN** используемое свойство только deprecated
- **THEN** отчёт MUST вернуть предупреждение без блокировки

#### Scenario: Свойство с новым типом

- **WHEN** сохранённый токен не подходит новому типу
- **THEN** сервер MUST вернуть конфликт; при доказанной совместимости MUST NOT блокировать только из-за смены типа

#### Scenario: Неизвестное ограничение

- **WHEN** нормализованная мета не задаёт допустимые enum значения
- **THEN** сервер MUST NOT объявлять недоказуемый enum-конфликт

### Requirement: Полный адрес проблемы и старое значение

DTO проблемы MUST содержать issueId/code/severity, компонент, оформление при наличии, свойство, вид и ID назначения, стили/подписи осей и значений, состояния, сохранённый литерал/токен/поправки/вложенную ссылку, revision и разрешённые действия. Отдельные платформенные поправки MUST включать их ID/revision, platformParamId, смещение и template, а не заменяться скалярным adjustment. Описание прошлого Core MUST включаться только при доказуемом происхождении.

#### Scenario: Сочетание

- **WHEN** неподдерживаемое свойство задано для Size=L и View=Primary в hovered
- **THEN** DTO MUST однозначно показать сочетание, состояние и сохранённое значение

#### Scenario: Инвариант

- **WHEN** конфликт относится к базовому значению
- **THEN** DTO MUST явно обозначить базовую область без выдуманной вариации

#### Scenario: Ссылка на токен

- **WHEN** назначение хранит tokenId
- **THEN** DTO MUST сохранить ID/доступное имя токена и поправки без обещания вычисленного значения до смены Core

### Requirement: Актуальность общего отчёта

Отчёт MUST иметь контекст границы, draftRevision, coreSelectionRevision, Core-релизы с каналами и версию проверки, общие blockingCount/warningCount и постраничные items. Фильтр componentId MUST возвращать те же проблемы, что сводка ДС. Устаревшие отчёты MUST NOT разрешать публикацию.

#### Scenario: Проблемы по компоненту

- **WHEN** одна проблема показана в сводке и секции компонента
- **THEN** issueId и причина MUST совпадать

#### Scenario: Пагинация

- **WHEN** возвращена первая страница
- **THEN** blockingCount MUST учитывать весь отчёт, не только страницу

#### Scenario: Core изменился

- **WHEN** draftRevision тот же, но пользователь сменил выбор A на B и coreSelectionRevision изменилась
- **THEN** кеш MUST быть инвалидирован, а проверка публикации MUST использовать B

### Requirement: Блокировка только несовместимой ДС

Публикация и получение нового экспорта для генерации MUST отклоняться при блокирующих конфликтах Core выбранной версии или черновика. Этот отказ MUST NOT запрещать локальную генерацию из ранее сохранённого снимка или требовать его обновления. Проверка публикации MUST быть согласована с фиксацией Core. Отсутствие preview и одни предупреждения MUST NOT блокировать конфигурационную публикацию; прочие существующие проверки сохраняются.

#### Scenario: Обход UI

- **WHEN** клиент напрямую публикует конфликтный черновик
- **THEN** сервер MUST вернуть 409 CORE_COMPATIBILITY_CONFLICT без новой версии или черновика

#### Scenario: Проверен A, выбирается B

- **WHEN** смена выбора Core и публикация выполняются одновременно
- **THEN** публикация MUST проверить и закрепить один согласованный набор Core; устаревшая coreSelectionRevision MUST отклоняться

#### Scenario: Нет preview

- **WHEN** конфликтов конфигурации нет, совместимая сборка ещё не загружена
- **THEN** публикация MUST разрешаться при соблюдении остальных проверок

#### Scenario: Экспорт

- **WHEN** CLI запрашивает экспорт конфликтного черновика
- **THEN** сервер MUST вернуть структурированную ошибку вместо частичного конфига

### Requirement: Различение общих и компонентных состояний

Проверка MUST NOT считать отсутствие системного состояния в мета-файле удалением из Core.

#### Scenario: Системное состояние сохранено

- **WHEN** значение использует предустановленное hovered, которого нет в мете B
- **THEN** checker MUST разрешить это состояние по системному набору

#### Scenario: Удалено компонентное состояние

- **WHEN** состояние конкретного компонента присутствовало в A, отсутствует в B и используется настройкой
- **THEN** checker MUST вернуть блокирующую проблему без удаления настройки

### Requirement: Область проверки скрытых компонентов

Собственные настройки компонентов со скрытой связью MUST сохраняться и MUST NOT блокировать публикацию/экспорт, поскольку не входят в выгрузку. Отчёт и его counts MUST учитывать эту область одинаково. Ссылки из активных компонентов MUST проверяться независимо от скрытия цели. Восстановление связи MUST сохранять настройки и возвращать их в область проверки без автоматической публикации или удаления данных.

#### Scenario: Скрытие несовместимого компонента

- **WHEN** компонент с конфликтным свойством скрыт и активные компоненты на него не ссылаются
- **THEN** его собственные настройки MUST исчезнуть из блокирующего отчёта и counts; экспорт MUST исключить компонент, сохранив настройки

#### Scenario: Восстановление связи

- **WHEN** скрытый компонент восстановлен с сохранённой несовместимой настройкой
- **THEN** связь MUST восстановиться, а публикация/экспорт MUST блокироваться до исправления настройки

#### Scenario: Активная ссылка на скрытую цель

- **WHEN** активное назначение ссылается на оформление скрытого компонента, недоступное в экспортируемом составе
- **THEN** отчёт MUST содержать блокирующую проблему активного назначения; скрытие цели MUST NOT обходить проверку

### Requirement: Отчёт без серверного кеша

Сервер MUST вычислять отчёт для каждого запроса страницы без обязательного серверного кеша. Порядок проблем MUST быть детерминирован, курсор MUST учитывать границу, draftRevision/coreSelectionRevision, Core, validatorVersion и фильтры. Разные экземпляры сервера MUST обслуживать страницы одинаково при неизменном контексте; устаревший курсор MUST давать 409 CORE_CONTEXT_STALE.

#### Scenario: Следующая страница на другом экземпляре

- **WHEN** вторую страницу неизменившегося отчёта обслуживает другой экземпляр сервера
- **THEN** он MUST продолжить тот же порядок без пропусков/повторов и сохранить counts без обращения к кешу первого экземпляра

#### Scenario: Настройки изменились между страницами

- **WHEN** следующая страница передаёт курсор отчёта до изменения предметной или Core-ревизии
- **THEN** сервер MUST вернуть 409 CORE_CONTEXT_STALE вместо смешанной страницы

### Requirement: Согласованный порядок блокировок одной ДС

Смена Core, запись/исправление и публикация MUST соблюдать единый порядок: блокировка редактирования/публикации ДС, строка активного черновика, привязки по platform, предметные строки по ID. Проверка публикации и фиксация MUST выполняться в одной согласованной транзакции. Импорт MUST NOT захватывать блокировки редактирования ДС или менять её выбор. Время полной проверки и ожидания параллельного сохранения MUST быть измерено на большой ДС до выпуска.

#### Scenario: Одновременные операции

- **WHEN** смена выбора, сохранение значения и публикация выполняются конкурентно для одной ДС
- **THEN** операции MUST завершаться согласованно либо отказом по устаревшей ревизии без взаимной блокировки из-за разного порядка захвата
- **AND** другая ДС MUST NOT ожидать их блокировку из-за общего указателя Core

### Requirement: Пакетное чтение назначений для проверки

Проверка MUST читать модели оформлений и справочники пакетно в том же согласованном контексте ДС/версии/Core, без повторного SQL-чтения общих данных для каждого оформления или вложенной ссылки. Оптимизация MUST сохранять состав проблем, точные значения, scope, issueId, ревизии, глобальные counts при componentId и историческую изоляцию; серверный кеш MUST NOT подменять повторную проверку актуального состояния.

#### Scenario: Растёт количество оформлений
- **WHEN** число оформлений увеличивается при тех же видах назначений
- **THEN** число SQL-обращений MUST оставаться ограниченным пакетными чтениями, а отчёт MUST содержать все соответствующие назначения

### Requirement: Линейная проверка и разрешение выбранного Core

Проверка устаревания MUST использовать индекс свойств из платформенных параметров текущего отчёта, без полного перебора параметров для каждого назначения. SQL-проекции MUST разрешать выбранный Core на уровне релиза, сохраняя проверку платформы сущности, глобальные нескоупированные чтения, общие состояния и диагностику отсутствующих компонентов. Оптимизация MUST NOT менять права, формат ответа, выбор Core или вводить постоянный кеш.

#### Scenario: Эквивалентность ускорения
- **WHEN** один и тот же снимок проверяется до и после оптимизации
- **THEN** MUST совпадать все проблемы, ревизии, значения и счётчики, а повторные замеры MUST фиксировать реальное время полного запроса

### Requirement: Подробности отчёта только для проблемных назначений

Проверка MUST охватывать все сохранённые назначения, но MAY отложить чтение отображаемых подробностей до нахождения проблем. Подробности MUST загружаться пакетно в той же границе ДС/версии/Core и сохранять исходные значения, имена токенов, состояния, сочетания и ревизии. Отчёт без проблем MUST NOT читать ненужные подробности. Обычная модель редактора MUST оставаться полной.

#### Scenario: Проблем нет
- **WHEN** все назначения совместимы с выбранным Core
- **THEN** MUST возвращаться прежний корректный пустой отчёт без дополнительной загрузки редакторских подробностей

#### Scenario: Есть проблемы
- **WHEN** найдены несовместимые либо устаревшие назначения
- **THEN** MUST возвращаться тот же полный отчёт, включая историю и исходные данные, без запросов по одному оформлению
