## MODIFIED Requirements

### Requirement: Публикация фиксирует текущий черновик

Публикация MUST дополнительно проверять совместимость и в той же согласованной операции закреплять Core-релизы платформ и preview по правилам core-preview-binding. Предметные редакции, sequenceNumber, права и согласование draftRevision сохраняются.

`POST /api/design-systems/{designSystemId}/versions` SHALL атомарно переводить активный черновик в опубликованную версию и создавать
следующий пустой черновик без копирования неизменившихся предметных данных.

#### Scenario: Черновик успешно опубликован

- **WHEN** уполномоченный пользователь передаёт `designSystemId`, актуальные `draftId` и `draftRevision`, уникальный
  номер `major.minor.patch` и `changelog`
- **THEN** API MUST изменить статус указанного черновика на `PUBLISHED`
- **THEN** API MUST назначить номер версии и время публикации на сервере
- **THEN** API MUST создать новый `DRAFT` со следующим `sequenceNumber`
- **THEN** API MUST NOT копировать предметные редакции опубликованного черновика в новый черновик

#### Scenario: Клиент пытается передать серверные поля публикации

- **WHEN** запрос публикации содержит `snapshot`, `changesSnapshot`, `publicationStatus` или `publishedAt`
- **THEN** API MUST отклонить запрос как не соответствующий контракту

#### Scenario: Черновик не содержит изменений

- **WHEN** вычисляемый журнал активного черновика пуст
- **THEN** API MUST отклонить публикацию без создания новой версии

#### Scenario: Черновик изменился после просмотра журнала

- **WHEN** переданные `draftId` или `draftRevision` не совпадают с заблокированным активным черновиком
- **THEN** API MUST вернуть `409 Conflict` с кодом `DRAFT_STALE` и актуальными `draftId` и `draftRevision`
- **THEN** API MUST NOT публиковать черновик или создавать следующую версию
- **THEN** клиент MUST обновить журнал и данные черновика без автоматического повторения публикации
- **THEN** повторная явная публикация MUST использовать новый ключ повторяемости

#### Scenario: Запись пришла во время публикации

- **WHEN** предметная запись получает блокировку черновика после начала публикации
- **THEN** она MUST продолжить выполнение в новом активном черновике
- **THEN** она MUST NOT изменить уже опубликованную версию

#### Scenario: После серверной версии запускается временная публикация npm-пакета

- **WHEN** веб-клиент публикует дизайн-систему через новый серверный черновик
- **THEN** клиент MUST сначала успешно создать версию через `POST /api/design-systems/{designSystemId}/versions`
- **THEN** только после этого клиент MUST вызвать существующую внешнюю публикацию npm-пакета
- **THEN** ошибка внешней публикации MUST NOT откатывать созданную серверную версию
- **THEN** клиент MUST показать, что версия создана, но внешний пакет не опубликован

#### Scenario: Конфликт Core

- **WHEN** черновик содержит несовместимые настройки
- **THEN** API MUST вернуть CORE_COMPATIBILITY_CONFLICT без изменения границ

#### Scenario: Изоляция Core

- **WHEN** V1 закреплена на A и затем импортирован B
- **THEN** V1 MUST сохранять A и свой preview; новый черновик MUST разрешать B

#### Scenario: Core обновился при пустом журнале

- **WHEN** импортирован B, но предметный журнал черновика по-прежнему пуст
- **THEN** импорт MUST NOT создавать версию ДС или изменение журнала
- **THEN** отдельный запрос публикации MUST быть отклонён без новой версии или следующего черновика
