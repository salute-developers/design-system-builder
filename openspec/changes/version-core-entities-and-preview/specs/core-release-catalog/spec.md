## ADDED Requirements

### Requirement: Неизменяемый API Core-релиза

Система MUST хранить релиз по libraryId/platform/version с исходной метой и SHA-256, составом компонентов/свойств/компонентных состояний/платформенных параметров и их используемыми характеристиками. Общие ID MUST сохраняться; чтение ДС MUST NOT брать изменяемое описание API из общего каталога.

#### Scenario: Новый релиз

- **WHEN** в B добавлен параметр и изменён deprecated существующего имени
- **THEN** API ДС на A MUST сохранить прежний состав и deprecated

#### Scenario: Повтор

- **WHEN** импорт повторяет координаты A
- **THEN** одинаковая мета MUST дать идемпотентный результат; другая MUST дать 409 CORE_RELEASE_IMMUTABLE

#### Scenario: Смена типа

- **WHEN** известное свойство получило другой поддерживаемый тип в B
- **THEN** система MUST сохранить типы A и B раздельно, не переписывая исторические данные

### Requirement: Удаление из Core сохраняет идентичность и данные

Импорт MUST разрешать отсутствие ранее существовавших сущностей, включая deprecated, без блокировки Core-релиза. Общие записи и настройки ДС MUST сохраняться. Состав нового релиза MUST строиться из его меты, не из накопленного каталога.

#### Scenario: Удалено deprecated свойство

- **WHEN** в B отсутствует свойство A
- **THEN** B MUST успешно импортироваться; ID и значения свойства A MUST остаться

#### Scenario: Удаление не используется

- **WHEN** ДС не содержит настроек удалённого свойства
- **THEN** это отсутствие MUST NOT создавать блокирующую проблему

#### Scenario: Пустой состав

- **WHEN** передана корректная мета релиза с пустым составом
- **THEN** импорт MUST сохранить пустой релиз без физического удаления каталога

### Requirement: Импорт пополняет канал и обновляет только явно выбранный latest

Каждый новый Core-релиз MUST иметь явный неизменяемый channel stable/dev. Канал MUST NOT выводиться из номера версии, окружения или типа ДС. Координаты libraryId/platform/version MUST оставаться уникальными независимо от канала; повтор с другим каналом MUST давать 409 CORE_RELEASE_IMMUTABLE. Для stable-поставки ранее проверенного dev-состава MUST создаваться отдельный стабильный релиз с его версией.

#### Scenario: Импорт B

- **WHEN** две обычные ДС закрепили A в режиме pinned и импортируется B в dev или stable
- **THEN** B MUST появиться в списке версий своего канала/платформы
- **AND** выбранные Core, модели, preview и отчёты обеих ДС с pinned MUST остаться на A до явного изменения настройки

#### Scenario: Повтор A

- **WHEN** после B повторён идентичный импорт уже известного A
- **THEN** импорт MUST быть идемпотентным и MUST NOT менять привязки ДС

#### Scenario: Изменение канала существующего релиза

- **WHEN** те же координаты и байты повторены с channel=stable вместо зарегистрированного dev
- **THEN** сервер MUST отклонить запрос без изменения канала, релиза и настроек ДС

#### Scenario: Неполный набор артефактов

- **WHEN** мета B загружена, preview и Markdown ещё нет
- **THEN** B MUST быть доступен для явного выбора без ожидания этих артефактов

### Requirement: Разделение Core и публикации ДС

Импорт Core MUST оставаться техническим пополнением каталога. Импорт и явный выбор Core в настройках MUST NOT создавать версию ДС, следующий черновик, предметную запись журнала, менять draftRevision или запускать публикацию пакета. Смена выбора MUST изменять отдельную coreSelectionRevision; опубликованные версии MUST сохранять закреплённый Core. Пустой предметный журнал MUST по-прежнему блокировать публикацию даже после смены выбора.

#### Scenario: Только импорт Core

- **WHEN** успешно импортирован B при существующей опубликованной V1 и черновике с pinned на A
- **THEN** количество и статусы версий ДС, draftId/draftRevision/coreSelectionRevision, предметный журнал и выбор A MUST остаться прежними

#### Scenario: Только выбор Core

- **WHEN** пользователь явно выбирает B для платформы черновика с пустым журналом
- **THEN** выбор и coreSelectionRevision MUST измениться без изменения предметных настроек, draftRevision и журнала
- **AND** отдельная публикация MUST быть отклонена из-за пустого журнала

### Requirement: Системные состояния и вложенность Core

Общие состояния взаимодействия MUST оставаться предустановленным системным набором вне меты и состава Core. Компонентные состояния и представленная метой вложенность MUST разрешаться из Core. Настройки ДС MUST NOT изменять вложенность, но MUST сохранять выбор оформлений/стилей вложенных свойств в предметных редакциях. Технические REUSE-связи MUST NOT расширять Core. Неописанные метой ограничения MUST NOT выдумываться.

#### Scenario: Общее состояние отсутствует в мете

- **WHEN** в настройке используется системное hovered, отсутствующее в мете релиза
- **THEN** это отсутствие MUST NOT считаться удалением состояния или блокирующим конфликтом

#### Scenario: Выбор оформления после импорта

- **WHEN** после импорта A пользователь меняет оформление предусмотренного Core вложенного свойства
- **THEN** назначение MUST сохраняться в границе ДС без изменения проекции A; опубликованная граница MUST сохранять своё прежнее назначение

#### Scenario: Вложенность изменилась в B

- **WHEN** мета B изменяет известную вложенность Core
- **THEN** модель V1 на A MUST сохранить прежнюю вложенность, а черновик, явно выбравший B, MUST проверять назначения по известным ограничениям B

### Requirement: Защита импортной идентичности

После включения сущности в Core административные операции MUST NOT менять её импортный ключ: имя/платформу компонента, имя и принадлежность свойства. Изменение отображаемого описания MUST NOT менять сопоставление при последующих импортах. Переименование в исходном API MUST трактоваться как исчезновение старой сущности и появление новой без автоматического переноса настроек.

#### Scenario: Ручное изменение ключа

- **WHEN** административный запрос пытается переименовать компонент, уже включённый в Core
- **THEN** операция MUST быть отклонена без изменения ключа; последующий импорт прежнего имени MUST сохранить ID

### Requirement: Технический снимок старых границ без восстановления истории

Миграция MUST закрепить технический снимок каталога за старыми опубликованными и архивными версиями без сохранённой привязки Core. Она MUST сохранять существующие ID, настройки, снимки настроек и известные привязки. Технический снимок MUST иметь неизвестное историческое происхождение и MUST NOT объявляться stable/dev по предположению. Миграция MUST NOT читать S3 или восстанавливать исторический Core по внешним артефактам. Неподтверждённый исторический preview MUST быть недоступен.

#### Scenario: Архивная версия со снимком настроек

- **WHEN** старая архивная версия имеет снимок настроек, но не содержит доказанной привязки Core
- **THEN** миграция MUST сохранить снимок настроек и закрепить технический Core с отметкой неизвестного исторического происхождения
- **AND** последующие импорты MUST NOT менять эту привязку или подставлять preview другого релиза

#### Scenario: Первый настоящий релиз меньше каталога

- **WHEN** существующие ДС используют технический снимок с накопленными сущностями, а первый импортированный релиз их не содержит
- **THEN** импорт MUST сохранить выбор и доступность ранее работавшего экспорта/публикации этих ДС
- **AND** несовместимость MUST проверяться для ДС, которая явно выбрала новый релиз; массовый отчёт влияния при импорте MUST NOT быть условием регистрации

#### Scenario: Известная привязка уже существует

- **WHEN** до миграции версия ДС уже закреплена за конкретным Core
- **THEN** миграция MUST сохранить эту привязку без замены техническим снимком
