# ИИ-чат в билдере

## Зачем

Сейчас дизайн-систему можно менять только вручную в редакторах билдера или через свой агент, подключённый к MCP. Чтобы подключить агента, нужно установить CLI, войти через PKCE и настроить клиент. Встроенный чат даёт ту же возможность прямо в интерфейсе: пользователь пишет «перекрась кнопку в красный», а изменение появляется в черновике. Инструменты редактирования в MCP уже есть (изменение `add-mcp-design-system-editor`), поэтому чат строится поверх них и не требует второй реализации операций.

## Что изменится

- В монолите `backend-kt/app` появится подсистема ИИ-ассистента с маршрутами `/api/projects/{projectId}/ai/chat` и `/ai/status`. Подсистема запускает цикл агента: отправляет модели запрос и описания инструментов, выполняет запрошенные инструменты и возвращает ответ.
- Реестр инструментов берётся из `DsBuilderMcpServerCore` (`frontend-kt/mcp-server-core`): методы `tools()` и `callTool()` вызываются внутри процесса, без транспорта MCP. Инструменты обращаются к публичному API того же процесса через `127.0.0.1` от имени пользователя, токен которого пришёл в запросе чата. Для этого в требование монолита «Независимость поведения от транспорта» вводится узкое исключение.
- Появится слой `LlmClient`, не зависящий от провайдера, с собственной моделью сообщений. В нём два адаптера:
  - `OpenAiCompatibleClient` — для провайдеров с API формата OpenAI (ZAI и другие); провайдер выбирается настройками, по умолчанию ZAI `glm-4.5-flash`;
  - `GigaChatClient` — OAuth, формат `functions`/`function_call`, один вызов инструмента за ответ.
- Модели доступен отобранный набор из 23 инструментов. Каждый передаётся, только если серверный `PolicyEvaluator` разрешает пользователю нужное право. Служебные поля мутаций и выбор DS подставляет сервер.
- Удаляющие операции и записи сверх лимита за ход выполняются только после подтверждения пользователя. Подтверждение подписано сервером и привязано к операции, пользователю и DS.
- Ход работы агента передаётся клиенту по SSE. Клиент перерисовывается через уже существующий поток изменений черновика.
- В `js/apps/client` появится панель чата в рабочей области DS.
- Появится набор эталонных сценариев, по которому проверяется, справляется ли модель с нашими инструментами.
- Добавится ADR-0008 о встраивании MCP-ядра в серверный процесс. Он фиксирует отступления от ADR-0004: отбор инструментов по серверным правам и учётные данные только из запроса. Удалённый MCP-сервер по-прежнему не делается.

## Возможности

### Новые возможности

- `builder-ai-chat` — HTTP-контракт чата: поток событий, проверки до потока, подтверждение операций, права, ограничения хода.
- `ai-agent-tooling` — цикл агента поверх MCP-ядра: отбор инструментов, сокрытие служебных полей, подстановка контекста, история для модели, эталонные сценарии.
- `llm-provider-adapters` — слой `LlmClient`, нейтральная модель сообщений, адаптеры OpenAI-совместимого API и GigaChat, их настройка.
- `web-ai-chat-panel` — панель чата в веб-клиенте: отправка хода, ход работы агента, подтверждения, обновление интерфейса.

### Изменённые возможности

- `frontend-mcp-server` — ядро MCP пригодно для встраивания в сервер: учётные данные из контекста вызова, публичная схема инструментов без служебных полей. Требование «Backend authorization остается серверной ответственностью» допускает отбор инструментов встраивающим сервером по серверным разрешениям.
- `multi-user-design-system-editing` — запись может передать ожидаемый черновик в `X-DS-Expected-Draft`; если DS опубликовали и черновик сменился, запись отклоняется с `409 draft_changed`. Так подтверждённая в чате операция не попадёт в следующий черновик.
- `backend-monolith-runtime` — монолит подключает подсистему ИИ-ассистента с выключателем `AI_ENABLED`. Требование «Независимость поведения от транспорта» получает исключение для обратных вызовов инструментов чата.

## Влияние

- **backend-kt.**
  - ds-service: необязательный заголовок `X-DS-Expected-Draft` в `DsRequestContext`, проверка в общей инфраструктуре записи, ошибка `409 draft_changed`, обновление OpenAPI.
  - Новая сборка `backend-kt/ai-assistant` (`runtime` и `feature-chat`) подключается в `backend-kt/app` и в корневую сборку `backend-kt` как включаемая сборка.
  - Префикс `/api/projects/` уже публичный, граница не меняется.
  - JVM-артефакт ядра берётся из локального репозитория, который публикует `frontend-kt`. `app/Dockerfile` и `.dockerignore` пропускают `frontend-kt` для этой публикации.
  - OpenAPI — `ai-assistant/runtime/src/main/resources/openapi/documentation.yaml`; при сборке `processResources` переносит ресурсы в `dsbuilder/ai/...`, как у документации. В каталог `backend-kt/api-reference/src/catalog.mjs` добавляется запись.
  - Новые переменные окружения: `AI_ENABLED`, `AI_PROVIDER`, `AI_BASE_URL`, `AI_API_KEY`, `AI_MODEL`, `AI_EXTRA_BODY`, `AI_RETRY_ERROR_CODES`, `AI_GIGACHAT_AUTH_KEY`, `AI_GIGACHAT_SCOPE`, `AI_GIGACHAT_OAUTH_URL`, `AI_GIGACHAT_BASE_URL`, `AI_GIGACHAT_CA_PATH`, `AI_MAX_STEPS`, `AI_MAX_WRITES`, `AI_TURN_TIMEOUT_SECONDS`, `AI_HISTORY_MAX_CHARS`, `AI_MESSAGE_MAX_CHARS`, `AI_TOOL_RESULT_MAX_CHARS`. Их нужно прописать в `docker-compose.prod.yml`, `backend-kt/docker-compose.local.yml` и `backend-kt/app/README.md`.
  - Отдельного контейнера, порта или проверки готовности нет: подсистема работает в процессе `backend` и использует его `/ready`.
- **frontend-kt.**
  - `core-application` получает `CallScopedCredentialProvider`.
  - `mcp-server-core` получает `mcpServerFilledFields` и `inputJsonSchema`; инструменты записи получают необязательное служебное поле `expectedDraftId`, которое `core-network` передаёт заголовком `X-DS-Expected-Draft`.
  - Сборка получает подмножество `dsbuilder.serverSubset` и задачу публикации JVM-артефактов для `backend-kt`.
  - Поведение CLI и `dsbuilder-mcp` не меняется.
- **CI.** `validate-backend-kt.yml` срабатывает и на `frontend-kt/**`, в его матрицы добавляется `ai-assistant`.
- **js.** В `js/apps/client` появляются панель и API-клиент чата и флаг `VITE_AI_CHAT_ENABLED`. Для него в процессы развёртывания клиента dev и prom добавляются переменные `_DEV` и `_PROM`. Работа с ZAI из браузера и прокси vite не используются.
- **Внешние сервисы.** API выбранного провайдера модели; ключи хранятся только в env монолита. Для GigaChat нужен корневой сертификат НУЦ Минцифры, смонтированный в контейнер.
- **Данные.** Новых таблиц и миграций нет. История разговора хранится в памяти вкладки и передаётся в каждом запросе. Изменения DS попадают в существующий журнал от имени пользователя.

## Вне целей

- Удалённый MCP-сервер по HTTP/SSE для внешних агентов.
- Хранение истории разговоров на сервере, общие чаты, учёт расхода токенов и квоты по проектам.
- Изменение общего каталога компонентов, публикация версий и управление участниками проекта из чата.
- Перенос клиентского чата из локальной ветки `AI-CHAT`.
- Отмена хода чата: нужны компенсирующие записи с проверкой ревизии, а не откат журнала.
- Поиск по документации: нужна проверка принадлежности публикации к DS.
