# Браузерные проверки пользовательских сценариев

## Purpose

Возможность обеспечивает локальные UI E2E DS Builder на подготовленном тестовом стенде: проверяет пользовательский результат и сохранение данных, изолирует данные теста и выполняет ограниченную очистку. Первый сценарий служит основой для постепенного расширения покрытия.

## ADDED Requirements

### Requirement: Явное окружение и собственная авторизация

Запуск SHALL принимать адреса клиента/Gateway и credentials тестовой учётной записи. Пилот MUST автоматически читать приватный .env.e2e.local клиента, использовать собственную сессию обычного пользователя без system_admin и находить либо создавать его выделенный active E2E-проект. Ручной projectId MUST NOT требоваться. Отсутствие credentials или неподходящие права MUST завершать запуск ошибкой до создания системы.

#### Scenario: Предусловия подтверждены

- **WHEN** указаны настройки подготовленного стенда и тестовая учётная запись успешно авторизована
- **THEN** защищённый GET выбранного проекта подтверждает active и обычного Owner без `system_admin`
- **AND** браузер и технические API-операции используют собственную сессию этого пользователя
- **AND** запуск не создаёт пользователя и не запускает сервисы, миграции или seed

#### Scenario: Первый запуск без ручного projectId

- **WHEN** credentials заданы в .env.e2e.local и собственного active-проекта с настроенным именем нет
- **THEN** helper выполняет один POST проекта, проверяет ответ 201 и защищённый GET Owner
- **AND** найденный ID передаётся UI и cleanup без ручного ввода; проект сохраняется между запусками

#### Scenario: Проект уже существует

- **WHEN** найден ровно один собственный active-проект с точным именем, по умолчанию E2E Automation
- **THEN** запуск переиспользует его без POST проекта после свежего GET Owner
- **AND** чужие/архивные проекты не используются; неоднозначное совпадение даёт отказ без мутаций

#### Scenario: Локальный файл credentials

- **WHEN** пользователь один раз копирует e2e.env.example в .env.e2e.local, заполняет тестовые credentials и запускает npm run test:e2e
- **THEN** файл автоматически читается без export и ручного пути независимо от cwd
- **AND** process env имеет приоритет; явный DSB_E2E_CREDENTIALS_FILE заменяет стандартный файл
- **AND** отсутствующие или пустые адреса/clientId используют локальные defaults: http://localhost:3002/, http://localhost:8080/, dsbuilder-api; непустые настройки переопределяют их
- **AND** .env.e2e.local исключён из Git, а публичный example не содержит реальных секретов

#### Scenario: Настройки или права не подходят

- **WHEN** обязательная настройка отсутствует, авторизация отклонена либо выбранный проект недоступен, архивирован или не принадлежит обычному Owner
- **THEN** запуск сообщает неподтверждённое предусловие и завершается ненулевым кодом без POST дизайн-системы
- **AND** значения credentials и токенов не выводятся

### Requirement: Пилот создания дизайн-системы через UI

Первый набор SHALL содержать один положительный поток создания дизайн-системы через интерфейс. Уникальное имя и projectId MUST совпадать с ответом успешного POST; подтверждённый ID MUST быть доступен очистке до последующих assertions. Вход в редакторы тем в этот поток не входит.

#### Scenario: Owner создаёт систему

- **WHEN** Owner открывает выбранный проект, заполняет название и отправляет форму создания
- **THEN** наблюдается один POST `/api/projects/{projectId}/ds/design-systems` со статусом 201
- **AND** возвращённые ID, имя и projectId соответствуют новой системе выбранного проекта
- **AND** ID регистрируется для очистки до дальнейших проверок
- **AND** браузер переходит в обзор по возвращённому ID

#### Scenario: Результат создания не подтверждён

- **WHEN** POST отклонён, ответ потерян либо не содержит пригодного ID и ожидаемого контекста
- **THEN** тест завершается ошибкой без автоматического повторения POST
- **AND** поиск и удаление объектов по одному лишь имени не выполняются
- **AND** доступные безопасные сведения о запросе и возможном остатке сохраняются для разбора

### Requirement: Сохранение и готовность обзора

Пилот SHALL подтвердить ID, имя и projectId независимым GET, полным reload со свежим GET и повторным открытием через каталог. Проверка обзора MUST дождаться его конечного состояния; заголовок, кеш SPA или ещё выполняющаяся загрузка MUST NOT считаться достаточным результатом.

#### Scenario: Созданная система сохраняется

- **WHEN** система создана и выполнен независимый GET через Gateway
- **THEN** ответ подтверждает её ID, имя и projectId
- **AND** после полного reload свежий GET подтверждает те же значения
- **AND** обзор показывает имя системы и готовое пустое состояние тем без ошибки или индикатора загрузки
- **AND** карточка в каталоге открывает тот же ID и готовый обзор

#### Scenario: Чтение или загрузка обзора не завершились успешно

- **WHEN** GET не подтверждает систему либо загрузка данных обзора завершилась ошибкой или превысила срок ожидания
- **THEN** тест падает на соответствующей проверке
- **AND** при наличии подтверждённого ID выполняется допустимая очистка

### Requirement: Ограниченная очистка после выполнения теста

После подтверждённого создания очистка SHALL выполняться после успеха и обычного исключения. Она MUST удалять только зарегистрированный новый ID после проверки выбранного проекта и принадлежности объекта. Ошибка удаления или проверки отсутствия MUST делать итог неуспешным, сохраняя исходную ошибку теста.

#### Scenario: Очистка подтверждена

- **WHEN** тест завершился успешно либо упал после регистрации ID
- **THEN** очистка проверяет права и соответствие объекта зарегистрированным ID, имени и projectId
- **AND** удаляет только эту систему, подтверждает GET 404 и отсутствие её карточки в ответе каталога
- **AND** существующий проект и исходные системы остаются с прежними проверяемыми полями

#### Scenario: Очистка не может быть подтверждена

- **WHEN** права или принадлежность не подтверждены, DELETE неуспешен либо контрольное чтение не доказало отсутствие
- **THEN** запуск завершается неуспешно с отдельным сообщением об очистке и известным ID
- **AND** чужие объекты не исправляются и не удаляются, неопределённый DELETE автоматически не повторяется
- **AND** ошибка очистки не скрывает первичную ошибку пользовательского потока

### Requirement: Независимость тестовых данных

Каждый тест SHALL владеть своим браузерным контекстом, уникальными изменяемыми данными и набором ID для очистки. Новый сценарий MUST добавляться без зависимости от порядка выполнения предыдущих тестов. Первый пилот выполняется последовательно на выделенном проекте без параллельных прогонов.

#### Scenario: Пилот запускается повторно

- **WHEN** завершён предыдущий запуск и запускается следующий
- **THEN** новый тест использует новое имя и собственный браузерный контекст
- **AND** не использует сохранённые ID или состояние предыдущего теста как предусловие успеха

#### Scenario: Набор расширяется

- **WHEN** добавлен следующий согласованный пользовательский сценарий
- **THEN** он обнаруживается обычной командой запуска и может выполняться отдельно
- **AND** его данные и очистка не зависят от запуска первого сценария
- **AND** роль пользователя соответствует цели нового сценария и не обязана быть Owner

### Requirement: Достоверное браузерное поведение

UI E2E SHALL выполнять пользовательские действия настоящим браузером и использовать реальные продуктовые ответы. Тест MUST сохранять браузерные сетевые ограничения и обнаруживать неисправность интеграции клиента/Gateway. Успех MUST определяться наблюдаемыми состояниями и ограниченными ожиданиями.

#### Scenario: Браузерная интеграция неисправна

- **WHEN** обычный браузер не может получить продуктовые данные из-за CORS, сетевой ошибки или отказа доступа
- **THEN** тест не исправляет заголовки/ответы и не выдаёт такую операцию за успешную
- **AND** технический API-клиент не заменяет браузерный запрос проверяемого UI-действия

#### Scenario: Ответ задержан

- **WHEN** переход, POST или чтение выполняется дольше обычного
- **THEN** тест ожидает соответствующий ответ и конечное состояние до ограниченного срока
- **AND** наблюдение ответа установлено до действия, вызывающего запрос; произвольная задержка не служит доказательством успеха

### Requirement: Понятный результат и защищённая диагностика

Запуск SHALL сохранять результат с названием теста, шагом и полезной причиной ошибки. Диагностика MUST различать падение потока и очистки, не раскрывать credentials в текстовых отчётах и сохранять доступные screenshot/trace ошибки в закрытых локальных артефактах вне Git.

#### Scenario: Проверка завершилась ошибкой

- **WHEN** assertion, ожидание или очистка завершается ошибкой
- **THEN** отчёт содержит конкретную проверку и безопасную причину, а исходная ошибка не заменяется общей фразой
- **AND** для ошибки после открытия браузера сохраняются штатные screenshot/trace, когда контекст доступен; сбой артефакта не подменяет первичную ошибку
- **AND** код завершения ненулевой независимо от успешности других шагов

#### Scenario: Используются секреты

- **WHEN** подготовка и тест работают с паролем или сессией
- **THEN** реальные credentials и состояние авторизации не попадают в Git или общедоступные отчёты
- **AND** необработанный trace, который может содержать сессию, считается закрытым материалом и автоматически не публикуется

### Requirement: Раздельный воспроизводимый локальный запуск

Набор SHALL предоставлять одинаковые команды обычного, видимого и отладочного запуска на Windows/macOS. Модульные/компонентные проверки и Compose Preview smoke MUST запускаться отдельно от Product E2E. Сбор списка и проверка типов MUST быть доступны без credentials и работающего стенда.

#### Scenario: Выполняется локальный запуск

- **WHEN** на подготовленном стенде выбран обычный либо видимый режим
- **THEN** выполняются те же пользовательские тесты и правила очистки
- **AND** отсутствие обязательных предпосылок или пустая выборка не выдаются за успешный E2E

#### Scenario: Проверяется состав набора

- **WHEN** без credentials и сервисов запущены проверка типов или список Product-тестов
- **THEN** проверка не выполняет авторизацию, мутации или подготовку окружения
- **AND** в пилоте обнаруживается ровно один Product-сценарий, отдельно от существующего Compose Preview smoke
