# Браузерные проверки пользовательских сценариев

## Purpose

Возможность обеспечивает локальные UI E2E DS Builder на подготовленном тестовом стенде: проверяет пользовательский результат и сохранение данных, изолирует данные теста и выполняет ограниченную очистку. Первый сценарий служит основой для постепенного расширения покрытия.

## ADDED Requirements

### Requirement: Локальный запуск на собранном UI

Набор SHALL по умолчанию собирать Client один раз и запускать локальный сервер
`dist` под управлением Playwright в `test:e2e`, `headed` и `debug`.
`test:e2e:built` SHALL сохраняться как совместимый алиас основного запуска.
Режим MUST сохранять реальные API/CORS, пользовательские проверки, правила
данных/очистки, UI-таймауты и отсутствие retries тестов.

#### Scenario: Пользователь проверяет стабильность сборки

- **WHEN** запускается `test:e2e` либо его алиас `test:e2e:built` с параметрами повторения или выбора сценариев
- **THEN** перед тестами выполняется обычная сборка и обслуживается `dist` на localhost4173 без HMR/dev-модулей
- **AND** API URL/clientId берутся из существующих E2E-настроек, credentials не передаются в публичные параметры Vite
- **AND** Client URL и origin авторизации согласованы с4173, флаги палитры/компонентов сохраняют API и доступность dev-стенда
- **AND** Playwright завершает только собственный preview; backend/dev3002/проект/исходные ДС сохраняются

#### Scenario: Порт занят или сборка не готова

- **WHEN** порт4173 занят либо сборка/запуск не завершились до ограниченного бюджета120s
- **THEN** запуск SHALL завершиться ошибкой без подстановки другого сервера/порта и без выдачи пропущенных тестов за успешные
- **AND** бюджет запуска MUST NOT увеличивать timeout пользовательских действий и ответов мутаций

#### Scenario: Запрошены список или справка

- **WHEN** режим собранного UI вызван с `--list` либо `--help`
- **THEN** команда SHALL выполняться без чтения credentials, сборки, запуска сервера, авторизации и мутаций

#### Scenario: Выбран готовый локальный или удалённый UI

- **WHEN** пользователь запускает `test:e2e:external` либо явно передаёт `--external-ui`
- **THEN** Client SHALL выбираться из существующих E2E-настроек, с default localhost3002
- **AND** сборка и preview SHALL отсутствовать, API/Client URL не переопределяются публичными настройками сборки
- **AND** обычный и external запуск SHALL выполнять тот же набор тестов и правила очистки

### Requirement: Ресурсные бюджеты и завершение клиентских действий

Ресурсные fixtures SHALL иметь отдельный ограниченный бюджет250s, покрывающий подготовку до70s,
до60s подтверждения мутации и разрешённую последовательность HTTP cleanup110s.
Session SHALL иметь общий timeout30s на вход и logout с запасом. Общий UI timeout90s MUST сохраняться.

#### Scenario: Ошибка действия или ожидания ответа

- **WHEN** действие UI или ожидание ответа T768/T660/T547/T555 завершается ошибкой
- **THEN** helper SHALL дождаться обоих клиентских Promise и сохранить все исходные ошибки
- **AND** перед DELETE SHALL отдельно действовать подтверждение полного ответа той же мутации до60s, без повтора POST/PATCH/DELETE

#### Scenario: Очистка укладывается в разрешённую HTTP-политику

- **WHEN** подтверждение мутации и последовательные HTTP cleanup занимают свои разрешённые бюджеты
- **THEN** ресурсный timeout SHALL позволять завершение Owner/ID/project/nontechnical/GET404/baseline проверок
- **AND** закрытие сессии SHALL иметь отдельный бюджет и сохранять свои ошибки

### Requirement: Диагностика готовности UI

Набор SHALL прикладывать ограниченную диагностику загрузки, сохраняя исходную
ошибку и действующие UI-лимиты без восстановления страницы.

#### Scenario: Загрузка не дошла до необходимого состояния

- **WHEN** исходное ожидание каталога/формы/журнала/версий/редактора завершается ошибкой
- **THEN** в отчёт SHALL добавляться stage/pathname/status/alert и pending/failed API GET без query/headers/body/секретов
- **AND** исходная ошибка SHALL сохраняться, без увеличения UI-лимита, подмены ответов, reload или повторного goto для восстановления

### Requirement: Завершение мутации до очистки T768

Тест SHALL по-прежнему требовать ответ POST за15s, сохраняя ошибку превышения.
Очистка SHALL отдельно дождаться полного ответа того же POST, не больше60s от
начала наблюдения. POST и DELETE MUST NOT повторяться автоматически.

#### Scenario: Поздний ответ подтверждён перед очисткой

- **WHEN** ответ POST пришёл после15s, но полный ответ завершился до60s
- **THEN** T768 остаётся failed из-за превышения15s
- **AND** DELETE собственной ДС выполняется после завершения ответа с прежними проверками Owner/ID/project/baseline

#### Scenario: Исход операции не подтверждён

- **WHEN** полный ответ POST не получен до60s или чтение завершилось сетевой ошибкой
- **THEN** DELETE не отправляется, отдельная ошибка cleanup содержит зарегистрированный ID ДС
- **AND** исходное падение не скрывается, повтор POST и очистка по имени отсутствуют

### Requirement: Независимые UI-проверки версий и журнала

T792/T660/T657 SHALL запускаться на текущей версии с отдельной ДС каждого теста.
Публикации подготовки SHALL создаваться через публичный API с актуальными
draftId/draftRevision и Idempotency-Key без повторов. Темы и версии SHALL
очищаться с родительской ДС; общий проект и стенд SHALL сохраняться.

#### Scenario: T792 — журнал и черновик после публикации пусты

- **WHEN** исходное состояние темы опубликовано в0.1.0
- **THEN** UI показывает отсутствие неопубликованных изменений, пустой состав нового черновика и недоступную публикацию
- **AND** возврат открывает редактор той же темы; UI не отправляет POST публикации

#### Scenario: T660 — непустой черновик опубликован с пустым описанием

- **WHEN** Owner открывает подтверждённое изменение, оставляет примечания пустыми и публикует0.1.1 через UI
- **THEN** наблюдается один POST201, версия появляется в списке, новый черновик пуст и остаётся пустым после reload
- **AND** история0.1.1 содержит подготовленную запись, пустое описание и доступна только для чтения

#### Scenario: T657 — выбор истории не меняет редактор

- **WHEN** у ДС есть0.1.0/0.1.1 и новое имя темы в активном черновике; Owner выбирает0.1.0 в списке истории
- **THEN** показаны метаданные и запись исходной темы, historyVersionId соответствует0.1.0, versionId не устанавливается
- **AND** при возврате редактор показывает актуальное имя темы, Черновик и доступность правки; публикации не отправляются

### Requirement: Ограниченный повтор технического GET

Технический HTTP helper SHALL разрешать не больше двух попыток GET только при
таймауте или известном сбросе соединения. Общий бюджет SHALL составлять 20 секунд,
каждая попытка не больше 10 секунд, включая чтение тела. Таймауты UI и его
проверки SHALL оставаться прежними. POST/DELETE и авторизация MUST NOT повторяться.

#### Scenario: GET восстановился после сетевого сбоя

- **WHEN** первая попытка GET завершилась транспортным timeout/сбросом соединения и общий бюджет ещё не исчерпан
- **THEN** helper выполняет ровно одну дополнительную попытку в оставшемся бюджете
- **AND** нативный отчёт показывает попытку, длительность, безопасный код ошибки и факт восстановления без заголовков, query, тела или секретов

#### Scenario: Повтор не разрешён

- **WHEN** получен HTTP-ответ с недопустимым статусом, невалидный JSON, несовпадение данных либо ошибка DNS/TLS
- **THEN** ошибка сохраняется без дополнительного GET
- **AND** после второй транспортной ошибки третья попытка отсутствует; POST/DELETE не повторяются даже при timeout/сбросе

### Requirement: Независимые проверки создания Theme

T768/T555 SHALL использовать отдельную новую ДС с существующей Owner API-fixture. Браузер MUST выполнять реальные запросы без подмены. После теста очистка родительской ДС SHALL удалять её дочерние темы и сохранять исходный baseline, проект и стенд.

#### Scenario: T768 объединяет прежние проверки без изменения

- **WHEN** запускается T768 вместо прежних отдельных T551/T556
- **THEN** сначала выполняются все прежние проверки невалидных HEX, восстановления формы, отмены и пустого списка после reload
- **AND** затем в новой форме выполняются все прежние проверки валидных HEX, POST 201, редактора и независимых чтений после reload
- **AND** обе части используют одну новую ДС и общую очистку; остальные тесты сохраняются

#### Scenario: Custom показывает введённые HEX

- **WHEN** Owner выбирает Custom и заполняет четыре валидных HEX
- **THEN** каждое HEX-поле видно и содержит точное введённое значение

#### Scenario: Редактор готов после перехода и reload

- **WHEN** создание Theme завершилось POST201 и клиент открывает промежуточный overview
- **THEN** T768 SHALL ждать видимый Text & Icons до30s, после чего проверять точный colors URL созданной темы
- **AND** после reload SHALL действовать то же ожидание готового содержимого без повторного создания или принудительного перехода
- **AND** ожидание ответа SHALL сопоставлять метод, origin и pathname независимо от query; GET текущего черновика MUST проверять отсутствие versionId отдельно, со смысловой ошибкой

#### Scenario: Custom Theme сохраняет палитру

- **WHEN** Owner отправляет заполненную валидную форму Custom
- **THEN** POST возвращает 201 с ожидаемыми name/designSystemId, профилем custom и четырьмя цветами
- **AND** открывается готовый редактор возвращённого ID, независимый GET и свежий GET после reload подтверждают `colorConfig.customPalette`
- **AND** в отдельной ДС остаётся ровно одна созданная тема

По уточнению пользователя сравнение API `preview` карточки, CSS-превью и
переключение Light/Dark не входят в T768 (прежний T551). Вопрос выбора backend-превью
не является условием прохождения этого UI-сценария.

#### Scenario: Имя Theme без учёта регистра уже занято

- **WHEN** API-подготовка создала Theme A и пользователь вводит theme a через форму
- **THEN** POST возвращает 409 TENANT_NAME_CONFLICT и показано «Theme с таким названием уже существует.»
- **AND** после возврата к списку и reload исходная тема сохраняет ID/имя; дубликат отсутствует

#### Scenario: Невалидный HEX блокирует форму

- **WHEN** в валидной Custom-форме Primary последовательно заменяется на #12345, #GGHHII и пустую строку с уходом фокуса через Tab
- **THEN** для каждого значения показана ошибка формата, кнопка создания disabled, браузер не отправляет POST темы
- **AND** возврат #3366CC убирает ошибку и разрешает создание; после отмены список остаётся пустым

### Requirement: Явное окружение и собственная авторизация

Запуск SHALL принимать адреса клиента/Gateway и credentials тестовой учётной записи. Пилот MUST автоматически читать приватный .env.e2e.local клиента, использовать собственную сессию обычного пользователя без system_admin и находить либо создавать его выделенный active E2E-проект. Ручной projectId MUST NOT требоваться. Отсутствие credentials или неподходящие права MUST завершать запуск ошибкой до создания системы.

#### Scenario: Предусловия подтверждены

- **WHEN** указаны настройки подготовленного стенда и тестовая учётная запись успешно авторизована
- **THEN** защищённый GET выбранного проекта подтверждает active и обычного Owner без `system_admin`
- **AND** браузер и технические API-операции используют собственную сессию этого пользователя
- **AND** запуск не создаёт пользователя и не запускает backend-сервисы, миграции или seed; только основной режим управляет локальным preview Client

#### Scenario: Первый запуск без ручного projectId

- **WHEN** credentials заданы в .env.e2e.local и собственного active-проекта с настроенным именем нет
- **THEN** helper выполняет один POST проекта, проверяет ответ 201 и защищённый GET Owner
- **AND** найденный ID передаётся UI и cleanup без ручного ввода; проект сохраняется между запусками

#### Scenario: Проект уже существует

- **WHEN** найден ровно один собственный active-проект с точным именем, по умолчанию E2E Automation
- **THEN** запуск переиспользует его без POST проекта после свежего GET Owner
- **AND** чужие/архивные проекты не используются; неоднозначное совпадение даёт отказ без мутаций

#### Scenario: Локальный файл credentials

- **WHEN** пользователь один раз копирует e2e.env.example в .env.e2e.local, заполняет тестовые credentials и запускает npm run test:e2e
- **THEN** файл автоматически читается без export и ручного пути независимо от cwd
- **AND** process env имеет приоритет; явный DSB_E2E_CREDENTIALS_FILE заменяет стандартный файл
- **AND** отсутствующие или пустые адреса/clientId используют локальные defaults Gateway/clientId: http://localhost:8080/, dsbuilder-api; основной Client использует4173, external допускает переопределение URL с default3002
- **AND** .env.e2e.local исключён из Git, а публичный example не содержит реальных секретов

#### Scenario: Настройки или права не подходят

- **WHEN** обязательная настройка отсутствует, авторизация отклонена либо выбранный проект недоступен, архивирован или не принадлежит обычному Owner
- **THEN** запуск сообщает неподтверждённое предусловие и завершается ненулевым кодом без POST дизайн-системы
- **AND** значения credentials и токенов не выводятся

### Requirement: Пилот создания дизайн-системы через UI

Первый набор SHALL содержать один положительный поток создания дизайн-системы через интерфейс. Уникальное имя и projectId MUST совпадать с ответом успешного POST; подтверждённый ID MUST быть доступен очистке до последующих assertions. Вход в редакторы тем в этот поток не входит.

#### Scenario: Owner создаёт систему

- **WHEN** Owner открывает выбранный проект, заполняет название и отправляет форму создания
- **THEN** наблюдается один POST `/api/projects/{projectId}/ds/design-systems` со статусом 201
- **AND** возвращённые ID, имя и projectId соответствуют новой системе выбранного проекта
- **AND** ID регистрируется для очистки до дальнейших проверок
- **AND** браузер переходит в обзор по возвращённому ID

#### Scenario: Результат создания не подтверждён

- **WHEN** POST отклонён, ответ потерян либо не содержит пригодного ID и ожидаемого контекста
- **THEN** тест завершается ошибкой без автоматического повторения POST
- **AND** поиск и удаление объектов по одному лишь имени не выполняются
- **AND** доступные безопасные сведения о запросе и возможном остатке сохраняются для разбора

### Requirement: Сохранение и готовность обзора

Пилот SHALL подтвердить ID, имя и projectId независимым GET, полным reload со свежим GET и повторным открытием через каталог. Проверка обзора MUST дождаться его конечного состояния; заголовок, кеш SPA или ещё выполняющаяся загрузка MUST NOT считаться достаточным результатом.

#### Scenario: Созданная система сохраняется

- **WHEN** система создана и выполнен независимый GET через Gateway
- **THEN** ответ подтверждает её ID, имя и projectId
- **AND** после полного reload свежий GET подтверждает те же значения
- **AND** обзор показывает имя системы и готовое пустое состояние тем без ошибки или индикатора загрузки
- **AND** карточка в каталоге открывает тот же ID и готовый обзор

#### Scenario: Чтение или загрузка обзора не завершились успешно

- **WHEN** GET не подтверждает систему либо загрузка данных обзора завершилась ошибкой или превысила срок ожидания
- **THEN** тест падает на соответствующей проверке
- **AND** при наличии подтверждённого ID выполняется допустимая очистка

### Requirement: Ограниченная очистка после выполнения теста

После подтверждённого создания очистка SHALL выполняться после успеха и обычного исключения. Она MUST удалять только зарегистрированный новый ID после проверки выбранного проекта и принадлежности объекта. Ошибка удаления или проверки отсутствия MUST делать итог неуспешным, сохраняя исходную ошибку теста.

#### Scenario: Очистка подтверждена

- **WHEN** тест завершился успешно либо упал после регистрации ID
- **THEN** очистка проверяет права и соответствие объекта зарегистрированным ID, имени и projectId
- **AND** удаляет только эту систему, подтверждает GET 404 и отсутствие её карточки в ответе каталога
- **AND** существующий проект и исходные системы остаются с прежними проверяемыми полями

#### Scenario: Очистка не может быть подтверждена

- **WHEN** права или принадлежность не подтверждены, DELETE неуспешен либо контрольное чтение не доказало отсутствие
- **THEN** запуск завершается неуспешно с отдельным сообщением об очистке и известным ID
- **AND** чужие объекты не исправляются и не удаляются, неопределённый DELETE автоматически не повторяется
- **AND** ошибка очистки не скрывает первичную ошибку пользовательского потока

### Requirement: Независимость тестовых данных

Каждый тест SHALL владеть своим браузерным контекстом, уникальными изменяемыми данными и набором ID для очистки. Новый сценарий MUST добавляться без зависимости от порядка выполнения предыдущих тестов. Первый пилот выполняется последовательно на выделенном проекте без параллельных прогонов.

#### Scenario: Пилот запускается повторно

- **WHEN** завершён предыдущий запуск и запускается следующий
- **THEN** новый тест использует новое имя и собственный браузерный контекст
- **AND** не использует сохранённые ID или состояние предыдущего теста как предусловие успеха

#### Scenario: Набор расширяется

- **WHEN** добавлен следующий согласованный пользовательский сценарий
- **THEN** он обнаруживается обычной командой запуска и может выполняться отдельно
- **AND** его данные и очистка не зависят от запуска первого сценария
- **AND** роль пользователя соответствует цели нового сценария и не обязана быть Owner

### Requirement: Достоверное браузерное поведение

UI E2E SHALL выполнять пользовательские действия настоящим браузером и использовать реальные продуктовые ответы. Тест MUST сохранять браузерные сетевые ограничения и обнаруживать неисправность интеграции клиента/Gateway. Успех MUST определяться наблюдаемыми состояниями и ограниченными ожиданиями.

#### Scenario: Браузерная интеграция неисправна

- **WHEN** обычный браузер не может получить продуктовые данные из-за CORS, сетевой ошибки или отказа доступа
- **THEN** тест не исправляет заголовки/ответы и не выдаёт такую операцию за успешную
- **AND** технический API-клиент не заменяет браузерный запрос проверяемого UI-действия

#### Scenario: Ответ задержан

- **WHEN** переход, POST или чтение выполняется дольше обычного
- **THEN** тест ожидает соответствующий ответ и конечное состояние до ограниченного срока
- **AND** наблюдение ответа установлено до действия, вызывающего запрос; произвольная задержка не служит доказательством успеха

### Requirement: Понятный результат и защищённая диагностика

Запуск SHALL сохранять результат с названием теста, шагом и полезной причиной ошибки. Диагностика MUST различать падение потока и очистки, не раскрывать credentials в текстовых отчётах и сохранять доступные screenshot/trace ошибки в закрытых локальных артефактах вне Git.

#### Scenario: Проверка завершилась ошибкой

- **WHEN** assertion, ожидание или очистка завершается ошибкой
- **THEN** отчёт содержит конкретную проверку и безопасную причину, а исходная ошибка не заменяется общей фразой
- **AND** для ошибки после открытия браузера сохраняются штатные screenshot/trace, когда контекст доступен; сбой артефакта не подменяет первичную ошибку
- **AND** код завершения ненулевой независимо от успешности других шагов

#### Scenario: Используются секреты

- **WHEN** подготовка и тест работают с паролем или сессией
- **THEN** реальные credentials и состояние авторизации не попадают в Git или общедоступные отчёты
- **AND** необработанный trace, который может содержать сессию, считается закрытым материалом и автоматически не публикуется

### Requirement: Раздельный воспроизводимый локальный запуск

Набор SHALL предоставлять одинаковые команды обычного, видимого и отладочного запуска на Windows/macOS. Модульные/компонентные проверки и Compose Preview smoke MUST запускаться отдельно от Product E2E. Сбор списка и проверка типов MUST быть доступны без credentials и работающего стенда.

#### Scenario: Выполняется локальный запуск

- **WHEN** на подготовленном стенде выбран обычный либо видимый режим
- **THEN** выполняются те же пользовательские тесты и правила очистки
- **AND** отсутствие обязательных предпосылок или пустая выборка не выдаются за успешный E2E

#### Scenario: Проверяется состав набора

- **WHEN** без credentials и сервисов запущены проверка типов или список Product-тестов
- **THEN** проверка не выполняет авторизацию, мутации или подготовку окружения
- **AND** обнаруживаются согласованные независимые Product-сценарии с понятными названиями и ключами кейсов; Compose Preview smoke остаётся отдельно

### Requirement: Проверки формы создания проекта без серверного создания

T521/T523/T566 SHALL выполняться независимо от пилота и от подготовки временной ДС.
Тесты MUST наблюдать POST проектов с начала действий и не создавать проекты
для проверки валидации, отмены и клавиатурного фокуса.

#### Scenario: Пустое имя и отмена

- **WHEN** T521 проверяет пустое имя и три пробела или T523 отменяет заполненную форму
- **THEN** T521 подтверждает недоступность «Далее», а T523 — отсутствие карточки после reload каталога
- **AND** ни один из этих сценариев не отправляет POST создания проекта

#### Scenario: Клавиатура и восстановление фокуса

- **WHEN** T566 выполняет Tab/Shift+Tab на шаге «Команда», затем выбирает «Назад» и «Отмена»
- **THEN** фокус циклически остаётся внутри окна, а после закрытия возвращается на «Создать проект»
- **AND** фокус меняет сам продукт; тест не вызывает focus для имитации результата
- **AND** запрос создания проекта не отправляется

### Requirement: Независимое переименование дизайн-системы через UI

PLASMABLDR-T547 SHALL получать отдельную ДС через API-fixture и менять её имя через
настоящую форму настроек. Тест MUST подтвердить сохранение нового имени и прежнего
ID без зависимости от запуска пилота и без подмены браузерных ответов.

#### Scenario: Имя изменено без создания другой ДС

- **WHEN** Owner переименовывает подготовленную ДС в её настройках и сохраняет форму
- **THEN** PATCH той же ДС возвращает 200 и подтверждает новый name, прежние id и projectId
- **AND** независимый GET и полный reload со свежим GET подтверждают те же значения
- **AND** в каталоге ровно одна карточка нового имени, старой карточки нет, набор ID не изменился
- **AND** карточка открывает тот же ID и готовый обзор

#### Scenario: Переименованная ДС очищается после успеха или исключения

- **WHEN** T547 завершился успешно либо обычным исключением после регистрации созданного ID
- **THEN** finally подтверждает актуальные права Owner и принадлежность обычной ДС по id/projectId
- **AND** изменение имени не блокирует удаление только зарегистрированной новой ДС и проверку GET 404
- **AND** исходные системы сверяются с baseline; общий проект не удаляется/не архивируется, стенд не останавливается

#### Scenario: Ответ подготовки неполон или потерян

- **WHEN** API-подготовка не подтверждает новый ID, ожидаемые name/projectId и отсутствие ID в baseline
- **THEN** тест завершается ошибкой без повторного POST и без автоматического удаления по имени
- **AND** имя попытки доступно в annotation для разбора возможного остатка
- **AND** после регистрации минимальной идентичности ошибка полной проверки DTO не препятствует ограниченной очистке
