# Предложение

## Зачем

Чтение значений темы занимает 4–11 секунд, а журнал после отмены изменений повторно сравнивает тысячи неизменённых значений. Планы PostgreSQL 17 на dev подтверждают повторные поиски ревизий, сканирование 124 тысяч строк ради одной темы и сравнение 9 639 значений ради пустого журнала за 4,17 секунды. Дополнительно отмена выбранных сущностей зависит от перебора общих технических состояний ради поиска changeId; размер несвязанного журнала не должен определять работу команды.

## Что меняется

- Чтение тем, палитры и размеров использует единожды разрешённую границу версии, ограниченные выборки и переиспользование данных внутри запроса.
- Журнал отбирает кандидатов по предметным ревизиям между сравниваемыми границами до загрузки и сравнения значений, сохраняя действующие правила видимости и отмены.
- Подтверждённые планами индексы добавляются отдельной Flyway-миграцией; существующие миграции не переписываются.
- Проверка производительности сравнивает ответы, планы, число SQL и длительности на одинаковом наборе данных; отдельно измеряет команду отмены и последующие чтения.
- Дополнительный этап устраняет повторное чтение цветовых значений при получении всех значений темы и повторные сканирования в SQL использования токенов размеров компонентами. Его результат сравнивается с уже оптимизированной версией отдельно от исходного `dev`.
- Следующий этап сокращает повторные чтения и пересчёты цветового семейства при пакетном откате, а клиент после сброса обновляет затронутые данные раздела через существующий `refreshChanges` вместо полной перезагрузки оболочки редактора.
- Вводится адресный пакетный откат по draftId, типу сущности, устойчивому ID и ожидаемой редакции. Сервер читает выбранные сущности и необходимые зависимости без поиска по общему журналу; для инспектора цели читаются только в области выбранных токенов и темы. Старые маршруты сохраняются для совместимости. Цели — ограниченный объём работы, масштабируемость и задержки; фиксированный бюджет SQL снят.
- В production compose период начального ожидания Keycloak увеличивается с 40 до 120 секунд. Эта узкая правка отдельно запрошена и уже внесена при подготовке предложения.

## Возможности

### Новые возможности

- `design-system-read-efficiency`: ограниченное чтение данных темы и воспроизводимая проверка его эффективности с сохранением выбранной версии и публичных ответов.

### Изменяемые возможности

- `design-system-change-journal`: отбор кандидатов перед предметным сравнением, сохранение точности журнала и поведения отмены.
- `container-image-delivery`: увеличенное начальное ожидание готовности Keycloak.

## Влияние

Затрагиваются `backend-kt/ds-service` (`core`, `feature-themes`, `feature-tokens`, `feature-design-systems`, адресные обработчики других типов, интеграционные проверки и ресурсы Flyway), клиент `js/apps/client` (репозиторий журнала, сброс инспектора и обновление раздела) и корневой `docker-compose.prod.yml`. Добавляются API адресной отмены и ограниченного чтения целей, их DTO, OpenAPI и манифест маршрутов; прежние API остаются совместимыми. Новых сервисов и зависимостей нет; `frontend-kt` не меняется. Адресный контракт использует существующие устойчивые ID и не требует новой схемы хранения. Общие SQL-помощники меняются после проверки потребителей, индексы — по планам. Общего кеша и новой таблицы журнала нет. Параметры диагностических логов не переносятся в Git; auto_explain на dev остаётся включённым по решению разработчика.
