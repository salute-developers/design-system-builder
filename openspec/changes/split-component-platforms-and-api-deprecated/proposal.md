## Why

Сегодня компонент в `db-service` один на все платформы: `components.name` уникально глобально, свойство уникально по `(component_id, name)`, а платформа живёт только в алиасах `property_platform_params` и в двух необязательных колонках (`properties.platform`, `appearances.platform`) из миграции `0005`. Из-за этого Compose, Android View, iOS и web делят одни строки: один тип свойства на все платформы (`typeMismatches` между платформами), веб-свойства обрастают нативными алиасами (114 из 3104 в локальной базе), `Checkbox` и `CheckBox` становятся разными компонентами, веб- и нативный импорт конфигураций затирают друг друга, а у платформы нет собственных вариаций и состояний.

Кроме того, формат API-меты расширен полем `deprecated` с сообщением (plasma-android, ветка `feature/fix-view-api-meta`, change `add-api-meta-deprecated`): помечаются устаревшие свойства Compose и устаревшие XML-атрибуты View. Это нужно уметь хранить и обновлять при повторных импортах, хотя остальной импорт остаётся аддитивным.

## What Changes

- **Платформа — часть идентичности компонента.** `components` получает обязательную колонку `platform` (`web`, `compose`, `xml`, `ios`), уникальность `(name, platform)`. У каждой платформы свои компоненты, а значит, свои свойства, состояния, вариации, конфиги оформления и значения: всё это уже висит на `component_id`. **BREAKING**: уникальность `components.name` исчезает.
- **Лишние колонки уходят.** `properties.platform` и `appearances.platform` удаляются: платформа берётся из компонента. Уникальность `appearances` становится `(design_system_id, component_id, name)`. Платформа алиаса в `property_platform_params` остаётся, но триггер требует, чтобы она совпадала с платформой компонента.
- **Единый словарь платформ компонентов.** `component_platform` получает значение `xml` и становится единственным словарём для компонентов, свойств и алиасов. `android` остаётся только у значений токенов (`token_values`).
- **Привязка дизайн-системы** (`design_system_components`) указывает на компонент конкретной платформы; набор платформ дизайн-системы — это платформы её компонентов.
- **Импорт API-меты** создаёт и ищет компонент по `(name, платформа запроса)`. Расхождения типа между платформами исчезают, остаются только внутри платформы. В отчёт добавляются сведения «в базе есть, в мете нет» (справочно, ничего не удаляется).
- **`deprecated` в мете и в базе.** Алиас получает `deprecated` (boolean) и `deprecated_message` (text, пустая строка допустима). Манифест принимает `platformNames` как объекты `{name, deprecated?: {message}}` и как прежние строки. Это единственное, что импорт обновляет у существующих строк: ставит пометку, меняет сообщение, снимает пометку, когда её в мете больше нет. Свойства, алиасы и состояния по-прежнему не изменяются и не удаляются. Строка в `platformNames` (старый CLI) пометку не трогает.
- **Платформа запроса из `config.json`.** `components push` и `components fetch` передают платформу проекта (из `.sdds/config.json`; если их несколько, нужен `--platform`), backend отвечает `400` без платформы, а не угадывает.
- **Одна миграция данных** (`0007`): существующие строки раскладываются по платформам по правилам из `design.md`; всё, что нельзя определить достоверно (нативные типы общих свойств), восстанавливается повторным запуском `components import-api` по метам платформ.

Не входит: ревизии и версии API (хранение нескольких версий API одной платформы), перенос контента дизайн-системы на версии, платформы iOS и web в CLI-нормализаторах, чтение `deprecated` потребителями (UI конструктора, генератор): здесь статус только хранится.

## Capabilities

### New Capabilities
- `component-platform-model`: идентичность компонента по платформе, единый словарь платформ, привязки дизайн-системы, хранение `deprecated` на алиасе и контракт миграции данных.

### Modified Capabilities
- `component-api-meta-import`: идентичность `(name, platform)`, объектная форма `platformNames` с `deprecated`, обновление `deprecated` при повторном импорте, отчёт со счётчиками `deprecated` и «нет в мете».
- `cli-components`: чтение `deprecated` нормализаторами Compose и View, печать новых строк отчёта, платформа push и fetch из `config.json`.

## Impact

- **js/db-service**: `db/schema.ts`, новая миграция `0007` с переносом данных и триггерами, `docs/db-schema.dbml`, `nl-query/schema-context.ts`, `db/import/apiMetaImport.ts` и `apiMetaManifest.ts`, `db/import/componentImport.ts` и `db/export/componentExport.ts`, `routes/api/component-config.ts`, `routes/api/design-systems.ts`, `routes/api/legacy.ts`, `queries/catalog.ts`, сиды (`db/seeds/**`), `openapi/spec.ts`, `validation/schema.ts`, регенерация типов админки (`/sync-all`), тесты `vitest`.
- **frontend-kt**: `feature-components` (манифест с `deprecated`, нормализаторы Compose и View, отчёт), `cli` (платформа push и fetch, вывод), `cli/USAGE.md`.
- **Потребители вне репозитория кода db-service**: generator, клиент и админка, читающие компоненты по имени, должны передавать платформу (инвентаризация в задачах).
- **Совместимость**: **BREAKING** для CLI, не передающих платформу в `push` и `fetch` (получат `400`), и для всего, что искало компонент по одному имени. Backend и CLI обновляются вместе.
- **Данные**: до миграции обязателен `pg_dump`; после неё нужен повторный импорт мет Compose, View и iOS, чтобы восстановить нативные типы общих свойств.
