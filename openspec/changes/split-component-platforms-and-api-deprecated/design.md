## Context

Состояние после `restrict-import-api-to-system-admin`: глобальный слой компонентной модели (`components`, `properties`, `states`, `property_platform_params`) пополняется админской ручкой `import-api-meta`. Компонент один на все платформы; платформа есть у алиаса (`xml|compose|ios|web`), а у свойства и конфига оформления — необязательная колонка `component_platform` (`web|compose|ios`, миграция `0005`), которая нужна лишь затем, чтобы веб- и нативный импорты не затирали друг друга. Нативные конфиги читаются как `appearances.platform IS NULL`.

Разведка локальной базы (`audit.sql`, `ds_registry`, 2026-10-06):

| Что | Значение |
|---|---|
| компонентов / свойств | 108 / 3104 |
| свойства `platform=web` / `NULL` | 1527 / 1577 |
| алиасы xml / compose / ios / web | 1211 / 1334 / 57 / 1991 |
| appearances | 66, все `web`; `NULL` нет |
| значения конфигов | 5764 вариационных + 78 инвариантных, **все** на свойствах `platform=web` |
| variations / styles | 168 / 581 (все в `base`, все в веб-appearances) |
| design_system_components | 142: `base` 63 (веб), `plasma_sd_service` 79 (без appearances) |
| платформы компонентов по признакам | web 25, compose 15, compose+xml 30, compose+xml+web 33, compose+xml+ios+web 5 |
| веб-свойства с нативными алиасами | 114 (45 compose+ios+web+xml, 38 compose+web+xml, 16 compose+web, 11 compose+ios+xml, остальные единичные), под ними 406 вариационных значений |

Выводы: весь контент дизайн-систем (appearances, значения, variations, styles, зависимости) принадлежит вебу; нативные данные в базе — только производные от импортов мет и привязки дизайн-системы без контента.

**Принятая предпосылка:** в продуктовых базах (stage, prod) есть только веб-компоненты, нативные мета-импорты туда не применялись. Это упрощает миграцию: нативные данные не переносятся и не копируются, а пересоздаются повторным импортом мет с независимыми по платформам типами. Предпосылка проверяется `audit.sql` до выката и защищается проверками внутри миграции (см. ниже), а не принимается на веру.

Мета-файлы: поле `deprecated` — объект `{message}`, присутствует только у помеченных свойств; пустое сообщение допустимо и означает «устарело». Compose: статус один на `id`, производитель сам распространяет его на все перегрузки. View: статус у конкретного `attrName`, без распространения по `id` (`sd_textColor` может быть устаревшим, а `android:textColor` нет).

## Goals / Non-Goals

**Goals:**
- Компонент, его свойства, состояния, вариации, конфиги и значения принадлежат ровно одной платформе.
- Повторные импорты мет по платформам не влияют друг на друга.
- Хранить и обновлять `deprecated` на уровне алиаса; остальной импорт аддитивный.
- Миграция существующих данных одной миграцией, без потери контента дизайн-систем.
- Платформа запроса определяется из `.sdds/config.json`, backend не угадывает.

**Non-Goals:**
- Версии и ревизии API платформы (несколько версий одной платформы одновременно).
- Версионирование контента дизайн-системы и перевод версии на другое API.
- Использование `deprecated` потребителями (UI, генераторы).
- Нормализаторы iOS и web в CLI.
- Удаление чего-либо из базы при отсутствии в мете.

## Decisions

### Идентичность: `components(name, platform)`

Колонка `components.platform` типа `component_platform` (`web`, `compose`, `xml`, `ios`), `NOT NULL`; `components_name_unique` заменяется на `components_name_platform_unique(name, platform)`. Свойства, состояния, вариации, appearances, `state_sets.owner_component_id` и привязки дизайн-систем ссылаются на `component_id` и разделяются автоматически.

`appearances.platform` и `properties.platform` удаляются как избыточные. Уникальность appearance: `(design_system_id, component_id, name)` (без `NULLS NOT DISTINCT`).

Альтернатива — платформа только на дочерних строках при общем компоненте (отвергнута: нельзя иметь компонент только одной платформы и общую идентичность одновременно с отдельными вариациями; «свои компоненты» не получаются).

Платформа алиаса остаётся (`ppp_property_id_platform_name_unique`, код и генераторы читают `platform='web'`), но триггер `property_platform_params_platform_matches_component` требует равенства платформы алиаса и платформы компонента свойства, чтобы не было двух источников правды.

### Словарь платформ

`component_platform` расширяется значением `xml` и используется для компонентов, свойств и алиасов (`property_platform` остаётся совместимым списком значений того же состава; допустимы значения только `web|compose|xml|ios`). `platform` у `token_values` (`web|android|ios`) не меняется: токены вне объёма.

Соответствие платформ CLI: `compose→compose`, `android-view→xml`, `swiftui→ios`, `react→web`.

### Дизайн-система и платформа

`design_system_components` указывает на компонент конкретной платформы. Платформа дизайн-системы отдельной колонки не получает: это платформы её компонентов. Запросы push и fetch получают платформу явно (см. ниже).

### `deprecated` хранится на алиасе

`property_platform_params.deprecated boolean not null default false` и `deprecated_message text null`, `CHECK (deprecated OR deprecated_message IS NULL)`. Пустая строка при `deprecated = true` допустима. Причина выбора алиаса: у View устаревает атрибут, а не свойство; «свойство устарело на платформе» вычисляется как «устарели все его алиасы», у Compose алиас один.

### Импорт: аддитивный, кроме `deprecated`

Идентичность — `(name, платформа запроса)`; компонент платформы создаётся, если нет. Для существующего свойства и алиасов правила прежние (ничего не меняется и не удаляется; расхождение типа — в `typeMismatches`, но теперь только внутри платформы). Новое:

| Мета | База | Результат |
|---|---|---|
| алиас без `deprecated` (объект) | `deprecated = true` | снять: `deprecated = false`, сообщение `NULL`; счётчик `deprecatedCleared` |
| алиас с `deprecated` | `deprecated = false` | поставить; `deprecatedMarked` |
| алиас с другим сообщением | `deprecated = true` | обновить сообщение; `deprecatedMessageChanged` |
| алиас строкой (старый CLI) | любое | не трогать |
| алиаса или свойства нет в мете | любое | не трогать; попадает в `absent` справочно |

Снятие пометки автоматическое: «последний импорт побеждает». Защита: dry run по умолчанию показывает `deprecatedCleared`, а старые CLI (строки) пометку не снимают. Риск, что мета от более старой библиотеки снимет пометки, принят и описан в USAGE.

Отчёт получает `deprecatedMarked`, `deprecatedMessageChanged`, `deprecatedCleared` и `absent`: список компонентов платформы, которых нет в мете, и свойств импортируемых компонентов, которых нет в мете (ключ `Component` или `Component.property`). Справочно, на код выхода и `--strict` не влияет.

Манифест: `platformNames: Array<string | {name: string, deprecated?: {message: string}}>`. Строка равнозначна «нет сведений о deprecated»; объект без `deprecated` равнозначен «не устарело».

### Платформа push и fetch — из `config.json`

CLI определяет платформу так же, как `import-api`: единственная платформа из `.sdds/config.json`, иначе обязательная `--platform`; передаёт её в теле запроса. Backend без `platform` отвечает `400` (угадывать нельзя: имя компонента больше не определяет платформу). Старые CLI получат `400` и должны обновиться вместе с backend.

### Миграция `0007` (одна)

Исходя из предпосылки, миграция не раскладывает данные по платформам, а превращает существующее в веб и удаляет производное нативное:

1. **Проверки-ограничители** в начале миграции (`RAISE EXCEPTION` с числами и именами, без изменения данных):
   - нет `appearances` с `platform IS NULL` (нативные конфиги);
   - нет значений конфигов и `appearances`, принадлежащих компонентам без веб-признака;
   - нет привязок дизайн-систем (`design_system_components`) к компонентам без веб-признака.
   Веб-признак компонента: свойство `platform = web`, appearance `web` или алиас `web`.
2. **Удаление производного нативного слоя** (перестраивается импортом мет):
   - алиасы платформ `compose`, `xml`, `ios` (`property_platform_params`), в том числе висящие на веб-свойствах, вместе с их поправками (`variation_platform_param_adjustments`, `invariant_platform_param_adjustments`), которые удаляются каскадом;
   - свойства без веб-признака (нативные, `platform IS NULL` и без веб-алиаса), их состояния и сами компоненты без веб-признака, у которых после этого ничего не осталось.
3. **Платформа компонентов:** все оставшиеся компоненты получают `platform = web`; идентификаторы, appearances, значения, вариации, стили, состояния, зависимости и привязки дизайн-систем не меняются.
4. **Схема:** уникальность `(name, platform)` вместо `name`, удаление `properties.platform` и `appearances.platform`, новые колонки алиасов, триггер совпадения платформы алиаса и компонента.
5. **Финальные проверки** (`RAISE EXCEPTION` и откат): нет компонента без платформы; нет алиаса, чья платформа не совпадает с платформой компонента; число appearances, значений, вариаций, стилей и привязок равно числу до миграции.

Миграция — одна транзакция. Откат — восстановление из `pg_dump`.

После выката: `dsbuilder components import-api --apply` для каждой платформы (Compose, View, iOS) по актуальным метам создаёт нативные компоненты с типами, взятыми из меты своей платформы, и пометками `deprecated`. До этого нативных компонентов в базе нет.

Локальные и dev-базы, где нативные данные уже есть и привязаны к дизайн-системам (например, `plasma_sd_service`), миграция остановит проверкой 1: такие привязки удаляются вручную или базы пересоздаются из сидов.

Триггеры состояний из `0004_component_import.sql` не затрагиваются: состояния остаются на том же компоненте, что и их наборы.

## Risks / Trade-offs

- **Предпосылка «в проде только веб» может оказаться неверной.** Защита: `audit.sql` до выката и проверки-ограничители в миграции останавливают её с ошибкой, ничего не меняя; нативные данные при этом не теряются молча.
- **Миграция необратима без дампа.** Обязателен `pg_dump` до выката.
- **Нативные компоненты временно отсутствуют** между выкатом и повторным импортом мет. Потребители нативных платформ (если такие есть) в это окно ничего не видят; повторный импорт занимает минуты и входит в порядок выката.
- **Legacy-выдача теряет нативные поля** у пяти компонентов сида (алиасы и поправки удаляются осознанно, см. «Decisions Resolved»).
- **Dev-базы с нативными привязками** остановят миграцию; их нужно привести в порядок вручную или пересоздать.
- **Широкий охват кода:** `appearances` в 95 файлах, `variations` в 248, `styles` в 176; выбор компонента по одному имени ломает потребителей, не передающих платформу.
- **Снятие `deprecated` по последнему импорту** может снять пометку, если импортировать мету старой библиотеки. Принято; защита — dry run и строки старых CLI.
- **BREAKING для CLI без платформы в push/fetch.** Backend и CLI выкатываются вместе.

## Migration Plan

1. `audit.sql` на целевой базе: подтвердить, что нативных данных нет (нет нативных appearances и привязок к нативным компонентам).
2. `pg_dump` целевой базы.
3. Выкатить backend с миграцией `0007` и новым CLI одновременно.
4. `dsbuilder components import-api --apply` для каждой платформы по актуальным метам; проверить отчёт: компоненты и свойства созданы, `typeMismatches` пусты.
5. Контрольные запросы: число веб-компонентов, appearances, значений, вариаций, стилей и привязок равно значениям до миграции.
6. Откат: восстановление из дампа и возврат предыдущих backend и CLI.

## Decisions Resolved During Exploration

- Нативные алиасы на веб-свойствах и их поправки удаляются. В сиде их 190 алиасов (`xml` 63, `compose` 70, `ios` 57) на компонентах Button, Checkbox, IconButton, Link, Radiobox и 90 поправок (30 веб-значений × 3 платформы: Button 51, Link 36, IconButton 3). Это ручное сопоставление имён и токенов нативных платформ для legacy-ручек (`/ds/legacy/design-systems/*`), которыми пользуется конструктор. Решено не учитывать legacy-выдачу: после миграции её поля `xml`, `compose`, `ios` у этих компонентов будут пустыми, код `legacy.ts` не меняется. Нативные значения и токены дальше приходят из импорта мет и конфигов платформ, а не из сопоставлений на веб-компонентах.

- Платформы дизайн-системы выводятся из платформ её компонентов, явной колонки `design_systems.platforms` нет: платформа и так явная в запросах (`config.json`), второй источник правды не нужен.
- Правила для нативных appearances без платформы и для привязок дизайн-систем без appearances не нужны: по принятой предпосылке в продуктовых базах их нет, а их наличие останавливает миграцию.
