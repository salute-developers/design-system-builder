## MODIFIED Requirements

### Requirement: Небезопасные повторные запросы имеют устойчивый результат

API SHALL принимать ключ повторяемости для мутаций `POST`, `PUT`, `PATCH`, `DELETE`, включая импорт,
публикацию и откат. Чтения `GET`, `HEAD`, `OPTIONS` SHALL NOT создавать результаты повторяемых команд. Для операций конкретной DS её ID из маршрута SHALL входить в отпечаток команды.

#### Scenario: Повторяется тот же запрос

- **WHEN** проект, ключ, операция и хэш тела совпадают с завершённым запросом
- **THEN** API MUST вернуть ранее сохранённые статус, тело и технические метаданные ответа без повторного предметного изменения
- **THEN** повтор MUST NOT создавать новые предметные редакции, отметки или уведомления

#### Scenario: Ключ повторён с другим телом

- **WHEN** тот же проект и ключ используются с другим хэшем тела
- **THEN** API MUST отклонить повтор без выполнения предметной операции

#### Scenario: В прежнем результате нет сохранённых метаданных

- **WHEN** повторяется результат, сохранённый до добавления технических метаданных
- **THEN** API MUST вернуть сохранённые статус и тело, не выполняя команду заново
- **THEN** API MUST явно сообщить о необходимости сверки через `X-DS-Mutation-Metadata-Truncated: true`

#### Scenario: Чтение содержит ключ повторяемости

- **WHEN** клиент читает данные через `GET`, `HEAD` или `OPTIONS` с `Idempotency-Key`
- **THEN** API MUST NOT сохранять результат этого чтения в таблицу повторяемых команд

#### Scenario: Повтор специализированного изменения размеров или типографики

- **WHEN** повторяется завершённый PUT /tenants/{tenantId}/size-tokens/{tokenId}/value для spacing, radius или shadow либо PATCH /tenants/{tenantId}/typography-styles/{tokenId} с тем же проектом, ключом, операцией и исходным телом
- **THEN** API MUST вернуть сохранённый статус, тело и технические метаданные до повторной предметной записи и сравнения базовых редакций
- **THEN** более поздняя правка другого пользователя MUST NOT перезаписываться повтором

#### Scenario: Ключ специализированной записи использован с другим телом

- **WHEN** ключ завершённого изменения размера или типографики повторяется с другим исходным телом
- **THEN** API MUST вернуть 409 с существующим кодом IDEMPOTENCY_KEY_REUSED без предметных изменений

#### Scenario: Совместимость специализированной записи без ключа

- **WHEN** существующий клиент отправляет изменение размера или типографики без Idempotency-Key
- **THEN** API MUST сохранить прежние правила записи и базовых редакций без требования нового параметра дизайн-системы

#### Scenario: Повтор удаления не требует действующего ресурса

- **WHEN** удаление в DS A завершилось, ответ потерян, а тот же запрос повторяется после перезапуска клиента
- **THEN** сервер MUST проверить доступ к A и вернуть сохранённый результат без требования существования ресурса в активном чтении

#### Scenario: Ключ команды использован в другой DS

- **WHEN** ключ завершённой команды повторён в том же проекте, но в URL другой DS
- **THEN** API MUST вернуть IDEMPOTENCY_KEY_REUSED без воспроизведения ответа или предметной записи

#### Scenario: Прежний результат без доказанной области

- **WHEN** в хранилище есть результат старого контракта, для которого область DS не подтверждена новым отпечатком
- **THEN** новый scoped-запрос MUST вернуть явный конфликт повторяемости с подсказкой сверить результат
- **THEN** сервер MUST NOT угадать DS, перезаписать старый результат или выполнить команду заново с тем же ключом

## ADDED Requirements

### Requirement: Запись ограничена областью дизайн-системы транзакции

Мутация через DS URL SHALL сохранять данные только указанной DS. Ограничение MUST охватывать предметные редакции, новые идентичности и прямые изменения принадлежащих DS связей. Ошибка области SHALL отменять всю транзакцию и MUST NOT трактоваться как временный конфликт сериализации.

#### Scenario: Запись ресурса другой доступной системы
- **WHEN** URL выбирает A, а команда пытается записать ресурс B при доступе пользователя к обеим
- **THEN** сервер MUST отказать без фиксации изменений любой DS
- **THEN** ошибка MUST быть отдельным отказом области DESIGN_SYSTEM_SCOPE_MISMATCH с HTTP 409, если операция дошла до общей проверки записи; прежний 404 при отсутствии ресурса в выбранной области MUST оставаться допустимым

#### Scenario: Частично подготовленная составная запись
- **WHEN** операция уже вставила идентичности или изменила зависимые строки и затем обнаружила несовпадение DS
- **THEN** вся операция MUST откатиться, включая редакции, технические состояния, журнал и сохранённый результат повторяемости

#### Scenario: Прямая связь без редакций
- **WHEN** изменяется принадлежащая DS связь, например property_variations, без вставки предметной редакции
- **THEN** общая защита MUST запретить запись вне DS транзакции

#### Scenario: Изменение владельца строки
- **WHEN** UPDATE пытается перенести строку из A в B
- **THEN** защита MUST проверить прежнюю и новую область и отклонить перенос через обычный DS-маршрут

### Requirement: Служебные операции имеют явную область

Публичный DS-запрос SHALL устанавливать область из path до выполнения предметной работы; отсутствие области MUST NOT неявно отключать защиту. Начальное заполнение и жизненный цикл DS SHALL использовать явно определённый служебный режим с сохранением проектных прав.

#### Scenario: Создание новой системы
- **WHEN** создаётся DS без существующего designSystemId в URL коллекции
- **THEN** сервер MUST выделить область создаваемой системы для её строк и начального заполнения
- **THEN** это MUST NOT разрешать запись в другую существующую DS

#### Scenario: Публикация и удаление системы
- **WHEN** существующая операция публикации, отката или удаления меняет предметные и служебные данные
- **THEN** она MUST сохранять атомарность и явно разрешённую область, не используя отсутствие DS как общий обход
