# Контракт модели состояний для сервиса `db-service`

Документ фиксирует, что должно появиться в `db-service` (`js/services/db-service`). Основная часть изменения
выполняется там; вне сервиса меняется один файл — `backend-kt/scripts/import-uikit-api-meta.sh`,
см. `proposal.md`.

Wire-контракт `POST /ds/component-config/import` и `GET /ds/component-config` сохраняется: набор
состояний и на входе, и на выходе остаётся списком имён.

## 1. Словарь состояний

```
states
  id            uuid pk
  component_id  uuid null → components.id  on delete cascade
  name          text not null
  description   text
  created_at / updated_at

  unique (component_id, name)
  unique (name) where component_id is null
```

`component_id IS NULL` — состояние взаимодействия. Семь таких: `pressed`, `hovered`, `focused`,
`selected`, `activated`, `readonly`, `disabled`. Засеиваются детерминированными идентификаторами,
чтобы код ссылался на них без обращения к справочнику.

`component_id NOT NULL` — состояние, объявленное кодом компонента через поле `stateEnum`
в `uikit-api-meta.json`. Имя хранится в форме, встречающейся в конфигурациях оформления
(`dragging-over`, а не `DraggingOver`); в api-meta для этого есть поле `configName`.

Тип `state` и таблица `component_states` удаляются.

## 2. Набор состояний

```
state_sets
  id                  uuid pk
  state_ids           uuid[] not null
  owner_component_id  uuid null → components.id  on delete cascade
  created_at / updated_at

  unique index on (state_ids)
  gin index on (state_ids)
```

`state_ids` хранится отсортированным и дедуплицированным. Уникальность массива в PostgreSQL
позиционная — `{A,B}` и `{B,A}` считаются разными, — поэтому канонизация обязательна и
обеспечивается триггером, а не индексом.

GIN-индекс нужен для `state_ids @> ARRAY[...]` в триггере удаления.

Пустой набор — строка-сентинел с `state_ids = '{}'`. Через `NULL` нельзя: NULL-ы в btree различны,
и уникальность значений перестала бы работать именно для базовых значений. Сентинел защищён от
удаления триггером 5.4.

### 2.1 Владелец набора

`owner_component_id` — компонент, которому принадлежат компонентные состояния набора. `NULL`, если
набор состоит из одних состояний взаимодействия: у таких наборов владельца нет, и они разделяются
всеми компонентами (`{hovered}` — одна строка на 359 значений в 20 компонентах). Значение
вычисляется при записи триггером 5.1, а не приходит от клиента.

Колонка закрывает две разные ошибки, и вторая — та, ради которой она заводится.

**Смешанный набор.** Схема сама по себе не запрещает `{CheckBox.checked, Switch.checked}`: обе
строки в `states` существуют, поэтому проверка элементов на существование их пропускает. Имя
состояния уникально только внутри компонента — unique стоит на паре (`component_id`, `name`), — и
одноимённые состояния на разных компонентах в корпусе есть. Замер после заливки api-meta: 39
состояний в источнике, из них 4 совпали по имени с состояниями взаимодействия и не заводятся
(см. раздел 9), остальные 35 дали 17 различных имён — то есть половина имён разделяется
компонентами. `checked` объявлен тремя (`CheckBox`, `RadioBox`, `Switch`), `active`, `inactive`
и `none` — четырьмя каждое.

**Чужой набор.** Однородный набор `{Switch.checked}`, прицепленный к значению компонента
`CheckBox`. Внутренне он безупречен — смешивать нечего, — и проверкой самого набора не ловится.
При этом рождается он чаще смешанного: достаточно разрешить имя `checked` в идентификатор запросом
без фильтра по компоненту.

```sql
-- правильно
SELECT id FROM states WHERE name = 'checked' AND component_id = :componentId;
-- неправильно, выглядит так же, вернёт лишнюю строку
SELECT id FROM states WHERE name = 'checked';
```

Это не гипотеза: тот же класс ошибки уже дал 19 расхождений между `states_key` и
`property_value_states` на дубле `Checkbox`/`CheckBox`, см. раздел 9.

Цена чужого набора после этого изменения выше, чем была. Раньше кривая связь портила одно значение.
Теперь `DELETE` компонента `Switch` каскадом сносит `Switch.checked`, триггер 5.2 сносит наборы с
этим идентификатором, а каскад раздела 3 — значения, которые на них ссылались. То есть удаление
`Switch` удаляет значения у `CheckBox`, и политика при этом отрабатывает штатно: дефект не в ней,
а в чужом идентификаторе внутри набора. Побочно `GET /ds/states/{id}/impact` покажет в списке
затронутых компонент, не имеющий к удаляемому состоянию отношения, и это будет выглядеть как
ошибка предпросмотра, а не как порча данных.

Тихая форма того же дефекта: условие «`CheckBox` в фокусе И `Switch` включён» не наступает никогда,
поэтому переопределение просто не применяется. Ошибок нет, в админке строка выглядит нормально.

Колонка выбрана вместо проверки когерентности внутри триггера без колонки именно потому, что
проверка без колонки ловит только смешанный набор. Для чужого набора нужно сравнить владельца
набора с компонентом значения (раздел 3.1), а владелец должен быть где-то записан: иначе на каждой
записи значения пришлось бы раскрывать массив и джойнить `states`, вычисляя заново то, что
определяется один раз при создании набора.

## 3. Ссылка со значений

```
variation_property_values.state_set_id   uuid not null → state_sets.id  on delete cascade
invariant_property_values.state_set_id   uuid not null → state_sets.id  on delete cascade
style_combinations.state_set_id          uuid not null → state_sets.id  on delete cascade
```

`on delete cascade` обязателен на всех трёх ссылках и является частью политики раздела 4, а не
умолчанием. По умолчанию PostgreSQL ставит `NO ACTION`; тогда триггер 5.2 не удалил бы значения,
а упал бы на нарушении внешнего ключа, и удаление состояния стало бы невозможным вместо того,
чтобы стать наблюдаемым. Каскад из набора в значения — единственный механизм, которым политика
исполняется.

Уникальные индексы:

```
vpv  unique (style_id, property_id, appearance_id, state_set_id)
ipv  unique (design_system_id, component_id, property_id, appearance_id, state_set_id)
sc   unique (property_id, appearance_id, combination_key, state_set_id)
```

Удаляются: `property_value_states`, `variation_property_values.states_key`,
`invariant_property_values.states_key`, `style_combinations.states`.

`style_combinations` перестаёт нести базовое значение плюс массив переопределений в jsonb: каждое
значение становится отдельной строкой со своим набором.

### 3.1 Когерентность значения и набора

Значение SHALL ссылаться либо на набор без владельца, либо на набор, чей `owner_component_id`
совпадает с компонентом самого значения. Проверка выполняется при записи значения.

Компонент значения достаётся по-разному, и обе дороги существуют:

```
invariant_property_values.component_id                          — прямо в строке
variation_property_values → styles.variation_id
                          → variations.component_id             — два джойна
style_combinations        → style_combination_members.style_id
                          → styles.variation_id
                          → variations.component_id             — три джойна
```

У сочетания компонент определяется через участников, поэтому проверка для `style_combinations`
выполняется после того, как участники записаны, — по той же причине, по какой `combination_key`
заполняется отдельным шагом (`seed-dev.ts:36`). Если участники сочетания принадлежат разным
компонентам, это отдельный дефект, и проверка обязана его отклонить, а не выбирать один из них.

Без этой проверки колонка ловит только смешанный набор, а чужой — нет; именно она делает
`owner_component_id` осмысленной, см. раздел 2.1.

## 4. Политика удаления

Удаление состояния удаляет все наборы, которые его содержат, и все значения, которые на эти
наборы ссылаются. Набор не сжимается. Значения удаляются каскадом `state_set_id` из раздела 3;
без него политика не исполняется.

Обоснование — в `design.md`, раздел «Удаление состояния». Кратко: сжатие набора означает
перезапись базового значения переопределением, потому что переопределение на `{hovered}`
существует ровно там, где есть базовое значение. Удаление же ничего не ломает — замер показал,
что для каждого удаляемого значения на тех же координатах остаётся базовое.

Каскад вниз объявлен и ожидаем:

```
values → variation_platform_param_adjustments     cascade
       → invariant_platform_param_adjustments     cascade
       → component_style_references               cascade
             → component_style_reference_styles   cascade   (питает граф component_deps)
```

## 5. Триггеры

Внешние ключи внутрь массива в PostgreSQL невыразимы, поэтому целостность массива обеспечивается
тремя триггерами (5.1–5.3). Все три обязательны; отсутствие любого — дефект, а не оптимизация.
Четвёртый триггер (5.4) охраняет не массив, а строку-сентинел, и нужен в любой форме хранения
набора.

**5.1 Канонизация, валидация и владелец при записи.** `BEFORE INSERT OR UPDATE ON state_sets`:

- привести `state_ids` к отсортированному дедуплицированному виду;
- отклонить запись, если хотя бы один элемент отсутствует в `states`;
- отклонить запись, если компонентные состояния набора принадлежат более чем одному компоненту;
- вычислить `owner_component_id`: общий компонент компонентных состояний либо `NULL`, если их нет.

```sql
-- Агрегат по массиву, а не min(): у uuid в PostgreSQL нет min/max, и обращение к ним
-- роняет любую запись набора с `function min(uuid) does not exist`.
SELECT count(DISTINCT component_id), (array_agg(DISTINCT component_id))[1]
  INTO cnt, owner
  FROM states
 WHERE id = ANY(NEW.state_ids) AND component_id IS NOT NULL;

IF cnt > 1 THEN RAISE EXCEPTION ...; END IF;
NEW.owner_component_id := owner;   -- NULL, когда компонентных состояний в наборе нет
```

Владелец вычисляется, а не принимается от клиента: колонка производна от состава, и приём её
значения снаружи вернул бы в схему второй источник истины — ровно то, что изменение устраняет.

**5.2 Удаление зависимых наборов.** `AFTER DELETE ON states`:

```sql
DELETE FROM state_sets WHERE state_ids @> ARRAY[OLD.id];
```

Дальше работает каскад `on delete cascade` по `state_set_id` из раздела 3 — тот, что объявлен там
явно. Без него этот `DELETE` не пройдёт вовсе.

**5.3 Запрет `TRUNCATE`.** `BEFORE TRUNCATE ON states FOR EACH STATEMENT` — отклонить операцию.
Строчные триггеры на `TRUNCATE` не срабатывают, поэтому без этого триггера
`TRUNCATE states CASCADE` оставляет висячие идентификаторы в наборах.

**5.4 Защита сентинела.** `BEFORE DELETE ON state_sets` — отклонить удаление строки с
`state_ids = '{}'`; плюс `BEFORE TRUNCATE ON state_sets FOR EACH STATEMENT` — отклонить операцию.

Сентинел — разделяемая строка с наибольшим радиусом поражения в схеме: на неё ссылается всякое
базовое значение, то есть 5426 строк из 6271 на замерном корпусе. Под каскадом раздела 3 одна
команда `DELETE FROM state_sets WHERE state_ids = '{}'` сносит их все. Триггер 5.2 сентинел не
затрагивает — пустой массив не содержит удаляемого состояния, — поэтому защиты у него нет ниоткуда.
Обоснование то же, что у раздела 7.3: цена ошибки на разделяемой строке не должна зависеть от
осторожности оператора.

Оговорка по механизму: `TRUNCATE state_sets` без `CASCADE` отклоняет внешний ключ со значений,
не доходя до триггера (`cannot truncate a table referenced in a foreign key constraint`). Триггер
нужен для формы с `CASCADE`, где ключи снимаются, — проверено, отклоняются обе.

**Оговорка про `session_replication_role = replica`.** В этом режиме отключаются и триггеры, и
внешние ключи — проверено, разницы между формами нет. Логическая репликация и
`pg_restore --disable-triggers` обходят защиту одинаково в любой схеме.

## 6. Аудит целостности

У массива нет объявленного инварианта, который можно перепроверить повторным добавлением
ограничения. Поэтому запрос ниже входит в объём изменения как артефакт репозитория:

```sql
SELECT s.id, s.state_ids
  FROM state_sets s
 WHERE EXISTS (
   SELECT 1 FROM unnest(s.state_ids) x
    WHERE NOT EXISTS (SELECT 1 FROM states st WHERE st.id = x)
 );
```

Пустой результат — инвариант держится.

Второй запрос — на когерентность владельца, для случаев, когда набор или значение записали в обход
триггеров (`session_replication_role = replica`, восстановление дампа):

```sql
-- набор, чей владелец разошёлся с составом
SELECT s.id
  FROM state_sets s
  LEFT JOIN LATERAL (
    SELECT count(DISTINCT st.component_id) AS cnt, min(st.component_id) AS owner
      FROM states st
     WHERE st.id = ANY(s.state_ids) AND st.component_id IS NOT NULL
  ) o ON true
 WHERE o.cnt > 1 OR s.owner_component_id IS DISTINCT FROM o.owner;

-- значение, ссылающееся на чужой набор (вариант для инвариантных значений)
SELECT v.id
  FROM invariant_property_values v
  JOIN state_sets s ON s.id = v.state_set_id
 WHERE s.owner_component_id IS NOT NULL
   AND s.owner_component_id <> v.component_id;
```

## 7. Endpoints

### 7.1 Словарь

```
GET    /ds/states                    список, фильтр по component_id
GET    /ds/states/{id}
POST   /ds/states
PATCH  /ds/states/{id}
DELETE /ds/states/{id}               применяет политику раздела 4
```

Заменяет `/ds/component-states`. Совместимость с прежним путём не планируется.

### 7.2 Разрешение набора

```
POST /ds/state-sets/resolve
{ "stateIds": ["...", "..."] }
→ 200 { "id": "...", "ownerComponentId": "..." | null }
→ 400 если хотя бы один идентификатор отсутствует в states
→ 400 если компонентные состояния принадлежат разным компонентам
```

`ownerComponentId` возвращается, чтобы вызывающий мог сверить набор с компонентом значения до
записи и получить внятную ошибку вместо отказа на уровне БД. Клиент это поле не присылает.

Отказы 400 приходят от триггера, и текст его сообщения лежит **не** в `message` верхнего уровня:
drizzle заворачивает ошибку драйвера, и наверху оказывается текст запроса. Распознавать отказ
нужно, разворачивая цепочку `cause`, иначе ручка отдаёт 500 с сырым SQL вместо 400.

Единственная точка конструирования набора. Импорт и админка обязаны ходить сюда; прямая запись
в `state_sets` из клиентского кода запрещена.

Операция не является CRUD над ресурсом: она не создаёт набор по запросу клиента, а возвращает
идентификатор существующего либо заводит недостающий. Поэтому действие вынесено отдельным
сегментом и не занимает слот идентификатора в коллекции.

Сегмент, а не двоеточие: конвенции custom method с двоеточием в репозитории нет. Единственный
аналог — загрузка конфигураций — смонтирован обычным сегментом: `router.post("/import", …)`
(`js/services/db-service/src/routes/api/component-config-import.ts:63`) под префиксом `/ds/component-config`
(`js/services/db-service/src/routes/index.ts:80`), то есть боевой путь `POST /ds/component-config/import`. Строка
`components:import` встречается там только как значение `entityType` в журнале изменений
(строка 83) и как тег лога — она именует операцию в данных, а не в маршруте. Вводить ради одной
ручки вторую конвенцию нет причины, тем более что в Express двоеточие начинает имя параметра и
такой путь пришлось бы объявлять экранированно.

### 7.3 Предпросмотр удаления

```
GET /ds/states/{id}/impact
→ 200 { "stateSets": N, "values": N, "components": N }
```

Данные не изменяет. Нужен потому, что наборы разделяются между значениями: `{hovered}` — одна
строка, на которую ссылается 359 значений в 20 компонентах, а прежняя схема связей ограничивала
цену ошибки одним компонентом.

## 8. Миграция: переписать `0004`, а не добавлять `0005`

Новой миграции не создаётся. Структуры, которые это изменение снимает, целиком заведены последней
миграцией `0004_component_import.sql`, и она **ещё не применена на проде** — как и само изменение.
Проще не создавать `component_states`, `property_value_states`, обе `states_key` и
`style_combinations.states`, чем создать их и следующей же миграцией с них мигрировать.

Условие проверить до начала: если `0004` успела уйти на прод, всё ниже недействительно и нужна
отдельная `0005` с полным переносом данных.

### 8.1 Что это убирает

Переноса из старых структур не остаётся вовсе — переносить неоткуда, они не появляются. Отпадает и
урок про порядок шагов: `drizzle-kit` выполняет миграцию одной транзакцией, и падение
`invalid input value for enum state: "checked"` на `0004` случалось именно из-за приведения к типу,
который тут же удаляется. Здесь тип `state` не создаётся, удалять нечего.

Остаются **два** переноса, а не один.

Первый — тот, что `0004` делает и сегодня: до неё значение несло **одно** состояние в колонке
`variation_property_values.state` / `invariant_property_values.state`. Теперь эта колонка переезжает
сразу в `state_set_id`, минуя `states_key` и `property_value_states`.

Второй — `style_combinations.states jsonb`. Здесь исходная оценка была неверна: колонка заведена
не миграцией `0004`, а `0000_hot_marrow.sql`, то есть существует с первой миграции и на базе уровня
`0003` может содержать данные. Не создавать её нельзя — её нужно **развернуть и удалить**:
каждое переопределение становится отдельной строкой сочетания со своим набором.

Разворачивание обязано копировать участников из `style_combination_members`: идентичность сочетания
задаётся ими, и новая строка без копии перестала бы быть тем же сочетанием. Неизвестное имя
состояния обязано ронять миграцию, а не молча отбрасывать переопределение: оно и есть те данные,
ради которых разворачивание затевается.

Состояний, специфичных для компонента, на этом шаге быть не может: их заводит заливка
`uikit-api-meta.json`, а не миграция — так же, как и в нынешней `0004`. Значит все наборы,
построенные миграцией, состоят из одного состояния взаимодействия, `owner_component_id` у всех
`NULL`, и аудит-запросы раздела 6 на выходе обязаны быть пустыми.

### 8.2 Порядок внутри `0004`

Сохранить всё, что `0004` делает помимо состояний — значения `property_type`, `combination_key`
и его заполнение с проверкой на дубли, — и заменить часть про состояния на:

1. `states` — создать, засеять семь состояний взаимодействия детерминированными идентификаторами.
2. `state_sets` — создать вместе со строкой-сентинелом (`owner_component_id` у него `NULL`).
3. Завести по набору на каждое значение, реально встречающееся в колонке `state`; канонизировать.
4. `state_set_id` — добавить на три таблицы, заполнить (`NULL` в колонке `state` -> сентинел),
   перевести в `NOT NULL`, объявить внешние ключи с `ON DELETE CASCADE`.
5. Развернуть `style_combinations.states` в отдельные строки, скопировав участников.
6. Удалить колонки `state` и `style_combinations.states`; собрать уникальные индексы значений и
   сочетаний сразу на `state_set_id`.
7. Создать триггеры 5.1–5.4.

Порядок внутри шага 5 существен: наборы, которые он заводит, создаются до триггеров, поэтому
массив приходится канонизировать **явно** (`array_agg(DISTINCT id ORDER BY id)`). Без сортировки
уникальность `uuid[]` позиционная, и один и тот же набор лёг бы двумя строками.

### 8.3 Как это делается механически

`0004` регенерируется, а не правится по кускам: `drizzle-kit` диффит её от снимка `0003`, поэтому
достаточно привести схему к целевому виду и пересобрать.

1. Удалить `js/services/db-service/drizzle/0004_component_import.sql`, `js/services/db-service/drizzle/meta/0004_snapshot.json` и запись
   `idx: 4` из `js/services/db-service/drizzle/meta/_journal.json`.
2. Довести `js/services/db-service/src/db/schema.ts` до целевой схемы этого изменения.
3. `npm run db:generate` — новая `0004` сгенерируется от снимка `0003`.
4. Вернуть руками то, чего генератор не выдумает: заполнение `combination_key` с проверкой на
   дубли, перенос колонки `state` в наборы, засев словаря, триггеры.

### 8.4 Последствия для существующих баз

База, где прежняя `0004` уже применена, обновляется **сбросом**, а не миграцией: тег в
`__drizzle_migrations` совпадёт, и переписанная `0004` не выполнится. Порядок — `db:reset`, затем
сиды и повторная заливка `uikit-api-meta.json` и библиотек `theme-converter`. Целевой
`DATABASE_URL` проверять перед сбросом: предохранителей у `db:reset` нет.

Обратной миграции по-прежнему нет; откат — восстановлением дампа.

## 9. Предусловие

Устранить дубль компонентов по регистру: `Checkbox` в prod-сиде против `CheckBox` в
`uikit-api-meta.json`.

Смысл предусловия сместился вместе с решением из раздела 8, но само оно стало **строже**.

Прежде оно защищало миграцию: 19 строк, где `states_key` не совпадает с `property_value_states`,
потребовали бы выбора источника истины. Мигрировать эти строки больше не нужно — они принадлежат
локальной базе, которая по 8.4 сбрасывается.

Зато дубль воспроизводится при заливке и **ломает импорт**. Воспроизведено на чистой базе после
сброса, сида и заливки api-meta:

```
components                       states  properties
  CheckBox   (из api-meta)            2          24
  Checkbox   (из prod-сида)           0          26
  RadioBox   (из api-meta)            1          24
  Radiobox   (из prod-сида)           0          25
```

`findComponent` в `componentImport.ts` сопоставляет имя канонически — `lower()` плюс удаление
разделителей, — поэтому `CheckBox` и `Checkbox` оба сводятся к `checkbox`, и запрос возвращает две
строки. `ORDER BY` в нём нет, победитель произволен. На проверке выиграл сидовый `Checkbox`, у
которого состояний нет, и импорт конфигурации `CheckBox` вернул:

```
"unknownStates": ["checked"]
```

То есть переопределение по состоянию не записалось. У `Switch`, где дубля нет, та же конфигурация
прошла и дала набор с владельцем `Switch` — при том что `checked` объявлен тремя компонентами.

Отсюда два следствия для объёма:

- дубль обязан быть устранён до заливки, иначе часть переопределений теряется молча для базы,
  хотя и с диагностикой в `unknownStates`;
- отсутствие `ORDER BY` в `findComponent` — самостоятельный дефект: пока дубль существует, какой
  компонент выиграет, зависит от порядка строк. Это тот же класс, что открытый пункт 14.7
  архивированного change.

Заливка api-meta при этом ведёт себя корректно: словарь `states` теперь общий, поэтому скрипт
обязан **не заводить** компонентный дубль состояния взаимодействия. Из 39 состояний api-meta
4 совпали по имени с состояниями взаимодействия (`focused`, `disabled` и подобные) и пропущены;
создано 35.

## 10. Сгенерированные артефакты

Правила репозитория (`CLAUDE.md`, раздел «Sync rules»): после правки
`js/services/db-service/src/db/schema.ts` — `npm run db:generate` для SQL-миграции, затем `/sync-all`. Скилл сам обновляет
`js/services/db-service/src/validation/schema.ts`, `js/services/db-service/src/routes/api/*`, `js/services/db-service/src/openapi/spec.ts` и перегенерирует
`js/apps/admin/src/api/{openapi.json,types.gen.ts}`. Эти файлы **не редактируются руками** — правки в
них вносит только скилл.

Действует «batch first, sync last»: закончить все правки схемы и маршрутов, затем один прогон
`/sync-all`, а не по прогону на каждую правку.

Отдельно и вручную: `js/docs/db-schema.dbml` — поддерживаемое вручную зеркало схемы, скиллами не
покрыто. Изменение сносит три таблицы и добавляет две, поэтому зеркало обновляется в том же
change. Замечание: на момент написания оно уже отстало — `component_states`,
`property_value_states` и `states_key`, добавленные миграцией `0004`, в нём отсутствуют. Привести
его к `schema.ts` целиком, а не только по своей дельте.

## 12. Известные дефекты исходных данных

Не относятся к этому изменению, но встречаются при проверке и объясняют расхождение чисел.
