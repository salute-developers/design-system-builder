## Context

Состояния в `db-service` появились вместе с загрузкой конфигураций компонентов
(change `add-cli-components-push`, архив `2026-08-18`). Тогда было установлено, что конфигурации
задают переопределение сразу для **набора** состояний, причём набор смешивает два вида: состояния
взаимодействия (`pressed`, `hovered`) и состояния, объявленные кодом компонента (`checked`,
`indeterminate`). Из 212 наборов на корпусе шести библиотек 126 состоят только из состояний
взаимодействия, 86 сочетают оба вида.

Принятое тогда решение:

```
stateEnum          7 значений взаимодействия
component_states   состояния компонента, (component_id, name) unique
property_value_states   связь значение → одно состояние, ровно одна из двух ссылок
states_key         денормализованный ключ на строке значения: отсортированные имена через запятую
```

`states_key` понадобился потому, что уникальность значения выражается индексом
`(style_id, property_id, appearance_id, <набор>)`, а набор лежит в другой таблице и индексом
невыразим. Ровно та же конструкция уже применена в этой схеме к `style_combinations`:
`combination_key` плюс `style_combination_members`.

Проблема в том, что `states_key` и `property_value_states` описывают один факт и ничем не связаны.

Все измерения — на локальной установке `db-service-postgres-dev`, база `ds_registry`:
сид (`base`, 21 appearance) плюс загруженный `sdds_serv` (143 appearance). Продовая база
не затрагивалась.

### Удаление состояния: почему выбрана политика «удалять значения»

Рассматривались четыре политики. Решающим оказался замер: что произойдёт с данными при каждой.

**P2 «сжать набор»** (S → S−{X}, разрулить столкновения) — отвергнута. Замер сделан по всем 14
состояниям, задействованным хотя бы одним значением; сам словарь на этом корпусе шире — 7 состояний
взаимодействия плюс 20 различных имён в `component_states` (39 строк). Состояния, не задействованные
ни одним значением, при удалении не затрагивают ничего и в замер не входят. Замер показал, что при
удалении состояния почти каждый затронутый набор после сжатия совпадает с уже существующим, и в 95%
случаев значения на этих координатах **различаются** (таблица приводит шесть самых крупных из 14):

| состояние | значений задето | схлопнется в пустой набор | столкнётся | из них с другим значением |
|---|---|---|---|---|
| `hovered` | 359 | 334 | 359 | 340 |
| `pressed` | 335 | 312 | 335 | 328 |
| `selected` | 88 | 40 | 75 | 67 |
| `activated` | 46 | 46 | 46 | 46 |
| `focused` | 31 | 31 | 31 | 28 |
| `readonly` | 2 | 2 | 2 | 0 |

Это не случайность данных. Переопределение на `{hovered}` существует ровно потому, что есть
базовое значение, которое оно переопределяет. Сжатие означает перезапись базового значения
переопределением — то есть P2 портит данные, а не только требует 340 ручных решений.

Побочный вывод: ветка «сжатый набор свободен», ради которой массив и рассматривался как способ
удешевить удаление, на корпусе **не срабатывает ни разу** — ноль из шестнадцати. Аргумент
«массив даёт дешёвое удаление» снят как неподтверждённый.

**P1 «удалить значения»** — принята. Замер показал, что она не оставляет дырок: для каждого
значения, которое будет удалено, на тех же координатах есть базовое значение, к которому
компонент откатится.

| состояние | удалится значений | из них с набором >1 | **без базового фолбэка** | компонентов задето |
|---|---|---|---|---|
| `hovered` | 359 | 25 | **0** | 20 |
| `pressed` | 335 | 23 | **0** | 19 |
| `selected` | 88 | 48 | **0** | 5 |
| `activated` | 46 | 0 | **0** | 4 |
| `focused` | 31 | 0 | **0** | 7 |
| `in-edit`, `text-inlined` | 6 | 0 | **0** | 1 |
| `vertical`, `error` ×2 | 4 | 0 | **0** | 1 |
| `readonly` | 2 | 0 | **0** | 1 |
| `checked`, `dragging-over`, `inactive` | 1 | 0 | **0** | 1 |

Ноль во всём столбце «без фолбэка». Компонент после удаления состояния рендерится базовым
значением.

### Каскад вниз от удаляемых значений

```
variation_property_values / invariant_property_values
  ├─▶ variation_platform_param_adjustments    cascade
  ├─▶ invariant_platform_param_adjustments    cascade
  └─▶ component_style_references              cascade
        └─▶ component_style_reference_styles  cascade   (питает граф component_deps)
```

Замер на текущем корпусе: обе таблицы `*_platform_param_adjustments` пусты целиком, поэтому ноль
в них ничего не доказывает. `component_style_references` — 855 строк, из них 506 висят на
значениях, и **ни одна не висит на значении с состояниями**. Механизм при этом действующий:
достаточно одной конфигурации вида «в `pressed` вложенная иконка берёт другое оформление», и
удаление `pressed` порвёт ребро графа зависимостей. Каскад фиксируется в спеке, паники не требует.

## Decisions

### Набор хранится массивом, а не таблицей участников

Рассматривались две формы.

```
        B. МАССИВ (принято)                  C. ТАБЛИЦА УЧАСТНИКОВ

 state_sets                                  state_sets
 ┌──────┬───────────────────────┐            ┌──────┬──────────────────┐
 │ id   │ state_ids uuid[]      │            │ id   │ key text  UNIQUE │
 │ s-01 │ {a1b2, c3d4}   UNIQUE │            │ s-01 │ a1b2,c3d4        │
 └──────┴───────────────────────┘            └──────┴──────────────────┘
              ссылок нет                              ▲ state_set_states
                                                      │ (set_id, state_id) FK
```

C даёт ссылочную целостность даром, но требует денормализованного ключа: уникальность «по набору
строк в другой таблице» индексом невыразима — это ровно то ограничение, из-за которого в схеме
появился `combination_key`. А ключ, который ведёт приложение (в проекте так и сделано,
`seed-dev.ts:36`, отдельным `UPDATE` после вставки участников), может разойтись с составом.

То есть C воспроизводит на уровне справочника ровно тот класс дефекта, ради устранения которого
затевается изменение. В B расходиться нечему: массив **и есть** набор, второго представления нет.

Подсчёт триггеров после этого:

| | B: массив | C: участники |
|---|---|---|
| удаление состояния | триггер | триггер *(FK сам только сожмёт набор)* |
| валидация элементов при записи | триггер | FK, даром |
| `TRUNCATE states` | триггер `ON TRUNCATE` | FK блокирует, даром |
| ведение ключа набора | — | триггер, иначе расхождение |
| канонизация | триггер **нормализует** | триггер только отвергает |
| **представлений набора** | **одно** | два |

Три триггера против двух — C дешевле по количеству, но у B нет второго источника истины, а это
та валюта, в которой сейчас платится за `states_key`. Охранный триггер на сентинеле в этот счёт
не входит: он нужен одинаково в обеих формах, потому что охраняет строку набора, а не состав. Дополнительно `BEFORE`-триггер в B может
канонизировать массив, а не отвергать запись; `CHECK` так не умеет и не может — subquery в
ограничении запрещён (проверено).

Решающим фактором стало число писателей. Наборы конструируют импорт и админка; копирование
дизайн-системы наборы **не создаёт** — состояния глобальны (`components` не имеет
`designSystemId`), поэтому копия переиспользует существующий `state_set_id`. Двух писателей мало,
и оба сводятся к одной серверной ручке `state-sets/resolve` — при единственной точке
конструирования FK перестаёт быть решающим преимуществом.

### Что именно проверено про целостность массива

Утверждения ниже измерены на этой же установке, а не приняты по аналогии.

**`session_replication_role = replica` — ничья, не аргумент.** Внешние ключи реализованы
системными триггерами и в этом режиме отключаются наравне с пользовательскими: в эксперименте
после удаления родителя осталась и строка-сирота в таблице участников, и висячий id в массиве.
Логическая репликация и `pg_restore --disable-triggers` обходят обе формы одинаково.

**`TRUNCATE` — не ничья.** `TRUNCATE states` при наличии FK отклоняется
(`cannot truncate a table referenced in a foreign key constraint`); с `CASCADE` участники
вычищаются, а массив остаётся с висячими id, потому что строчные триггеры на `TRUNCATE` не
срабатывают. Отсюда третий триггер — `FOR EACH STATEMENT ... ON TRUNCATE`, отклоняющий операцию.

**Уникальность по `uuid[]` позиционная.** Проверено: `{A,B}` и `{B,A}` приняты как два разных
набора. Канонизация обязательна и индексом не обеспечивается — отсюда нормализация в
`BEFORE`-триггере.

**Пере-проверка постфактум.** У FK инвариант объявлен и перепроверяется повторным добавлением
ограничения. У массива объявленного инварианта нет, поэтому в объём входит аудит-запрос как
артефакт, а не как устная договорённость.

### Пустой набор — сентинел, а не NULL

`state_set_id NULL` сломал бы уникальность базовых значений: NULL-ы в btree различны, и
`unique(style_id, property_id, appearance_id, state_set_id)` перестал бы работать именно для
базовых значений — то есть для большинства. Это ровно та дыра, которую сегодня закрывает
`states_key NOT NULL DEFAULT ''`.

PostgreSQL 16.14 поддерживает `NULLS NOT DISTINCT` (проверено), но установленная в проекте версия
drizzle не выражает этот флаг на индексах: в `drizzle-orm@0.45.1` `nullsNotDistinct` есть только
на `unique()`-ограничениях (`pg-core/unique-constraint.js`), в билдере `uniqueIndex()`
(`pg-core/indexes.js`) его нет. Поэтому: строка-сентинел с `state_ids = '{}'` и
`state_set_id NOT NULL`.

Цена сентинела — одна разделяемая строка, от которой зависит всё: базовых значений на замерном
корпусе 5426 из 6271, и все они ссылаются на неё. Под `ON DELETE CASCADE`, которого требует
политика удаления, обычный `DELETE` этой строки сносит их разом, а триггер удаления зависимых
наборов её не прикрывает — пустой массив не содержит удаляемого состояния. Отсюда отдельный
охранный триггер на `state_sets`, см. `backend-contract.md` 5.4.

### `style_combinations.states` нормализуется

Сегодня строка сочетания несёт базовое `value text NOT NULL` плюс массив переопределений в jsonb:

```json
[{"state": ["activated"], "value": 32}]
```

Это четвёртое представление состояний, вне словаря и вне какой-либо ссылочной целостности. Под
P1 удаление `activated` снесло бы 46 значений и не тронуло эти строки — в jsonb осталось бы имя
несуществующего состояния.

Решение: строка сочетания несёт одно значение и один `state_set_id`, уникальность становится
`(property_id, appearance_id, combination_key, state_set_id)`. Переопределения разворачиваются в
отдельные строки. Затронуто 4 строки из 2303, стоимость миграции околонулевая.

Альтернатива «оставить jsonb вне объёма» отвергнута: после всей работы остался бы четвёртый
способ хранить состояния, и обнаружился бы он на следующем удалении состояния.

### Предпросмотр удаления

Сегодня `DELETE /ds/component-states/:id` (`component-states.ts:56`) — обычный CRUD без единой
проверки, и цена ошибки ограничена одним компонентом, потому что связи лежат по одной на значение.
После перехода на разделяемые наборы та же кнопка на глобальном состоянии стоит 359 значений в
20 компонентах: `{hovered}` — одна строка, на которую ссылается всё.

Поэтому в объём входит `GET /ds/states/{id}/impact`. Обоснование то же, что у `--dry-run` в
`components push`: разрушительная операция должна быть наблюдаемой до выполнения.

## Risks / Trade-offs

- [Забытый триггер портит данные молча] → В отличие от C, где забытый триггер даёт громкую ошибку
  на уникальности ключа, в B висячий id не обнаруживается ничем. Смягчение: три триггера вынесены
  в спеку поимённо как требования, плюс аудит-запрос как отдельный артефакт. Без этого условия
  вариант B не защищается.
- [Админка соберёт массив сама] → Конструирование набора вынесено в `state-sets/resolve`; сборка
  массива на клиенте запрещена требованием спеки.
- [Потеря типизированного union состояний в admin] → `validation/schema.ts:34` выводит
  `StateSchema` из `stateEnum.enumValues`, и оттуда типы уезжают в OpenAPI и в сгенерированные
  типы админки. Закрытый словарь становится открытым: админка переходит на валидацию по
  справочнику в рантайме. Тот же класс регрессии, что чинился в `PROP_TYPES`, но в обратную
  сторону и осознанно.
- [Набор ссылается на состояние чужого компонента] → Схема сама по себе не запрещает ни
  смешанный набор `{CheckBox.checked, Switch.checked}`, ни однородный чужой `{Switch.checked}`
  на значении `CheckBox`. Второй опаснее: он внутренне безупречен, рождается из разрешения имени
  без фильтра по компоненту — тот же механизм, что дал 19 расхождений на дубле
  `Checkbox`/`CheckBox`, — и после этого изменения удаление компонента `Switch` каскадом сносит
  значения `CheckBox`. Принято: колонка `state_sets.owner_component_id`, вычисляемая триггером из
  состава, плюс проверка когерентности при записи значения. Обоснование выбора и разбор обоих
  случаев — в `backend-contract.md` разделы 2.1 и 3.1.
- [Миграция вмораживает расхождение] → 19 строк, где `states_key` не совпадает со связями,
  требуют выбора источника истины. Устранение дубля `Checkbox`/`CheckBox` вынесено в предусловие,
  а не в эту миграцию.
- [Каскад рвёт граф зависимостей компонентов] → На корпусе `component_style_references` ни разу не
  висит на значении с состояниями, но механизм действует. Фиксируется в спеке как объявленное
  поведение, чтобы не обнаружиться как сюрприз.

### Что подтвердилось прогоном

Модель проверена на локальной установке после сброса, миграции, сидов и заливки api-meta.

- Предпросмотр удаления совпал с фактом до единицы: `impact` для `hovered` обещал 2 набора и
  93 значения в 10 компонентах, удаление сняло ровно столько. У всех 93 жертв на тех же
  координатах осталось базовое значение — столбец «без фолбэка» и здесь нулевой.
- Одноимённые состояния разных компонентов различаются на практике: `checked` объявлен тремя
  компонентами, и конфигурация `Switch` дала набор с владельцем `Switch`, а не чужой.
- Отвергаются: смешанный набор, чужой набор на значении, неизвестный элемент, удаление сентинела,
  `TRUNCATE` словаря и наборов. Аудит-запросы после всех операций пусты.

Проверено и на корпусе: сброшенная база, миграция, оба сида, заливка api-meta и `components push`
пяти библиотек `theme-converter` дали 6264 значения, 1573 сочетания и 20 наборов. `impact` для
`hovered` предсказал 178 значений в 13 компонентах, удаление сняло ровно столько, фолбэк остался
у всех. Все четыре аудит-запроса пусты.

Число наборов — 20, а не ожидавшиеся ~212. Оценка 212 снималась со старого корпуса шести
библиотек; в этом прогоне грузилась одна дизайн-система, две библиотеки не конвертируются из-за
дефекта исходных конфигураций, а часть компонентных состояний не доходит до значений из-за дубля
по регистру. К модели это отношения не имеет, но ожидание в спеке было завышено.

Побочно корпус подтвердил исходную посылку изменения: `error` существует двумя разными наборами —
у `CodeField` и у `CodeInput`. По именам они склеились бы в один.

## Migration Plan

Отдельной миграции нет: переписывается последняя, `0004_component_import.sql`. Она ещё не применена
на проде — там же, где и само это изменение, — а снимаемые структуры заведены целиком ею.
`component_states`, `property_value_states`, обе `states_key` и `style_combinations.states` дешевле
не создавать, чем создать и следующей же миграцией с них уйти.

Решение снимает большую часть плана и вместе с ним — риск, ради которого план был выстроен именно
так. Порядок шагов был существен потому, что `drizzle-kit` выполняет миграцию одной транзакцией и
приведение к типу, который тут же удаляется, падает на непустой базе; это и есть урок `0004`
(`invalid input value for enum state: "checked"`). Здесь тип `state` не создаётся вовсе, поэтому
падать нечему.

Остаются два переноса. Первый — тот же, что `0004` делает и сегодня: колонка `state` переезжает
сразу в `state_set_id`, минуя `states_key` и `property_value_states`. Компонентных состояний на
этом шаге не бывает — их заводит заливка `uikit-api-meta.json`, — поэтому построенные миграцией
наборы одноэлементны, а `owner_component_id` у них `NULL`.

Второй перенос обнаружился уже при реализации и опровергает первоначальную оценку. Считалось, что
`style_combinations.states jsonb` заводится самой `0004`, а значит после её переписывания
«разворачивать нечего». На деле колонка заведена `0000_hot_marrow.sql` и существует с первой
миграции, то есть на базе уровня `0003` может нести данные. Разворачивание входит в объём:
переопределения становятся отдельными строками, участники сочетания копируются, неизвестное имя
состояния роняет миграцию.

Порядок и механика регенерации — в `backend-contract.md`, разделы 8.2 и 8.3.

Цена решения — в 8.4: база, где прежняя `0004` уже применена, обновляется сбросом, а не миграцией.
Тег в `__drizzle_migrations` совпадёт, и переписанная `0004` не выполнится. На локальной установке
это приемлемо; после сброса корпус восстанавливается сидами и повторной заливкой.

Условие, при котором всё это верно, стоит проверить перед началом: если `0004` уходит на прод
раньше этого изменения, план возвращается к отдельной `0005` с полным переносом данных.

Откат: обратной миграции нет, выполняется восстановлением дампа.

## Open Questions

- **Именование ручки словаря.** `/ds/states` вместо `/ds/component-states` ломает admin API.
  Совместимость с прежним путём не планируется — потребителей вне админки нет, но это стоит
  подтвердить перед реализацией.
- ~~**Владелец набора.**~~ Закрыт: принята колонка `state_sets.owner_component_id`. Вариант
  «требование к триггеру без колонки» отвергнут не по стоимости, а по охвату: проверка одного лишь
  состава ловит смешанный набор, но не чужой — а чужой и есть та форма, которую даёт разрешение
  имени состояния без фильтра по компоненту. Чтобы поймать его, нужно сравнить владельца набора с
  компонентом значения, а для этого владелец должен быть записан: иначе на каждой записи значения
  пришлось бы раскрывать массив и джойнить `states`. То, что случаев смешивания в корпусе нет,
  против колонки не играет — корпус не содержит и чужих наборов только потому, что предусловие
  требует устранить дубль `Checkbox`/`CheckBox` до миграции.
- **Судьба `readonly`.** Открытый пункт 14.4 архивированного change. После этого изменения он
  становится решением про строку данных, а не про миграцию схемы: `readonly` задействован
  на 2 значениях, оба совпадают с базовыми, то есть удаляется без потерь.
