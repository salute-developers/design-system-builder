## 3. Триггеры и целостность

- [x] 3.1 Триггер `BEFORE INSERT OR UPDATE ON state_sets`: канонизировать `state_ids` (сортировка и дедупликация); отклонить запись, если хотя бы один элемент отсутствует в `states`; отклонить, если компонентные состояния набора принадлежат более чем одному компоненту; вычислить `owner_component_id` — общий компонент компонентных состояний либо `NULL`, если их нет. Владельца брать через `(array_agg(DISTINCT component_id))[1]`: у `uuid` в PostgreSQL нет `min`/`max`, и обращение к ним роняет любую запись набора. Владелец вычисляется, а не принимается от клиента: колонка производна от состава.
- [x] 3.2 Триггер `AFTER DELETE ON states`: удалить все наборы, чей `state_ids` содержит удалённое состояние. Требуется GIN-индекс на `state_ids`.
- [x] 3.3 Триггер `BEFORE TRUNCATE ON states FOR EACH STATEMENT`: отклонить операцию. Строчные триггеры на `TRUNCATE` не срабатывают, поэтому без него `TRUNCATE ... CASCADE` оставляет висячие идентификаторы.
- [x] 3.4 Триггеры защиты сентинела: `BEFORE DELETE ON state_sets` отклоняет удаление строки с `state_ids = '{}'`, `BEFORE TRUNCATE ON state_sets FOR EACH STATEMENT` отклоняет операцию. Под каскадом из 2.3 удаление этой одной строки сносит все базовые значения — 5426 из 6271 на замерном корпусе, — а триггер 3.2 её не прикрывает: пустой массив не содержит удаляемого состояния.
- [x] 3.5 Проверка когерентности значения и набора при записи значения: значение ссылается либо на набор без владельца, либо на набор, чей `owner_component_id` равен компоненту значения. Компонент берётся из `invariant_property_values.component_id` напрямую, для вариативных — через `styles.variation_id → variations.component_id`, для сочетаний — через `style_combination_members.style_id → styles → variations`. Без этой проверки колонка ловит только смешанный набор `{CheckBox.checked, Switch.checked}`, но не чужой `{Switch.checked}` на значении `CheckBox` — а именно чужой рождается из разрешения имени состояния без фильтра по компоненту.
- [x] 3.6 Для сочетаний проверку выполнять после записи участников: компонент сочетания определяется только через них. Участники из разных компонентов — отдельный дефект, проверка обязана его отклонить, а не выбирать один из компонентов.
- [x] 3.7 Оформить аудит-запросы как артефакты репозитория, а не как устную договорённость: у массива объявленного инварианта нет. Три запроса — висячие идентификаторы в наборах, расхождение `owner_component_id` с составом, значения на чужом наборе. Тексты в `backend-contract.md` разделе 6.
