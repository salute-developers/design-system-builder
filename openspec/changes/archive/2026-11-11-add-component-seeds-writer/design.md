## Контекст

`GeneratedDesignSystemComponentInitializer` ds-service заполняет новую дизайн-систему из `component-seeds.json`: компонент — вариации со стилями, привязки свойств к вариациям (`propertyVariations`), appearance с `defaults`, `values` по вариации и стилю, `invariants`; значение — `prop` и `token` или `value`, необязательно `state` и `adjust`; связи — отдельный список `dependencies`. Инициализатор проверяет сиды целиком и при пропущенном свойстве или токене не заводит ничего. Пакет `dsbuilder components fetch` описывает те же данные в другом виде: файл на appearance, `props`, `bindings`, `variations`, значения с `type`, `value`/`default` и `states`.

## Цели / Вне целей

**Цели:**
- Перенос в сиды названных компонентов и appearance без ручного редактирования JSON.
- Неназванные записи файла не меняются: точечное обновление не затирает остальные 63 компонента.

**Вне целей:**
- Перегенерация всех сидов из базы стенда: в базе стенда есть локальные правки, которых в сидах быть не должно.
- Изменения ds-service и формата сидов.

## Решения

### Источник — пакет `components fetch`, выбор — флагами

Пакет уже нормализован базой (типы свойств глобального слоя), его же пишет `import:plasma`. Команда берёт из него только то, что названо флагами, поэтому выгрузку всей ДС стенда можно передавать целиком: локальные правки других компонентов в сиды не попадут. Альтернатива — писать сиды прямо из `import:plasma` — отвергнута: часть значений после импорта дорабатывается (состояния, шрифты, строки из конфига), и сиды должны совпадать с тем, что реально залито.

### `token` по определениям токенов ds-service

Ссылка на токен — значение, имя которого есть в `token-definitions.json`; так проверяет и `SeedResourcesContractTest`. Путь по умолчанию — ресурс ds-service в репозитории, флаг `--token-definitions` его подменяет.

### Описания вариаций

Пакет не хранит описаний. Описание вариации берётся из уже существующих сидов по имени вариации (`view` → «Вид», `size` → «Размер»), без совпадения — имя вариации; описание стиля — его имя, как в текущих сидах.

### Формат записи

Файл пишется `JSON.stringify` без отступов и без перевода строки в конце — так записан текущий файл, и повторная запись без изменений даёт тот же файл. Компоненты упорядочены по имени, связи — по родителю, затем по порядку.

## Риски / Компромиссы

- [В пакет попадут локальные правки названного компонента] → для сидов передаются компоненты и appearance, импортированные из ядра и sdds-serv и не правленные вручную на стенде; скилл `add-component` фиксирует это правило.
- [Сиды сошлются на свойство, которого нет в глобальном слое стенда] → инициализатор не заведёт ни одного компонента; перед публикацией сидов на стенд залить глобальный слой из актуальной меты, проверка — создание новой ДС на чистой базе.
