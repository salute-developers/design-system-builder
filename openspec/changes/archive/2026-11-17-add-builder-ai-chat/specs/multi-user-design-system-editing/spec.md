## ADDED Requirements

### Requirement: Запись с ожидаемым черновиком

Прикладная запись DS MAY получать в контексте запроса идентификатор ожидаемого черновика. Сервер SHALL сверять его с активным черновиком в той же транзакции и под той же блокировкой, в которых запись получает границу активного черновика. При расхождении запись MUST NOT выполняться, и use case MUST вернуть конфликт `draft_changed`. Без ожидаемого черновика поведение записи MUST оставаться прежним. Публичный HTTP API ds-service MUST NOT меняться: ожидаемый черновик задают только вызовы внутри процесса.

#### Scenario: Черновик не менялся
- **WHEN** запись получает ожидаемый черновик, совпадающий с текущим активным
- **THEN** запись MUST выполниться так же, как без него

#### Scenario: DS опубликовали после выдачи идентификатора
- **WHEN** запись получает идентификатор черновика, который после публикации перестал быть активным
- **THEN** use case MUST вернуть конфликт `draft_changed`, а в новом активном черновике MUST NOT появиться изменений

#### Scenario: Публикация и запись одновременно
- **WHEN** публикация и запись с ожидаемым черновиком выполняются одновременно
- **THEN** запись MUST либо попасть в публикуемый черновик до его закрытия, либо получить `draft_changed`, но MUST NOT попасть в следующий черновик

#### Scenario: Повтор с тем же ключом после смены черновика
- **WHEN** запись с ключом идемпотентности и ожидаемым черновиком уже выполнилась, DS опубликовали, и та же команда повторена с тем же ключом
- **THEN** сервер MUST воспроизвести сохранённый результат первой записи по существующим правилам повторяемости

#### Scenario: HTTP-запрос не задаёт ожидаемый черновик
- **WHEN** изменяющий HTTP-запрос к ds-service приходит с любыми заголовками
- **THEN** ожидаемый черновик MUST NOT задаваться, и запись MUST выполняться в текущий активный черновик, как до этого изменения
