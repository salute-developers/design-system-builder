# ИИ-чат в билдере

## Зачем

Сейчас дизайн-систему можно менять только вручную в редакторах билдера или через свой агент, подключённый к MCP. Чтобы подключить агента, нужно установить CLI, войти через PKCE и настроить клиент. Встроенный чат даёт ту же возможность прямо в интерфейсе: пользователь пишет «перекрась кнопку в красный», а изменение появляется в черновике. Прикладные операции редактирования уже есть в ds-service, поэтому инструменты чата — тонкие адаптеры к ним внутри монолита, без второй реализации предметной логики.

## Что изменится

- В монолите `backend-kt/app` появится подсистема ИИ-ассистента. `POST /api/projects/{projectId}/ai/chat` запускает ход агента в фоне и отвечает `turnId`. `GET /ai/turns/{turnId}/events?after=N` отдаёт возобновляемый поток событий хода, `DELETE` останавливает ход, `GET /ai/status` сообщает, включён ли чат. Ход не зависит от соединения: отключение клиента не прерывает запись, а клиент переподключается и дочитывает события.
- Подсистема объявляет свой каталог инструментов и порт их выполнения. Реализация порта — адаптер в `backend-kt/app`, который вызывает use case ds-service внутри процесса с участником проекта из проверенного контекста запроса. MCP-ядро `frontend-kt` чат не использует: оно остаётся входом для внешних агентов, и инструменты двух входов могут расходиться.
- Появится слой `LlmClient`, не зависящий от провайдера, с собственной моделью сообщений. В нём два адаптера:
  - `OpenAiCompatibleClient` — для провайдеров с API формата OpenAI (ZAI и другие); провайдер выбирается настройками, по умолчанию ZAI `glm-4.5-flash`;
  - `GigaChatClient` — OAuth, формат `functions`/`function_call`, один вызов инструмента за ответ.
- Модели доступен отобранный набор из 23 инструментов. Каждый передаётся, только если серверный `PolicyEvaluator` разрешает пользователю нужное право. DS, версию и ключ идемпотентности задаёт сервер, в схемах для модели их нет.
- Удаляющие операции и записи сверх лимита за ход выполняются только после подтверждения пользователя. Подтверждение подписано сервером и привязано к операции, пользователю и DS.
- События хода хранятся в памяти процесса до 10 минут после завершения, только для переподключения. Разговор между ходами хранит клиент. Редакторы перерисовываются через уже существующий поток изменений черновика.
- Клиентская панель чата — отдельное изменение. Этот контракт рассчитан на неё: `POST /ai/chat` принимает необязательный контекст экрана (раздел редактора, тема, выбранный токен или открытый компонент с конфигурацией), чтобы модель понимала «сделай её красной» без поиска объекта и не трогала общие токены, когда речь о компоненте.
- Появится набор эталонных сценариев, по которому проверяется, справляется ли модель с нашими инструментами.
- Добавится ADR-0008 о встроенном ассистенте: свои инструменты поверх use case ds-service внутри монолита, а не MCP-ядро и не HTTP к собственному API. ADR-0004 для внешних агентов не меняется, удалённый MCP-сервер по-прежнему не делается.

## Возможности

### Новые возможности

- `builder-ai-chat` — HTTP-контракт чата: запуск хода, возобновляемый поток событий, остановка, проверки, подтверждение операций, права, ограничения хода.
- `ai-agent-tooling` — цикл агента и каталог инструментов: отбор по разрешениям, контекст вызова, адаптер к use case ds-service, история для модели, эталонные сценарии.
- `llm-provider-adapters` — слой `LlmClient`, нейтральная модель сообщений, адаптеры OpenAI-совместимого API и GigaChat, их настройка.

### Изменённые возможности

- `multi-user-design-system-editing` — прикладная запись может получить ожидаемый черновик в контексте запроса; если DS опубликовали и черновик сменился, запись отклоняется с `draft_changed`. Так подтверждённая в чате операция не попадёт в следующий черновик. Публичный HTTP API не меняется.
- `backend-monolith-runtime` — монолит подключает подсистему ИИ-ассистента с выключателем `AI_ENABLED` и при остановке дожидается начатых вызовов инструментов чата до закрытия подсистемы DS. Инструменты чата вызывают DS внутри процесса через адаптер в `app`, как и другие связи подсистем.

## Влияние

- **backend-kt.**
  - ds-service: необязательное поле `expectedDraftId` в `DsRequestContext`, проверка в общей инфраструктуре записи, отказ `draft_changed`. HTTP API и OpenAPI не меняются.
  - Новая сборка `backend-kt/ai-assistant` (`runtime` и `feature-chat`) подключается в `backend-kt/app` и в корневую сборку `backend-kt` как включаемая сборка.
  - Префикс `/api/projects/` уже публичный, граница не меняется.
  - `backend-kt/app` получает адаптер `InProcessChatTools` к use case ds-service и зависимости от модулей `feature-tokens`, `feature-themes`, `feature-components` ds-service. Сборка монолита от `frontend-kt` не зависит.
  - OpenAPI — `ai-assistant/runtime/src/main/resources/openapi/documentation.yaml`; при сборке `processResources` переносит ресурсы в `dsbuilder/ai/...`, как у документации. В каталог `backend-kt/api-reference/src/catalog.mjs` добавляется запись.
  - Новые переменные окружения: `AI_ENABLED`, `AI_PROVIDER`, `AI_BASE_URL`, `AI_API_KEY`, `AI_MODEL`, `AI_EXTRA_BODY`, `AI_RETRY_ERROR_CODES`, `AI_GIGACHAT_AUTH_KEY`, `AI_GIGACHAT_SCOPE`, `AI_GIGACHAT_OAUTH_URL`, `AI_GIGACHAT_BASE_URL`, `AI_GIGACHAT_CA_PATH`, `AI_MAX_STEPS`, `AI_MAX_WRITES`, `AI_TURN_TIMEOUT_SECONDS`, `AI_TOOL_CALL_TIMEOUT_SECONDS`, `AI_HISTORY_MAX_CHARS`, `AI_MESSAGE_MAX_CHARS`, `AI_TOOL_RESULT_MAX_CHARS`, `AI_TURN_STORE_MAX_MB`. Их нужно прописать в `docker-compose.prod.yml`, `backend-kt/docker-compose.local.yml` и `backend-kt/app/README.md`.
  - Отдельного контейнера, порта или проверки готовности нет: подсистема работает в процессе `backend` и использует его `/ready`.
- **frontend-kt.** Не меняется.
- **CI.** В матрицы `validate-backend-kt.yml` добавляется `ai-assistant`.
- **js.** В этом изменении не меняется: панель чата в `js/apps/client` и её флаги развёртывания делаются отдельной задачей по этому контракту.
- **Внешние сервисы.** API выбранного провайдера модели; ключи хранятся только в env монолита. Для GigaChat нужен корневой сертификат НУЦ Минцифры, смонтированный в контейнер.
- **Данные.** Новых таблиц и миграций нет. История разговора хранится в памяти вкладки и передаётся при каждом новом ходе. События и итог хода, включая данные DS из результатов инструментов, хранятся в памяти процесса до 10 минут после завершения хода. Решение рассчитано на один экземпляр `backend`. Изменения DS попадают в существующий журнал от имени пользователя.

## Вне целей

- Удалённый MCP-сервер по HTTP/SSE для внешних агентов.
- Хранение истории разговоров на сервере, общие чаты, учёт расхода токенов и квоты по проектам.
- Изменение общего каталога компонентов, публикация версий и управление участниками проекта из чата.
- Перенос клиентского чата из локальной ветки `AI-CHAT`.
- Отмена хода чата: нужны компенсирующие записи с проверкой ревизии, а не откат журнала.
- Поиск по документации: нужна проверка принадлежности публикации к DS.
- Клиентская панель чата в `js/apps/client`: отдельное изменение по HTTP-контракту из этого.
