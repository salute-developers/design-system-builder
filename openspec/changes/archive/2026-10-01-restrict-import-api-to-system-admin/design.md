## Context

Состояние после архивных change `add-cli-components-import-api` и `add-cli-import-api-android-view`: CLI запускает Gradle-задачу плагина `dsBuilder`, читает файл меты, нормализует его (Compose и Android View) и шлёт манифест на `POST /api/projects/{projectId}/ds/component-config/import-api-meta`. Ручка требует scope `components:write`, привязывает компоненты к дизайн-системе из тела запроса и пишет строку в `design_system_changes` с `design_system_id` этой дизайн-системы.

Как устроен признак системного администратора (проверено по коду):

```
Keycloak: realm-роль `system_admin`
   │  JWT: realm_access.roles
   ▼
gateway (KeycloakJwtVerifier → GlobalRole.SYSTEM_ADMIN → actor.isSystemAdmin)
   │  доверенный заголовок X-System-Admin: true
   ▼
db-service: isSystemAdmin(req)  (routes/api/utils.ts)
```

- Ключ проекта никогда не системный администратор: `TrustedProjectPrincipalFactory` отбрасывает ключ с admin-флагом, а gateway выставляет ему `X-System-Admin: false`.
- Сегодня в `db-service` признак только **открывает обход** (scope и фильтр по проекту пропускаются); требования «обязательно администратор» нет нигде. Маршруты `/api/admin/*` (`tables`, `queries`, `nl-query`, `schema`) тоже его не проверяют: gateway требует лишь залогиненного пользователя (`auth_request /_auth_user`, принимает только `Bearer` JWT; `ProjectKey` даёт `401`).
- Маршрут `/api/admin` уже есть в локальном и prod-конфиге gateway, передаёт `X-User-Id` и `X-System-Admin` и имеет общий лимит тела 2 МБ.

`design_system_changes` — лента изменений **одной** дизайн-системы: её читают `GET /design-system-changes/by-design-system/:id`, `/design-systems/:id/changes` и запросы каталога («неопубликованные черновые изменения» после последней опубликованной версии, по фиксированному списку типов). Колонки `design_system_id` и `entity_id` сейчас обязательные, `entityType` — свободный текст (`components:import-api-meta` в списки каталога не входит).

CLI: user session уже есть (`dsbuilder auth login`, политика `CredentialPolicy.USER_SESSION`, forced `user-session` обходит источники ключей). Сессия привязана к точному API URL.

## Goals / Non-Goals

**Goals:**

- Только системный администратор может импортировать мету; проверка выполняется сервером и не зависит от клиента.
- Ключ проекта не имеет доступа к операции вообще: отсекается gateway'ем и ещё раз `db-service`.
- Команда не зависит от проекта, дизайн-системы, `.sdds` и Gradle: нужны файл меты, платформа, API URL и user session.
- Импорт по-прежнему записывается в `design_system_changes`.
- Администратор видит причину отказа, а не общий текст про проект.

**Non-Goals:**

- Проверка роли в CLI (источник истины — сервер).
- Защита существующих `/api/admin/*` маршрутов `db-service` (отдельная задача).
- Платформа iOS и `react`.
- Автоматический запуск из CI: ключи не принимаются, а user session требует интерактивного `auth login`.
- Привязка компонентов к дизайн-системам другим способом: для этого остаются существующие маршруты `design-system-components`.

## Decisions

### Административный маршрут и двойная защита

Новый маршрут `POST /api/admin/component-config/import-api-meta`; проектный маршрут `.../ds/component-config/import-api-meta` удаляется вместе с `requireScope("components:write")` для него. Защита двухслойная:

1. **Gateway.** `/api/admin` использует `auth_request /_auth_user`: принимает только `Bearer` JWT. Ключ проекта получает `401` до обращения к `db-service`.
2. **db-service.** Middleware `requireSystemAdmin` стоит **до** разбора тела и отвечает `403`, если `X-System-Admin` не равен `true`.

Проверка в `db-service` **строгая**, в отличие от `requireScope`, который пропускает запрос вообще без заголовков (прямой вызов без gateway). Для административной ручки отсутствие заголовка означает отказ: иначе прямой вызов в обход gateway сам стал бы «административным». Цена — тестам и ручному `curl` на `3008` придётся передавать заголовок явно.

Альтернативы:

- **Проектный маршрут с проверкой администратора только в `db-service`.** Работает, но ключ проекта доходит до `db-service`, а `projectId` в пути не имеет смысла для операции над глобальным слоем.
- **Проверка роли только в gateway.** Нарушает принцип «доверенный заголовок проверяет и сервис, который его использует»: `db-service` доступен на `3008` в локальном контуре.
- **Отдельный scope ключа.** Оставляет возможность писать в общий слой ключу проекта, чего мы и хотим избежать.

`db-service` остаётся недоступным напрямую из сети в prod (его развёртывание вне этого репозитория): надёжность `X-System-Admin` опирается на эту изоляцию, как и у остальных мест, где заголовок используется.

### Запрос и отчёт без дизайн-системы

Тело: `platform`, `meta.source`, `dryRun`, `components`. Нет `designSystemId`, не создаются `design_system_components`, из отчёта уходит `createdLinks`. Поиск дизайн-системы и ответ `404` исчезают. `meta.source` содержит **имя файла**, а не путь: локальный путь администратора не должен попадать в журнал сервера.

### Журнал: `design_system_id` необязателен

Миграция `ALTER TABLE design_system_changes ALTER COLUMN design_system_id DROP NOT NULL`; в `schema.ts` колонка теряет `.notNull()`, в `docs/db-schema.dbml` и `nl-query/schema-context.ts` отражается необязательность.

Импорт пишет строку с `design_system_id = NULL`, `entity_type = components:import-api-meta`, `operation` (`created`, если созданы компоненты или свойства, иначе `updated`), `entity_id` — свежий `uuid` запуска (у глобальной операции своего идентификатора нет, а колонка обязательна), `data` — `userId` из `X-User-Id`, `platform`, `source` (имя файла), `dryRun` и счётчики отчёта. Строка пишется в той же транзакции, поэтому dry run откатывает и её.

Строки с `NULL` не попадают в ленты дизайн-систем: запросы по ним фильтруют по идентификатору, запрос ленты каталога делает `inner join` с `design_systems`, а запросы «черновиков» ограничены фиксированным списком типов. Общий `GET /design-system-changes/` вернёт их, что для общей ленты уместно. Публичный `POST /design-system-changes/` продолжает требовать `designSystemId` (необязательность — свойство хранилища, а не контракта создания).

Альтернативы:

- **Хранить `design_system_id` обязательным и требовать его в запросе** (дизайн-система как контекст журнала): не нужна миграция, но запись принадлежала бы одной дизайн-системе, хотя операция общая, и администратор вынужден был бы выбирать её без причины.
- **Одна запись на каждую дизайн-систему**: шум во всех лентах и рост с их числом.
- **Отдельная таблица журнала**: чище по смыслу, но требуемый журнал — именно `design_system_changes`.

### CLI без проекта: файл, платформа, user session

Контракт команды: `dsbuilder components import-api --from <файл> --platform <compose|android-view> --api-url <url> [--apply] [--dry-run] [--strict] [--map-type from:to]`.

- `--from` и `--platform` обязательны: платформа нужна для выбора нормализатора и поля `platform`, а автоопределение по форме ненадёжно (меты Compose и iOS обе массивы). Неверный файл по-прежнему даёт понятную ошибку (мета View вместо Compose отклоняется как «not a …»).
- Use case не читает project context и не знает `projectId`/`designSystemId`. Последовательность: явный API URL (`resolveForWrite`), credential, чтение и нормализация файла, печать цели, запрос.
- Credential всегда `CredentialPolicy.USER_SESSION`: ключи проекта и `--api-key` для этой команды не принимаются; отсутствие session даёт сообщение «run dsbuilder auth login».
- Путь файла читается через `WorkspaceFileSystem`, относительный путь приводится к абсолютному. Файл может быть как сырым выводом генератора, так и выводом плагина: нормализаторы читают обе формы.
- Цель перед отправкой: платформа, путь файла, число компонентов, свойств и состояний, API URL с источником. Строки `Project:` и `Design system:` уходят.

Версия меты теперь определяется выбором файла администратором, а не зависимостью проекта; это осознанная потеря гарантии «мета соответствует версии uikit проекта», потому что импорт перестал быть проектной операцией. Отчёт печатает путь, размер которого администратор видит сам.

### Удаление пути через Gradle

`Capability.API_META`, ветки `API_META` в `AndroidGradleDelegate` и `IosCliDelegate`, `PlatformApiMetaSource`, порт `ApiMetaSource` в нынешней форме (запуск делегата), опция `--tool` команды и соответствующие требования спек удаляются: после перехода на файл они были бы мёртвым кодом со спеками, которые никто не использует. Порт `ApiMetaSource` остаётся как чтение локального файла.

### Причина отказа в сообщении

`AuthenticatedHttpClient` сейчас печатает для `403` «Credential has no access to this project», а для `401` «Credential is missing or invalid», независимо от причины. Для админской ручки это вводит в заблуждение (отказ значит «нужна роль», а не «проект»). При `401` и `403` клиент дописывает к сообщению текст `error` или `message` из JSON-тела ответа, если он есть (`Server: <причина>`). Тела без этих полей и пустые тела ведут себя как раньше, поэтому остальные команды не меняются; значения секретов в таких ответах не возвращаются.

### Размер тела на административном маршруте

У `/api/admin` нет собственного `client_max_body_size`, действует общий лимит 2 МБ (у проектного маршрута `ds` — 16 МБ). Манифест Compose порядка 1300 свойств занимает сотни килобайт, поэтому лимит не нарушается, но запас всего в несколько раз. В локальном и prod-конфиге gateway для `/api/admin` задаётся тот же лимит 16 МБ, что у `ds`.

## Risks / Trade-offs

- **BREAKING для вызовов с ключом проекта.** Все, кто сегодня использует `import-api` с ключом, перестанут работать; выпущенные CLI получат `404` на старый маршрут. Backend и CLI нужно обновлять вместе; в `USAGE.md` описывается новый способ.
- **Нет автоматического запуска.** Ключи не принимаются, user session интерактивна; для разового наполнения глобального слоя администратором это допустимо, для CI — нет.
- **Строгая проверка заголовка ломает прямые вызовы `db-service`.** Тестам и локальной отладке нужен `X-System-Admin: true`; это намеренно.
- **Надёжность `X-System-Admin`** опирается на недоступность `db-service` напрямую. В локальном контуре `3008` открыт, и заголовок можно подставить вручную; в prod защита зависит от сети.
- **Необязательный `design_system_id` — изменение схемы общей таблицы.** Затронуты `schema.ts`, `db-schema.dbml`, типы админки (поле становится `string | null`) и текст для nl-query; потребители, группирующие записи по дизайн-системе, должны учитывать `NULL`. Проверено, что запросы лент и каталога фильтруют по идентификатору или делают `inner join`.
- **Версия меты не гарантируется проектом.** Администратор может выбрать не тот или устаревший файл; смягчение — печать пути и чисел до отправки, dry run по умолчанию и аддитивная запись.
- **Остальные `/api/admin/*` маршруты по-прежнему не проверяют роль.** Это отдельная находка, вне объёма change.
