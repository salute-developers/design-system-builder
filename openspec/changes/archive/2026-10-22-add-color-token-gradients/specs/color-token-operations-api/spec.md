## ADDED Requirements

### Requirement: Тип семейства следует из вида значений

`ds-service` SHALL хранить у всех определений цветового токена тип `gradient`, если хотя бы одно значение
хотя бы одного члена семейства в какой-либо теме дизайн-системы, режиме или на платформе — градиент, и тип
`color` в остальных случаях. Тип SHALL вычисляться на границе активного черновика операциями создания и
изменения значений цветового токена, записью значений через общие маршруты значений токенов, удалением темы и откатом её создания, а также откатом любой записи журнала о цветовом токене (значения или определения) в той же транзакции. Членами семейства SHALL считаться определения по правилу имени независимо от их текущего типа.
Перед вычислением операция SHALL блокировать технические состояния определений всех членов семейства в
устойчивом порядке. Смена типа SHALL записываться предметными редакциями определений с путём `/type` и SHALL NOT
изменять значения других тем.

#### Scenario: Градиент в одном режиме одной темы

- **WHEN** в дизайн-системе с темами A и B токен `surface` / `accent` типа `color` получает в теме B градиент
  в режиме `dark` на web, iOS и Android
- **THEN** в активном черновике все определения семейства MUST получить тип `gradient` редакциями с путём
  `/type`
- **THEN** значения темы A MUST NOT получить новых редакций
- **THEN** `X-DS-Mutation-Metadata` MUST содержать технические редакции изменённых значений и определений

#### Scenario: Убран последний градиент

- **WHEN** у семейства типа `gradient` единственное градиентное значение заменено цветом
- **THEN** все определения семейства MUST получить тип `color` в активном черновике

#### Scenario: Тип не меняется

- **WHEN** изменение значений не меняет вычисленный тип семейства
- **THEN** операция MUST NOT создавать редакции определений

#### Scenario: Одновременная запись в двух темах

- **WHEN** одна транзакция добавляет градиент в теме A, а параллельная убирает последний градиент в теме B
- **THEN** вычисления типа MUST выполняться последовательно под блокировкой определений семейства
- **THEN** после обеих транзакций тип семейства MUST соответствовать итоговым значениям всех тем

#### Scenario: Откат значения

- **WHEN** пользователь откатывает запись журнала о значении, которая внесла единственный градиент семейства
- **THEN** откат MUST в той же транзакции вернуть семейству тип `color`

#### Scenario: Откат переименования

- **WHEN** у определения в черновике изменились имя и производный тип, и пользователь откатывает переименование
- **THEN** после отката тип семейства MUST соответствовать действующим значениям, а не прежнему типу записи

#### Scenario: Откат определения одного члена

- **WHEN** у семейства `{brand, brand-hover}` градиент задан только у `brand-hover`, и пользователь откатывает
  запись определения `brand`
- **THEN** все члены семейства MUST иметь один тип, соответствующий действующим значениям

#### Scenario: Удалена тема с единственным градиентом

- **WHEN** удаляется тема, в которой было единственное градиентное значение семейства
- **THEN** семейство MUST получить тип `color` в той же транзакции

#### Scenario: Новая тема

- **WHEN** создаётся тема в дизайн-системе с несидовым токеном типа `gradient`
- **THEN** тема MUST получить начальные значения этого токена так же, как для несидового токена типа `color`

#### Scenario: Создание с градиентом

- **WHEN** запрос создания содержит `type: "color"`, а значение какого-либо члена — градиент
- **THEN** API MUST создать определения с типом `gradient`
- **THEN** ответ MUST содержать `type: "gradient"`

#### Scenario: Пакетная запись не меняет тип

- **WHEN** значения пишутся через `PUT /tenants/{id}/token-values`
- **THEN** API MUST NOT менять тип определений

#### Scenario: Общий маршрут значения

- **WHEN** значение цветового токена пишется через `PATCH /api/ds/token-values/{id}`
- **THEN** API MUST проверять его по правилам вида значения, хранить сплошное значение платформы строкой и
  пересчитывать тип семейства

### Requirement: Сплошные значения платформ хранятся строкой

`ds-service` SHALL хранить сплошное значение `ios` и `android` цветового токена массивом из одной строки цвета
при любом типе семейства. Значение, переданное слоем `[{ "kind": "color", "background": <цвет> }]`, SHALL
сохраняться строкой `[<цвет>]`. `GET /api/ds/tenants/{tenantId}/token-values` и общий `GET /api/ds/token-values` SHALL отдавать сплошные
значения `ios` и `android` семейства типа `gradient` слоем `[{ "kind": "color", "background": <цвет> }]`, а семейства
типа `color` — строкой, так что потребители пакета получают значения в форме своего типа без перезаписи других
тем при смене типа.

#### Scenario: Чтение градиентного семейства

- **WHEN** у семейства типа `gradient` значение `android` в теме A режима `light` хранится как
  `["[general.green.500]"]`
- **THEN** `token-values` темы A MUST вернуть `value: [{ "kind": "color", "background": "#RRGGBBAA" }]` с цветом
  по палитре темы и `paletteRef: "[general.green.500]"`, без `sourceValue`

#### Scenario: Общий маршрут значений

- **WHEN** плагин читает те же значения через `GET /api/ds/token-values`
- **THEN** сплошное значение `android` градиентного семейства MUST прийти слоем `color`, как в чтении по теме

#### Scenario: Запись слоем цвета

- **WHEN** клиент передаёт значение `ios` как `[{ "kind": "color", "background": "#1A9E32FF" }]`
- **THEN** API MUST сохранить `["#1A9E32FF"]`

#### Scenario: Историческая версия

- **WHEN** `token-values` читается с `versionId` опубликованной версии
- **THEN** форма сплошных значений MUST определяться типом семейства на границе этой версии

### Requirement: Градиентные семейства приводятся к виду значений миграцией

Миграция Flyway V15 `ds-service` SHALL привести существующие семейства типа `gradient` к правилу вида значений
во всех дизайн-системах, темах и границах версий без создания черновых редакций и записей журнала.
Семейство без градиентной функции хотя бы в одном web-значении SHALL считаться цветовым: его нативные градиенты
— заглушки сида, которые на web не видны. Строки редакций SHALL изменяться на месте с отключением защитных
триггеров только на время миграции, как в V7.

#### Scenario: Семейство-заглушка

- **WHEN** у всех членов семейства `text` / `accent-minor-gradient` во всех темах web-значение — HEX, а
  `ios` и `android` — слой `linear` «белый → чёрный»
- **THEN** после миграции все редакции определений семейства MUST иметь тип `color`
- **THEN** web-значения MUST стать массивом из одной строки — первого HEX, а значения `ios` и `android` MUST
  стать тем же значением

#### Scenario: Семейство с градиентом

- **WHEN** хотя бы одно web-значение семейства `surface` / `accent-gradient` — градиентная функция
- **THEN** определения MUST сохранить тип `gradient`
- **THEN** у членов, чьё web-значение в той же теме и режиме — HEX, значения `ios` и `android` MUST стать
  `[<тот же HEX>]`
- **THEN** градиентные значения `ios` и `android` MUST NOT измениться

#### Scenario: Журнал после миграции

- **WHEN** миграция применена к базе с активным черновиком
- **THEN** журнал черновика MUST NOT содержать записей, вызванных миграцией

#### Scenario: Сид после миграции

- **WHEN** миграция применена к базе с сидом дизайн-системы
- **THEN** тип `gradient` MUST остаться у 5 из 17 сидовых семейств: `text`, `surface` и `outline` /
  `accent-gradient`, `surface` / `skeleton-gradient` и `surface` / `skeleton-deep-gradient`
- **THEN** признак `overridden` у всех значений MUST быть `false`

#### Scenario: Сид новой дизайн-системы

- **WHEN** после миграции создаётся дизайн-система или тема из сидов
- **THEN** её определения и значения MUST соответствовать тем же правилам, что и после миграции

### Requirement: Собственное значение платформы

Элемент значения операций цветового токена SHALL иметь необязательное поле `overridden` (по умолчанию `false`).
Для `ios` и `android` `overridden: true` SHALL означать значение, заданное отдельно для платформы, `false` —
значение, построенное клиентом из web. `ds-service` SHALL хранить признак в предметной редакции значения как
путь `/overridden` и SHALL возвращать его в `GET /tenants/{id}/token-values`. Для `web` признак SHALL быть
`false`.

#### Scenario: Своё значение Android

- **WHEN** Editor отправляет изменение значений, где у члена `surface.default.accent` значение `android` в
  режиме `dark` передано с `overridden: true`
- **THEN** чтение значений темы MUST вернуть это значение с `overridden: true`, а значения `web` и `ios` — с
  `overridden: false`
- **THEN** редакция значения MUST содержать изменённые пути `/value` и `/overridden`

#### Scenario: Признак у web

- **WHEN** значение `web` передано с `overridden: true`
- **THEN** API MUST вернуть `400 INVALID_TOKEN_VALUE` и MUST NOT менять значения

#### Scenario: Признак без поля

- **WHEN** элемент значения не содержит `overridden`
- **THEN** API MUST сохранить значение с `overridden: false`

#### Scenario: Изменился только признак

- **WHEN** значение платформы не изменилось, а признак `overridden` изменился
- **THEN** API MUST записать новую редакцию значения с путём `/overridden`

## MODIFIED Requirements

### Requirement: Цветовой токен — семейство определений

`ds-service` SHALL считать цветовым токеном семейство определений одного типа (`color` или `gradient`) с
общими группой и именем: `<group>.<subgroup>.<name>` и `<group>.<subgroup>.<name>-<state>`, где `subgroup` —
`default`, `on-dark`, `on-light`, `inverse`, а для группы `background` — `dark`, `light`, `inverse`; `state` —
`hover`, `active`, `brightness`. Операции над токеном SHALL адресовать семейство любым `tokenId` его члена. Тип
семейства SHALL определяться видом его значений, а не выбором пользователя.

#### Scenario: Семейство по идентификатору члена

- **WHEN** операция получает `tokenId` определения `text.on-dark.accent-hover`
- **THEN** API MUST работать с семейством `text` / `accent` того типа, который действует у его определений на
  границе активного черновика

#### Scenario: Определение вне правила семейства

- **WHEN** имя определения не соответствует правилу семейства
- **THEN** операции над цветовым токеном MUST отклонять его с `400 INVALID_TOKEN_FAMILY`

### Requirement: Изменение значений цветового токена

`ds-service` SHALL предоставлять `PUT /api/ds/tenants/{tenantId}/color-tokens/{tokenId}/values`, которая
записывает переданные значения членов семейства в текущей теме предметными редакциями активного черновика с
базовой редакцией каждого значения и в той же транзакции вычисляет тип семейства.

#### Scenario: Успешное изменение

- **WHEN** Editor отправляет значения членов `text.default.accent` и `text.default.accent-hover` с
  `baseRevision` каждого значения
- **THEN** API MUST записать редакции изменившихся значений этих членов в текущей теме
- **THEN** значения других членов семейства, других токенов и других тем MUST NOT получить новых редакций
- **THEN** тело ответа MUST содержать `type` семейства, а технические редакции изменённых значений и
  определений — заголовок `X-DS-Mutation-Metadata`; поле `editRevision` остаётся совместимым и не используется

#### Scenario: Неполный набор значений члена

- **WHEN** у переданного члена нет значения для какой-либо пары платформы и режима
- **THEN** API MUST вернуть `400 INVALID_TOKEN_FAMILY` и MUST NOT менять значения

#### Scenario: Токен из пути вне семейства

- **WHEN** `tokenId` из пути принадлежит дизайн-системе, но его тип не `color` и не `gradient` или имя вне
  правила семейства
- **THEN** изменение значений и удаление MUST вернуть `400 INVALID_TOKEN_FAMILY`

#### Scenario: Член другого семейства

- **WHEN** запрос содержит `tokenId`, не входящий в семейство токена из пути
- **THEN** API MUST вернуть `400 INVALID_TOKEN_FAMILY` и MUST NOT менять значения

### Requirement: Операции опубликованы в контракте ds-service

Операции SHALL быть описаны в группе `contracts/route-manifest.json` с `origin: ds-service` и в контракте
`openapi/documentation.yaml` с `x-permission: tenants:write`, схемами запросов и ответов и кодами ошибок.
Схема `ColorTokenValueItem` SHALL описывать поле `overridden` и формы значения: цвет, web-градиент и слои
`ios` и `android`; ответ изменения значений SHALL содержать `type`.

#### Scenario: Документ OpenAPI

- **WHEN** `ds-service` отдаёт OpenAPI
- **THEN** документ MUST содержать четыре операции цветового токена — создание, изменение значений,
  удаление и перенос — с их схемами
- **THEN** `ColorTokenValueItem` MUST содержать `overridden`, а ответ изменения значений — `type`

#### Scenario: Тесты манифеста db-service

- **WHEN** выполняются тесты манифеста маршрутов db-service
- **THEN** операции MUST пропускаться как операции с `origin: ds-service`
