## Контекст

`ds-service` перенесён с `db-service` в рамках Change `migrate-db-service-to-kotlin-ds-service` и развивался параллельно задачам PLASMABLDR-186 и PLASMABLDR-187. В итоге в общей ветке `dev` обе реализации расходятся в четырёх местах:

| Поведение `db-service` | Коммит | Состояние в `ds-service` |
| --- | --- | --- |
| `POST /ds/component-config/web-adapter` | `db429a7f` (187) | маршрута нет, Gateway отдаёт `404` |
| смещения из поправок платформенных параметров в `/export` | `db429a7f` (187) | берётся только колонка `adjustment` |
| ссылки на палитру в `GET /tenants/:id/token-values` | `b4a5bb76` (186) | отдаётся сохранённое `value`; не переносится, см. решение 3 |
| `List.listItemDividerHeight` в сидах | `b4a5bb76` (186) | в снимке осталось `listItemDividerWidth` |

Требования к самому поведению уже есть в основных спецификациях (`cli-components`, `design-system-model-api`); они написаны для эталонной реализации. Этот Change закрепляет их за `ds-service` и добавляет то, чего в них нет: правила доступа к web-адаптеру.

Ограничения: схема PostgreSQL и Flyway-миграции не меняются; `ds-service` собирается без Node.js и файлов `db-service`; в application-слое один UseCase на сценарий, агрегирующие классы запрещены архитектурными тестами.

## Цели / Вне целей

**Цели:**

- `components fetch` для React и загрузка значений темы в CLI работают через `ds-service` так же, как через `db-service`.
- Ответы двух затронутых маршрутов совпадают с эталоном на одной базе.
- Снимок компонентов не ломает инициализацию на базе с актуальными метаданными.

**Вне целей:**

- Изменение `db-service`, CLI, генератора и клиента.
- Начальная опубликованная версия дизайн-системы `base`: `ds-service` не создаёт `base` и не владеет prod-сидером. Если версия понадобится на стенде, её по-прежнему пишет сидер `db-service`.
- Удаление web-параметра `iconButtonPadding` у `IconButton.paddingEnd`: это строка глобальных метаданных, в снимке `ds-service` её нет.
- Отказ от поправок платформенных параметров как источника смещений и от самого web-адаптера — оба решения временные и в эталоне, переносятся как есть.

## Решения

### 1. Web-адаптер — отдельный сценарий, а не расширение выгрузки

Новый порт `ComponentWebAdapterRepository` и `GetComponentWebAdapterUseCase` рядом с существующими сценариями `component-config`. Метод в `ComponentConfigRepository` не добавляется: порт уже обслуживает три сценария, а web-адаптер — временное решение, которое должно удаляться целиком, одним набором файлов.

Маршрут регистрируется в том же блоке `/api/ds/component-config`, что и `/export`: адресация телом, тот же permission `components:read`, та же проверка принадлежности через `ComponentOwnership.canReadDesignSystem`. Отсутствие доступа к дизайн-системе скрывается ответом `404`.

Альтернатива — отдавать данные адаптера внутри `/export`. Отклонена тем же доводом, что и в эталоне: формат выгрузки общий для платформ.

### 2. Смещения подставляются только в выгрузке

`ComponentConfigBuilder` общий для чтения одного конфига и выгрузки и различает их флагом `exported`. В эталоне смещения из поправок читает только `buildComponentPackage`; маршрут одного конфига собирает ответ отдельным кодом и поправки не смотрит. Поэтому источник смещений подключается отдельным признаком `withPlatformOffsets`, который выставляет только выгрузка, и только для инвариантов и значений вариаций — комбинации стилей эталон не трогает. Импорт собирает конфиг тем же сборщиком для сравнения «до и после», но смещений из поправок не видит: эталон в этом сравнении их тоже не учитывает.

Числом считается непустая строка в десятичной записи с необязательными знаком, дробной частью и экспонентой. Эталон проверяет `Number.isFinite(Number(value))`, который дополнительно принимает шестнадцатеричную запись и окружающие пробелы; в данных таких поправок нет, а `String.toDoubleOrNull` разошёлся бы с эталоном в другую сторону (`NaN`, `1f`). Расхождение ограничено явным шаблоном и покрывается тестом.

### 3. Ссылки на палитру в значениях темы не переносятся

Формат `GET /api/ds/tenants/{id}/token-values` в `ds-service` задаёт `theme-palette-api`: у каждой темы своя копия палитры и группы токенов, поэтому сервис сам раскрывает цвет по палитре темы, обнуляет `paletteId` и отдаёт исходную ссылку в `paletteRef`. Строка `[type.shade.saturation]` из эталона заставила бы потребителя раскрывать её по общей палитре и давала бы неверные цвета темы с изменённой палитрой, а поверх раскрытого цвета перезаписала бы его ссылкой. CLI раскрывает только значения вида `[...]` и пропускает HEX без изменений, поэтому генерация темы работает с обоими форматами.

### 4. Порядок ответа web-адаптера

Записи, ключи `styles` и `templates` сортируются тем же сравнением строк, которое `ds-service` уже применяет в выгрузке (`toSortedMap`, `compareBy`). Эталон использует `localeCompare`, и порядок ключей может отличаться там, где первое различие имён — заглавная буква против строчной (`textColor` и `textarea`): это camelCase-ключи `templates` и имена стилей. Порядок записей по `componentName` совпадает. Содержимое при этом одинаково, а детерминированность в пределах одной реализации сохраняется; подключать `Collator` ради побайтного совпадения порядка ключей не стоит.

### 5. Снимок правится вручную

`component-seeds.json` — зафиксированный ресурс, генерация из `db-service` удалена намеренно. Переименование — одна ссылка в `List.propertyVariations`; вместе с ней обновляется контрольная сумма в `ComponentSeedsResourceTest`.

## Программное проектирование

```kotlin
// domain
data class ComponentWebAdapterEntry(
    val componentName: String,
    val name: String,
    val description: String?,
    val compose: List<String>,
    val styles: Map<String, Map<String, Map<String, String>>>, // стиль -> свойство -> параметр -> шаблон
)

// application
interface ComponentWebAdapterRepository {
    /** `null`, когда дизайн-система недоступна проекту или не существует. */
    suspend fun load(projectId: ProjectId, systemAdmin: Boolean, designSystemId: UUID): List<ComponentWebAdapterEntry>?
}

class GetComponentWebAdapterUseCase(
    policy: DsAccessPolicy,
    transactions: TransactionRunner,
    repository: ComponentWebAdapterRepository,
) {
    suspend fun execute(context: DsRequestContext, designSystemId: UUID): DsResult<List<ComponentWebAdapterEntry>>
}

// data
internal class ExposedComponentWebAdapterRepository : ComponentWebAdapterRepository
internal class PlatformParamOffsets { // источник смещений для ComponentConfigBuilder
    fun load(appearanceId: UUID): Offsets
    data class Offsets(val invariant: Map<UUID, String>, val variation: Map<UUID, String>)
}

// presentation
@Serializable data class ComponentWebAdapterRequest(val designSystemId: String)
@Serializable data class ComponentWebAdapterEntryResponse(
    val componentName: String,
    val name: String,
    val description: String? = null,
    val compose: List<String>? = null,
    val styles: Map<String, Templates>? = null,
)

```

Необязательные поля ответа со значением `null` не кодируются — это часть контракта, а не настройка по умолчанию, и закрепляется контрактным тестом ответа.

## Риски / Компромиссы

- [На стенде свойство `List` ещё называется `listItemDividerWidth`] → после выкладки снимок ссылается на `listItemDividerHeight`, проверка метаданных находит пропуск, и инициализация компонентов новых тем молча не выполняется. Сейчас та же поломка на любой базе с актуальными сидами. Снимается переименованием свойства на стенде до выкладки (см. план).
- [Порядок ключей web-адаптера может отличаться от эталона] → после переключения бэкенда первый `components fetch` может дать разовый дифф порядка в `web-adapter.json`; содержимое то же.
- [Число в поправке определяется иначе, чем в эталоне, для редких записей] → шаблон перечислен в решении 2 и проверяется тестом; в сидах и на стендах таких значений нет.
- [Смещения читаются на каждую конфигурацию отдельным запросом] → `ComponentConfigBuilder` уже строит ответ по одной конфигурации; два дополнительных запроса на конфигурацию не меняют порядок затрат. Пакетное чтение — отдельная оптимизация всей выгрузки.

## План проверки и развёртывания

**Локальные автоматические проверки:** модульные тесты сценария и ответов, интеграционные тесты `ds-service` на PostgreSQL через Testcontainers, проверка манифеста маршрутов, `tools/verify fast` и `tools/verify full`.

**Внешняя проверка до архивирования:** сравнение ответов `db-service` и `ds-service` на одной локальной базе с prod-сидами для двух маршрутов — `web-adapter` и `export`. Признак успеха: нормализованные через `jq -S` ответы совпадают по данным; порядок ключей web-адаптера может отличаться по правилу из решения 4.

**Перед выкладкой на стенд:** свойство `List.listItemDividerWidth` и его web-параметр должны быть переименованы в `listItemDividerHeight` — подготовленным SQL или повторным импортом метаданных. Без этого выкладывать снимок нельзя. Правка стенда выполняется отдельной командой разработчика и в задачи Change не входит.

**После выкладки:** `components fetch --platform react` и загрузка темы в CLI через Gateway стенда завершаются успешно, `web-adapter.json` не пуст; создание темы в новой дизайн-системе создаёт конфигурации компонентов.

**Откат:** возврат Gateway на `db-service` штатным переключением из Change миграции; данных и схемы изменение не трогает.
