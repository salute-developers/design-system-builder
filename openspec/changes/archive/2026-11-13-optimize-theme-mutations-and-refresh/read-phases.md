# Поэтапное измерение чтения значений

Измерена текущая реализация после оптимизаций, не исходная версия. Изолированные Netty и PostgreSQL 17,
тот же синтетический снимок: 9804 значения цветов и градиентов в выбранной теме. Двадцать запросов
после прогрева. Временные замеры связаны по correlationId; после измерения код замеров удалён.
Исходные данные локально: `/tmp/token-read-phase-results-final.json`,
`/tmp/token-read-phases-measured.xml`. Общие проверки не запускались.

Для долей использована сумма времён двадцати запросов, а не сумма медиан. Вложенные интервалы
не складываются с родительскими. Среднее измеренного участка маршрута — 79,52 мс.
Это диагностический прогон с дополнительным выводом логов, а не итоговая серия скорости.

## Разбивка основного чтения

Внутри чтения значений JDBC execute занимает в среднем 22,51 мс; получение и материализация
строк после execute — 4,83 мс. Остальное — подготовка и фильтрация. JDBC execute включает
обмен с PostgreSQL и первоначальное получение результата, а не только выполнение плана.

Отдельно разность total_exec_time в pg_stat_statements до и после двадцати запросов дала
21,26 мс на основной SELECT значений: около 26,7% измеренного времени маршрута. Время PostgreSQL
вложено в строку 29,06 мс таблицы и не прибавляется к ней. Оно не равно чистому CPU PostgreSQL.

## Следующие решения

1. Сравнить существующий поиск последней ревизии для каждого значения с наборным выбором на том же
   ограниченном наборе темы и токенов. Сохранить историческую границу и фильтрацию deleted/type после
   выбора актуальной ревизии; не менять общий алгоритм для всех потребителей без результата.
2. Упростить чтение технических редакций: сравнить массив идентификаторов или JOIN с большим IN.
   Измерять всё чтение и обработку результатов, а не только SQL-план: доля этапа около 9%.
3. Вынести чистое раскрытие ссылок за границу транзакции после материализации согласованных значений
   и снимка. Это сокращает удержание соединения примерно на стоимость этого этапа в локальном сценарии,
   но само по себе не устраняет его время из HTTP-запроса. DTO уже формируется вне транзакции.
4. Исследовать оставшиеся 9% преобразования моделей и 11% снимка палитры, не подменяя их целиком временем CPU.

## Предел переноса на dev

Проценты локального прогона определяют кандидатов, но не прогнозируют доли dev: отдельно меняются
ожидания пула, выполнение и передача SQL, загрузка CPU, паузы JVM, конкуренция и скорость клиента.
Нельзя умножить каждую локальную долю на dev-задержку 5–12 с. Для объяснения именно этих секунд нужны
такие же поэтапные измерения на dev либо профиль процесса во время медленного запроса.
