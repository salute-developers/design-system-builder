# Исправления после проверки Astra

## Четыре замечания

1. Сохраняется контракт 200 UUID. Начальная строка HTTP/1.1 ограничена 16 КиБ в монолите и самостоятельном запуске DS. `AddressedReadTransportTest` использует настоящий Netty, HTTP/1.1, публичные пути, авторизацию и штатный parser tokenIds: 200 UUID с кодированными запятыми, фильтрами версии/типов/платформ доходят до маршрута; запрос без авторизации возвращает 401. Это локальная проверка прикладного публичного входа, а не внешнего прокси dev после деплоя.
2. `mergeAddressedTokens` удаляет ключи только соответствующего типа и точного модального имени. Регрессионный тест одновременно проверяет color → gradient и сохранение shape с именем `light.text.default.primary`, его метаданных, номера редакции и устойчивого адреса.
3. Обе точки отката передают неизвестный результат до `ThemeEditorSession`: адресная ветка исключается, инвалидируются все области и сверяется активная. Ошибка чтения остаётся видимой. Повтор сверки из журнала и инспектора не повторяет POST; тесты имитируют потерю ответа после COMMIT. Для инспектора цветов добавлена кнопка повторения чтения.
4. Адресное чтение проверяет штатный предикат очереди до GET и перед слиянием. Сессия дополнительно проверяет очередь и поколение активности непосредственно перед обновлением runtime. Тесты покрывают pending до GET, изменение очереди во время GET и реальную очередь: переименование, сверка, следующий ввод до ACK сохраняют устойчивый ID и новое имя в отправляемой команде.

Узкие клиентские тесты: 103 проверки в шести файлах прошли после окончательной защиты очереди. Дополнительно ранее прошли тесты экранов цветов и журнала. Проверка TypeScript прошла; сборка клиента не запускалась.

## Проверки PostgreSQL

- Два PUT одновременно создают один отсутствующий адрес. Временный триггер тестовой БД задерживает INSERT, чтобы оба запроса увидели отсутствие строки. Оба ответа успешны, устойчивый ID один, итоговая редакция 2; конкурентная запись возвращает предупреждение. Новый production-код блокировок для этого не потребовался: существующий serializable retry разрешил конфликт. Для цветового API mode обязателен; `mode=null` проверен как 400 без изменения данных, а не как допустимый адрес.
- Чтения разделов выполняются ролью NOSUPERUSER/NOBYPASSRLS с выданными DML-правами, без права миграций. Проверяются ненулевые редакции, полный и точечный фильтры, редкие типы, опубликованная граница, удаление без возврата старой ревизии, отсутствие доступа чужого проекта и роли без разрешения.
- Отдельный сценарий `gradient in one mode of one theme derives the family type` прошёл на окончательном mapper: две темы, смена производного типа, конкурентная запись и разные значения ссылки на текущей и опубликованной границах.
- В фактической тестовой схеме **0 таблиц с включённым RLS**; это совпадает с миграциями. Поэтому результат подтверждает явные проверки области в приложении и работу непривилегированной роли. Он не доказывает защиту несуществующими RLS-политиками; новые политики в этом Change не вводятся.

## Продолжение оптимизации

GET переиспользует выбор границы и LATERAL из `ResolvedSubjectRows`, но выбирает 10 нужных колонок и сразу формирует `TenantTokenValue` из JDBC. Строки ResultRow значений и повторная массовая сборка моделей больше не нужны. Остальные потребители общего reader и пути записи сохраняют прежнюю материализацию. Отсутствующие технические редакции по-прежнему дают 0.

Первый эксперимент присоединял редакцию к основному SELECT; на пустых редакциях он дал 70 мс вместо прежних 59,5–61,5 мс и удалён. Второй вариант с JOIN технических редакций для любого раздела замедлил типографику с 10 до 18,5 мс на заполненных редакциях. Итоговый путь для среза до 200 определений читает редакции по точным ID найденных значений; широкий путь использует JOIN темы с фильтром выбранных токенов. После этого типографика дала 9 мс. Порог связан с размером адресного контракта, а не объявлен универсальной точкой пересечения стоимости SQL.

В измерительном клиенте убрано построение диагностической строки со всем телом при успешном ответе. Тот же helper скопирован в baseline; production-код baseline не изменялся. Добавлены сценарий `value-reads` и параметр `performanceEditDensity=partial|full`: в выбранной теме выставляются синтетические технические редакции 7 для части или всех адресов. Данные значений и исторические границы не меняются.

Метод: тот же снимок 153 105 значений, 10 407 в выбранной теме; standalone Netty, loopback, пул 4, 3 запроса перед каждой серией и 20 измерений. Проверяются все поля каждого значения и контрольные суммы. Это последовательное локальное чтение без монолитного gzip и нагрузки; оно не объясняет непосредственно секунды dev и не доказывает изменение ожидания пула при конкуренции.
