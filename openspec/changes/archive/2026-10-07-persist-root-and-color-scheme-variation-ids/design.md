## Context

`appearances` описывает вариант компонента в дизайн-системе, `appearance_variations` — оси, объявленные у него (связь с `variations`, поля `position`, `default_style_id`, `is_color_scheme`, `declared_type`). Common-конфиг ссылается на оси двумя полями верхнего уровня:

- `colorSchemeVariationId` — сохраняется флагом `is_color_scheme` на связи; выгрузка читает флаг ([ComponentConfigBuilder.kt:24](../../../backend-kt/ds-service/feature-components/src/main/kotlin/com/dsbuilder/ds/components/data/ComponentConfigBuilder.kt));
- `rootVariationId` — не сохраняется: `ComponentConfigImporter` его не читает, а `ComponentConfigBuilder` ищет ось с именем `size`.

Схему БД ведёт Flyway `ds-service` (миграции в `backend-kt/ds-service/app/src/main/resources/db/migration`); `db-service` остаётся откатной веткой HTTP и читает те же таблицы, но не мигрирует их. Идентификатор оси в конфиге зависит от режима: при выгрузке это имя оси, при чтении через API — UUID `variations.id`.

## Goals / Non-Goals

**Goals:**

- Хранить обе роли явно и восстанавливать их при выгрузке без эвристик по имени.
- Закрепить инварианты схемой: роль указывает на ось этого же appearance, на каждую роль не больше одной оси.
- Единое правило выбора корня, когда конфиг его не указал.
- Не сломать `db-service`, пока он остаётся откатной веткой.

**Non-Goals:**

- Изменения в `js/db-service` и его drizzle-схеме.
- Удаление колонки `is_color_scheme`.

## Decisions

### 1. Колонки на `appearances`, а не флаги на связи

`appearances.root_variation_id uuid` и `appearances.color_scheme_variation_id uuid`, обе nullable. Это ровно та форма, в которой роли лежат в конфиге, и «одна ось на роль» следует из самой структуры, без частичных уникальных индексов.

Альтернатива: флаг `is_root` рядом с `is_color_scheme` с частичным уникальным индексом по `appearance_id`. Отвергнута: инвариант держится индексом, а не формой данных, а чтение роли требует выборки по осям.

### 2. Составной внешний ключ на `appearance_variations`

Простой FK на `variations.id` не гарантирует, что ось объявлена у этого appearance. Поэтому:

- опорой служит уже существующий уникальный индекс `av_appearance_variation_unique (appearance_id, variation_id)`;
- `FOREIGN KEY (id, root_variation_id) REFERENCES appearance_variations (appearance_id, variation_id) ON DELETE SET NULL (root_variation_id)`, то же для `color_scheme_variation_id`.

`ON DELETE SET NULL (column_list)` обнуляет только колонку роли, а не `appearances.id`; требует PostgreSQL 15 и новее. Версию в окружениях проверить до миграции (см. задачи); если версия ниже, запасной вариант — снимать роль в коде репозитория и оставить `NO ACTION` на уровне БД.

Alternative: FK на `appearance_variations.id`. Отвергнута: в конфиге и API ось адресуется `variations.id`, лишний переход через `appearance_variations.id` пришлось бы делать во всех ручках.

### 3. Правило фолбэка корня

Применяется в одном месте домена, а не размазано по ручкам. Когда `rootVariationId` в конфиге не указан или не найден среди осей:

Из осей, кроме оси цветовой схемы:

1. ось с именем `size`;
2. иначе первая по `position`;
3. иначе корня нет (`null`).

Правило вызывается при заливке и при снятии корневой роли удалением оси. Явно указанный в конфиге `rootVariationId`, ссылающийся на несуществующую ось, — ошибка валидации заливки, а не повод для фолбэка: молчаливая подмена скрыла бы опечатку в конфиге.

Корень может совпадать с осью цветовой схемы, только если оба поля явно указаны в конфиге одним значением; фолбэк такого результата не даёт.

### 4. Миграция данных

Одна миграция `V3__persist_appearance_axis_roles.sql`:

1. добавить колонки;
2. `color_scheme_variation_id` заполнить из `appearance_variations WHERE is_color_scheme`; если в одном appearance таких строк больше одной (замер на корпусах исключений не нашёл), миграция берёт строку с наименьшим `position` и не падает;
3. `root_variation_id` заполнить правилом фолбэка по `position` и имени оси (`variations.name = 'size'`), оценив его на уже перенесённой роли цветовой схемы;
4. добавить внешние ключи после заполнения.

`contracts/schema-fingerprint.json` не меняется: он описывает базовую схему (версия Flyway 1), с которой adopt принимает уже существующую БД, а `V3` накатывается поверх неё.

### 5. Синхронный `is_color_scheme`

`is_color_scheme` остаётся и пишется вместе с `color_scheme_variation_id` (запись в одной транзакции), чтобы откат на `db-service` не терял роль. Читать его `ds-service` перестаёт. Удаление колонки — отдельное изменение после вывода `db-service` из эксплуатации.

`isColorScheme` в запросах и ответах `appearance-variations` сохраняется для совместимости клиентов и является производным: `true` ровно у той оси, на которую указывает `color_scheme_variation_id`. Рядом появляется `isRoot`.

### 6. Назначение и снятие роли через CRUD осей

- `PATCH`/`POST` с `isColorScheme: true` или `isRoot: true` ставит указатель на `appearances` этой оси; прежняя ось роль теряет автоматически.
- `isColorScheme: false` (`isRoot: false`) для оси, не несущей роль, — без изменений; для оси с ролью снимает указатель. Для корня после снятия действует фолбэк (решение 3), для цветовой схемы указатель остаётся пустым.
- Удаление оси с ролью обнуляет указатель внешним ключом; корень затем пересчитывается фолбэком в том же запросе.
- Ось не может быть корнем и осью цветовой схемы одновременно через CRUD: ответ 409, потому что такое сочетание не нужно ни одному корпусу, а фолбэк его не создаёт.

### 7. Клиент выбирает корень тем же правилом

`ConfigCodec.decode` возвращает `rootVariationId` по правилу фолбэка (решение 3), применённому к осям `bindings`: ось `size`, иначе первая по порядку объявления, оба случая без оси цветовой схемы. Правило дублируется в клиенте и сервисе, потому что клиент всегда присылает корень и сервисный фолбэк до срабатывания не доходит; разные правила дали бы разный корень у одного и того же конфига в зависимости от пути (`push` или заливка без корня).

Альтернатива: клиент не присылает корень, когда не знает его наверняка, и решение остаётся за сервисом. Отвергнута: в native-конфигурации корень нигде не объявлен, клиент не знает его «наверняка» никогда, а значит сервис выбирал бы всегда, и поле в common-конфиге теряло бы смысл.

## Risks / Trade-offs

- [Откат на `db-service` читает устаревший `is_color_scheme`] → дублирующая запись в одной транзакции; тест на равенство колонок.
- [Запись роли через `db-service` после отката идёт мимо ссылки] → `db-service` пишет только флаг `is_color_scheme`, а `ds-service` читает ссылку на `appearances`, поэтому роль, назначенная через `db-service`, не будет видна `ds-service` после возврата. Синхронизация идёт в одну сторону (`ds-service` → флаг). Принято: `db-service` остаётся только откатной веткой для чтения; при записи через неё роль нужно переназначить через `ds-service`.
- [Фолбэк корня в миграции сменит корень там, где выгрузка раньше отдавала `null`] → ранее у appearance без оси `size` корень был `null`; теперь это первая ось. Об этом сказано в спеке как о намеренном изменении; потребители выгрузки (CLI `components fetch`) обязаны принимать любой корень.
- [`ON DELETE SET NULL (column)` недоступен на PostgreSQL ниже 15] → проверка версии в задачах, запасной путь через репозиторий.
- [Составной FK усложняет Exposed-таблицы] → ссылки описываются колонками без `reference(...)`, ограничения живут в SQL-миграции, как и остальные в этой схеме.
- [Клиент и сервис выбирают корень двумя копиями одного правила] → общие сценарии в спеках обоих, тесты на оба набора случаев; при расхождении правил `push → fetch` перестанет возвращать исходный корень.

## Migration Plan

1. Применить `V3` на локальной БД, сверить `color_scheme_variation_id` с `is_color_scheme` и посчитать appearance с `root_variation_id IS NULL` при непустом наборе осей (ожидаем ноль).
2. Выкатить `ds-service` с чтением новых колонок.
3. Откат: `ds-service` предыдущей версии продолжает работать, колонка `is_color_scheme` синхронна; новые колонки и внешние ключи игнорируются.
