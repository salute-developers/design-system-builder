# Проверка на локальном контуре

Дата прогона: 2026-10-07. Путь запросов: CLI → gateway (`:8080`) → ds-service (`:8085`) → БД `ds_registry` (`:5433`).
Для прогона создан временный проект `rt-verify-axis-roles`, ключ проекта на 4 часа и три design system
(`rt-verify-axis-roles`, `rt-verify-edge-cases`, `rt-verify-compose`); данные существующей design system `base` не менялись.

## Эталон «как было» (прежний ds-service, схема до `V3`)

- Корпус: `~/data/code/TestCli/test/.sdds/components`, платформа `android-view` (в БД `xml`), 143 конфигурации.
- `components push --apply`: создано 121, отклонено 22 (компонентов нет в глобальном слое платформы `xml`).
- `components fetch`: 121 файл, снят в `fetch-baseline-xml`.
- Сырая выгрузка: `rootVariationId` = `size` у 108, `null` у 13; `colorSchemeVariationId` = `view` у 46.

## Вторая платформа

Корпус `~/data/code/theme-converter/components/sdds_sbcom`, платформа `compose`: создано 45, выгружено 45.
Оси цветовой схемы `mode-color` (3), `mode` (2), `mute` (2), `variant`, `state`, `view`; корень `size` у 10,
`type` у 3, `chip-slot` у 2, у остальных корня нет; корень никогда не совпадает с осью схемы, при наличии
`size` корнем всегда `size`. Имена и типы `bindings` и ключи `view` совпали у 43 из 43 сравниваемых файлов.

## Откат

Прежняя версия ds-service (сборка из `HEAD`) стартует на БД с `V3` (Flyway по умолчанию игнорирует «будущие»
миграции) и отдаёт тот же `colorSchemeVariationId` во всех 45 конфигурациях за счёт синхронного `is_color_scheme`.
Отличаются только 5 корней там, где оси `size` нет: прежняя версия выводит корень по имени и отдаёт `null`.

## Замечания

- Круг «push → fetch» не побайтный и на прежнем сервисе (из 98 исходных файлов равны 61): выгрузка не возвращает
  свойства, которых нет в глобальном слое. Это прежнее свойство и к изменению не относится.
- Установленный `~/.local/bin/dsbuilder` (0.1.0) не обновлялся; новый клиент собран командой
  `./gradlew :cli:installJvmDist` и запускался из `frontend-kt/cli/build/install/cli-jvm/bin/dsbuilder`.
- Процесс ds-service на `:8085` до прогона был запущен из уже удалённого worktree; он заменён сборкой из этого
  изменения (jar в каталоге сессии), а дамп БД до миграции сохранён в каталоге сессии.
