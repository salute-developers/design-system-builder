## Context

`titleFor` в `journalPresenter.ts` для всех типов из `componentEntityTypes` возвращает `${операция} компонента «${имя}»`. Имя компонента ищется по идентификаторам записи через `componentIndex`. Имена стилей, вариаций, конфигураций и свойств есть в `componentMetadata.referenceNames`, вариация стиля — в `styleVariations`.

## Goals / Non-Goals

**Goals:**
- По заголовку понятно, какая структурная часть компонента создана, изменена или удалена.

**Non-Goals:**
- Менять порядок, фильтры и отмену журнала.

## Decisions

### Заголовок по типу сущности

`titleFor` получает метаданные и для структурных сущностей строит заголовок по таблице из proposal. Имена берутся так:

- стиль — `name` записи или `referenceNames[entityId | style_id]`;
- вариация — `referenceNames[variation_id]` или `styleVariations[style_id]`;
- конфигурация — `name` записи или `referenceNames[appearance_id]`.

Глагол зависит от сущности:

- для подключений (`appearance-variation`, `appearance-variation-value`) — «Подключение/Изменение/Отключение»;
- для связи компонента с дизайн-системой — «Добавление … в дизайн-систему / Изменение / Скрытие»;
- для остальных — «Создание/Изменение/Удаление».

Неизвестная часть пропускается вместе со своим словом-связкой, без идентификаторов.

### Склейка парных записей

Для пользователя добавление стиля в вариацию — одно действие, а сервер пишет две записи:

- `style` — сам стиль вариации;
- `appearance-variation-value` — подключение стиля к конфигурации, его `position` — место в списке стилей.

Со вариацией то же самое: `variation` и `appearance-variation`.

Перед построением строк `presentJournal` находит пары среди загруженных записей:

- `style` (created) и `appearance-variation-value` (created) с `style_id` = `style.entityId`;
- то же для `deleted`;
- `variation` и `appearance-variation` по `variation_id` с той же операцией.

В паре должен быть один автор. Пара становится одной строкой: `changes` содержит обе записи, заголовок и поля строятся по таблице proposal.

Отмена строки уже проходит по `action.changes` последовательно (`useJournalRevert`), поэтому порядок записей в паре задаёт порядок отмены:

- для созданной пары — сначала подключение, затем сущность: удалить стиль, пока он подключён, нельзя;
- для удалённой пары — сначала сущность, затем подключение: подключение ссылается на сущность.

Запись без пары, например если вторая половина не попала на страницу журнала, показывается отдельной строкой с прежним заголовком.

Альтернатива — скрывать подключения совсем. Отклонена: тогда отмена строки «Создание стиля» упиралась бы в оставшееся подключение, а перестановку стиля в списке не было бы видно вовсе.

### Подключение без пары

- Изменение `position` — «Перемещение стиля «xxxs» в вариации «size» компонента «Button»».
- Поле `position` подписывается «Место в списке» и показывается с отсчётом от единицы.
- Создание и удаление без пары — «Добавление стиля «xxxs» в конфигурацию компонента «Button»» / «Исключение стиля …».

```ts
function pairStructureChanges(changes: DraftChangeDto[]): DraftChangeDto[][]; // группы в порядке отмены
```

## Risks / Trade-offs

- **[Пара на разных страницах журнала]** Половины пары могут оказаться на разных страницах. → Тогда каждая показывается отдельной понятной строкой; отмена работает как раньше.
- **[Счётчик записей]** Число строк в разделе «Компоненты» уменьшится: пара считается одним действием, как её видит пользователь.
