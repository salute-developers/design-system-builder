# Решение

## Подготовка и независимость данных

Использовать отдельную ДС каждого сценария, Owner для публичной API-подготовки и проверенного Editor в браузере. Переиспользовать существующие RSS-BASE и FIX-BASE, контроль завершающихся записей и политику очистки: успешная собственная ДС удаляется после подтверждения записей; неуспешная сохраняется для диагностики. Начальные значения и ревизии читать после завершения подготовки.

Соседние токены, незатронутые экраны и начертания сравнивать с исходными значениями, включая ревизии. Платформенные значения проверять через независимый GET; одинаковое вычисленное значение само по себе не доказывает наличие собственного значения. Для радиусов использовать флаг overridden и платформенные данные размеров, для типографики — действующий контракт различий платформ. Значения теней проверять в опубликованной платформенной форме по актуальному API, не предполагать одинаковый DTO для Web, iOS и Android.

## Взаимодействия и ожидания

До написания каждого блока исследовать соответствующие взаимодействия через MCP Playwright. Предпочитать роли, названия и существующие test-id. Подписку на точные метод и URL ответа устанавливать до действия; успешное сохранение подтверждать ответом, статусом UI, независимым чтением и перезагрузкой. Не использовать координаты, произвольные задержки или повторы мутаций.

Для неверного ввода проверить сообщение или состояние ошибки, отсутствие запросов записи и неизменность значений/ревизий. Ожидание ошибки UI отделяет проверку отсутствия записи от возможного debounce. Слишком низкая положительная высота строки допустима и вызывает предупреждение; её не включать в набор отвергаемых значений.

## Пределы проверки и дефектов

Разрешён запуск только новых десяти E2E с явным перечнем Jira-ключей либо четырьмя новыми файлами; прежние сорок E2E не запускать. Встроенную сборку клиента, проверки типов, обнаружение сценариев и относящиеся к изменению статические проверки выполнять отдельно. Полный E2E-набор не входит в FAST/FULL JavaScript-контура.

При несовпадении тестового предположения с подтверждённым действующим контрактом исправить тест. Небольшой дефект клиента исправлять только при однозначном ожидаемом поведении и с узкой проверкой. Изменение архитектуры, публичного API, отсутствие обязательных данных, недоступность стенда либо неоднозначное ожидаемое поведение — блокер: остановиться и запросить решение пользователя.
