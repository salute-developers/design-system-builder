## Context

Конфигурация компонента — `appearance` в `ds-service`. Клиент загружает все конфигурации компонента в
`Meta.sources.configs` (id — id `appearance`), но `Config` строится из первой, а автосохранение пишет в
`meta.serverBinding.appearanceId` (основная или первая конфигурация). Структурные правки клиент сейчас делает только
через автосохранение (стиль: `POST /styles` + `POST /appearance-variation-values`; стиль по умолчанию:
`PATCH /appearance-variations`). В `ds-service` есть редакторский API конфигураций, которым клиент не пользуется.

Имена вариаций и значений в экспорте конфигурации берутся из `displayName` оси или значения, а если его нет — из имени
вариации или стиля; вместе с именами экспорт отдаёт ID вариации и стиля. Клиент сопоставляет вариации и стили по
имени. У каждой конфигурации свой набор осей. Добавление оси создаёт новую вариацию (служебное имя с суффиксом, если
имя занято другой конфигурацией компонента, а введённое имя — `displayName` оси). Дублирование конфигурации ссылается
на те же вариации и стили, копируя значения свойств.

## Goals / Non-Goals

**Goals:**
- Вкладка «Структура» с блоками «Конфигурации» и «Вариации» по прототипу.
- Открытая конфигурация выбирается и в «Структуре», и в «Variants»; превью, инспектор и автосохранение работают с ней.

**Non-Goals:**
- «Дерево вариаций» и пересечения — отдельное изменение.
- Порядок конфигураций и смена конфигурации по умолчанию: маршрутов нет.
- Изменения бэкенда, кроме ID вариаций и стилей в выгрузке для редактора.

## Decisions

1. **Структурные операции — сразу запросом, не через автосохранение.** Создание, дублирование, переименование,
   удаление конфигурации, вариации и значения, порядок вариаций и стиль по умолчанию выполняются отдельным запросом к
   редакторскому API. Перед запросом очередь автосохранения дожидается отправки, после — компонент перечитывается
   (как после автосохранения), а выбор переводится на созданную или оставшуюся сущность. Альтернатива — новые виды
   изменений в диффе автосохранения — сложнее и не даёт серверной логики (генерация имён, каскад, защита).
2. **Маршруты:**
   - конфигурации: `POST /appearances/new {designSystemId, componentId, name?}`,
     `POST /appearances/{id}/duplicate {name?}`, `PATCH /appearances/{id} {name}`, `DELETE /appearances/{id}`;
   - вариации: `POST /appearances/{id}/axes {name, values: ['default'], defaultValue: 'default'}`,
     `DELETE /appearances/{id}/axes/{axisId}?confirmCascade=true`, `POST /appearances/{id}/axis-order {axisIds}`;
   - значения: `POST /appearances/{id}/axes/{axisId}/values {name}`,
     `DELETE /appearances/{id}/axis-values/{valueId}?confirmCascade=true`;
   - стиль по умолчанию: `PATCH /appearance-variations/{id} {defaultStyleId}`.
3. **Сопоставление по ID, переименование — `displayName` в конфигурации.** Выгрузка по умолчанию кладёт в `id` оси
   её имя и не несёт ID стилей. Флаг `editorIds` (клиент шлёт его в выгрузке, бандл редактора включает его сам)
   добавляет `variationId` оси и `styleId` значения; пакеты `.sdds` не меняются. Альтернатива — читать
   `editor-model` каждой конфигурации при открытии компонента — отвергнута: открытие компонента остаётся одним
   чтением. `toLegacyComponentConfig` берёт ID вариации и стиля из выгрузки, имя — отображаемое. Переименование вариации — `PATCH /appearance-variations/{id}
   {displayName}`, значения — `PATCH /appearance-variation-values/{id} {displayName}`: меняется только открытая
   конфигурация. Переименование основного имени (`PATCH /variations`, `PATCH /styles`) отвергнуто: вариации и стили
   общие у дублированных конфигураций, и правка задела бы другие конфигурации. Сопоставление по имени отвергнуто: оно
   ломается, когда ось конфигурации названа так же, как вариация другой конфигурации.
4. **Перечитывание после операции.** Чтение компонента пропускается, пока данные раздела не помечены устаревшими, а
   уведомление сервера приходит позже. Поэтому `loadComponent(name, force)` сначала помечает конфигурации компонентов
   устаревшими, затем читает компонент.
5. **Конфигурация по умолчанию** определяется по `isDefault` из бандла редактора и стоит первой; к ней же по
   умолчанию привязано автосохранение. Выгрузка сортирует конфигурации по имени и на порядок не влияет.
6. **Открытая конфигурация.** `Components.tsx` строит `Config` из данных компонента по id выбранной конфигурации
   (`new Config(meta, configID)`), выбор хранится в адресе (`?configuration=`) и сбрасывается при смене компонента.
   `Config` отдаёт id своей конфигурации, операция автосохранения несёт `appearanceId`, и запись идёт в неё. Ключ очереди
   и сохранённой операции у конфигурации по умолчанию — прежний (имя компонента), у остальных — с ID конфигурации,
   поэтому неотправленные правки, сохранённые до изменения, по-прежнему восстанавливаются.
7. **«Показать все свойства».** Строки стиля по-прежнему строятся из свойств API, привязанных к его вариации. Кнопка
   в заголовке секции показывает пустыми строками и остальные свойства компонента (кроме иконок и ссылок на стили);
   стили новой вариации (ни привязок, ни значений в её стилях) показывают все свойства сами. У старой вариации без
   привязок, но со значениями (данные без привязок) строки по-прежнему строятся из привязанных и заданных свойств,
   иначе у них появились бы десятки пустых строк. Первое значение непривязанного свойства перед
   записью создаёт привязку `POST /property-variations {propertyId, variationId}`. Альтернативы — всегда все свойства
   (лишние строки у `size` и `view`) и только привязанные (новая вариация остаётся пустой) — отвергнуты.
8. **Подтверждение удаления** — общий диалог подтверждения клиента с названием сущности и предупреждением, что значения
   свойств удаляются вместе с ней; диалог рисуется в `body`.
9. **Вёрстка** — по прототипу (`component-variation-tree`, `component-configuration-tree`, `component-axis-group`),
   действия строк видны при наведении и фокусе; перетаскивание осей — HTML5 drag-and-drop по ручке, как в прототипе,
   плюс стрелки клавиатуры на ручке.

## Risks / Trade-offs

- [Какое имя попадает в генерацию] → выгрузка `.sdds` пишет ось и значение под действующим именем (`displayName`,
  если задано, иначе имя вариации или стиля), поэтому переименование в конфигурации доходит до сгенерированного кода.
- [Перечитывание компонента после каждой структурной операции] → операции редкие; выбор сохраняется по имени стиля
  (как после автосохранения).
- [Удалённая вариация остаётся в базе без осей] → маршрута удаления вариации нет; на редактор не влияет.
