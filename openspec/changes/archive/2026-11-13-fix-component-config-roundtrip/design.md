## Контекст

Экспорт конфигураций (`ComponentConfigBuilder`) показывает ссылку по `token_id` именем из `referenceName`: у токена типографики отбрасывается экран (`screen-s.body.m.normal` → `body.m.normal`), потому что компоненты по контракту ссылаются на стиль типографики без экрана, а привязка по `token_id` идёт к токену `screen-s` того же начертания. Это же правило записано у редактора типографики (`TypographyStyleStructure`: «ссылка без экрана — к `screen-s` своего начертания»).

Импорт (`ComponentConfigImporter.token`) ищет имя в `context.tokens` — словаре точных имён токенов дизайн-системы. Обратного шага нет, поэтому `body.m.normal` не находится: значение пишется текстом, `token_id` пустой, имя уходит в `unresolvedTokens`. Снимок конфигурации после импорта отличается от исходного — отсюда `updated`.

Для свойств токенных типов (`color`, `gradient`, `typography`, `shape`, `shadow`) импорт считает именем токена любую непустую строку. Литералы цвета не находятся и сохраняются текстом (`value.takeIf { token == null }`) — данные верны, но отчёт засорён.

## Цели / Вне целей

**Цели:**
- экспорт и импорт конфигураций симметричны: неизменённая выгрузка загружается без изменений;
- в списке ненайденных токенов остаются только настоящие ненайденные ссылки.

**Вне целей:**
- формат пакета и экспорт не меняются;
- CLI не меняется;
- ссылки на стили компонентов (`component_style`) — их разрешение не затронуто.

## Решения

### 1. Обратное правило имени типографики в импорте

`token(name, type, context)` для типа `typography` сначала ищет точное имя, а если имя без экрана (`^screen-[sml]\.` нет) — ищет `screen-s.<имя>`. Правило живёт рядом с `referenceName` в `TokenReferenceName.kt`, как обратная функция, чтобы оба направления менялись вместе.

Альтернатива — писать в экспорт имя с экраном. Отклонено: это меняет формат пакета, на который опираются генератор и сиды (`body.m.normal` без экрана — контракт компонентов), и ломает уже выгруженные пакеты.

### 2. Литерал — не ссылка

Значение, в котором нет точки, либо которое начинается с `#`, `rgb(`, `rgba(`, импорт сразу считает литералом: `token = null`, без поиска и без записи в `unresolvedTokens`. Имя токена в DS Builder всегда содержит точку (`группа.подгруппа.имя`), поэтому правило не задевает настоящие ссылки.

### 3. Корень по фолбэку при создании из сидов

`GeneratedDesignSystemComponentInitializer` назначает корень тем же `fallbackRoot`, что импорт, по объявленным осям appearance (писатель сидов пакетный, поэтому корень вычисляется до записи, а не через `AppearanceAxisRoleStore.ensureRoot`). Так дизайн-система из сидов сразу хранит то, что спека `component-appearance-model` («Absent root falls back to a derived axis») требует от любого места без явного корня, и выгрузка пишет `rootVariationId` явно.

Альтернативы:
- **Импорт не назначает корень, если его нет в пакете.** Отклонено: противоречит действующей спеке, и импорт нового компонента без корня перестал бы его получать.
- **Выгрузка пишет вычисленный корень вместо `null`.** Отклонено: импорт всё равно сохранит его, а в базе был `null` — `updated` останется; к тому же выгрузка начнёт показывать то, чего нет в данных.
- **Миграция, проставляющая корень существующим appearance.** Не нужна сейчас: первая загрузка или правка осей назначит его по тому же правилу. Можно добавить позже, если пустой корень где-то мешает.

### 4. Позиции и смещение значений при создании из сидов

Импорт задаёт позицию значения по месту в конфигурации: базовое — `0`, состояния — `1…n`. Создание из сидов писало `0` всем, и повторная загрузка переставляла состояния. Теперь инициализатор нумерует состояния каждого свойства по порядку в сидах.

Смещение значения импорт пишет в колонку `adjustment`; выгрузка читает колонку, а при её отсутствии — числовую поправку платформенного параметра (`PlatformParamOffsets`, помечено как наследие). Инициализатор теперь кладёт то же смещение, выбранное тем же `PlatformParamOffsets.pick`, сразу в колонку. Поправки web-параметров в базе остаются как были.

### 5. Стили Badge в сидах

У `Badge` в сидах два набора стилей одной вариации, отличающиеся регистром: appearance `default` использует `Default`, `Accent`, `L`, `M`, `Pilled`, `Rounded`, а `clear` и `transparent` — строчные. Импорт сравнивает имена без учёта регистра (`canonical()`) и склеивает пары. Стили приведены к строчным, как у остальных компонентов; значения appearance `default` и его значения по умолчанию переписаны на новые имена — пересечений значений между наборами нет.

### 6. Использования производных радиусов не теряют параметр

`ExposedSizeTokenUsageRepository.adjustments` предпочитает смещение из колонки значения и показывает его без имени платформенного параметра. Когда смещение лежит в колонке (после импорта и теперь сразу из сидов), а рядом есть поправка параметра с тем же числом, использование берёт имя параметра из неё: `Button.shape` со смещением `-2` остаётся использованием `buttonRadius`.

## Риски / Компромиссы

- **[Риск] В дизайн-системе нет токена `screen-s` для стиля.** → Как и сейчас: значение сохраняется текстом, имя попадает в отчёт.
- **[Риск] Дизайн-системы, созданные до исправления, остаются с пустым корнем.** → Их первая загрузка изменит корень на вычисленный — это приведение к спеке, а не случайная правка. Критерий «`updated = 0`» проверяется на дизайн-системе, созданной после исправления, и повторной загрузкой на старой.
- **[Риск] На стендах дизайн-системы, созданные раньше, хранят `Badge` с дублями и позиции `0`.** → Исправление сидов действует на новые дизайн-системы. Существующим первая загрузка выровняет позиции; дубли `Badge` в них — отдельная правка данных через редактор.
- **[Риск] Где-то уже сохранены текстовые значения вместо привязок.** → Повторная загрузка теперь привяжет их к токену; это исправление, а не регрессия. По словам команды, `push` к существующим дизайн-системам ещё не применялся.
