## Context

Конфигурации компонентов дизайн-систем публикуются в репозитории `salute-developers/theme-converter`, директория `components`. Структура:

```
components/
  config_scheme.json          схема native формата
  common_config_scheme.json   схема common формата
  <design-system>/
    meta.json                 {name, version, components:[{componentName, styleName, config}]}
    <style>_config.json       native конфигурация одного компонента
    <version>.zip             версионированный архив, содержит meta.json и конфигурации
                              (CLI его не скачивает — пакет доставляется в рабочую директорию)
```

Native-формат потребляется Gradle-плагином `plugin_theme_builder` в `plasma-android` для генерации Compose и View стилей. Common-формат — модель DS Builder. Преобразование между ними реализовано в PR `salute-developers/plasma-android#386` (модуль `sdds-core/config-codec`, JVM, `kotlinx.serialization`).

Текущее состояние CLI `dsbuilder`:

- команды `init`, `status`, `theme fetch`, `theme alias` — все на чтение;
- `core/http/AuthenticatedHttpClient.kt` — `fun interface` с единственным методом `get`;
- `core/config/CliFileSystem.kt` — текстовый интерфейс, без бинарных операций;
- targets: `jvm`, `macosArm64`, `macosX64`; `macosMain` уже использует POSIX cinterop;
- тесты изолированы через `MockEngine`.

Ограничения, установленные измерениями по фактическим данным (шесть живых дизайн-систем: `plasma_b2c`, `plasma_giga`, `plasma_homeds`, `plasma_stards`, `sdds_sbcom`, `sdds_serv`; директории `stylesSalute` и `plasma_giga_app` признаны неактуальными):

- 500 конфигураций компонентов, перечисленных в `meta.json`, при 507 файлах на диске: семь файлов не упомянуты в meta и источником не читаются;
- 3328 вариаций, из них 1726 (52%) кросс-осевые, то есть с `binding` длиной два и более;
- модель данных из PR не соответствует фактическому формату: поле `kind` не встречается ни разу, вместо него используется `binding` в виде массива `{name, value}`; верхнеуровневый блок `bindings` в PR не объявлен вовсе;
- common-схема использует ключ `properties` внутри значения вариации, PR использует `props`;
- 11 конфигураций не содержат `bindings` — все с пустым массивом `variations`;
- вариаций без поля `binding` в живых директориях нет;
- 55 вариаций содержат дополнительное поле `key`, дублирующее имя собственной оси.

## Goals / Non-Goals

**Goals:**

- Перенести логику преобразования конфигураций из PR #386 в CLI, приведя модель данных к фактическому формату.
- Реализовать `dsbuilder components push` с двумя источниками конфигураций.
- Сделать первую пишущую операцию CLI безопасной по умолчанию.
- Зафиксировать контракт import-endpoint как требование к соседнему репозиторию.
- Покрыть codec тестами на корпусе реальных конфигураций, поскольку в исходном PR тестов нет.

**Non-Goals:**

- Команда `components pull`. Направление `encode` реализуется и тестируется, команда не добавляется.
- Реализация endpoint `components:import` и миграций `db-service`. Выполняется в репозитории `design-system-builder`.
- Согласование словарей осей и свойств между дизайн-системами. Расхождения измерены и признаны допустимыми для импорта; приведение их к общему словарю — работа владельцев дизайн-систем.
- Команда `components pull`. Требование к проекции компонента на дизайн-систему фиксируется сейчас, реализация — отдельным change.
- Изменение поведения существующих команд `init`, `status`, `theme`.

## Decisions

### Источник пакета: только локальная директория

Пакет читается из директории: `.sdds/components` по умолчанию либо заданной `--from`.

Скачивание версионированного архива из `theme-converter` было реализовано и снято. Оно тянуло
за собой платформенное чтение zip через `expect/actual` для трёх таргетов, отдельный
HTTP-клиент без авторизации в публичном `CliRuntime` и знание CLI о структуре чужого
репозитория — при том что доставка пакета в рабочую директорию решается любым способом вне CLI.

Следствие: `meta.json` и все перечисленные в нём файлы конфигураций должны лежать в директории.

### `bindings` обязателен при наличии вариаций

Codec читает оси вариаций, их порядок, дефолты и признак цветовой схемы из блока `bindings`, а собственную ось значения и его targets — из `binding` конкретной вариации.

Алгоритм из PR, восстанавливающий принадлежность оси разбором составных идентификаторов вида `xl.pilled` против реестра вариаций, не переносится. Он не нужен на фактических данных и является источником тихой порчи: выражение `variationRegistry["$targetId$id"]?.kind.orEmpty()` при неудачном поиске подставляет пустую строку в идентификатор target вместо ошибки.

Отсутствие `bindings` при непустых `variations` — детерминированная ошибка. Отсутствие `bindings` при пустых `variations` — валидный случай, покрывающий 11 конфигураций `plasma_homeds` без осей.

Следствия для codec: из PR уходят `targetRegistry`, `toNativeVariation` и разбор идентификаторов; хардкод `rootVariationId = "size"` и `colorSchemeVariationId = "view"` заменяется чтением `bindings`; поле `defaults`, которое `decode` в PR никогда не заполнял, восстанавливается из `bindings[].defaultValue`.

### Round trip проверяется в направлении common

Точное равенство `native -> common -> native` недостижимо, и это свойство форматов, а не реализации: common не несёт `variations[].id`, `variations[].parent`, `bindings[].type`, порядок `bindings[].values` и признак присутствия `binding` внутри записи `view`. Замер по корпусу: из 500 конфигураций точный round trip возможен у 224. Не восстанавливаются `bindings[].values` у 215 конфигураций (объявленный список значений оси шире встречающегося в вариациях: у `plasma_b2c/badge_clear` ось `shape` объявляет `default` и `pilled`, а в вариациях есть только `pilled`), `variations[].id` у 118 (`plasma_b2c/switch` имеет `id = "l"` при `binding` из двух элементов со значением `l`), `variations[].parent` у 71, признак `binding` в `view` у 20.

Протаскивание native-полей через common отвергнуто: оно загрязняет формат DS Builder ради теста.

Поэтому проверяются два свойства. Точное равенство требуется в направлении `common -> native -> common`: оно доказывает взаимную обратность `encode` и `decode` на модели, которая реально хранится, и именно оно нужно будущему `pull`. В направлении `native -> common -> native` проверяется эквивалентность выразимой части: оси и их порядок, дефолты, множества значений осей, наборы свойств с типами и состояниями, targets.

### Модель данных codec строится по фактическим данным

Схема `config_scheme.json` датирована декабрём 2024 и не описывает ни `bindings`, ни `binding`, ни `key` — она отстала от данных. Модель native-формата строится по фактическим конфигурациям. Common-формат строится по `common_config_scheme.json` (обновлена в апреле 2026), в частности ключ значения вариации — `properties`, а не `props`.

### Расположение codec

Codec размещается в `dsbuilder-frontend/cli` как отдельный пакет `feature/components/domain/codec` в `commonMain`, а не отдельным Gradle-модулем. Обоснование: единственный потребитель сейчас — CLI; выделение модуля добавляет границу API без пользы. Пакет остаётся чистым от ввода-вывода, поэтому выделение в модуль позже не потребует переписывания.

Класс `App.kt` из PR не переносится: его роль выполняет Clikt-команда.

### Идентичность компонента

Ключ — пара (`componentName`, `styleName`) из `meta.json`. `componentName` не уникален: например, `badge` в `sdds_serv` соответствуют `badge-clear`, `badge-solid`, `badge-transparent`. Пара используется и в payload, и как ключ upsert на стороне backend.

### Сверка дизайн-системы не выполняется

`meta.json.name` содержит имя вида `sdds_serv`, а `.sdds/config.json` — `designSystemId` в виде UUID. Первоначально предполагалась сверка `meta.json.name` с именем дизайн-системы, полученным через `GET /api/projects/{projectId}/ds/design-systems/{designSystemId}`. От неё решено отказаться.

Причина: не установлено, какое поле backend вообще сопоставимо с `meta.json.name`. Сид-данные `db-service` разделяют уровни — `design_systems` содержит `name: 'SDDS'` при `projectName: 'sdds'`, тогда как `tenants` содержит `sdds_cs`, `sdds_serv`, `plasma_web`, `plasma_giga`, — но эти данные синтетические. Косвенная улика из боевой установки указывает в другую сторону: `theme fetch` запрашивает все тенанты дизайн-системы без фильтра (`HttpRemoteThemeDataSource.kt:35`), а `plasma-android/tokens/plasma.homeds.compose/.sdds/config.json` содержит ровно один тенант `plasma_homeds_default`, что говорит о соответствии дизайн-системы директории `theme-converter` один к одному. Фактическое значение `design_systems.name` из боевой установки не наблюдалось ни разу.

Строить проверку, отменяющую push, на неустановленном соответствии хуже, чем не иметь её: ложный отказ приучает пользоваться флагом обхода, после чего проверка перестаёт защищать. Поэтому сверка и флаг `--skip-name-check` не реализуются.

Защита от записи не в ту дизайн-систему остаётся на трёх барьерах, не требующих догадок о семантике имён: обязательный явный API URL, печать цели и состава пакета перед отправкой, режим `--dry-run` по умолчанию. Печать расширена так, чтобы обе стороны сравнения были видны человеку: `meta.json.name`, источник пакета и число конфигураций рядом с URL, его источником, `projectId` и `designSystemId`.

`TenantDirectoryNormalizer` остаётся в feature `theme` и в этом change не используется.

### Проекция компонента на дизайн-систему

Глобальный слой `db-service` (`components`, `variations`, `properties`) хранит объединение по всем дизайн-системам: `components.name` уникален глобально, `designSystemId` в этих таблицах нет. Это корректно — компонент один, — и подтверждается данными: у 48 из 68 компонентов, встречающихся более чем в одной живой ДС, наборы свойств образуют цепочку по включению, то есть расхождение действительно является пропуском. Цена объединения мала: 1189 свойств против 1122 при максимуме по одной ДС, раздувание 1.06x.

Следствие для codec: набор свойств и осей конкретной дизайн-системы **не восстанавливается** из глобального слоя. Он восстанавливается только из таблиц значений — `variation_property_values` через `styles.design_system_id`, `invariant_property_values` через собственную колонку `design_system_id`, `style_combinations` через `appearances.design_system_id`.

Для `push` это ограничение ничего не меняет: `decode` работает с файлом, а не с базой. Оно становится обязательным для будущего `components pull`: если `encode` возьмёт набор свойств из `properties`, для `plasma_b2c` он выдаст 28 свойств компонента `card` вместо семи и round trip `push -> pull` перестанет сходиться. Поэтому требование к проекции фиксируется в контракте для соседнего репозитория сейчас, до реализации `pull`.

### Отображение `targets` на модель backend

Кросс-осевые значения common-формата (`variations[].values[].targets[].properties[]`) ложатся на существующую пару таблиц `style_combinations` и `style_combination_members`: комбинация ссылается на свойство и appearance, участники — на стили с разных осей. Сид `seeds/dev/style_combinations.ts` подтверждает семантику комментарием «SDDS: primary + s + rounded → width = 500».

Значения без `targets` ложатся на `variation_property_values`, инварианты — на `invariant_property_values`.

Это не краевой путь: кросс-осевых вариаций в корпусе 1726 из 3328. Отсутствие уникального индекса на `style_combinations` поэтому является не гигиеническим замечанием, а прямым дефектом повторного импорта: без него второй push продублирует больше половины значений.

### Барьеры на запись

Умолчание `DEFAULT_API_URL` указывает на публичную установку gateway. Для команд на чтение оно сохраняется, для `components push` — запрещается: команда требует `--api-url` или `DSBUILDER_API_URL`. Дополнительно команда печатает разрешённый URL и его источник перед отправкой и по умолчанию работает в режиме `--dry-run`.

Риск не гипотетический: в `plasma-android` уже лежат конфигурации с боевыми идентификаторами проектов, например `tokens/plasma.homeds.compose/.sdds/config.json`.

### Контракт import-endpoint

CLI отправляет один запрос:

```
POST /api/projects/{projectId}/ds/design-systems/{designSystemId}/components:import
{
  "meta": { "name": "...", "source": "..." },
  "dryRun": true,
  "components": [ { "componentName": "...", "styleName": "...", "config": { ...common... } } ]
}
```

Ответ — отчёт с числом созданных, обновлённых, неизменённых и отклонённых записей, с причинами отклонения.

Тело не сжимается: gzip в `commonMain` недоступен без платформенных реализаций, а объём приемлем. Ориентир по крупнейшему пакету `sdds_serv`: 144 конфигурации, 637 КБ компактного JSON. Значение 1.7 МБ, встречавшееся в ранних оценках, относится к тексту с отступами; `kotlinx.serialization` по умолчанию сериализует без них (`prettyPrint = false`), поэтому в расчёт идёт компактная форма.

Ожидаемый масштаб записи на стороне backend для одной дизайн-системы: порядка 1151 style, 1743 property, 5500 значений свойств, 616 комбинаций с targets. Поэтому операция должна быть транзакционной.

## Risks / Trade-offs

- [Логика из PR #386 не покрыта тестами и не соответствует фактическому формату] → Модель переписывается по данным; вводится корпус round trip тестов на конфигурациях живых дизайн-систем, включая краевые случаи без вариаций и с вложенными вариациями.
- [Ошибочный запуск против общей установки backend] → Запрет умолчания API URL для записи, печать цели перед отправкой, `--dry-run` по умолчанию.
- [Существующие ключи проектов могут не различать чтение и запись] → До первой боевой проверки убедиться, что gateway и `db-service` проверяют scope `COMPONENTS` на запись. Gateway уже передаёт заголовок `X-Project-Scopes`.
- [Деструктивные скрипты `db:reset` и `db:clear` в соседнем репозитории не имеют предохранителей] → Добавить проверку `DATABASE_URL` на локальный шаблон в рамках работ соседнего репозитория; до этого проверять import только на локальной установке.
- [Пакет уезжает не в ту дизайн-систему, автоматической сверки нет] → Сверка имён снята сознательно: сопоставимое поле на стороне backend не установлено. Остаются обязательный явный API URL, печать `meta.json.name`, источника пакета, числа конфигураций, URL, его источника, `projectId` и `designSystemId` перед отправкой, и `--dry-run` по умолчанию. Ошибочный `--apply` остаётся возможным; его цена ограничена тем, что импорт транзакционный и пишется в `design_system_changes`.
- [Типы свойств из конфигураций не покрываются `propertyTypeEnum`] → Вне enum около 19% типизированных свойств. Расширение аддитивно и вынесено в требования к соседнему репозиторию.
- [Состояния из конфигураций не покрываются `stateEnum`] → Enum смешивал бы состояния двух разных природ. Решено разделением: взаимодействия остаются в enum, специфичные для компонента переезжают в `component_states` с источником в коде компонента. Отдельно: переопределение задаётся набором состояний, поэтому связь вынесена в `property_value_states`. Подробности — `backend-contract.md`, разделы 5.2 и 5.2.1.
- [Повторный импорт дублирует кросс-осевые значения] → На `style_combinations` нет уникального индекса, а через эту таблицу проходит более половины значений. Индекс вынесен в требования к соседнему репозиторию как блокирующий, а не как гигиенический.
- [Импорт разных дизайн-систем переключает колонки глобального слоя туда-обратно] → У семи свойств тип зависит от значения оси, а `properties.type` — одна ячейка на все дизайн-системы. Правило «глобальный слой пишется при создании и не обновляется» распространяется и на скалярные колонки, иначе каждый push порождает ложные записи в `design_system_changes` и искажает отчёт импорта.
- [Отказ всего пакета из-за одной некорректной конфигурации] → Осознанный выбор: частичная загрузка компонентной модели хуже отказа. Диагностика называет компонент и файл.
- [Опечатка в `plasma_homeds/card_config.json` блокирует push этой дизайн-системы] → Вариация `xl.has-inner-paddings` объявляет `key` в единственном числе при оси во множественном. Правило сверки `key` отвергает конфигурацию, и это верное поведение: расхождение единственное на все 500 конфигураций корпуса, то есть это дефект данных, а не формата. Исправляется в `theme-converter`; до исправления `plasma_homeds` не загружается целиком.

## Migration Plan

Изменение не требует миграции данных в этом репозитории. Порядок работ определяется зависимостью от соседнего репозитория.

1. Перенос codec и покрытие тестами. Не зависит от backend, проверяется автономно.
2. Чтение пакета из директории. Не зависит от backend.
3. Расширение `cli-core`: `post`, источник разрешения API URL, запрет умолчания для записи.
4. Команда `components push` в режиме `--dry-run` против локальной установки.
5. Повышение `client_max_body_size` внутри существующего location `~ ^/api/projects/([^/]+)/ds(/.*)?$` в `nginx.local.conf` и `nginx.prod.conf.template`. Выполняется в этом репозитории. Не блокирует пункт 7: крупнейший пакет — 637 КБ при действующем лимите 2 МБ, то есть запас 3.2x. Изменение вносится как страховка на рост числа компонентов.
6. Работы в репозитории `design-system-builder` (вне объёма этого change, но блокирующие пункт 7):
   - расширение `propertyTypeEnum` значениями `component_style`, `value`, `icon`, `boolean`, `gradient`, `blur`;
   - разделение состояний: `stateEnum` дополняется одним значением `activated`, специфичные для компонента переезжают в новую таблицу `component_states`, наполняемую из `uikit-api-meta.json`;
   - вынос связи значения с состояниями в `property_value_states`: переопределение задаётся набором, который колонкой не выразить;
   - транзакционный endpoint `components:import` с upsert по паре (`componentName`, `styleName`);
   - уникальный индекс на `style_combinations`;
   - снятие прежнего `is_default` перед установкой нового;
   - резолв имён токенов в `tokenId`;
   - заполнение `component_deps` рёбрами parent -> child по значениям типа `component_style`, с разрешением `styleName` в `componentName` через `meta.json`; `component_reuse_configs` не используется;
   - запись в `design_system_changes`;
   - проверка write-scope `COMPONENTS`.
7. Приёмка `--apply` на локальной установке, затем на изолированном проекте.

Локальный контур для проверки собирается из существующих средств: `docker-compose.dev.yml` соседнего репозитория поднимает `db-service` на порту 3008, `./start-local.sh --detach` поднимает gateway на 8080, а `identity-gateway/gateway/nginx.local.conf` уже маршрутизирует `/api/projects/{id}/ds/**` на `host.docker.internal:3008`. Отсутствует только helper для выпуска ключа проекта — он выпускается запросом `POST /api/projects/{projectId}/access-keys`.

Откат: команда новая, существующее поведение не меняется, кроме сигнатуры `AuthenticatedHttpClient`. Откат сводится к удалению feature и возврату интерфейса.

## Open Questions

### Разрешено проверкой

- **Что именует `meta.json.name`.** Вопрос снят вместе со сверкой. Он возник из наблюдения, что сид-данные `db-service` разделяют уровни: `design_systems` содержит `name: 'SDDS'` при `projectName: 'sdds'`, тогда как `tenants` содержит `sdds_cs`, `sdds_serv`, `plasma_web`, `plasma_giga`, то есть формы, совпадающие с именами директорий `theme-converter`. Проверка этой гипотезы дала обратный результат: `theme fetch` запрашивает все тенанты дизайн-системы без фильтра, а боевой `plasma-android/tokens/plasma.homeds.compose/.sdds/config.json` содержит ровно один тенант `plasma_homeds_default`; будь дизайн-системой `PLASMA`, тенантов было бы четыре по числу продуктов. Значит в боевой установке дизайн-система соответствует директории один к одному, сид-данные структуру прода не отражают, и исходное предположение о сверке по имени дизайн-системы, вероятно, было верным.

  «Вероятно» здесь и есть причина отказа: фактическое значение `design_systems.name` из боевой установки не наблюдалось, и проверка, отменяющая push, на такой основе не строится. Решение зафиксировано в разделе «Сверка дизайн-системы не выполняется». Наблюдение остаётся дешёвым: `dsbuilder status` уже печатает `designSystemName` (`HttpProjectAccessVerifier.kt:44`), поэтому при желании ввести сверку позднее её основание получается одной командой на чтение.

- **Свойства, тип которых определяется значением оси.** Пар (компонент, свойство) с расхождением типа — семь, из них шесть встречаются более чем в одной дизайн-системе. Все семь — пара `color` и `gradient`: `progress-bar.indicatorColor`, `circular-progress-bar.indicatorColor`, `slider.indicatorColor`, `overlay.backgroundColor`, `rect-skeleton.gradient`, `avatar.textColor`, `text-skeleton.gradient`. У пяти из семи оба типа присутствуют **внутри одной** дизайн-системы.

  Это не конфликт данных: тип определяется значением оси. В `progress_bar_config.json` при `view=gradient` свойство держит `{"type": "gradient", "default": "surface.default.accent-gradient"}`, при остальных семи значениях `view` — `{"type": "color", ...}`. То же у `overlay` (`direction-top`, `direction-bottom` против `default`) и у `rect-skeleton` (`default` против `pulse`). В обоих форматах конфигураций `type` стоит рядом со значением, а `properties.type` в `db-service` — одна колонка `notNull` на пару (компонент, имя).

  Перестройка модели не требуется. `properties.type` в `db-service` только читается: проецируется в выборках `catalog.ts`, служит фильтром ровно в одном запросе `properties-by-type` (`catalog.ts:673`) и упоминается в подсказке `nl-query/schema-context.ts:27`. Ни `CHECK`-констрейнта, ни валидации значения против типа свойства нет. Фактический тип каждого значения при этом сохраняется верно: `variation_property_values.token_id` ссылается на `tokens.type`, а `tokenTypeEnum` уже содержит `gradient`. Из всех рассмотренных вариантов требуется только добавление `gradient` в `propertyTypeEnum`, уже включённое в требования к соседнему репозиторию.

  Остаётся правило записи одной ячейки, и оно продиктовано идемпотентностью. `properties` — глобальный слой: у `avatar.textColor` тип `color` в `sdds_sbcom` и `gradient` в остальных пяти дизайн-системах, поэтому перезапись при каждом импорте переключала бы колонку туда-обратно, выводя свойство из категории неизменённых и порождая ложные записи в `design_system_changes`.

  Решение: `properties.type` записывается при создании строки и не обновляется при последующих импортах — та же аддитивность глобального слоя, что принята для наборов свойств и осей. При создании берётся тип значения на дефолтном значении оси из `bindings[].defaultValue`; для `progress-bar` это `view=default`, то есть `color`, совпадающий с семью значениями из восьми. На CLI решение не влияет: codec несёт тип на каждом значении, payload от него не зависит.

- **Многоосевые ссылки `component_style`.** Значение имеет вид `divider`, `avatar.s`, `check-box.m.default`, `badge-solid.l.pilled.accent` — то есть до трёх осей. Распределение по 2210 вхождениям и 521 различному значению: один сегмент 62, два 554, три 1194, четыре 400.

  Первый сегмент всегда является `styleName`, а не `componentName`: проверка по всем шести дизайн-системам не нашла ни одной ссылки на чистый `componentName`, который не был бы одновременно `styleName`. Висячая ссылка на весь корпус одна — `icon-button-clear` в `sdds_sbcom`. `styleName` в модели `db-service` соответствует `appearances`, что подтверждается сидами: `appearances.name` принимает значения `default` и `outline`.

  Таблица `component_reuse_configs` эту форму выразить не может, и это доказуемо её собственным уникальным индексом `crc_dep_ds_appearance_variation_unique` на (`componentDepId`, `designSystemId`, `appearanceId`, `variationId`). Компонент `button-group` ссылается на `basic-button.l.default`, `.m.`, `.s.`, `.xs.`, `.xxs.` — пять разных стилей одной оси `size` одного дочернего компонента, в зависимости от собственного размера родителя; все пять строк дали бы один ключ индекса, а колонки под стиль родителя в таблице нет. Пар (ДС, родитель, ребёнок) с более чем одним различным значением — 205.

  Она и не нужна: `component_style` — обычное свойство с обычным значением, а `variation_property_values` уже хранит `value` текстом. Решение: добавить `component_style` в `propertyTypeEnum`, значение писать текстом, `component_deps` заполнять рёбрами графа, `component_reuse_configs` не использовать.

- **Слияние компонентной модели между дизайн-системами.** Из 68 компонентов, встречающихся более чем в одной живой дизайн-системе, наборы свойств образуют цепочку по включению у 48, оси — у 52. То есть для большинства расхождение действительно является пропуском, а не конфликтом, и объединение равно максимальному набору.

  Несравнимых, где у каждой пары ДС есть свойства, отсутствующие у другой в обе стороны, — 20 по свойствам и 16 по осям. Это не пропуск, а другое решение той же задачи: у `card` — `shape` и `contentShape` против `contentPadding*`, у `tab-bar` — `dividerColor` и `shadow` против `backgroundBlurColor` и `backgroundBlurRadius`. По осям 13 из 16 приходится на `sdds_sbcom`, где `bg` и `mode` стоят там, где у остальных `view`, а `chip-slot` — вместо `shape`, `size`, `view`.

  Ни то, ни другое не требует изменения схемы: запись корректна, значения разложены по дизайн-системам, проекция восстановима из таблиц значений. Цена объединения — 1189 свойств против 1122, раздувание 1.06x. Практическое следствие одно и зафиксировано решением «Проекция компонента на дизайн-систему»: набор свойств для `pull` берётся из значений, а не из глобального слоя. Согласование словаря осей `sdds_sbcom` с остальными дизайн-системами — предмет отдельной работы владельцев, вне объёма этого change.

- **Типы свойств вне enum.** `propertyTypeEnum` содержит шесть значений, конфигурации используют одиннадцать. Отсутствуют `component_style` (2210 вхождений), `value` (1244), `icon` (394), `boolean` (61), `gradient` (39) — 3948 из 20 443, то есть 19.3% типизированных свойств. Закрывается аддитивным расширением enum, плюс `blur`, объявленный в `common_config_scheme.json` и в корпусе не встречающийся.

- **Состояния двух разных природ.** `stateEnum` содержит `pressed`, `hovered`, `focused`, `selected`, `readonly`, `disabled`. Конфигурации используют шестнадцать состояний, 2727 вхождений. Дополнить enum недостающими одиннадцатью нельзя: `checked`, `indeterminate`, `collapsed` и подобные принадлежат конкретному компоненту, их множество открыто и растёт с каждым новым компонентом, а enum принадлежности не выражает. Решение — разделение по источнику: состояния взаимодействия остаются в enum (плюс `activated`, который используют пять компонентов и не объявляет ни один), состояния компонента переезжают в `component_states`, наполняемую из поля `stateEnum` в `uikit-api-meta.json` — тем же принципом «глобальный слой из кода», что и свойства.

- **Набор состояний не выражается колонкой.** Переопределение задаётся набором: `["checked", "focused"]` означает конъюнкцию «отмечен И в фокусе». В корпусе 212 таких наборов, из них 86 сочетают состояние взаимодействия с состоянием компонента. Колонка вмещает одно состояние, поэтому набор пришлось бы разворачивать в отдельные строки, превращая конъюнкцию в независимые переопределения; пара `pressed + hovered` не выражается и двумя строками. Связь вынесена в `property_value_states`, в таблицах значений остаётся `states_key` — канонический ключ набора для уникального индекса.

- **Предел размера тела запроса на gateway.** Значение `client_max_body_size 2m` установлено в `identity-gateway/gateway/nginx.local.conf:65` и `nginx.prod.conf.template:64`. Крупнейший пакет `sdds_serv` в компактном JSON — 637 КБ, далее `plasma_b2c` 429 КБ, `plasma_giga` 411 КБ, `plasma_stards` 204 КБ, `plasma_homeds` 170 КБ, `sdds_sbcom` 75 КБ. Запас 3.2x, вопрос не блокирующий. Ранняя оценка 1.67 МБ считала текст с отступами.

  Изменение вносится внутрь существующего location `~ ^/api/projects/([^/]+)/ds(/.*)?$`, а не отдельным location под `components:import`: вся поверхность DS обслуживается одним regex-location, и более специфичный пришлось бы вставлять перед ним, дублируя блок `auth_request` целиком — около 25 строк в двух файлах. Глобальное значение остаётся прежним. Разбиение на пачки отвергнуто: требует идентификатора импорта, серверного состояния и допускает частично применённый импорт, что противоречит транзакционности.
