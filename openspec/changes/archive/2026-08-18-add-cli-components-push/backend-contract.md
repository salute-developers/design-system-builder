# Контракт `components:import` для репозитория `design-system-builder`

Документ описывает контракт `components:import`. **Endpoint реализован** в ветке
`feat/components-import` репозитория `design-system-builder` и проверен на локальном контуре:
пакет `sdds_serv` из 144 конфигураций загружается за 2.7 с без отклонений, повторный запуск
даёт 144 «без изменений».

Отличия реализации от первоначального замысла отмечены ниже пометкой «в реализации».

Все числа получены измерением по шести живым дизайн-системам `theme-converter` —
`plasma_b2c`, `plasma_giga`, `plasma_homeds`, `plasma_stards`, `sdds_sbcom`, `sdds_serv`, —
500 конфигураций, перечисленных в `meta.json`.

## 1. Endpoint

```
POST /api/projects/{projectId}/ds/design-systems/{designSystemId}/components:import
Authorization: ProjectKey <api-key>
Content-Type: application/json
```

Тело:

```json
{
  "meta": { "name": "sdds_serv", "source": ".sdds/components" },
  "dryRun": true,
  "components": [
    {
      "componentName": "badge",
      "styleName": "badge-solid",
      "config": { "...common-формат..." }
    }
  ]
}
```

- `meta.name` — имя из `meta.json` пакета. **Не** сверяется с чем-либо на стороне CLI: сопоставимое
  поле на стороне backend не установлено. Передаётся для аудита.
- `meta.source` — разрешённый источник пакета: путь локальной директории либо адрес архива.
- `dryRun: true` — импорт не сохраняет изменения, но возвращает тот же отчёт.
- `components[]` — весь пакет целиком, один запрос. Разбиение на пачки отвергнуто: оно требует
  идентификатора импорта, серверного состояния и допускает частично применённый импорт.

Ответ — отчёт:

```json
{
  "created": 12,
  "updated": 30,
  "unchanged": 100,
  "rejected": [
    { "componentName": "badge", "styleName": "badge-solid", "reason": "unknown property type" }
  ]
}
```

Поля `created`, `updated`, `unchanged`, `rejected` необязательны и по умолчанию равны нулю и
пустому списку. Успешный ответ с телом, которое не разбирается как отчёт, CLI считает ошибкой.

**В реализации** отчёт содержит два дополнительных поля, которые CLI игнорирует:
`unresolvedTokens` — имена токенов, не найденные в дизайн-системе, и `unresolvedComponentStyles` —
ссылки `component_style`, чей стиль не сопоставлен компоненту. Оба случая не отклоняют
конфигурацию: значение сохраняется текстом, а ссылка остаётся пустой. Отклонение целого
компонента из-за одного незнакомого имени сделало бы импорт в пустую дизайн-систему невозможным.

**В реализации** `dryRun` выполняет всю работу и откатывает транзакцию, поэтому отчёт плана
тождественен отчёту применения, а не вычисляется отдельной веткой кода.

Гранулярность отчёта — конфигурация компонента: `created`, если appearance не существовал;
`unchanged`, если значения совпали посимвольно с прежними; `updated` в остальных случаях.

## 2. Идентичность компонента

Ключ upsert — пара (`componentName`, `styleName`). `componentName` не уникален: `badge` в
`sdds_serv` соответствуют `badge-clear`, `badge-solid` и `badge-transparent`.

`styleName` соответствует `appearances.name`: сиды `seeds/dev/appearances.ts` дают значения
`default` и `outline`, то есть именно вариант оформления компонента.

## 2.1 Глобальный слой импорт не создаёт

**В реализации** источник глобального слоя — `uikit-api-meta.json`, файл, который KSP-процессор
генерирует из исходников `plasma-android` при сборке uikit. Его заливает скрипт
`scripts/import-uikit-api-meta.sh` (в репозитории `design-system-builder-kt`) через публичные
CRUD-эндпоинты: `POST /components`, `POST /properties`, `POST /property-platform-params`.

Это соответствует устройству системы: легаси-импорт `/legacy/design-systems/create` компоненты
тоже не создаёт, а пропускает ненайденные (`if (!component) continue`). Ответственность
разделена так:

| источник | что наполняет |
|---|---|
| `uikit-api-meta.json`, из кода компонентов | компоненты, свойства, типы, описания, платформенные алиасы |
| конфигурации `theme-converter`, из дизайна | appearances, стили, значения, оси вариаций |

Причина разделения измерима. Свойства из api-meta приходят с описанием и платформенным алиасом,
которых в конфигурациях оформления нет вовсе: до разделения импорт создавал 39 свойств
`text-field` с нулём описаний и нулём алиасов, тогда как курируемый `Button` имел 10 свойств
с 33 алиасами. После разделения все 1267 свойств имеют описание.

Поведение импорта:

- **компонент не найден** — конфигурация отклоняется, попадает в `rejected` с причиной
  `Component '<имя>' is not present in the global layer`, остальные конфигурации грузятся;
- **свойство не найдено** — имя попадает в `unknownProperties`, значения для него не пишутся,
  остальная часть конфигурации грузится.

Оси вариаций импорт по-прежнему создаёт: в `uikit-api-meta.json` понятия оси нет, это категория
дизайна, а не кода.

**Имена сопоставляются по каноничной форме** — нижний регистр без разделителей. Источники
записывают их по-разному: api-meta даёт имена Kotlin-функций (`AccordionItem`),
`theme-converter` — kebab-case (`accordion-item`). Без канонизации возникали дубликаты,
что уже наблюдалось в базе как `TextField` рядом с `text-field`.

Замеры соответствия источников: 77 общих компонентов из 78 в каждом, 1132 общих свойства из
1176 в конфигурациях (96%), тип совпадает у 1123 из 1132 (99.2%). Расхождения типов — девять:
четыре `color` против `gradient` (те самые свойства, чей тип зависит от значения оси), пять
`integer` против `value` и `float`. Первые остаются открытым вопросом модели, вторые сняты
добавлением `integer` в `propertyTypeEnum`.

Свойств, которые есть в дизайне и отсутствуют в коде, — 44. Они не дозаполняются из конфигураций,
а возвращаются в `unknownProperties`: это сигнал разработчикам uikit о расхождении, а не повод
искажать модель.

## 3. Операция транзакционна и авторитетна для appearance

**В реализации** импорт заменяет значения целиком: перед записью удаляются прежние
`variation_property_values`, `invariant_property_values` и `style_combinations` этого appearance.
Иначе свойство, снятое из конфигурации, оставалось бы в базе навсегда. Глобальный слой при этом
остаётся аддитивным: строки `components`, `variations` и `properties` не удаляются.

Отдельная деталь, найденная на данных: общий формат законно задаёт одну координату
(свойство, стиль, состояние) дважды — корневым блоком `view` и блоком `view` внутри вариации.
Уникальный индекс `vpv_style_property_appearance_no_state_unique` это запрещает, поэтому строки
собираются в отображение с правилом «побеждает последняя» до вставки.



Ожидаемый объём записи для одной дизайн-системы: порядка 1151 style, 1743 property,
5500 значений свойств, 616 комбинаций с targets. Частично применённый импорт компонентной
модели хуже отказа, поэтому вся операция выполняется в одной транзакции.

## 4. Отображение common-формата на таблицы

| common | таблица |
|---|---|
| `invariants` | `invariant_property_values` |
| `variations[].values[].properties` без `targets` | `variation_property_values` |
| `variations[].values[].targets[].properties` | `style_combinations` + `style_combination_members` |
| `defaults` | `styles.is_default` |
| свойства типа `component_style` | обычное значение текстом, плюс ребро в `component_deps` |

Механизм `style_combinations` — не краевой путь: из 3328 вариаций корпуса **1726 (52%)**
кросс-осевые, то есть имеют `binding` длиной два и более. Распределение: длина 1 — 1602,
длина 2 — 792, длина 3 — 931, длина 4 — 3. На загруженной `sdds_serv` это 2303 строки сочетаний
против 4344 обычных значений.

**В реализации** стили создаются для всех значений оси, встречающихся где угодно, включая те,
что фигурируют только внутри `targets`. Ось может не иметь собственных значений вовсе: у
`basic-button` в `sdds_sbcom` ось `size` встречается исключительно как target, потому что ни
одна native-вариация не берёт её последним элементом `binding`. Если создавать стили только по
собственным значениям осей, ссылка на такой стиль не разрешается, сочетание теряет участника,
а лишившись участника — совпадает по ключу с другими и затирает их. На этом компоненте потеря
составляла 128 сочетаний из 130.

Значения из `defaults` при этом источником не являются: объявленный дефолт не всегда указывает
на существующее значение. У того же `basic-button` ось `mode` объявляет `defaultValue: "primary"`,
тогда как фактические значения называются `mode-primary` и далее, — это частный случай того же
расхождения объявленных и встречающихся значений, что описано в разделе про round trip.

## 5. Требуемые доработки схемы

### 5.1 Расширить `propertyTypeEnum`

Сейчас шесть значений, конфигурации используют одиннадцать. Отсутствуют:

| тип | вхождений |
|---|---|
| `component_style` | 2210 |
| `value` | 1244 |
| `icon` | 394 |
| `boolean` | 61 |
| `gradient` | 39 |

Итого 3948 из 20 443, то есть **19.3%** типизированных свойств. Плюс `blur`, объявленный в
`common_config_scheme.json` и в корпусе пока не встречающийся, и `integer` — тип из
`uikit-api-meta.json`, которым описаны счётчики и длительности: `PaginationDots.edgeCount`,
`Wheel.wheelCount`, `Wheel.visibleItemsCount`, `RectSkeleton.duration`, `TextSkeleton.duration`.
В конфигурациях оформления те же свойства записаны как `value` или `float`; тип глобального
слоя берётся из кода, поэтому в базе они имеют тип `integer`.

Расширение аддитивное, ломающих изменений нет.

### 5.2 Разделить состояния на два вида

Сейчас `stateEnum` содержит шесть значений: `pressed`, `hovered`, `focused`, `selected`,
`readonly`, `disabled`. Конфигурации используют шестнадцать.

Расширять enum недостающими одиннадцатью — неверно. Они разной природы:

| вид | примеры | множество | источник |
|---|---|---|---|
| взаимодействия | `pressed`, `hovered`, `focused` | закрытое, одно на все компоненты | модель ввода |
| специфичные для компонента | `checked`, `indeterminate`, `collapsed` | открытое, у каждого своё | код компонента |

Второй вид в enum не помещается: множество растёт с каждым новым компонентом, а
принадлежность состояния компоненту при этом теряется. `checked` осмыслен у `CheckBox`
и бессмыслен у `Card`, но enum этого различия не проводит.

**`stateEnum` получает седьмое значение — `activated`.** Это вывод из данных: его используют
пять компонентов (`code-field`, `list-item`, `pagination-dots`, `text-area`, `text-field`),
и ни один не объявляет его собственным состоянием в `uikit-api-meta.json`.

**Состояния, специфичные для компонента, переезжают в `component_states`** — пара
(`component_id`, `name`). Источник, как и для свойств, — код: у компонента в
`uikit-api-meta.json` есть поле `stateEnum`, и в нём уже готова форма имени для конфигураций:

```json
"stateEnum": {
  "qualifiedName": "com.sdds.compose.uikit.CheckBoxStates",
  "values": [{ "name": "Checked" }, { "name": "Indeterminate" }]
}
"stateEnum": {
  "values": [{ "name": "DraggingOver", "configName": "dragging-over" }]
}
```

`configName` даёт kebab-case имя, встречающееся в конфигурациях, но задан он не везде:
11 значений из 39 имеют его, остальные 28 записаны в PascalCase. Скрипт
`import-uikit-api-meta.sh` приводит имя к единой форме — kebab-case в нижнем регистре —
и заводит 39 состояний у 18 компонентов из 78.

Единая форма обязательна, а не косметична. `states_key` хранит имена в написании из
конфигураций, и если связь ведёт на имя в другом написании, набор состояний нельзя
восстановить из связанных строк текстуально — а именно это потребуется обратной проекции
для `components pull`.

Покрытие проверено по корпусу: из 18 семантических состояний, встречающихся в конфигурациях,
13 объявлены в api-meta, а оставшиеся 5 — все `activated`, который отнесён к взаимодействиям.
Расхождений не осталось.

### 5.2.1 Набор состояний вместо одного

Переопределение задаётся **набором** состояний, а не одним:

```json
{ "state": ["checked", "focused"], "value": "outline.default.accent" }
```

Это означает «отмечен И в фокусе» — конъюнкцию. В корпусе 212 таких наборов:

| состав набора | наборов |
|---|---|
| взаимодействие + взаимодействие | 126 |
| взаимодействие + состояние компонента | 86 |

Колонка в таблице значений вмещает одно состояние, поэтому набор пришлось бы разворачивать
в отдельные строки — и конъюнкция превратилась бы в независимые переопределения. База стала бы
утверждать «при `focused` цвет A, при `checked` цвет B», а что при `checked + focused` — вывести
было бы нельзя. Пара `pressed + hovered` не выражается и двумя строками: обе легли бы в одну
колонку и столкнулись на уникальном индексе.

Поэтому колонки `state` и `component_state_id` из таблиц значений убраны, а связь вынесена
в отдельную таблицу:

```
property_value_states
  variation_property_value_id  ┐ ровно одна ссылка на значение
  invariant_property_value_id  ┘
  state              stateEnum          ┐ ровно одно
  component_state_id → component_states ┘
```

В таблицах значений остаётся `states_key` — канонический ключ набора (отсортированные имена
через запятую, пустая строка у базового значения). Он нужен уникальному индексу: идентичность
строки определяется набором, а набор лежит в связанной таблице.

Значение без записей в `property_value_states` является базовым, то есть действует вне состояний.

### 5.2.2 Состав миграции

Изменения схемы уместились в одну миграцию `drizzle` — `0004_component_import`, 51 оператор.
Она заводит `component_states`, `property_value_states` и пару таблиц реляционных ссылок
`component_style`, добавляет `states_key` в таблицы значений, `combination_key`
в `style_combinations`, семь типов в `propertyTypeEnum` и `activated` в `stateEnum`.

Изначально миграций было три. Объединены, потому что описывают одну фичу и в прод не уходили,
а объединение оказалось не механическим: две из них расширяли и сужали `stateEnum`, и эти шаги
взаимно уничтожаются. Чистая разница с `0003` сводится к одному добавленному значению, поэтому
исчезли `DROP TYPE`, пересоздание типа и обратное приведение колонок — а вместе с ними класс
отказа, который они порождали: приведение к суженному типу не переживало значение `checked`.

Существующие данные переносятся: состояние из колонки раскладывается в запись
`property_value_states` плюс канонический ключ набора, после чего колонка снимается.
Переносить семантические состояния не требуется — до этой миграции enum их не содержал,
значит в базе их быть не может.

**Порядок операций существен:**

1. прежние частичные уникальные индексы снимаются **до** переноса — обнуление колонки `state`
   делает базовую и семантическую строки неразличимыми для индекса `WHERE state IS NULL`;
2. колонки состояний снимаются **после** переноса, но до создания новых индексов;
3. внешние ключи на добавляемые колонки ставятся **после** `ADD COLUMN`.

Все три требования проверены накатом на непустую базу. **На пустой базе ни одно нарушение
не проявляется**, поэтому проверки накатом с нуля недостаточно.

### 5.3 Уникальный индекс на `style_combinations`

Таблица не имеет уникального индекса, тогда как у соседней `variation_property_values`
естественный ключ выражен колонками и индексом закрыт
(`vpv_style_property_appearance_no_state_unique`). Асимметрия возникла из-за того, что
идентичность строки сочетания — это тройка (свойство, appearance, **набор** стилей-участников),
а участники лежат в отдельной таблице `style_combination_members`: индексом по связанной
таблице уникальность не выразить.

Наглядно, на компоненте `segment` из `sdds_serv`, свойство `segmentItemStyle`:

```
segment-item.l.pilled.accent      при  size=l  и shape=pilled и view=accent
segment-item.l.pilled.primary     при  size=l  и shape=pilled и view=primary
segment-item.m.pilled.accent      при  size=m  и shape=pilled и view=accent
segment-item.xl.pilled.accent     при  size=xl и shape=pilled и view=accent
```

Одно свойство одного appearance, 30 сочетаний и 30 различных значений — строки различаются
только составом сочетания. Поэтому очевидный вариант «уникальность по (`property_id`,
`appearance_id`)» неприменим: у одной такой пары в корпусе встречается до 48 сочетаний.

**В реализации** добавлена колонка `combination_key` — отсортированные идентификаторы
стилей-участников через запятую, то есть набор, поднятый из связанной таблицы в колонку, —
и уникальный индекс `sc_property_appearance_combination_unique` на (`property_id`,
`appearance_id`, `combination_key`).

**Чего эта правка не делает.** Первоначальная формулировка утверждала, что без индекса
повторный push продублирует больше половины значений и что правка блокирующая. Применительно
к реализованному импорту это неверно, и обоснование сужается. Импорт авторитетен для appearance
и удаляет прежние сочетания перед записью, поэтому дубли от повторного push предотвращает
удаление, а не ключ. Дублей внутри одного пакета тоже нет: на `sdds_serv` отправляется 2303
кросс-осевых значения и ровно 2303 различных ключа, то есть `ON CONFLICT` не срабатывает ни разу.

Индекс остаётся оправданным по трём причинам, более скромным: он делает идентичность сочетания
выразимой в SQL, делает возможной форму upsert (`ON CONFLICT` требует констрейнта) и страхует
от дублей, если запись пойдёт в обход удаления — частичным импортом, из UI или из другого
сервиса.

### 5.4 Снятие прежнего `is_default`

Партиальный уникальный индекс `styles_variation_id_ds_id_is_default_unique` не допускает двух
стилей по умолчанию на одну ось в одной дизайн-системе. Импорт должен снимать прежний флаг перед
установкой нового, иначе повторная загрузка с изменившимся дефолтом упадёт на констрейнте.

### 5.5 Резолв имён токенов в `tokenId`

Значения свойств ссылаются на токены по имени (`surface.default.accent`). Импорт разрешает имя в
`tokens.id` в пределах дизайн-системы и пишет `token_id`; неразрешённое имя попадает в `rejected`
с причиной.

### 5.6 Запись в `design_system_changes` и проверка write-scope

Импорт пишет аудит-запись. Gateway уже передаёт заголовок `X-Project-Scopes`; `db-service` должен
проверять наличие write-scope `components:write`, поскольку это первая пишущая операция CLI. Формат scope — `entity:action`, значения перечислены в `ProjectEntity` и `AccessKeyAction` сервиса `projects-service`; строка `COMPONENTS` отклоняется как неподдерживаемая.

## 6. Решения, не требующие изменения схемы

### 6.1 `component_style` пишется значением, `component_reuse_configs` не используется

Значение имеет вид `divider`, `avatar.s`, `check-box.m.default`, `badge-solid.l.pilled.accent` —
до трёх осей. Первый сегмент всегда `styleName`: проверка по всем шести дизайн-системам не нашла
ни одной ссылки на чистый `componentName`, который не был бы одновременно `styleName`. Висячая
ссылка на весь корпус одна — `icon-button-clear` в `sdds_sbcom`.

Таблица `component_reuse_configs` эту форму выразить не может, и это следует из её собственного
уникального индекса `crc_dep_ds_appearance_variation_unique` на
(`componentDepId`, `designSystemId`, `appearanceId`, `variationId`). Компонент `button-group`
ссылается на `basic-button.l.default`, `.m.`, `.s.`, `.xs.`, `.xxs.` — пять разных стилей одной
оси `size` одного дочернего компонента, в зависимости от собственного размера родителя. Все пять
строк дали бы один ключ индекса, а колонки под стиль родителя в таблице нет. Пар
(ДС, родитель, ребёнок) с более чем одним различным значением — **205**.

Решение: значение пишется текстом в обычное свойство типа `component_style`; `component_deps`
заполняется рёбрами parent -> child с разрешением `styleName` в `componentName` через `meta.json`;
`component_reuse_configs` не трогается.

### 6.2 `properties.type` не обновляется импортом конфигураций

У семи пар (компонент, свойство) тип зависит от значения оси. В `progress_bar_config.json` при
`view=gradient` свойство держит `{"type": "gradient", ...}`, при остальных семи значениях `view` —
`{"type": "color", ...}`. Полный список: `progress-bar.indicatorColor`,
`circular-progress-bar.indicatorColor`, `slider.indicatorColor`, `overlay.backgroundColor`,
`rect-skeleton.gradient`, `avatar.textColor`, `text-skeleton.gradient`. У пяти из семи оба типа
присутствуют внутри одной дизайн-системы.

Перестройка модели не требуется: `properties.type` только читается — проецируется в выборках
`catalog.ts`, служит фильтром ровно в одном запросе `properties-by-type` (`catalog.ts:673`) и
упоминается в подсказке `nl-query/schema-context.ts:27`. Ни `CHECK`-констрейнта, ни валидации
значения против типа свойства нет. Фактический тип каждого значения сохраняется верно:
`variation_property_values.token_id` ссылается на `tokens.type`, а `tokenTypeEnum` уже содержит
`gradient`.

Требуется правило записи, продиктованное идемпотентностью: у `avatar.textColor` тип `color` в
`sdds_sbcom` и `gradient` в остальных пяти дизайн-системах, поэтому перезапись при каждом импорте
переключала бы колонку туда-обратно, выводя свойство из категории неизменённых и порождая ложные
записи в `design_system_changes`.

**Правило:** `properties.type` записывается при создании строки типом значения на дефолтном
значении оси из `bindings[].defaultValue` и не обновляется при последующих импортах.

**Правило относится к импорту конфигураций.** У колонки есть второй писатель — заливка
`uikit-api-meta.json`, и она ведёт себя иначе: при расхождении типа она его **обновляет**,
потому что глобальный слой принадлежит коду. На prod-сиде это сработало один раз —
`List.listItemStyle` сменил `typography` на `component_style`.

Значения при этом не меняются: тип лежит в `properties`, значения в `variation_property_values`,
и пересчитывать их некому. У `List.listItemStyle` после смены типа остались типографические
токены `body.l.normal`, тогда как `component_style` предполагает ссылку вида `list-item.l`.
Такое расхождение ловит `typeMismatches` (раздел 6.6), но только при импорте конфигураций —
сид пишет в базу напрямую, минуя проверку.

### 6.3 Глобальный слой аддитивен

Таблицы `components`, `variations` и `properties` не содержат `designSystemId` и хранят
объединение по всем дизайн-системам. Это корректно и подтверждается данными: у 48 из 68
компонентов, встречающихся более чем в одной живой дизайн-системе, наборы свойств образуют
цепочку по включению, то есть расхождение действительно является пропуском. Цена объединения —
1189 свойств против 1122 при максимуме по одной ДС, раздувание 1.06x.

Несравнимых, где у каждой пары ДС есть свойства, отсутствующие у другой в обе стороны, — 20 по
свойствам и 16 по осям. По осям 13 из 16 приходится на `sdds_sbcom`, где `bg` и `mode` стоят там,
где у остальных `view`. Приведение словарей к общему виду — работа владельцев дизайн-систем, вне
объёма импорта.

### 6.4 Требование к проекции для будущего `components pull`

Набор свойств и осей конкретной дизайн-системы **не восстанавливается** из глобального слоя. Он
восстанавливается только из таблиц значений: `variation_property_values` через
`styles.design_system_id`, `invariant_property_values` через собственную колонку
`design_system_id`, `style_combinations` через `appearances.design_system_id`.

Если чтение возьмёт набор свойств из `properties`, для `plasma_b2c` оно выдаст 28 свойств
компонента `card` вместо семи, и round trip `push -> pull` перестанет сходиться.

### 6.5 Обратная проекция: `GET /ds/component-config`

Требование 6.4 реализовано ручкой, пришедшей из ветки `dev`. Она собирает конфигурацию одного
компонента в общем формате — том же, что потребляет импорт.

Ручка потребовала трёх правок, чтобы требованию соответствовать:

- читала снятую колонку `state` и умела вернуть лишь одно состояние на переопределение
  (`state: [sr.state]`). Переведена на `states_key`, набор отдаётся целиком;
- **теряла кросс-осевые значения целиком.** Она читала `style_combinations`, но брала оттуда
  только группировку стилей: из выбранных строк использовался единственный `id`, а `propertyId`
  и `value` не читались нигде. Свойство, живущее только в сочетаниях, исчезало из ответа —
  у `Segment` так пропадал `segmentItemStyle`, по `sdds_serv` это 2303 сочетания;
- отдавала оси без значений. Ось объявлена кодом и есть у компонента всегда, а наполняет её
  конкретная дизайн-система: `variant` у `CheckBox` наполняет только `sdds_sbcom`.

Сочетание принадлежит ровно одному стилю-участнику, иначе попадало бы в ответ столько раз,
сколько в нём осей. Владелец выбирается детерминированно: ось цветовой схемы, если она в
сочетании есть, иначе наименьший `styleId`. На восстановление конфигурации выбор владельца
не влияет — координата владельца и `targets` в сумме дают тот же набор осей.

Проверено сверкой с базой по всем 493 конфигурациям шести дизайн-систем: 6700 сочетаний,
10 750 вариационных значений, 2594 инварианта, 2478 переопределений состояний — расхождений нет.

**Оговорка.** Массивы в ответе не отсортированы: запросы идут без `ORDER BY`, и порядок
элементов `values` и `states` между вызовами меняется. Сравнивать ответы `diff` без
нормализации нельзя.

### 6.6 Диагностика расхождений кода и дизайна

Отчёт импорта содержит три перечня, не отменяющих загрузку:

| поле | смысл |
|---|---|
| `unknownProperties` | свойство есть в конфигурации, но не в глобальном слое — значения не записаны |
| `unknownStates` | состояние не входит ни в enum, ни в объявленные компонентом |
| `typeMismatches` | тип глобального слоя не встречается в конфигурации ни разу |

Типы сравниваются семьями, а не поимённо: `integer`, `float`, `dimension` и `value` считаются
одной семьёй, потому что различаются лишь записью одного и того же значения. Без этого пять
срабатываний из шести на корпусе были бы пустыми.

`typeMismatches` сообщается, только когда тип из базы не встречается в конфигурации ни разу —
иначе проверка ругалась бы на семь свойств, законно принимающих и цвет, и градиент.

На корпусе: 44 свойства вне глобального слоя у успешно загружаемых компонентов и по одному-трём
расхождению типа на пакет.

## 7. Предохранители до первой боевой проверки

`src/db/reset.ts` выполняет `DROP SCHEMA public CASCADE`, `src/db/clear.ts` —
`TRUNCATE TABLE ... CASCADE`. Ни один не проверяет, на какую базу указывает `DATABASE_URL`.
До первой проверки против непустой установки требуется проверка на локальный шаблон.

## 8. Со стороны gateway

Проверено на локальном контуре: тело 4 МБ проходит на маршруте `/ds` и отклоняется с `413` вне его. `client_max_body_size` поднят до `16m` внутри существующего location
`~ ^/api/projects/([^/]+)/ds(/.*)?$` в `identity-gateway/gateway/nginx.local.conf` и
`nginx.prod.conf.template`. Глобальное значение `2m` не изменялось.

Крупнейший пакет `sdds_serv` в общем формате — 583 КБ (597 379 байт, 144 конфигурации), измерено на реальной отправке. Оценка по native давала 637 КБ. Далее `plasma_b2c`
429 КБ, `plasma_giga` 411 КБ, `plasma_stards` 204 КБ, `plasma_homeds` 170 КБ, `sdds_sbcom` 75 КБ.

## 9. Известный дефект исходных данных

`plasma_homeds/card_config.json`: вариация `xl.has-inner-paddings` объявляет
`key: "has-inner-padding"` в единственном числе при оси `has-inner-paddings` во множественном.
CLI отвергает такую конфигурацию, и это верное поведение — расхождение единственное на все 500
конфигураций. Исправляется в `theme-converter`; до исправления `plasma_homeds` не загружается
целиком.
