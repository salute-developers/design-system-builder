## Context

Глобальный слой компонентной модели хранит объединение по всем дизайн-системам и платформам: `components.name` уникален глобально, `properties` уникальны по `(component_id, name)`, платформенные имена вынесены в `property_platform_params` по ключу `(property_id, platform, name)`. Слой заводит скрипт `backend-kt/scripts/import-uikit-api-meta.sh`, читающий `uikit-api-meta.json`; `components push` и `components fetch` его только используют и сообщают `unknownProperties` / `unknownStates`, если слой неполон.

Как устроена мета. Для Compose это файл `uikit-compose-api-meta.json`, который KSP-процессор `api-info-ksp` кладёт в ресурсы модуля `sdds-core/uikit-compose`. Gradle-плагин `dsBuilder` (`sdds-core/plugin_theme_builder`) в проекте пользователя держит задачу `readUikitComposeApiMeta`: она ищет `uikit-compose-api-meta.json` в jar и `android-java-res` артефактах `compileClasspath` и пишет копию в `build/theme-builder/components/uikit-compose-api-meta.json` (`COMPONENTS_PATH = "theme-builder/components"`). Если файл не найден, пишется пустой массив. Так мета всегда соответствует версии uikit, от которой зависит проект, — той же, по которой работает генератор.

Замеры по `uikit-compose-api-meta.json` (1.08 МБ):

- 79 компонентов, ни одного с пустым `componentName`;
- 2315 параметров, 1263 уникальных пары `(componentName, id)`: один `id` повторяется, когда билдер принимает слот в нескольких перегрузках (`Color`, `InteractiveColor`, `StatefulValue`); все 742 группы повторов лежат в одной `group` (`colors`, `dimensions`, `root` и др.);
- конфликтов типа среди дублей нет (0 из 742 групп);
- 11 типов: `boolean`, `color`, `component_style`, `dimension`, `float`, `icon`, `integer`, `shadow`, `shape`, `typography`, `value` — все есть в `propertyTypeEnum`;
- `stateEnum` у 20 компонентов; `configName` задан не у каждого значения, у остальных имя PascalCase.

Поле `group` в БД не хранится: скрипт кладёт его только в текст `description`, а генератор использует его для раскладки параметров по блокам стиля. Алиас `property_platform_params.name` читает `routes/api/legacy.ts` (поле `platformMappings` в выгрузке для клиента билдера) — это платформенное имя свойства.

Прежний путь скрипта по умолчанию (`ksp/release/resources/...`) больше не существует: модуль стал Kotlin Multiplatform, файл лежит в `ksp/metadata/commonMain/resources/sdds/api/`. Этот сдвиг сам по себе показывает, почему CLI не должен знать расположение файла в исходниках plasma-android.

## Goals / Non-Goals

**Goals:**

- Заводить глобальный слой из CLI, без `jq`, `curl` и без рабочей копии plasma-android.
- Один запрос вместо тысяч; результат dry run тождественен результату применения.
- Брать мету оттуда же, откуда берёт генератор, то есть из артефакта uikit проекта пользователя.
- Оставить запись безопасной для ключа проекта: только добавление, без изменения существующих строк.
- Заложить порт, чтобы View и iOS добавлялись без перестройки.

**Non-Goals:**

- Платформы `android-view`, `swiftui`, `react`. Для них команда отказывает явно; формат View и iOS отличаются от Compose и разбираются отдельными нормализаторами в следующих change.
- Единый формат меты для платформ. Каждая платформа читает свой формат своим нормализатором; общий у них только выход — манифест.
- Разделение глобального слоя по платформам. Модель «одно свойство — N платформенных имён» сохраняется.
- Поле `values` свойств типа `value`, `styleQualifiedName`, `resolvedTypes`.
- Подсказка в отчёте `components push` о необходимости импорта меты.
- Миграции схемы и изменения `property_type`.

## Decisions

### Мету достаёт платформенный делегат, а не CLI

Извлечение файла — работа Gradle-плагина `dsBuilder`, который уже умеет разбирать classpath проекта. В CLI для этого добавляется capability `API_META`; делегат `android` для `compose` запускает `readUikitComposeApiMeta` тем же способом, что `generateComposeComponents` (`gradlew -p <workspaceDir> <task>`), затем CLI читает `<workspaceDir>/build/theme-builder/components/uikit-compose-api-meta.json`.

Альтернативы:

- **CLI сам резолвит артефакт и читает jar/aar.** Требует чтения zip на трёх таргетах через `expect/actual`, знания Maven-координат и версии uikit и обхода Gradle-кэша. Тот же вариант уже отвергнут в `add-cli-components-push`, где он тянул за собой три платформенные реализации ради одного файла.
- **Пользователь сам передаёт `--from <file>`.** Проще, но у пользователя нет ни файла, ни способа его получить, кроме той же Gradle-задачи.

Путь результата определяется соглашением плагина, а не ответом задачи. Риск: модуль с переопределённым `buildDir` положит файл в другое место; в этом случае CLI сообщает ожидаемый путь и предлагает проверить конфигурацию (см. Risks).

### CLI нормализует, backend принимает манифест

Формат KSP-меты не покидает границы CLI. Backend не знает ни `stateEnum`, ни `paramSimpleType`, ни `group`. Это повторяет решение `components push`: codec в CLI, `commonConfig.ts` на backend. Нормализатор — чистая функция в `feature-components/domain`, без ввода-вывода, и покрывается тестами на реальном файле.

Альтернатива — отправлять сырой JSON и разбирать на backend: связывает `db-service` с форматом plasma-android, а при добавлении View и iOS backend растёт тремя разборщиками.

Правила нормализатора Compose:

- компоненты и свойства сводятся по `(componentName, id)`; порядок и имена берутся из первого вхождения;
- `type` берётся как есть; `--map-type from:to` подменяет тип до отправки;
- `description` строится из `methodName` первого вхождения и всех встреченных `paramSimpleType` (`method: X; param: Color/InteractiveColor`). `group` не включается: это деталь раскладки параметров по блокам стиля для генератора, а не свойство слота. Тип параметра у перегрузок разный: сверка показала, что он различается у всех дублей (один слот приходит как `Color` и как `InteractiveColor`), а `methodName` — у одного из 770, поэтому в описание идут все типы в порядке появления, а не тип первого вхождения. Платформенное имя (алиас) равно `id`, как у прежнего скрипта: `methodName` — имя параметра метода билдера, и у 58 параметров из 2315 он отличается от `id`;
- `platformName` равен `id` (для Compose он совпадает с именем метода);
- состояния берутся из `stateEnum.values[]`: `configName`, если задан, иначе `name`, приведённое к kebab-case в нижнем регистре; результат уникален внутри компонента;
- компонент без параметров не отправляется.

### Список поддерживаемых типов принадлежит backend

Скрипт хранит `supported_types`, продублированный из `propertyTypeEnum`, и молча пропускает несовпадения. CLI списка не знает: backend проверяет тип по enum и возвращает неизвестный в `rejected[]` с причиной. `--strict` в CLI означает «завершиться с кодом 1, если `rejected` не пуст». Новый тип в мете поэтому не теряется: команда громко о нём сообщает, а его поддержка — добавление значения enum миграцией и код, который умеет с ним работать; `--map-type` позволяет временно отобразить его в существующий.

Альтернативы: сделать `type` текстовым (теряется проверка, миграция схемы) и добавлять значения enum прямо из импорта (DDL из запроса, что недопустимо для ключа проекта).

### Запись аддитивная

Ручка создаёт то, чего нет, и не меняет существующего:

| Сущность | Ключ | Если есть |
|---|---|---|
| компонент | `name` | не трогается |
| состояние компонента | `(componentId, name)` | не трогается |
| свойство | `(componentId, name)` | не трогается; если `type` отличается — запись в `typeMismatches` |
| алиас | `(propertyId, platform, name)` | не трогается |
| привязка `design_system_components` | `(designSystemId, componentId)` | не трогается |

Причина. Глобальный слой общий для всех дизайн-систем; ключ проекта с правом `components:write` не должен менять тип свойства, на который опираются чужие значения. Скрипт делал `PATCH` типа, и это единственное поведение, которое здесь сознательно убирается (**BREAKING**). Смена типа — отдельная осознанная операция и при необходимости делается миграцией или админкой.

Следствия: описание существующего свойства не обновляется; алиасы накапливаются (если раньше алиасом записали другое имя, у свойства появятся оба); порядок импорта платформ влияет на тип только при расхождении, и это расхождение видно в `typeMismatches`.

Привязка к дизайн-системе идёт к той, что указана в теле запроса (`designSystemId` из `.sdds/config.json`). Флаг `--link-design-systems` скрипта («привязать ко всем») не переносится: у CLI есть контекст проекта, а массовая привязка к чужим дизайн-системам не нужна и небезопасна.

Альтернатива — `upsert` с обновлением типа и описания: удобнее для исправления данных, но даёт ключу проекта запись в общие данные.

### Endpoint и права

`POST /api/projects/{projectId}/ds/component-config/import-api-meta`, `designSystemId` в теле, как у `/import`. Путь не содержит идентификатора дизайн-системы и custom method через двоеточие, потому что gateway и клиентские соглашения этого проекта уже отказались от них для `components push`. Роутер лежит рядом с `component-config-import.ts` и использует те же `requireScope("components:write")`, проверку принадлежности дизайн-системы проекту (`designSystemScopeFilter`, `designSystemBelongsToScope`) и `validateBody`.

Новый scope не вводится: ключу проекта достаточно `components:write`. Разделение «пишет значения» и «заводит глобальный слой» отложено; это осознанный компромисс, зафиксированный в Risks.

Запрос — один, тело компактно порядка сотен КБ (1263 свойства); лимит `express.json` — 50 МБ. Разбиение на пачки не вводится по тем же причинам, что у `components push`: оно требует серверного состояния и допускает частично применённый импорт. Таймаут CLI (5 минут, `configureCliTimeouts`) уже согласован с proxy timeout gateway.

### dry run через откат транзакции

Как в `/import`: вся работа выполняется в транзакции и затем откатывается (`DryRunRollback`), поэтому отчёт dry run тождественен отчёту применения и не считается отдельной веткой кода. Запись в `design_system_changes` делается внутри той же транзакции и откатывается вместе с ней.

### Отчёт

```json
{
  "createdComponents": 0,
  "createdProperties": 0,
  "createdStates": 0,
  "createdAliases": 0,
  "createdLinks": 0,
  "unchangedProperties": 0,
  "rejected": [{ "component": "X", "property": "y", "reason": "unknown property type: z" }],
  "typeMismatches": ["Component.property: db=color, meta=dimension"]
}
```

Гранулярность отказа — свойство: одно свойство с неизвестным типом не отменяет остальной импорт (иначе первый же новый тип блокировал бы загрузку всего слоя). CLI печатает счётчики, затем `rejected` и `typeMismatches`; разделы печатаются только непустые.

### Платформа

Платформа берётся из `.sdds/config.json`, `--platform` переопределяет — как у `components generate`. В запросе она передаётся полем `platform` со значением из словаря БД. Соответствие значений CLI и БД задаётся в CLI:

| `TargetPlatform` (CLI) | `platform` (запрос и БД) |
|---|---|
| `compose` | `compose` |
| `android-view` | `xml` |
| `swiftui` | `ios` |
| `react` | `web` |

Backend принимает все четыре значения enum `property_platform`: он не ограничен платформами, которые CLI уже умеет читать. Ограничение первой версии — на стороне CLI: остальные платформы отвечают «not supported yet» до какого-либо запуска процесса.

### Границы слоёв в CLI

- `core-platform`: значение `Capability.API_META`; `PlatformDelegate.capabilities` его объявляет; результат — существующий `DelegateResult`. Путь результата не возвращается делегатом.
- `platform-android`: `AndroidGradleDelegate` получает пару `API_META × COMPOSE → readUikitComposeApiMeta` в карте задач. Пара `API_META × ANDROID_VIEW` не добавляется: делегат отвечает `Unsupported`.
- `feature-components/domain`: манифест (`ApiMetaManifest`), нормализатор Compose, правила состояний и описаний. Без ввода-вывода и без зависимостей от Ktor.
- `feature-components/application`: `ImportApiMetaUseCase`, порты `ApiMetaSource` (запускает делегата и читает файл) и `ApiMetaRemoteSource` (отправляет манифест).
- `feature-components/data`: адаптер `ApiMetaSource` над `PlatformCapabilityRunner` и `WorkspaceFileSystem`; HTTP-адаптер `ApiMetaRemoteSource` в стиле `HttpComponentConfigRemoteSource`.
- `feature-components/di`: Koin-wiring.
- `cli`: `ComponentsImportApiCliCommand` — разбор опций, печать плана и отчёта, коды выхода; регистрируется в `ComponentsCliCommand`.

### Барьеры записи

Повторяют `components push`: явный API URL (`--api-url` или `DSBUILDER_API_URL`, публичное умолчание для записи запрещено), печать цели (URL и его источник, `projectId`, `designSystemId`, платформа, путь файла меты, число компонентов и свойств) перед отправкой, dry run по умолчанию, `--apply` для записи. Ключ проекта не выводится. Команда не запускает Gradle, если запись всё равно отклонилась бы на раннем этапе (нет контекста, нет URL, нет credentials).

## Risks / Trade-offs

- **Свежесть меты.** Задача читает jar из Gradle-кэша пользователя, значит, версия определяется его `build.gradle.kts`. Если версия uikit старая, в базу попадёт старое API. Версия артефакта из файла меты не видна, поэтому отчёт печатает путь файла, число компонентов и свойств; версию вывести нечем.
- **Соглашение о пути.** `build/theme-builder/components/...` — соглашение плагина, а не контракт. Если модуль переопределяет `buildDir` или плагин переместит вывод, чтение сломается. Смягчение: явная диагностика с ожидаемым путём и тест, который падает при сдвиге; долгосрочно — попросить плагин печатать путь результата.
- **Пустая мета.** Задача при отсутствии файла в classpath пишет пустой массив. Команда отказывает с понятным сообщением («артефакт uikit не найден в classpath проекта») и не отправляет пустой манифест, иначе dry run покажет нули, похожие на «всё импортировано».
- **Права.** Ключ с `components:write` может заводить строки в общий слой всех дизайн-систем. Добавление безвредно для существующих значений, но засоряет слой при ошибке. Отдельный scope отложен; dry run по умолчанию и явный URL — барьеры, как у `components push`.
- **Накопление алиасов.** Аддитивность не убирает старые алиасы. Если плагин позже поменяет имя параметра, у свойства окажутся оба имени. Чистка — отдельная задача.
- **Расхождение платформ.** При добавлении View 4 из 796 общих пар `(component, id)` различаются по типу (`Slider.orientation`, `Tabs.orientation`, `ToolBar.orientation`, `Spinner.angle`). При аддитивной записи победит тип платформы, импортированной первой. Порядок описывается в документации; сверка результатов импорта Compose и View — задача следующего change.
- **Порядок относительно `components push`.** Команда `push` использует слой, но не требует его: подсказка о необходимости импорта меты сознательно не добавляется.
