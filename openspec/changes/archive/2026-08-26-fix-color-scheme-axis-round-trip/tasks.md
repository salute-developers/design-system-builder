## 6.6 Роль оси и её объявленный тип — разные вещи (найдено при приёмке)

`counter_config.json` в `sdds_sbcom` объявляет ось `mute` как **`enum`**, но её значения записывает
блоком `view` внутри вариации `danger`. Наш кодек опознаёт `mute` осью цветовой схемы (иначе записи
`view` некуда девать) и вместе с ролью меняет объявленный тип на `view`:

```
исходник: ('mute', 'enum', ['no','yes'], 'no')
выгрузка: ('mute', 'view', ['no','yes'], 'no')
```

Следом расходится и структура вариаций: `Counter.Mute` против `Counter.MuteNo` в сгенерированном
коде.

Причина в том, что требование `Codec derives axis type` отождествляет роль и тип: «ось цветовой
схемы получает тип `view`». Оно писалось на корпусе `sdds_serv`, где ось схемы всегда объявлена
как `view`, и там отождествление незаметно. `counter` показывает, что это два независимых факта:
**роль** говорит, куда уезжают значения, **тип** — как ось объявлена в `bindings`.

- [x] 6.6.1 Объявленный тип оси хранится: столбец `declared_type` на `appearance_variations`, поле `declaredType` в общем формате и в `CommonVariation`. Кодек отдаёт приоритет объявленному типу, а выводит только при его отсутствии. Декодирование сразу даёт действующий тип, иначе круг `common -> native -> common` переставал быть точным на осях, которых нет в `bindings` (`tab_bar_clear`).
- [x] 6.6.2 Требование `Codec derives axis type` переписано: объявленный тип воспроизводится как есть, вывод применяется только когда конфигурация тип не объявила. Добавлен сценарий «ось цветовой схемы, объявленная перечислением». В модель добавлено требование `Declared axis type is stored beside the role`.
- [x] 6.6.3 Проверено на обоих корпусах: **287 объявленных типов осей из 287 воспроизводятся точно** — 27 в `sdds_sbcom`, 260 в `sdds_serv`, расхождений ноль. `bindings` у `counter` теперь совпадают с исходником посимвольно.

## 6.7 Владелец кросс-осевого сочетания (найдено при проверке 6.6.3)

Починка типа оси не сдвинула сборку: `counter` по-прежнему даёт 2 различающихся файла из 10.
Причина оказалась третьей и независимой.

В исходнике значения оси схемы `mute` лежат **под** координатой `type=danger`:

```
variations: [ {id: danger, binding: [(type, danger)], view: {mute-no: …, mute-yes: …}} ]
```

То есть владелец сочетания — значение оси схемы, а `type=danger` ему цель. Выгрузка же
приписывает сочетание оси `type`, а `mute` делает целью:

```
ось mute:  name=no      targets=None            ← цель потеряна
ось type:  name=danger  targets=[(mute, no)]    ← владелец не тот
```

Владение сочетанием в модели не хранится: сочетание — это набор стилей-участников, а кто из них
«свой», а кто «цель», выводится при сборке. Правило вывода не знает про роль оси схемы и выбирает
не то значение.

- [x] 6.7.1 Владение **выводится при сборке ответа**, а не хранится: `componentExport.ts` брал участника с наибольшей позицией оси. У `counter` оси `mute`(0) и `type`(1), поэтому владельцем оказывалась `type`.
- [x] 6.7.2 Решено выводить, а не хранить — но по верному правилу: **ось цветовой схемы владеет сочетанием, в котором участвует**, иначе владеет последняя по позиции. В native-формате значения оси схемы лежат записями `view` **внутри** вариации, то есть координата вариации им цель. Замер по двум корпусам: новое правило верно на **973 сочетаниях из 973**, прежнее ошибалось в 236 (234 в `sdds_serv`, 2 в `sdds_sbcom`).
- [x] 6.7.3 Структура `counter` совпала с исходником — вариация `danger` с записями `mute-no`/`mute-yes`, — а расхождение файлов сократилось с 76 строк до 25. Но сборка осталась на 180 из 190: остаток `Counter` объясняется потерей пустой вариации, см. 6.8.

## 6.8 Пустая вариация исходника теряется (проверено и отвергнуто)

`counter` объявляет вариацию `mute` с координатой `type=mute`, у которой **нет ни свойств,
ни записей `view`**. Кодек такие не порождает: значение остаётся в `bindings[].values`,
а записи вариации не возникает. Плагин из-за этого теряет обёртку `Counter.Mute` целиком.

Проверена правка «раз у значения есть авторский идентификатор, значит вариация в исходнике была,
и координату надо достроить». Идентификатор ставится только из `variations[].id`, так что признак
выглядел надёжным.

**Правка отвергнута замером: сборка ухудшилась со 180 файлов из 190 до 174**, сломав
`BasicButtonStyles`, `IconButtonStyles` и `LoaderStyles` — по два файла на каждый. Авторский
идентификатор носят и значения, у которых собственной вариации не было, поэтому достройка
порождает лишние.

Пустая вариация в корпусе одна на 1219 (`counter.type=mute` в `sdds_sbcom`). **Принимать эту
потерю нельзя** — оценка исправлена при разборе последствий:

`mute` — значение **по умолчанию** оси `type`. Вместе с вариацией из сгенерированной библиотеки
исчезают две записи публичного перечисления `CounterStyles` и, главное, обе ветви `resolve`
для `type == Mute`:

```kotlin
public fun CounterStyles.Default.resolve(
    mute: CounterDefaultMute = CounterDefaultMute.No,
    type: CounterDefaultType = CounterDefaultType.Mute,   // умолчание
): CounterStyles = when {
    mute == No  && type == Danger -> CounterStyles.CounterDangerMuteNo
    mute == Yes && type == Danger -> CounterStyles.CounterDangerMuteYes
    else -> error("Unsupported counter style combination")
}
```

`resolve()` и `style()`, вызванные без аргументов, падают в рантайме. Заодно меняется порядок
`CounterDefaultType`, то есть порядковые номера значений перечисления.

Редкость причины не равна тяжести следствия: одна пустая вариация на 1219 выносит путь
по умолчанию у публичного API. Правило и причина отказа записаны в комментарии `ConfigCodec.add`,
чтобы отвергнутую правку не переоткрывали, но задача остаётся открытой — см. 6.9.
