## Context

`add-cli-components-fetch` принимался на корпусе `sdds_serv`. В нём ось цветовой схемы
всегда называется `view` (525 записей из 525), а ключ записи всегда совпадает со значением
оси (525 из 525). Оба совпадения зашились в код как правила.

На пакете `sdds_sbcom` оба неверны:

| | `sdds_serv` | `sdds_sbcom` |
|---|---|---|
| имена оси схемы | `view` — 525 из 525 | `mode-color` 30, `mode` 24, `mute` 6, `state` 5, `view` 3, `variant` 2 |
| ключ записи совпадает со значением | 525 из 525 | **3 из 70** |

Следствие проверено сборкой: генератор компонентов `plasma-android` из выгруженного пакета
даёт 164 файла из 190 побайтово как из исходного, 26 различаются, 0 потеряно. Все 26 — эта
причина.

Пример, `indicator_config.json`. Исходник объявляет ось `state` со значениями
`accent … warning`, а записи `view` называет ключами `state-accent … state-warning`,
где каждая несёт `binding: [{name: state, value: accent}]`. То есть **ключ — это подпись
записи, а значение оси несёт `binding` внутри неё**. Импорт принял ключ за значение и завёл
рядом с пятью настоящими значениями пять фантомных: у оси `state` компонента `Indicator`
в базе десять значений вместо пяти.

## Goals / Non-Goals

**Goals:**

- Роль оси цветовой схемы хранится, а не выводится из имени.
- Значение оси у записи `view` берётся из её `binding`, ключ хранится отдельно как подпись.
- Круг `push → fetch` на `sdds_sbcom` становится неподвижной точкой, а тема из выгруженного
  пакета собирается побайтово как из исходного.
- `sdds_serv` не регрессирует: там оба факта совпадают, и новое правило обязано давать
  прежний результат.

**Non-Goals:**

- Чистка фантомных значений миграцией. Отличить фантом от настоящего значения без исходного
  пакета нечем — см. «Migration Plan».
- Пересмотр того, как кодек определяет ось схемы на заливке. `resolveColorSchemeAxis`
  работает верно на обоих корпусах; теряется её результат, а не он сам.

## Decisions

### 1. Роль оси хранится в объявлении оси, а не выводится

`componentExport.ts:354` сейчас ищет ось по имени:

```ts
const colorSchemeVariationId = axes.find((axis) => axis.name === "view")?.name ?? null;
```

Роль при этом **известна на заливке**: CLI вычисляет её (`resolveColorSchemeAxis`) и передаёт
полем `colorSchemeVariationId`, схема импорта поле принимает (`commonConfig.ts:53`), а
`componentImport.ts` его отбрасывает — 0 вхождений.

Решение: добавить булев столбец на `appearance_variations` и заполнять его из
`colorSchemeVariationId`. Выгрузка читает столбец.

Замер подтверждает, что одного столбца достаточно: **в конфигурации не бывает больше одной
оси схемы** (`sdds_sbcom` — 10 конфигураций с одной осью и 37 без, `sdds_serv` — 59 и 85),
и ни один компонент не использует разные оси схемы в разных конфигурациях.

*Альтернатива:* хранить роль на `variations`, то есть на уровне компонента. Замер её
допускает, но объявление оси уже живёт в `appearance_variations`, и разносить два факта
об одной оси по разным таблицам — худший выбор без выигрыша.

### 2. Значение оси у записи `view` — то, что говорит её `binding`

Замер: значение из `binding` объявлено в `bindings[].values` во **всех 70** записях
`sdds_sbcom`, тогда как ключ — лишь в 3. В `sdds_serv` совпадают и те и другие.

Решение: импорт связывает запись `view` со значением оси по `binding`, а не по ключу карты.
Фантомные значения после этого не возникают: значение из `binding` уже заведено объявлением
оси.

### 3. Ключ записи хранится в существующем `native_id`

Ключ — подпись записи в родном формате, ровно та же роль, что у `variations[].id`.
Под неё в `appearance_variation_values` уже есть `native_id`, заведённый этим же change'ем
для вариаций, и у значений оси схемы он сейчас пуст.

Решение: переиспользовать `native_id`, нового столбца не заводить. Общий формат его уже
возит — `CommonVariationValue.nativeId`, — значит круг замыкается без правки контракта.

*Альтернатива:* отдельный столбец `native_key`. Отвергнута: одно и то же понятие
(«как эта величина называется в родном формате») получило бы два места хранения, а
коллизии между ролями нет — значение принадлежит объявлению ровно одной оси.

### 4. Кодек собирает запись по ключу, а не по значению

Правка 12.3 из `add-cli-components-fetch` восстанавливала вложенный `binding` по правилу
«значение равно ключу записи». На `sdds_serv` это верно всегда, на `sdds_sbcom` — в 3 случаях
из 70. Правило заменяется на явное: ключом служит `nativeId`, значением в `binding` — имя
значения оси.

### 5. Родитель вариации выводится, а не хранится

`add-cli-components-fetch` завёл `native_parent` рядом с `native_id`, потому что проверка
показала: из **координаты** — набора пар «ось-значение» — родителя не вывести. У `basic_button`
в `sdds_sbcom` есть вариация с двумя осями и `parent: null`, тогда как у соседней с той же парой
осей родитель задан; выбор авторский.

Проверка была верной, но неполной: вывод из **сохранённого идентификатора** тогда не проверялся,
хотя идентификатор к тому моменту уже хранился. Правило «родитель — самый длинный точечный
префикс, принадлежащий другой вариации» точно на **1219 вариациях из 1219**: 68 из 68
в `sdds_sbcom` и 1151 из 1151 в `sdds_serv`, ни одного промаха.

```
size-48.bg-no   -> size-48    (префикс есть среди id)
xs.wide.default -> xs.wide
size-48         -> null       (точки нет)
```

Решение: снять столбец, выводить родителя в кодеке. Одно и то же знание не должно храниться
дважды, тем более что вторая копия дороже: её надо заполнять на заливке и отдавать на выгрузке.

*Альтернатива:* оставить как есть — работает же. Отвергнута: столбец не выпущен, снять его сейчас
дешевле, чем нести в модели поле, чьё значение полностью определяется соседним.

*Замечание о порядке правил:* правило берёт самый длинный префикс **среди существующих
идентификаторов**, а не механически отрезает последний сегмент. Это важно: в корпусе есть
вариации с пропущенным звеном, и отрезание дало бы ссылку в пустоту.

### 6. Идентификатор хранится, но называется по причине, а не по платформе

Прежде чем закреплять хранение, проверены два способа обойтись без него. Оба отвергнуты замером.

**Переименовать значения осей так, чтобы значение совпадало с сегментом.** Лечит 251 вариацию
из 1219, **215 остаются**. Булевы оси непреодолимы: сегмент несёт имя оси, и одна и та же
`has-shadow=true` даёт `has-shadow` в `drawer_close_inner` и `shadow`
в `navigation_bar_internal_page` — одному значению понадобилось бы два имени, а переименовать
`true` нечем, оно задано типом оси. Ещё 131 вариация имеет меньше сегментов, чем осей.

**Хранить сегмент на значении оси, а `id` собирать склейкой.** Это было бы вчетверо экономнее
и убрало бы слово «native» само собой: хранилось бы имя значения оси в генерируемом коде.
Перебором найден словарь `(ось, значение) -> сегмент` для **180 конфигураций из 191**.
Оставшиеся 11 не решаются структурно:

```
note_config.json, оси: size, content-before, has-close, view

id='l.has-close'                  binding=[(size,l), (has-close,true)]
id='l.has-close-content-scalable' binding=[(size,l), (content-before,scalable), (has-close,true)]
```

Две оси слиты в **один** сегмент через дефис, а не разделены точкой, причём порядок внутри
слитого сегмента обратен порядку объявления осей. Словаря, дающего обе строки, не существует:
приписав `has-close=true` сегмент `has-close-content-scalable`, ломаем первую.

Вывод: идентификатор — свободная авторская строка. Правила сборки нет — где-то точка, где-то
дефис, где-то ось опущена, где-то порядок обратный.

Решение: хранить, но назвать по причине существования. `native_id` -> `authored_id`,
`nativeId` -> `authoredId`. Поле отвечает на вопрос «почему оно здесь»: автор написал,
вычислить нельзя. Признака платформы в модели не остаётся.

Типы `NativeConfig`, `NativeVariation`, `NativeBinding` в CLI не переименовываются: они именуют
реальный формат пакета, а не поле модели.

### 7. Невыводимые идентификаторы предъявляются на заливке

Раз хранение — следствие отсутствия конвенции, дрейф стоит держать на виду. `components push`
сообщает о конфигурациях, чьи идентификаторы не выводятся из значений осей, тем же способом,
каким сообщает о свойствах вне глобального слоя.

Это ничего не запрещает и ничего не ломает, но делает измеримым: сегодня выводимы 753 вариации
из 1219. Если доля дойдёт до полной, столбец снимется без сюрпризов; если нет — по крайней мере
видно, что происходит.

## Risks / Trade-offs

- **Уже залитые дизайн-системы несут фантомные значения.** → Миграция их не чистит;
  восстановление — повторной заливкой пакетов. Отличить фантом от настоящего значения
  без исходного пакета нечем: в модели обе величины лежат одинаковыми строками.
- **Регрессия на `sdds_serv`.** → Там ключ и значение совпадают, поэтому новое правило обязано
  дать прежний результат. Проверяется тем же прогоном, каким принимался прошлый change:
  круг `push → fetch → push` и сборка темы `playground/theme-builder`.
- **Правило родителя проверено на двух корпусах, а не на всех.** → 1219 из 1219 — сильное
  свидетельство, но не доказательство. Реализация обязана падать заметно, если префикс не найден
  там, где исходный `parent` был задан: молчаливый `null` увёл бы вариацию в корень дерева.
- **Ось схемы без `binding` внутри записи.** → Замер нашёл 2 такие записи в `sdds_sbcom`.
  Поведение для них надо задать явно, а не оставить на волю случая, иначе появится третье
  негласное правило вместо двух убранных.

## Migration Plan

**Новой миграции нет.** Все три затронутых столбца — роль оси, `authored_id`, снимаемый
`native_parent` — заводит `0005_appearance_declarations.sql`, а она не выпущена: её нет ни
в `dev`, ни в `master`, ни на `origin` ни в одной из них. Накладывать `0006`, который
переименовывает и удаляет столбцы, созданные в неотпущенной `0005`, значит возить в истории
следы черновика. Правится сама `0005` — ровно так же в этой линии уже поступили с `gradient`
и `blur` в `0004`.

Граница правила простая: неотпущенная миграция ещё пишется, выпущенная — неприкосновенна.

1. Столбец роли добавляется в `CREATE TABLE "appearance_variations"` внутри `0005`. Значение
   по умолчанию — «не ось схемы».
2. Перенос данных в `0005` дополняется проставлением роли там, где её можно восстановить
   достоверно, то есть для оси с именем `view` — прежнее правило верно ровно для неё.
   Остальные остаются без роли до повторной заливки.
3. Фантомные значения не удаляются. В комментарии миграции записывается, чем они опознаются
   и почему автоматически это сделать нельзя.
4. Дизайн-системы, залитые прежним импортом, приводятся в порядок повторным
   `components push`.

Хеш `0005` от правки изменится, поэтому базы, где она уже накатана, нужно переподписать:
заменить строку в `drizzle.__drizzle_migrations` на новый хеш. Это касается локальных и приёмочных
баз; продовых среди них нет, потому что не выпущена и `0004`.

Откат: столбец удаляется, выгрузка возвращается к выводу по имени. Данные, залитые новым
импортом, при этом останутся корректными — фантомов новый импорт не создаёт.
