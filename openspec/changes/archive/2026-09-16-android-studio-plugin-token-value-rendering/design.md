## Context

`TokenList.kt` сегодня умеет строить превью только для `TokenType.COLOR` — парсит hex из `rawValue` и рисует квадрат (`parseHexColor`, `TokenRow`). Для остальных пяти типов подпись строки — это `item.value?.rawValue` как есть.

`rawValue` формируется в `HttpDesignSystemDataClient.extractDisplayValue()` и разворачивает только один частный случай: одноэлементный JSON-массив с примитивом внутри (`["#F5F5F5F5"]` → `"#F5F5F5F5"`) — это и есть форма `color`. Для всех остальных типов значение в БД — тоже массив (`jsonb`), но с объектами внутри, и `extractDisplayValue` в этом случае возвращает `element.toString()` — то есть весь массив как JSON-текст, а не сам объект/список объектов. Форма разбора по типу токена уже задокументирована как контракт в `frontend-kt/feature-theme/.../TokenValueNormalizer.kt` (используется CLI для локального `theme fetch`, не плагином):

- `color` → единственная строка;
- `typography`, `fontFamily` → единственный объект;
- `shape`, `spacing` → объект (или строка для `web`);
- `gradient`, `shadow` → массив объектов (все элементы — слои).

Реальные формы JSON по платформам подтверждены сидами `js/services/db-service/src/db/seeds/prod/token_values/*.ts`:

| Тип | android/ios (общая форма для shape/spacing/gradient/shadow) |
|---|---|
| `shape` | `{"kind":"round","cornerRadius":<Int dp>}` |
| `spacing` | `{"value":<Int dp>}` |
| `gradient` | `[{"kind":"linear","locations":[Float,...],"colors":["#..",...],"angle":Int}]` |
| `shadow` | `[{"color":"#..","offsetX":Int,"offsetY":Int,"spreadRadius":Int,"blurRadius":Int,"fallbackElevation":Int?}]` |
| `typography` (android) | `{"fontFamilyRef","fontWeight":Int,"fontStyle":String,"textSize":Int,"lineHeight":Int,"letterSpacing":Float}` |
| `typography` (ios) | `{"fontFamilyRef","weight":String,"style":String,"size":Int,"lineHeight":Int,"kerning":Float}` |

`web` использует CSS-строки (`"0.75rem"`, `["linear-gradient(45deg, ...)"]`, `["0rem 1.5rem 3rem -0.5rem #00000014"]`) — принципиально другой формат разбора (парсинг CSS, а не JSON-объектов).

Полная форма значений (а не только то, что встретилось в сидах) подтверждена авторитетным источником — TS-типами редактора токенов клиентского приложения, `js/apps/client/src/controllers/themeBuilder/tokens/*/types.ts` (в отличие от `db-service`, где `value` — непровалидированный `jsonb`, это единственное место в репозитории, где форма значения по типу токена типизирована):

- `shape.kind` — литерал `'round'`, других вариантов нет ни на android, ни на ios.
- `gradient` — union из **четырёх** вариантов по `kind`, не только `linear`: `linear` (`locations`, `colors`, `angle`), `radial` (`locations`, `colors`, `centerX`, `centerY`, + android: `radius`, ios: `startRadius`/`endRadius`), `angular` (`locations`, `colors`, `centerX`, `centerY`, + ios дополнительно: `startAngle`/`endAngle`), `color` (`background: string` — сплошная заливка без `colors`/`locations`).
- `typography.weight` на ios — фиксированный enum из 9 значений: `black`/`bold`/`heavy`/`light`/`medium`/`regular`/`semibold`/`thin`/`ultraLight` (не только 4, что встретились в сидах). На android `fontWeight` — числовой литерал `100..900` с шагом 100, совпадает с CSS-шкалой.

`frontend-kt/plugins/android-studio/build.gradle.kts` уже подключает `implementation("io.github.salute-developers:sdds-uikit-compose:0.51.0")` — библиотеку, в которой продакшен design-system-приложения реально рисуют градиенты и тени. Поля её публичных моделей совпадают с полями токенов бэкенда один в один (см. Decisions) — это тот же домен, а не совпадение.

## Goals / Non-Goals

**Goals:**
- Дать содержательное визуальное превью значения токена для `gradient`, `typography`, `shadow`, `shape`, `spacing` на платформах `android` и `ios`, аналогично уже существующему превью для `color`.
- Переиспользовать уже подключённые к плагину production-примитивы рендера (`sdds-uikit-compose`) там, где они есть и дают видимый результат на компактном превью (`gradient`), вместо переизобретения математики; для `shadow` эта библиотека визуально нечитаема на масштабе превью — см. Decisions.
- Сохранить read-only природу плагина — превью ничего не пишет и не изменяет.

**Non-Goals:**
- Рендер значений платформы `web` (CSS-строки) — остаются как сырой текст, как сегодня; отдельное будущее изменение, если понадобится.
- Сверка отображаемого значения с версией `sdds-serv-compose`/другой библиотеки, реально подключённой в проекте пользователя, — не входит (то же ограничение, что и в исходном token-browser change).
- Превью токена как применённого к реальному UI-компоненту (кнопке, карточке) — рендерится только сырое значение токена, не стилизованный компонент.
- Копирование значения как кода (например «скопировать как Kotlin-константу») — вне скоупа, это только визуальное превью.

## Decisions

### Типизированная модель значения вместо `rawValue: String`, парсинг — по контракту `TokenValueNormalizer`

Вводится sealed-модель распарсенного значения (например `TokenValuePayload`: `ColorValue`, `ShapeValue`, `SpacingValue`, `GradientValue(layers)`, `ShadowValue(layers)`, `TypographyValue`, `Unsupported` как fallback) в пакете `tokens` плагина. Разбор per-type зеркалит уже существующий контракт `TokenValueNormalizer` (`color` — строка, `shape`/`spacing`/`typography` — объект, `gradient`/`shadow` — массив), но не переиспользует сам класс напрямую — он `internal` в `feature-theme` и рассчитан на `theme fetch` CLI, а не на UI-модель. `rawValue: String` в `TokenValue` не удаляется — остаётся как fallback-текст для `web`-значений и для случаев, когда разбор не удался (`Unsupported`), чтобы не потерять функциональность отображения «как есть», которая работает сегодня.

**Альтернатива — парсить JSON прямо внутри `TokenRow`/Composable**: отклонено — это распределяет знание о форме каждого типа токена по UI-коду вместо одного места, и уже дублирует контракт, который есть в `TokenValueNormalizer`.

### Значение нормализуется в платформенно-независимую модель до рендера

Поскольку скоуп включает и `android`, и `ios`, а их JSON для `typography` расходится по именам полей (`fontWeight`/`textSize`/`letterSpacing` у android против `weight`/`size`/`kerning` у ios), парсер для каждой платформы приводит значение к одной и той же `TypographyValue` (например `fontSizeSp: Float, lineHeightSp: Float, weightValue: Int, letterSpacingEm: Float, fontStyle: String, fontFamilyRef: String`) — `TokenRow` не ветвится по платформе, только по типу токена. Для `shape`/`spacing`/`gradient`/`shadow` android и ios уже структурно совпадают, отдельной нормализации не требуют.

### `gradient` и `shadow` — через `sdds-uikit-compose`, `shape`/`spacing` — локальным маппингом, `typography` — новый локальный маппер

- **`gradient`**: `kind` определяет, какой конструктор `Gradients` использовать — `linear` → `Gradients.Linear(colors, stops, angleInDegrees)` (поля дословно совпадают с `colors`/`locations`/`angle`); `radial` → `Gradients.Radial(colors, stops, radius, centerX, centerY)` (android даёт `radius` напрямую, ios — `startRadius`/`endRadius`; для ios в `radius` кладётся `endRadius`, `startRadius` не имеет прямого аналога в `Gradients.Radial` и намеренно не используется — см. Open Questions); `angular` → `Gradients.Sweep(colors, stops, centerX, centerY)` (ios-поля `startAngle`/`endAngle` не имеют аналога в `Gradients.Sweep`, который всегда полный оборот, — тоже не используются, см. Open Questions); `color` — не градиент, а сплошная заливка (`background: string`), рендерится как обычный цветной swatch через `parseHexColor`, без обращения к `Gradients`. `kind`, отличный от этих четырёх, — fallback на сырой текст.
- **`shadow`**: изначально — `com.sdds.compose.uikit.shadow.ShadowLayer`/`Modifier.shadow(ShadowAppearance(layers), shape)` из `sdds-uikit-compose`, поля дословно соответствуют токену. **Найдено на визуальной проверке (задача 6.3, реальный `runIde`), пять проходов** — первые три ушли на то, чтобы этот примитив стало хоть немного видно (светлая подложка независимо от темы IDE; `Modifier.clip` на подложке — иначе рисуемое утекает в тёмный фон строки снаружи неё; чисто-белая подложка + тёмная поверхность для максимального контраста, размер унифицирован с `color`/`gradient` в `TYPE_SWATCH_SIZE` = 64dp). Тени всё равно не стало видно совсем. Причина оказалась не в контрасте, а в самой технике рендеринга: `Shadows.skiko.kt` симулирует блюр несколькими полупрозрачными копиями контура, деля и без того низкую альфу токена (обычно ~8%) ещё на число шагов блюра (`layer.color.alpha * (1f - progress * 0.85f) / blurSteps`), а самая плотная из этих копий рисуется почти по размеру самой поверхности (`spread` при `progress→0`) — на превью в десятки dp результат неразличим на глаз ни при каком контрасте окружения.
  - Проход 4: заменить `Modifier.shadow` на честный гауссов блюр (`androidx.compose.ui.draw.blur`, `BlurredEdgeTreatment.Unbounded`) — каждый слой рисуется как обычный цветной `Box` нужного размера (surface + spread×2) со смещением (`Modifier.offset`). Тоже не помогло: физика блюра работает в обратную сторону, чем интуитивно ожидалось — размазывая и без того слабую заливку (~8% альфы) по большей площади, блюр **снижает** пиковую видимую плотность, а не создаёт заметный ореол. Корень проблемы — не техника рендеринга, а масштаб: реальные компоненты, использующие эти токены в `plasma-android` (`Modal`, `ToolBar`, `NavigationBar`, `TabBar`, `DropdownMenu`, `Popover` — см. usage grep по `.shadow(`), — это поверхности в сотни dp, где абсолютные `blur`/`offset` токена (до 112dp/60dp) составляют малую долю размера; на свотче 64dp то же абсолютное значение уже сопоставимо с самим свотчем.
  - Проход 5 (пользователь: «попрежнему нет теней», «проанализируй, как в plasma-android применяются токены теней»): раз масштаб принципиально другой, точная фотореалистичная передача тени на превью-свотче недостижима в принципе — вместо неё альфа теневого цвета явно поднимается для читаемости (`SHADOW_ALPHA_BOOST` = 6×, клэмп до 100%), а `offsetX`/`offsetY` — клэмпятся (`MAX_SHADOW_OFFSET_PREVIEW_DP` = 14dp), иначе крупные offset-токены (`downSoftL`/`downHardL` — 60dp) уводят пятно почти целиком за пределы `TYPE_SWATCH_SIZE`; `blurRadius` клэмпится дальше, до `MAX_SHADOW_BLUR_PREVIEW_DP` = 10dp.
  - Проход 6 (пользователь: «я всё ещё не вижу тень» — даже с 6-кратной альфой): гипотеза на тот момент — `Modifier.blur` (GPU-эффект `RenderEffect`) не рендерится в `ComposePanel`. Заменён на ручную имитацию блюра слоями (`ShadowBlur`) — тоже не решило проблему до конца (см. проход 7).
  - Проход 7 (пользователь указал на `PopoverStory`/`BasePopover.kt` в `plasma-android`, где `Modifier.shadow` из `sdds-uikit-compose` даёт хорошо видимую тень на реальном компоненте — «может проблема в самих токенах?»): токены ни при чём, `Modifier.shadow` тоже работает нормально — гипотеза про GPU/`RenderEffect` из прохода 6 была неверна. Настоящая причина — отсутствие отступа вокруг «приподнятой» поверхности под размер тени. `BasePopover.kt` явно резервирует его через `getShadowSafePaddings()` (`ShadowUtils.kt`: `radius = spreadRadius + blurRadius`, отступ на сторону — `radius ∓ offset`) **до** применения `.shadow(...)` — потому что сам Popover это поверхность в сотни dp, где токен (blur до 112dp, offset до 60dp) — малая доля размера. У нашего свотча подложка всего 64dp, и без такого отступа `Modifier.clip` подложки обрезал тень раньше, чем она становилась видна — независимо от того, каким примитивом её рисовать (сам `Modifier.shadow`, `Modifier.blur` или ручной alpha-blending: все три подхода без отступа давали один и тот же результат — ничего не видно). Решение: вернуться к настоящему `Modifier.shadow(ShadowAppearance(layers), shape)` (тот же код, что и у `Popover`), но клэмпнуть `blurRadius`/`offset` каждого слоя так, чтобы `spreadRadius + blurRadius + |offset|` укладывалось в свободное место вокруг уменьшенной `SHADOW_PREVIEW_SURFACE_SIZE` (20dp → 12dp) внутри `TYPE_SWATCH_SIZE` (64dp). `getShadowSafePaddings()` сам недоступен (`internal` в `sdds-uikit-compose`) — вместо точного повторения формулы используется более простой клэмп с тем же смыслом.
- **`shape`**: `{"kind":"round","cornerRadius":N}` → `RoundedCornerShape(N.dp)`. **Найдено на визуальной проверке, три прохода**: (1) на квадратном свотче (32dp) `round.xxl` (32dp) и `round.circle` (9999dp) давали идентичный полный круг → превью сделано прямоугольным. (2) Первая версия прямоугольника (56×32dp) не решала проблему до конца: `RoundedCornerShape` клэмпит радиус до половины короткой стороны (16dp), а `round.xl`/`round.xxl`/`round.circle` все превышают этот порог и выглядели одинаковой предельной «таблеткой» → высота увеличена до `SHAPE_PREVIEW_HEIGHT` = 72dp (порог клэмпа — 36dp), ширина — до `SHAPE_PREVIEW_WIDTH` = 96dp: `round.xxl` (32dp < 36dp) теперь видимо не до конца скруглён, только `round.circle` — по-настоящему полная таблетка. (3) Подпись всё ещё показывала `9999dp` для `round.circle` — вводит в заблуждение, это сентинел «максимально круглая форма», а не реальное измерение → `describeValue` показывает `"circle"` вместо dp, когда `cornerRadiusDp >= SHAPE_CIRCLE_THRESHOLD_DP` (999dp — с запасом ниже сентинела 9999, но заведомо выше любого реального радиуса UI). `kind`, отличный от `"round"` (в сидах не встречается, но поле есть неспроста), не рендерится как форма — используется fallback на сырой текст, вместо угадывания.
- **`spacing`**: `{"value":N}` → полоска фиксированной высоты шириной `N.dp` рядом с числовой подписью — без обращения к `sdds-uikit-compose`, значение самодостаточно.
- **`typography`**: готового рантайм-конвертера в `plasma-android` нет — там типографика запекается в статические `TextStyle`-константы на этапе кодогенерации конкретной дизайн-системы (см. сгенерированные `*Typography.kt` в `tokens/*/theme`), а не парсится динамически. Пишется новый локальный маппер в модель → `TextStyle(fontSize = fontSizeSp.sp, lineHeight = lineHeightSp.sp, fontWeight = FontWeight(weightValue), letterSpacing = letterSpacingEm.em)`, текст-сэмпл рендерится этим стилем. `fontFamilyRef` показывается как текст (имя референса), а не резолвится в реально загруженный шрифт — плагину неоткуда взять файл шрифта произвольной дизайн-системы. Android `fontWeight` (числовой `100..900`) идёт в `FontWeight(weightValue)` напрямую. Ios `weight` (enum из 9 строк) требует явной таблицы маппинга в ту же числовую шкалу — используется стандартное соответствие названий начертания CSS/`FontWeight`-константам: `thin→100`, `ultraLight→200`, `light→300`, `regular→400`, `medium→500`, `semibold→600`, `bold→700`, `heavy→800`, `black→900`. Значение, не входящее в этот словарь, — fallback на `FontWeight.Normal` (см. Risks), не исключение.

**Альтернатива для `gradient`/`shadow` — переизобрести градиентный угол и слои тени на голом Compose** (`Brush.linearGradient`, `Modifier.shadow(elevation)`): отклонено. У голого `Brush.linearGradient` нет параметра «угол в градусах» — пришлось бы заново выводить ту же тригонометрию, что уже решена в `Gradients.Linear`; у голого `Modifier.shadow(elevation)` нет offset/spread/нескольких слоёв. Самодельная версия была бы заведомо хуже уже иду протестированной библиотечной логики и разошлась бы с ней при следующем обновлении `sdds-uikit-compose`.

Требует подтверждения при реализации: `Gradients`/`ShadowAppearance`/`ShadowLayer` прочитаны из рабочего дерева `plasma-android` на сегодняшнем `HEAD` — нужно проверить, что те же публичные символы существуют именно в опубликованной `sdds-uikit-compose:0.51.0`, а не только в более свежем неопубликованном коде.

## Risks / Trade-offs

- **[Риск] Версионный разрыв между `plasma-android` HEAD и опубликованной `sdds-uikit-compose:0.51.0`** — читанные `Gradients`/`ShadowAppearance` могут отличаться в опубликованной версии (сигнатура, публичность). → **Митигация**: на старте реализации явно проверить API опубликованного артефакта (декомпиляция/javadoc) до того, как проектировать вокруг него весь рендер; при расхождении — точечный локальный воркэраунд только для разошедшегося примитива.
- **[Риск, снят] Словарь `kind` для `shape`/`gradient` и `weight` для ios `typography` изначально подтверждён только по примерам в сидах.** → Снято чтением авторитетного источника — `js/apps/client/src/controllers/themeBuilder/tokens/*/types.ts` (TS-типы редактора токенов; `db-service` эти формы не валидирует вовсе, `value` — непровалидированный `jsonb`). Полные словари см. в Context. Парсинг всё равно остаётся defensive: значение вне словаря — `Unsupported`/сырой текст, а не исключение.
- **[Trade-off, принято] `startRadius`/`endRadius` у ios `radial`-градиента и `startAngle`/`endAngle` у ios `angular`-градиента не имеют аналога в `Gradients.Radial`/`Gradients.Sweep` из `sdds-uikit-compose`.** Для `radial` используется только `endRadius` (ближе к дизайн-намерению, чем `startRadius`); для `angular` полный диапазон ios-полей игнорируется — `Gradients.Sweep` всегда рисует полный оборот. Превью в этих двух случаях будет приближённым, а не пиксель-точным воспроизведением ios-рендера — приемлемо для read-only визуального ориентира, не для сверки значений.
- **[Риск] `TokenValue.rawValue: String` — часть существующей внутренней модели плагина (`DesignSystem.kt`), уже покрытой тестами (`HttpDesignSystemDataClientTest`, `ParseHexColorTest`).** Расширение типизированным payload'ом рядом с `rawValue`, а не замена, минимизирует изменения в существующих тестах и других потребителях модели (поиск/фильтрация в `TokenList` работает по `token.name`, значения не касается — blast radius низкий).
- **[Trade-off] Значения платформы `web` продолжат показываться как сырой текст для всех типов, кроме `color`.** Осознанный компромисс по явному выбору скоупа (android/ios в этой итерации); стоит держать в уме как известный гэп, а не молчаливое упущение.

## Migration Plan

Аддитивное изменение, полностью внутри `frontend-kt/plugins/android-studio` — не трогает бэкенд, REST-контракт, схему БД или другие модули `frontend-kt`.
