# Design

## Context

См. proposal.md, раздел Why. Что уже есть и на что опирается решение:

- Схема `db-service` готова: `appearance_variations` с `position` и `default_style_id`,
  `component_deps` с типами `compose | reuse`, `style_combinations`, тип свойства `value`,
  колонка `platform` у `appearances` и `properties`. Миграций это изменение не добавляет.
- Спека `component-appearance-model` уже требует, чтобы состав, порядок и дефолт вариаций
  принадлежали appearance. Legacy-роут `component-configs` этого не соблюдал: брал все вариации
  компонента. Изменение доводит роут до спеки.
- ADR-0006 описывает граф `component_deps` для превью нового клиента. Текущий React-клиент остаётся
  потребителем legacy-роута, и связи ему нужны уже сейчас, до Preview Protocol.
- Генератор и клиент держат две копии `componentBuilder`. Это изменение синхронизирует их, но
  не объединяет: общего пакета в `js/` нет (нет npm workspace), и выносить его в этом изменении
  значило бы менять сборку всех сервисов.
- Ядро `@salutejs/plasma-new-hope`: `mergeConfig` подменяет `variations` целиком, `PropsType`
  типизирует проп как `boolean` только при ключах вариации ровно `'true'`, объекты токенов
  у части компонентов общие (`tabsTokens` для Tabs/TabItem/IconTabItem) или называются иначе
  (`lineSkeletonConfig`). Все три факта продиктовали решения ниже.

## Goals / Non-Goals

**Goals:**

- Добавление компонента plasma сводится к запуску инструмента, чтению отчёта и стори.
- Один формат данных компонента для сида, выгрузки и импорта, сверяемый по именам.
- Пакет из генератора структурно совпадает с `sdds-serv` для всех включённых компонентов.
- Превью показывает вложенные компоненты с темой ДС, а не с дефолтами ядра.

**Non-Goals:**

- Изменение схемы БД, контракта `components push/fetch` и codec `component-config-codec`.
- Переключатель appearance в интерфейсе редактора.
- Редактирование свойств `value` и сочетаний стилей в панели.
- Общий npm-пакет `componentBuilder` для генератора и клиента.
- Preview Protocol и плагины из ADR-0006.

## Decisions

### Сиды по папкам без идентификаторов, реестр сканированием

Альтернативы: оставить файлы по таблицам с id; папки по компонентам, но с явным списком в
`index.ts`. Отвергнуты: id в сидах требовали префиксной схемы (`tea_`, `base_tea_`) и коллизий
между компонентами, а регулярные правки таблиц по заголовкам ломали соседей при `--remove`.
Явный реестр — лишняя точка правки при каждом добавлении. Разрешение имён в id делает сидер
единственным местом, где знают о структуре таблиц, и позволяет сверять круговой прогон по именам.

### Один writer для выгрузки и импорта

`component-seed-writer.ts` пишет папку из `ComponentSeed`; `seed-generate-prod.ts` и
`import-plasma-component.ts` только собирают эту структуру. Иначе два формата разъехались бы на
первом же новом поле.

### Импорт не ходит в базу и не зависит от node_modules db-service

Инструмент запускается с хоста, где есть клон plasma, и пишет только файлы. Причина практическая:
база и db-service живут в контейнере, клон plasma — на хосте. Спорные места идут в отчёт, а не
в сид: молчаливое приближение стоило дорого (Accordion потерял вертикальный отступ, Steps
остались без части стилей из-за фрагментов-вставок).

### Web-параметр равен ключу токена ядра

Альтернатива: хранить имя CSS-переменной (`--plasma-button-height`), как раньше. Отвергнута:
у части компонентов имена переменных не выводятся из ключа, и билдер строил их неверно.
Ключ объекта токенов ядра стабилен и единственно верен для обоих потребителей: генератор пишет
`${buttonTokens.buttonHeight}` и получает имя из ядра на сборке, превью читает объект токенов
ядра в рантайме. Модель перестаёт знать о CSS-переменных.

### Манифест генератора вместо колонок в базе

Альтернатива: колонки `core_tokens_export`, `core_config_export` на `components`. Отвергнута:
имя экспорта ядра, форма обёртки и реэкспорты — нюанс одного пакета для одной платформы, а не
факт дизайн-системы; в базе они были бы мертвы для всех остальных потребителей и потребовали бы
миграции ради web-специфики. Манифест лежит рядом с шаблонами и пишется инструментом импорта.
Цена: клиент держит зеркало `coreTokensByComponent` для компонентов с чужим объектом токенов,
и его правят руками. Зеркало мало (десяток строк) и меняется только при новом компоненте с
общим объектом токенов.

### Флаг — единственный стиль `true`, без стиля `false`

Продиктовано типизацией ядра: с ключом `false` проп становится `'true' | 'false'`, и `<Tabs pilled>`
в чужом приложении не компилируется. Выключенное состояние — отсутствие дефолта, что уже
допускает спека (`Ось может не иметь дефолта`). В редакторе это переключатель и пункт меню
«Снять по умолчанию».

### Пять стратегий обёртки в фиксированном порядке

Multi-appearance → пустой → шаблон → дженерик → обычная. Порядок важен: пустой конфиг темы
нельзя писать никогда (подменит вариации ядра), шаблон побеждает дженерик, потому что шаблон
пишут руками именно там, где генерация не справляется. `compose`-дети складываются в папку
родителя, как в `sdds-serv`, чтобы `import { TabItem } from '<pkg>/Tabs'` совпадал.

### Превью: `relatedComponents` вместо переменных для `reuse`

Для `reuse` класть на сцену переменные ребёнка неверно: одно вычисленное значение переменной
побеждает все стили ребёнка, и кнопка внутри Drawer теряет `view="clear"`. Поэтому превью
собирает `component(mergeConfig(core, themeConfig))` для каждого связанного компонента, тем же
`createThemeConfig`, что даёт объект, идентичный `<X>.config.ts` генератора. Для `compose`
переменные всё же нужны: дочерний живёт внутри родителя и делит с ним одноимённые вариации.

### Клиент редактирует первый appearance

Переключатель appearance требует изменений в сохранении и панели, не связанных с остальным.
Сохранение не трогает прочие appearance, так что ограничение безопасно и снимается отдельным
изменением.

## Risks / Trade-offs

- [Две копии `componentBuilder` расходятся] → в tasks сверка diff генератора и клиента; вынос в
  общий пакет — отдельное изменение.
- [Клон plasma другой версии, чем `@salutejs/plasma-new-hope` в генераторе] → скилл требует сверить
  мажор перед импортом; расхождения ключей идут в «пропущено».
- [Карта `coreTokensByComponent` клиента забыта при новом компоненте] → симптом виден сразу
  (компонент без стилей в превью), правило записано в скилле.
- [Фрагменты-вставки и `intersections` конфига не переносятся] → в отчёте и в скилле; сверка числа
  свойств с числом ключей `tokens.` в конфиге.
- [Шаблон многозначного значения точен только для размера по умолчанию] → известное ограничение
  модели, фиксируется в «приближениях».
- [Полный пересев удаляет и заново создаёт стили базовой ДС] → пользовательские ДС не трогаются;
  на проде сиды применяются только к `base`, и `--component` сужает область.

## Migration Plan

1. Прогнать полный `db:seed:prod` на пустую базу локально и сверить с выгрузкой по именам.
2. На dev выполнить `db:seed:prod` без `--component`: старые строки базовой ДС удаляются и
   пересоздаются, пользовательские ДС не затрагиваются.
3. Пересобрать генератор (`app/templates` попадают в `dist`).
4. Откат: вернуть предыдущую ревизию сидов и генератора; схема не менялась, миграций для отката нет.

## Open Questions

- Нужен ли переключатель appearance в редакторе до появления нового клиента из ADR-0006, или
  Tabs остаётся единственным multi-appearance компонентом и правится через сиды.
