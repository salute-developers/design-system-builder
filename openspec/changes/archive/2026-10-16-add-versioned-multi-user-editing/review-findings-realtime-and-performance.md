# Замечания: оперативное обновление редакторов и скорость сохранения

Документ фиксирует обязательные к устранению замечания, обнаруженные во время ручной проверки, и фактическое состояние
их исправления.

## 1. Другой открытый редактор не получает изменения автоматически

Статус: **реализовано в коде; требуется ручная проверка в двух браузерах**.

Замечание считается закрытым только после реализации доставки серверных событий, безопасного обновления
открытого редактора, обработки пересекающихся локальных изменений и повторного подключения без рассинхронизации.

### Наблюдаемое поведение

После успешного сохранения изменения одним пользователем другой пользователь видит новое состояние только после
повторного чтения данных, например после обновления страницы. Существующие технические редакции позволяют обнаружить
устаревшую запись во время следующего изменения, но сами по себе не доставляют сведения об изменении в уже открытый
редактор.

### Реализованное решение

Добавлены серверные события как канал уведомления об изменении черновика. Событие не становится новым источником данных
и не заменяет предметные маршруты: после получения события клиент читает актуальную сущность из `ds-service`.

Предлагаемый маршрут сервиса:

```http
GET /api/ds/design-systems/{designSystemId}/events
Accept: text/event-stream
```

Через шлюз клиент обращается к нему в области проекта:

```http
GET /api/projects/{projectId}/ds/design-systems/{designSystemId}/events
```

Один атомарный пакет сохранения создаёт одно компактное событие, даже если пакет изменил несколько связанных токенов
или платформенных значений. Событие не содержит предметные значения и потому не ограничивает размер пакетной операции:

```json
{
    "designSystemId": "ba270bad-40ac-4410-82b0-a54ddc84276e",
    "draftId": "a66baf9f-4573-49a1-bca8-6fc046a1594e",
    "draftRevision": 128,
    "actorId": "e6ee9919-d990-48e4-bf01-99afe0e1bfe8",
    "clientId": "browser-tab-123",
    "changedAt": "2026-10-15T13:30:00Z",
    "scopes": ["theme-tokens"]
}
```

Событие должно формироваться в общей точке завершения предметного изменения после увеличения редакции черновика, а
не отдельно в каждом HTTP-маршруте. Оно должно становиться видимым только после успешной фиксации транзакции.

Для нескольких экземпляров `ds-service` используется PostgreSQL `LISTEN/NOTIFY`:

- уведомление выполняется внутри предметной транзакции и доставляется после её фиксации;
- каждый экземпляр сервиса слушает общий канал и передаёт сообщение своим SSE-соединениям;
- при переподключении клиент передаёт известные `draftId` и `draftRevision`;
- если редакция уже изменилась, сервер немедленно отправляет новое состояние курсора;
- периодический пульс только поддерживает HTTP-соединение и не обращается к БД;
- при восстановлении служебного `LISTEN`-соединения сервер сверяет курсор отдельным лёгким запросом, а одновременные
  соединения одного проекта и дизайн-системы разделяют его результат внутри экземпляра сервиса.

Предметные триггеры одной транзакции накапливают уникальные области `theme-tokens`, `theme-metadata`,
`component-configurations` и `design-system`. Клиент перечитывает только отмеченные части и не устанавливает уже
показанный редактор в пустое состояние. При публикации, неизвестной области или обнаруженном пропуске события сервер
использует `all`, а клиент выполняет полное чтение в фоне без визуального исчезновения редактора.

Хранить отдельный долговечный журнал событий для первой реализации не требуется. Он понадобится только при требовании
воспроизводить все пропущенные события без повторного чтения предметных данных.

В памяти хранится только последнее уведомление, необходимое для закрытия гонки между начальным чтением курсора и
подпиской. Новое соединение не перебирает прежний буфер из 256 событий. Начальное и восстановительное чтение используют
специализированный сценарий, который возвращает только `draftId` и `draftRevision` без списка и превью тем.

### Авторизация и шлюз

Клиент сейчас передаёт токен доступа в заголовке `Authorization`. Браузерный `EventSource` не позволяет добавить этот
заголовок, поэтому соединение следует открывать потоковым `fetch` с действующим токеном, разбором
`text/event-stream`, повторным подключением и обновлением токена. Передавать токен в параметре адреса нельзя.

Сервис возвращает `X-Accel-Buffering: no`, сервер отправляет пульс каждые 15 секунд, а соединение планово
переоткрывается через пять минут для повторной проверки токена и прав. CORS шлюза разрешает `X-DS-Client-Id`.

### Правила применения удалённого изменения

Клиент не заменяет состояние редактора, пока существует хотя бы одна неподтверждённая очередь токенов или компонентов:

| Локальное состояние | Поведение клиента |
|---|---|
| Локальных операций нет | В фоне перечитать и применить отмеченные области |
| Есть ожидающий или выполняющийся запрос | Запомнить аннулирование и не заменять локальный ввод |
| Все локальные запросы подтверждены | Перечитать серверный черновик один раз |
| Локальная операция завершилась ошибкой | Сохранить локальный ввод до ручного повтора операции |

Каждая вкладка получает собственный `clientId`. Изменяющие запросы и SSE-соединение передают этот идентификатор, чтобы
вкладка не применяла повторно собственное изменение. Сервер при этом продвигает её внутренний курсор редакции: резервная
сверка по таймеру не принимает собственное изменение за пропущенное чужое. Другая вкладка того же пользователя получает
событие, поскольку у неё другой `clientId`.

Отдельное клиентское разрешение конфликтов и обязательный диалог не вводятся. Если удалённое изменение пересеклось с
локальным, сервер сохраняет действующее правило «последняя успешно зафиксированная запись побеждает» и возвращает
структурное предупреждение. SSE гарантирует, что удалённое состояние не перезапишет ввод до его отправки, но не меняет
это правило конкурентной записи.

Проверено узкими тестами: разбор SSE при разделении сетевых фрагментов, выбор токенной или компонентной загрузки,
ожидание завершения нескольких локальных очередей, разбор PostgreSQL-уведомления и доставка одного уведомления с
несколькими объединёнными областями после фиксации транзакции.

## 2. Подтверждение автосохранения воспринимается медленным

Статус: **лишние серверные задержки устранены; клиентское окно объединения скорректировано, требуется повторный замер
в браузере**.

### Наблюдаемое поведение

Даже в локальном окружении после изменения значение заметное время остаётся в состоянии ожидания или сохранения,
вместо почти немедленного подтверждения.

### Уже подтверждённые источники задержки

Первоначальное сокращение окна объединения до 150 мс ускорило начало запроса, но позволило сохранять промежуточные
значения многосимвольного ввода. Другие редакторы получали каждое подтверждённое состояние через SSE. Кроме того,
изменение, появившееся во время выполняющегося запроса, отправлялось сразу после его завершения без нового окна.

Очередь теперь использует завершающее окно 400 мс от последнего изменения. Каждый новый ввод переносит границу
отправки. Если предыдущий запрос ещё выполняется, после его завершения очередь ждёт оставшуюся часть того же окна;
если пользователь уже не вводил данные более 400 мс, новое поколение можно отправить сразу. Принудительная отправка
при уходе со страницы не задерживается. Это намеренная клиентская задержка, отделённая от времени HTTP-запроса.

Для изменения значения существующего токена после этой задержки выполняется пакетный `PUT` значений темы. Если вместе
со значением меняется определение токена, клиент сначала ожидает отдельный `PATCH` определения и только затем отправляет
значения. Для создания токена аналогично последовательно выполняются `POST` определения и `PUT` значений.

Пакетное серверное сохранение значений выполняется одной транзакцией уровня `SERIALIZABLE`. До исправления для каждой
платформы отдельно выполнялся поиск с блокировкой. Теперь все затронутые существующие строки выбираются и блокируются
одним запросом в устойчивом порядке, после чего предметные редакции записываются последовательно. Повторное чтение
результата сохранено намеренно: политика может удалить черновую редакцию, совпавшую с опубликованным состоянием, и
ответ должен содержать фактически разрешённое значение.

Сохранение конфигурации компонента потенциально дороже: перед вычислением записи клиент параллельно выполняет семь
читающих запросов (`axes`, значения осей, инвариантные и вариантные значения свойств, состояния, наборы состояний и
токены), а затем часть предметных изменений отправляет последовательно отдельными запросами. Поэтому задержку токенов и
компонентов необходимо измерять раздельно.

### Что необходимо измерить при повторной ручной проверке

Нужно снять длительности одного изменения токена и одного изменения компонента по этапам:

1. время от последнего ввода до начала HTTP-запроса;
2. время прохождения шлюза и проверки доступа;
3. время ожидания соединения с PostgreSQL;
4. время серверной транзакции с количеством SQL-запросов;
5. время передачи и разбора ответа;
6. время от получения ответа до перехода индикатора в подтверждённое состояние;
7. наличие автоматического повтора запроса и его причину.

Сервер уже пишет длительность HTTP-запроса и состояние пула в существующие метрики. Если после исправлений задержка
остаётся заметной, перечисленные этапы нужно измерить до следующей оптимизации.

### Оставшиеся возможные направления

- не выполнять `PATCH` определения токена, если изменилось только его значение;
- исключить повторное чтение неизменившихся справочников при каждом сохранении компонента;
- отправлять независимые компонентные изменения параллельно только после проверки порядка блокировок;
- показывать отдельно состояния «ожидает объединения» и «сервер сохраняет», чтобы намеренная задержка не выглядела как
  медленная работа сервера.

Эти направления не применялись без замеров, поскольку они затрагивают более широкий порядок компонентных операций.

## Независимое ревью безопасности и стоимости

После независимого ревью устранены дополнительные риски:

- `clientId` создаётся для экземпляра страницы только в памяти; сервер подавляет событие лишь при совпадении автора и
  `clientId`, а клиент больше не отбрасывает событие только по недоверенному идентификатору;
- `ds-service` допускает не более восьми SSE-соединений участника проекта на экземпляр, шлюз — не более шестнадцати
  одновременных запросов одного IP к одному DS-маршруту;
- ошибки и повреждённые данные `localStorage` не мешают компонентной очереди в памяти и не меняют результат уже
  подтверждённого сервером запроса;
- детальные запросы компонентной модели ограничены четырьмя параллельными обращениями и не превышают пакет шлюза;
- проверка непустого черновика перед публикацией использует `hasChanges` с ранним завершением и не материализует
  журнал, когда применённые политики гарантируют сохранение непустого результата;
- список дизайн-систем получает количество тем и первые четыре превью одним оконным запросом вместо запроса на каждую
  дизайн-систему и чтения всех её тем.

## Повторное независимое ревью

- При пропуске редакции SSE сервер отправляет область `all`; такое восстановительное событие не подавляется как
  собственное.
- `X-DS-Client-Id` обязателен и в контракте, и в фактическом SSE-маршруте.
- Основной токенный черновик и служебные записи автосохранения используют браузерное хранилище только как необязательное
  средство восстановления; ошибки чтения, записи и удаления не блокируют очередь памяти.
- SQL каждого предметного обработчика публичного журнала ограничен 100 001 строкой, полный ответ — 10 000 изменениями;
  превышение возвращает `422 JOURNAL_LIMIT_EXCEEDED` без выдачи усечённых данных.

## Финальное независимое ревью

- Публикация ожидает фактические очереди токенов и компонентов через реестр памяти и не читает `localStorage`.
- Поиск записи для отката использует тот же предел, что публичный журнал, до и после предметной блокировки.
- Чтение `entity_edit_states` ограничено идентификаторами видимых изменений; откат читает одну строку по составному
  ключу.
- Общее число запросов загрузки компонентной модели остаётся пропорциональным числу компонентов и вариантов. В этом
  изменении ограничен одновременный веер; устранение общего N+1 потребует нового пакетного API компонентов и вынесено
  в отдельное архитектурное изменение.
- Начальные значения темы сворачиваются политикой после предметного SQL. Поэтому внутренний предел кандидатов выше
  публичного; перенос этого сворачивания непосредственно в SQL предметного обработчика остаётся отдельной оптимизацией.
