# Замечания по безопасности и работе с PostgreSQL

Документ фиксирует результаты статического ревью реализации версий дизайн-системы. Он не меняет продуктовые
требования Change и используется как перечень дефектов, которые должны быть закрыты до повторного независимого
ревью.

## Состояние исправлений

Все перечисленные ниже дефекты исправлены в реализации. Для журнала количество SQL-запросов теперь ограничено
количеством зарегистрированных типов предметных сущностей и не растёт на каждую запись журнала. Постраничный
публичный контракт остаётся отдельным совместимым расширением API: текущая оптимизация устраняет N+1 и чтение
данных чужих проектов, но не обрезает результат журнала незаметно для клиента.

Повторное независимое ревью выявило ещё один дефект: после отмены предметной редакции оставались технические сведения
о затронутых путях. Теперь обычная отмена очищает пути сущности, а отмена создания — также состояние уже не
существующей в черновике сущности. Интеграционный тест проверяет повторное изменение от исходной редакции без ложного
предупреждения о конфликте.

Финальное ревью также обнаружило, что публичное `updatedAt` временно вычислялось из времени создания границы версии.
Метки изменения перенесены из прежних предметных строк в соответствующие редакции, новые редакции получают собственное
время записи, а чтение текущего и исторического состояния возвращает метку выбранной предметной редакции.

Следующее ревью выявило два граничных случая. Списочные маршруты агрегата теперь проверяют, что выбранная историческая
версия относится именно к дизайн-системе из пути, а не только к тому же проекту. Пустое изменение темы возвращает
текущее значение без записи предметной или технической редакции. Оба случая покрыты HTTP-тестами.

Защитное замечание финального ревью также закрыто: предметные редакции исходной версии разрешены только во время
первичного заполнения новой дизайн-системы, пока для неё ещё не создан черновик. С появлением черновика исходная версия
становится неизменяемой; все вставки в опубликованную версию также отклоняются триггером БД. Ограничения проверяются
миграционным тестом.

Последующее ревью обнаружило и позволило закрыть три обхода защитных условий. Строки предметных редакций теперь
неизменяемы: изменение выполняется заменой редакции только в черновике, поэтому перенос строки из опубликованной версии
невозможен. Первичное заполнение исходной версии и создание первого черновика используют одну блокировку. Признак
содержимого повторяемого запроса строится из типизированного представления с длинами полей вместо `toString()` команды.
Все три случая покрыты отдельными модульными и PostgreSQL-тестами.

Повторная проверка выявила и позволила закрыть обход через жизненный цикл самой границы: опубликованную версию можно
было снова перевести в черновик, после чего заменить её предметные редакции. Автомат состояний теперь закреплён на
уровне БД: исходная и опубликованная границы неизменяемы, прямое создание опубликованной границы запрещено, а для
существующей версионной границы разрешён только переход из черновика в опубликованную версию. Негативный тест
воспроизводит полный сценарий повторного открытия и изменения истории.

## Блокирующие дефекты

### 1. Обратный порядок блокировок

Одиночное изменение значения токена блокирует `entity_edit_states`, а затем активный черновик. Пакетное сохранение
значений tenant сначала блокирует активный черновик, а затем через триггер обновляет `entity_edit_states`. При
параллельном изменении одной сущности возможна взаимная блокировка PostgreSQL с кодом `40P01`.

Критерий исправления: все изменяющие пути сначала проверяют принадлежность ресурса проекту, затем блокируют активный
черновик и после него технические состояния сущностей в устойчивом порядке. Транзакционный исполнитель повторяет как
ошибки сериализации `40001`, так и взаимные блокировки `40P01`.

### 2. Разрешение редакций в памяти приложения

Чтение tenant, токенов, значений токенов и дизайн-систем загружает историю нескольких дизайн-систем, сортирует её и
выбирает последние редакции через `toList().distinctBy(...)`. Даже точечное чтение зависит от общего объёма истории.

Критерий исправления: проект, дизайн-система, сущность и временная граница ограничиваются в SQL, а последняя редакция
выбирается PostgreSQL через `LATERAL ... ORDER BY ... LIMIT 1`, `DISTINCT ON` или эквивалентное оконное выражение.

### 3. N+1 при построении журнала и публикации

Журнал выполняет два запроса снимка для каждого обработчика и отдельный запрос технического состояния для каждого
изменения. Публикация строит полный журнал под блокировкой черновика, хотя ей требуется только проверить наличие
изменений. Откат повторно перебирает все обработчики.

Критерий исправления: снимки двух границ и технические состояния читаются пакетно; публикация использует отдельную
проверку наличия изменений без построения DTO журнала; поиск изменения для отката не создаёт запрос на каждую запись.

## Безопасность

### 4. Ручное экранирование значений raw SQL

Значения `Idempotency-Key`, идентификатора проекта, автора, изменённых путей и других параметров экранируются заменой
одинарной кавычки и интерполируются в SQL. Защита зависит от `standard_conforming_strings` PostgreSQL и слабее
параметризованного запроса.

Критерий исправления: все предметные значения передаются bind-параметрами Exposed/JDBC. Динамические имена таблиц и
столбцов разрешены только из закрытого набора метаданных приложения и экранируются как идентификаторы.

### 5. Блокировка ресурса до проверки проекта

Некоторые изменяющие операции находят устойчивую строку только по UUID и берут блокировку до проверки `project_id`.
Пользователь другого проекта, знающий UUID, не получает данные, но способен создавать конкуренцию за чужие строки.

Критерий исправления: принадлежность проекту проверяется тем же запросом, который выбирает ресурс для изменения, до
блокировки черновика или технического состояния.

### 6. Исторический расчёт влияния состояния читает активный черновик

Маршрут принимает `versionId`, но запрос влияния состояния использует границу со статусом `draft`. Результат запроса
к опубликованной версии меняется после последующих черновых правок и может раскрывать агрегированную информацию о них.

Критерий исправления: запрос использует уже проверенную границу из `ds.version_id`, а без неё — активный черновик.

### 7. Неограниченное усиление чтения

Список версий и журнал не ограничивают объём работы областью проекта достаточно рано. Журнал не имеет внутреннего
ограничения размера результата; список версий выполняет отдельную проверку принадлежности для каждой строки.

Критерий исправления: список версий фильтруется одним SQL-запросом с соединением по проекту; журнал не выполняет
запрос на каждую запись. Верхний предел или постраничное чтение должны добавляться только явно в публичный контракт,
чтобы сервис не возвращал клиенту незаметно обрезанный журнал.

### 8. Перенос опубликованной редакции в черновик через `UPDATE`

Триггер неизменяемости выбирает границу через `COALESCE(NEW.design_system_version_id,
OLD.design_system_version_id)`. Для изменения строки всегда выбирается новая граница, поэтому редакцию можно перенести
из опубликованной или закрытой исходной версии в активный черновик и одновременно изменить данные.

Критерий исправления: граница, дизайн-система и порядковый номер версии являются неизменяемой частью редакции;
изменение строки отдельно проверяет старую границу. PostgreSQL-тест пытается перенести редакции из исходной и
опубликованной версий в черновик.

### 9. Гонка первичного заполнения исходной версии с созданием черновика

Вставка исходной редакции блокирует строку исходной версии, но создание строки черновой версии не использует ту же
блокировку. Две транзакции могут одновременно принять взаимоисключающие решения и зафиксировать исходную редакцию уже
после появления черновика.

Критерий исправления: вставка исходной редакции и создание первого черновика сериализованы общей блокировкой строки
исходной версии. Двухсоединительный тест проверяет оба порядка получения блокировки.

### 10. Неоднозначный признак содержимого повторяемого запроса

`toString()` Kotlin-команды не является каноническим форматом: значения с текстом, похожим на разделители полей,
позволяют двум разным телам запроса получить одинаковую строку и один хеш. Сервер может ошибочно вернуть сохранённый
ответ вместо ошибки повторного использования ключа.

Критерий исправления: все команды кодируются однозначным структурным форматом или последовательностью с длинами полей;
тест воспроизводит коллизию прежнего формата и подтверждает разные хеши нового.

### 11. Повторное открытие опубликованной версии

Ограничения формы строки допускают изменить опубликованную границу обратно на черновую, если одновременно очистить
номер версии и время публикации. После такого изменения триггеры предметных редакций считают историю черновиком и
разрешают удалить либо заменить её строки.

Критерий исправления: триггер жизненного цикла запрещает изменение исходных и опубликованных границ, запрещает прямое
создание опубликованной границы и разрешает только переход существующей версионной границы `draft -> published`.
PostgreSQL-тест проверяет попытки повторно открыть исходную и опубликованную версии, а также удалить опубликованную
предметную редакцию.

## Остальные оптимизации

- добавить индексы `(design_system_id, id)` устойчивым таблицам, которые используются обработчиками журнала;
- убрать дополнительные запросы на каждую тему при построении списка tenant;
- заменить проверки исторических дочерних редакций по одной строке на один `EXISTS`;
- убрать полный просмотр `component_style_references` и повторный выбор черновика в циклах импорта;
- ограничить длину ключа повторяемости; автоматическую очистку не добавлять, поскольку она явно вынесена в отдельное
  эксплуатационное решение утверждённого Change.

## Архитектурное условие развёртывания

`ds-service` доверяет заголовкам, нормализованным `identity-gateway`. Сервис должен быть недоступен напрямую
недоверенным клиентам, а шлюз обязан удалять присланные клиентом `X-Project-*`, `X-Actor-*` и `X-System-Admin` и
формировать их заново после проверки полномочий. Нарушение этого условия является критическим обходом авторизации,
но не исправляется внутри предметных репозиториев этого Change.
