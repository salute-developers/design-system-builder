# Замечания ручного ревью

Документ фиксирует проблемы, обнаруженные при ручной проверке Change
`add-versioned-multi-user-editing`. Наличие записи здесь не означает, что причина уже установлена или исправление
согласовано.

## Состояние

Все замечания исправлены в рабочем дереве и прошли три итерации независимого ревью. Узкие клиентские и
PostgreSQL-интеграционные проверки, сборки затронутых приложений и проверки качества изменённого клиентского кода
проходят. Общая проверка доходит до неизменённого `js/cli` и останавливается из-за устаревшей контрольной базы
Strictacode: код CLI совпадает с `origin/dev`, поэтому эта проблема не относится к Change и не исправляется обновлением
контрольной базы. Ручная проверка двух браузеров остаётся частью внешней задачи 9.5.

## 1. Другой пользователь не видит сохранённое изменение после обновления страницы

Статус: исправлено, покрыто клиентскими и серверными проверками; внешний сценарий двух браузеров остаётся в задаче 9.5.

Наблюдаемое поведение:

1. Один пользователь изменяет значение в редакторе в одном браузере.
2. Другой пользователь открывает ту же дизайн-систему в другом браузере под другим пользователем.
3. После обновления страницы второй пользователь не видит изменение первого пользователя.

Ожидаемое поведение: после успешного сохранения изменения на сервере повторная загрузка редактора другим
пользователем должна вернуть актуальное состояние общего черновика дизайн-системы.

Причина:

- редактор сразу изменяет объект темы и сохраняет ожидающее изменение в `localStorage`, поэтому первый пользователь
  видит новое значение ещё до успешного ответа сервера;
- отправка на сервер выполняется через 400 мс после изменения;
- любая ошибка автосохранения перехватывается и выводится только в `console.error`. Локальное значение остаётся в
  редакторе, а пользователь не получает признака, что общий черновик не обновился;
- при размонтировании редактора отложенные запросы отменяются без немедленной отправки. Запись остаётся только в
  `localStorage` исходного браузера и будет повторена при следующем открытии редактора именно в нём;
- `saveTokenMutation` всегда формирует значения для `web`, `ios` и `android`. Если у токена отсутствует значение одной
  из платформ, в запрос попадает `undefined`; после JSON-сериализации обязательное поле `value` отсутствует, и
  `ds-service` отклоняет весь пакет как `invalid_body`. Эта ошибка также остаётся только в консоли.

Таким образом, другой браузер загружает корректное серверное состояние, но первый браузер мог показывать ещё не
сохранённое локальное состояние. Точный сработавший вариант — ошибка запроса, неполное платформенное значение или
отмена таймера при уходе со страницы — следует подтвердить по Network/Console для конкретного воспроизведения.

Серверная выборка не является причиной наблюдаемого поведения: интеграционный сценарий `ds-service` изменяет значение
от имени редактора и затем успешно читает его от имени другого участника проекта из того же активного черновика.

Реализованное исправление:

1. Считать сервер источником истины, а `localStorage` использовать только как устойчивую очередь ещё не
   подтверждённых сервером операций. При загрузке сначала читать серверное состояние, затем накладывать локальные
   ожидающие операции и повторять их отправку.
2. Вынести управление автосохранением из `useDesignSystem` в отдельную очередь. Для одного токена одновременно
   выполняется не более одного запроса; новое изменение во время запроса остаётся следующим элементом. Промежуточные
   изменения одного токена можно схлопывать до последнего состояния. Разные токены сохраняются независимо.
3. Присваивать ожидающей операции идентификатор или номер поколения. Успешный ответ удаляет запись из
   `localStorage`, только если там по-прежнему находится подтверждённая операция. Ответ старого запроса не должен
   удалить более новое изменение того же токена.
4. Не включать в пакет `token-values` платформенное значение, равное `undefined`: после сериализации у него отсутствует
   обязательное поле `value`, и сервер отклоняет весь запрос. Явное JSON-значение `null`, если оно допустимо для
   предметного типа, не фильтровать. Для такого исправления новая серверная ручка не требуется.
5. При переходе внутри приложения немедленно запускать отложенную отправку вместо простой отмены таймера. При закрытии
   вкладки пытаться завершить запрос в режиме `keepalive`; если браузер завершил работу раньше, операция остаётся в
   `localStorage` и повторяется при следующем открытии редактора. Гарантировать выполнение сетевого запроса после
   аварийного закрытия браузера невозможно.
6. Возвращать из механизма автосохранения состояние `ожидает`, `сохраняется`, `сохранено` или `ошибка`. В интерфейсе
   показывать ненавязчивый статус без обязательного диалога. Сетевые ошибки и ответы `5xx` повторять с увеличивающейся
   задержкой; постоянную ошибку валидации оставлять видимой с возможностью ручного повтора.
7. После успешного ответа обновлять подтверждённые предметные редакции. Если за время запроса появилось новое
   изменение, сразу отправлять его с полученными редакциями. После подтверждения сервера другой браузер увидит
   изменение при обычной повторной загрузке данных.

Минимальные проверки исправления:

- токен только с `web`-значением сохраняется без пустых значений `ios` и `android`;
- уход со страницы до окончания задержки запускает сохранение;
- завершение старого запроса не удаляет более новое ожидающее изменение;
- изменение во время выполняющегося запроса отправляется следом;
- временная сетевая ошибка оставляет операцию для повторения;
- успешный ответ удаляет только подтверждённую операцию из `localStorage`;
- после успешного сохранения другой пользователь получает новое значение повторной загрузкой редактора.

Та же модель последовательной очереди, поколений, повторов и видимого состояния сохранения применяется к редактору
компонентов. Промежуточный ответ не удаляет более новую локальную операцию и не перезаписывает её служебные данные.

Связанный код:

- `js/apps/client/src/hooks/useDesignSystem.ts` — отложенная отправка, локальное подтверждение и обработка ошибки;
- `js/apps/client/src/api/themeEditorRepository.ts` — формирование трёх платформенных значений;
- `js/apps/client/src/utils/designSystemDraft.ts` — оптимистичное состояние в `localStorage`;
- `backend-kt/ds-service/app/src/test/kotlin/com/dsbuilder/ds/app/DsServiceHttpPostgresIntegrationTest.kt` — чтение
  изменённого значения другим участником проекта.

## 2. Создание темы создаёт чрезмерно подробный журнал

Статус: исправлено и покрыто PostgreSQL-интеграционным тестом.

Наблюдаемое поведение: при создании темы журнал содержит отдельные записи для большого количества созданных токенов
и заданных значений.

Причина состояла из двух независимых частей. `CreateTenantUseCase` после создания темы синхронно запускает
`TenantTokenValueInitializer`.
`GeneratedTenantTokenValueInitializer` создаёт устойчивые строки и редакции активного черновика для каждого начального
значения токена, платформы и режима. Общий журнал не знает, что эти редакции относятся к одной операции создания темы:
он сравнивает предметные таблицы текущего черновика с предыдущей границей и формирует отдельное изменение для каждой
сущности. У редакций нет признака исходной пользовательской операции или группы.

Кроме того, `CreateDesignSystemUseCase` создавал канонические определения токенов после исходной границы и записывал
их в первый активный черновик. Поэтому после скрытия начальных `token-value` журнал новой дизайн-системы всё ещё
показывал отдельную запись `token / created` для каждого из 1335 автоматически созданных определений. Эти записи не
относились к пользовательскому изменению темы, но выглядели результатом её создания, поскольку тема создавалась в том
же первом черновике.

В результате технические действия, необходимые для начального заполнения темы, показываются пользователю
как множество самостоятельных изменений. Журнал становится шумным и плохо передаёт пользовательское действие
«создать тему».

Принятое поведение:

- если тема создана в текущем черновике, журнал показывает одну запись `tenant / created`;
- созданные вместе с ней начальные значения токенов не показываются отдельными строками;
- канонические определения токенов новой дизайн-системы относятся к её исходному состоянию и не попадают в журнал
  первого черновика;
- запись создания темы представляет итоговое состояние новой темы в текущем черновике, включая изменения её
  начальных значений до первой публикации;
- после публикации последующие изменения значений темы снова показываются самостоятельными записями журнала.

Для этого не требуется вводить общий идентификатор пользовательской операции или отдельный механизм группировки.
При построении журнала достаточно определить темы, отсутствовавшие на предыдущей опубликованной границе, и исключить
из выдачи изменения `token-value / created`, принадлежащие таким темам. Предметные редакции значений при этом остаются
в БД: они необходимы для восстановления состояния черновика и опубликованной версии.

Канонические определения токенов не фильтруются эвристикой при чтении журнала. Инициализатор записывает их сразу в
`BASELINE`, поэтому последующее ручное создание или изменение токена в первом черновике остаётся обычным видимым
изменением. Полный HTTP-сценарий проверяет, что после создания новой дизайн-системы и первой темы журнал содержит
только одну запись создания `tenant`.

Отмена единственной записи создания темы должна быть агрегатной. Простого удаления только редакции `tenant`
недостаточно: дочерние `token_value_revisions` не позволят удалить устойчивую строку темы либо оставят технические
следы скрытых изменений. В одной транзакции отмена должна:

1. удалить редакции и данные отслеживания изменений начальных значений этой черновой темы;
2. удалить устойчивые строки значений, если у них нет опубликованной истории;
3. удалить редакцию и устойчивую строку самой темы;
4. завершиться целиком ошибкой, если обнаружена опубликованная история или другая зависимость, делающая такую отмену
   небезопасной.

Близкая логика уже используется при удалении черновой темы в `removeDraftOnlyTenant`, но универсальный обработчик
журнала её не вызывает. Исправление должно оформить это как специализированное поведение журнала тем, а не расширять
универсальный обработчик знаниями о таблицах токенов.

- `backend-kt/ds-service/feature-tokens/src/main/kotlin/com/dsbuilder/ds/tokens/data/GeneratedTokenDefinitionInitializer.kt`;
- `backend-kt/ds-service/feature-themes/src/main/kotlin/com/dsbuilder/ds/themes/data/GeneratedTenantTokenValueInitializer.kt`;
- `backend-kt/ds-service/feature-themes/src/main/kotlin/com/dsbuilder/ds/themes/data/ExposedTenantRepository.kt`;
- `backend-kt/ds-service/feature-themes/src/main/kotlin/com/dsbuilder/ds/themes/data/ThemeDraftChangeHandlers.kt`;
- `backend-kt/ds-service/feature-design-systems/src/main/kotlin/com/dsbuilder/ds/designsystems/data/ExposedDraftChangeRepository.kt`;
- `backend-kt/ds-service/core/src/main/kotlin/com/dsbuilder/ds/core/data/ExposedDraftChangeHandler.kt`.

## 3. Активный черновик сериализует все изменения одной дизайн-системы

Статус: исправлено и покрыто проверкой параллельной записи разных сущностей.

Наблюдаемое поведение: практически каждая запись предметной редакции блокирует одну и ту же строку активного
черновика в `design_system_versions`. Поэтому изменения разных токенов, тем и компонентных конфигураций одной
дизайн-системы выполняются последовательно, хотя предметно не конфликтуют.

Причина состоит из двух частей:

- репозитории явно выбирают активный черновик через `SELECT ... FOR UPDATE`;
- триггер `touch_design_system_draft_revision` при каждой вставке или удалении предметной редакции увеличивает
  `design_system_versions.revision`, что также получает блокировку той же строки до конца транзакции.

Простого удаления явного `FOR UPDATE` недостаточно: обновление общей редакции продолжит сериализовать транзакции.
Особенно долго блокировка удерживается при создании темы, импорте и пакетной записи большого количества значений.
Обычное чтение при этом не блокируется.

Реализованное решение:

1. Обычные изменения получают разделяемую транзакционную именованную блокировку PostgreSQL по идентификатору
   дизайн-системы.
2. Публикация получает исключительную именованную блокировку по тому же ключу, ждёт текущие изменения и не допускает
   новые до создания следующего черновика.
3. Конкурирующие записи блокируют только конкретные `entity_edit_states`; разные предметные сущности могут изменяться
   параллельно.
4. Общая редакция черновика увеличивается один раз в конце HTTP-транзакции непосредственно перед её фиксацией, а не
   предметным триггером при каждой записи.
5. Пакетное сохранение значений не блокирует всю тему: метаданные и удаление темы продолжают блокировать `tenant`, а
   значения блокируются по устойчиво отсортированным идентификаторам `token-value`.

Ожидаемый результат: разные сущности одной дизайн-системы изменяются параллельно; изменения одной сущности остаются
последовательными; публикация получает согласованную границу и не пересекается с предметной записью.

- `backend-kt/ds-service/feature-themes/src/main/kotlin/com/dsbuilder/ds/themes/data/ThemeRevisionQueries.kt`;
- `backend-kt/ds-service/feature-themes/src/main/kotlin/com/dsbuilder/ds/themes/data/ExposedTenantRepository.kt`;
- `backend-kt/ds-service/app/src/main/resources/db/migration/V6__finalize_versioned_design_system_state.sql`.

## 4. Переходный триггер наследования области создаёт лишнюю работу при массовой записи

Статус: исправлено в завершающей фазе миграции; измерения производительности не проводились.

Триггер `inherit_design_system_from_owner` был добавлен на время переключения репозиториев: если старый путь записи
не передавал `design_system_id`, база находила его по владельцу сущности. Триггер выполняется для каждой создаваемой
строки в 11 устойчивых таблицах и делает дополнительный индексированный запрос к таблице владельца. При одиночных
изменениях его стоимость невелика, но она умножается на количество строк при создании темы, импорте и начальном
заполнении конфигурации компонента.

Текущие Kotlin-репозитории и инициализаторы явно передают `design_system_id`. Согласованность области уже защищена
`NOT NULL` и составными внешними ключами вида `(owner_id, design_system_id) -> owner(id, design_system_id)`. Поэтому
переходные триггеры и функция отсутствуют в итоговой схеме после выполнения
`V6__finalize_versioned_design_system_state.sql`. Последовательность перехода:

1. Выпустить версию сервиса, в которой проверены все рабочие пути вставки и изменения затронутых таблиц.
2. Дождаться остановки старых экземпляров сервиса, которые ещё могут записывать данные без `design_system_id`.
3. Проверить существующие данные на `NULL` и несоответствие области сущности области её владельца.
4. Выполнить интеграционные сценарии с предварительно удалёнными переходными триггерами.
5. Следующей миграцией удалить 11 триггеров и функцию `inherit_design_system_from_owner`.

Удалять составные внешние ключи и `NOT NULL` вместе с триггером нельзя: после переходного периода именно ограничения
БД должны отклонять ошибочную межсистемную ссылку, а не исправлять её неявно.

Оценка влияния связанных механизмов:

| Механизм | Ожидаемое влияние | Причина |
| --- | --- | --- |
| Наследование `design_system_id` триггером | Низкое при одиночной записи, среднее при массовой | Дополнительный запрос к владельцу для каждой строки |
| `NOT NULL`, внешние и уникальные ключи | Низкое при наличии индексов | Индексированные проверки при записи; это необходимая защита целостности |
| Проверка жизненного цикла версии | Низкое | Выполняется преимущественно при редкой операции публикации |
| Запись предметных редакций | Среднее | Дополнительная строка и обновление индексов на каждое изменение |
| Отслеживание изменённых полей | Среднее | Обновление состояния сущности и записей изменённых путей |
| Удаление пустых и взаимно погашающих редакций | Среднее | Поиск предыдущей редакции, сравнение данных и иногда удаление строки |
| Построение журнала | Зависит от размера черновика | Журнал вычисляется при чтении как разница границ версий; отдельной записи журнала при изменении нет |
| Обновление общей редакции активного черновика | Высокое при параллельной работе | Все изменения одной дизайн-системы конкурируют за одну строку |

Таким образом, переходный триггер удалён ради упрощения и снижения стоимости массовых операций. Главное ограничение
производительности — длительная блокировка общей строки активного черновика — устранено решением из замечания 3:
строка кратко изменяется только перед фиксацией транзакции. Точные величины оставшихся накладных расходов нужно
определить нагрузочными испытаниями для массового создания темы, параллельного изменения разных сущностей и чтения
большого журнала.

Связанный код:

- `backend-kt/ds-service/app/src/main/resources/db/migration/V4__prepare_versioned_design_system_state.sql`;
- `backend-kt/ds-service/app/src/main/resources/db/migration/V6__finalize_versioned_design_system_state.sql`.

## 5. Дополнительные замечания независимого ревью

Статус: исправлено и покрыто узкими регрессионными проверками.

После первичного исправления независимое ревью обнаружило ещё шесть дефектов:

1. Изменение только значения токена также отправляло устаревшие `description` и `enabled`. Теперь `PATCH` определения
   токена содержит только поля, которые пользователь действительно изменил; изменение только значения не меняет
   определение токена.
2. Переименование меняло ключ очереди с прежнего имени на новое. Теперь очередь использует устойчивый логический ключ,
   связанный с идентификатором токена; последовательности «переименовать → изменить» и «переименовать → отменить» не
   создают параллельный запрос или второй токен.
3. Автосохранение компонентов допускало параллельные запросы и скрывало ошибку в консоли. Оно переведено на ту же
   последовательную очередь с поколениями, повтором временных ошибок, восстановлением из `localStorage` и видимым
   состоянием сохранения.
4. Триггер жизненного цикла не запрещал прямое удаление границы версии, способное каскадно удалить историю. Прямое
   удаление границы запрещено; каскад при удалении всей дизайн-системы сохранён.
5. Схема `DraftChange` в OpenAPI требовала отсутствующие поля старого контракта. Список обязательных полей приведён в
   соответствие фактическому DTO.
6. Общая схема `TokenValue` одновременно описывала ответы двух разных DTO. Для ответа в области темы введена
   расширяющая схема `TenantTokenValue` с `editRevision`; дублирующееся описание `Tenant.editRevision` удалено.

Повторное независимое ревью выявило дополнительные пограничные случаи. Они также исправлены:

1. `null` и отсутствующее локальное описание теперь сравниваются как одно неизменённое значение, поэтому сохранение
   значения не формирует скрытый `PATCH description: null`.
2. Старое имя удаляется из таблицы соответствия после подтверждения переименования. Создание токена под этим именем
   получает новую логическую идентичность, но до ответа переименования остаётся в той же последовательной очереди.
3. Временная ошибка частично выполненной составной операции больше не отбрасывается новым поколением. Сначала с теми
   же ключами повторяется прежняя операция, и только после её успеха отправляется новое состояние.
4. Пакет значений использует совместимую блокировку существования темы (`FOR KEY SHARE`) вместо исключительной
   блокировки её строки. Параллельные пакеты не сериализуются на теме, а её удаление не пересекается с записью.
5. Служебная отметка каскадного удаления учитывается только во вложенном вызове триггера. Пользовательский `SET LOCAL`
   не позволяет удалить границу версии или опубликованную предметную редакцию прямым запросом.
6. Обязательные поля `Tenant`, `TokenValue` и `DraftChange` в OpenAPI сверяются с фактическими DTO точными контрактными
   проверками.
7. Общий локальный запуск больше не выполняет legacy Drizzle seed поверх схемы `ds-service`: проект и минимальная
   дизайн-система `base` создаются через API `projects-service` и `ds-service` после миграций Flyway.

Финальное независимое ревью добавило ещё три проверки границ:

1. После перезапуска редактор восстанавливает точный сохранённый вид операции переименования, прежнее имя, логическую
   идентичность и ключ повторяемости. Он не выводит `create` из ещё не обновившегося серверного снимка.
2. Подтверждённая конфигурация компонента связана с его именем. Поздний ответ очереди предыдущего компонента не меняет
   исходное состояние текущего компонента и не искажает следующий расчёт изменений.
3. Удаление темы берёт исключительную блокировку её устойчивой строки, а пакет значений — совместимую блокировку
   существования. После ожидания пакет повторно проверяет актуальную редакцию темы, поэтому удаление и сохранение
   получают определённый порядок без скрытых значений удалённой темы и без технического исключения.

## 6. Промежуточные миграции усложняли первый выпуск новой модели

Статус: исправлено объединением ещё не выпущенных миграций в четыре эксплуатационные фазы.

Во время разработки последовательность V4–V20 фиксировала каждое уточнение схемы отдельной версией. Для постоянного
окружения эти версии ещё не выпускались, поэтому хранить внутреннюю историю разработки в Flyway не требуется. Перед
слиянием цепочка объединена в `V4`–`V7`: подготовка схемы, перенос данных, включение окончательных ограничений и
уведомления SSE. Порядок SQL сохранён, а массовый перенос остаётся отдельной транзакционной фазой.

Интеграционная проверка применяет первые пять версий, затем обновляет базу миграциями `V6` и `V7` и сравнивает
отпечаток итоговой схемы с чистой установкой. Базы временных окружений, успевшие применить прежние номера V4–V20,
должны быть пересозданы; изменение контрольных сумм или `flyway repair` для постоянной базы не допускается.

## 7. Браузер блокировал автосохранение из-за CORS

Статус: исправлено в локальной конфигурации и production-шаблоне gateway; фактический предварительный запрос
проверен на запущенном локальном контейнере.

Наблюдаемое поведение: при сохранении значения токена браузер не отправлял `PUT /tenants/{id}/token-values` и
сообщал, что заголовок `X-DS-Base-Revision` отсутствует в `Access-Control-Allow-Headers`. Устойчивая очередь считала
ошибку сетевой и повторяла запрос, поэтому сообщение появлялось несколько раз.

Причина: nginx gateway разрешал только прежний набор заголовков
`Authorization, Content-Type, Accept, X-Requested-With`. Новый технический заголовок базовой редакции не был добавлен
в ответы на `OPTIONS`, `401` и `403`. По той же причине последующие браузерные операции с `Idempotency-Key` также были
бы заблокированы.

Исправление добавляет `X-DS-Base-Revision` и `Idempotency-Key` во все три набора CORS-заголовков локальной и
production-конфигурации. Проверка конфигурации требует их присутствия во всех ответах. Реальный `OPTIONS` для
пакетного сохранения темы возвращает `204` и оба разрешённых заголовка.

## 8. Автосохранение значений отклонялось, а служебные данные переполняли `localStorage`

Статус: исправлено и покрыто узкими клиентскими и PostgreSQL-интеграционными проверками.

После устранения CORS браузер отправлял `PUT /tenants/{id}/token-values`, но получал `400 invalid_body`. Клиент
использовал почти полный ответный DTO значения как тип входного элемента и добавлял в тело `tenantId`. Входной
контракт пакетной операции определяет tenant только идентификатором в адресе и не принимает это поле; строгая
Kotlin-сериализация отклоняла всё тело до прикладного сценария. Для входного элемента введён отдельный клиентский
тип, содержащий только `tokenId`, `platform`, `mode`, `paletteId`, `value` и `baseRevision`.

Одновременно каждая ожидающая операция записывала в `ds_pending_meta:*` полную копию изменения токена и карту
редакций всех значений темы. Для темы с тысячами значений несколько операций быстро достигали ограничения браузерного
хранилища. Ошибка `QuotaExceededError` выходила в общий обработчик загрузки и ошибочно помечала уже загруженную тему
как не загруженную.

Теперь тело изменения хранится один раз в `ds_draft:*`, а служебная запись содержит короткий отпечаток, ключ
повторяемости, поколение и ревизии только затронутого токена. Актуальное поколение также отслеживается в памяти, поэтому
переполнение `localStorage` не мешает текущей очереди отправить и подтвердить запрос. Сервер после пакетного сохранения
возвращает только затронутые значения, а не все значения темы; это устраняет многомегабайтный ответ на изменение одного
токена и лишнее чтение полного набора из PostgreSQL.

## 9. Изменение значения новой темы не видно в журнале

Статус: исправлено и покрыто узкими серверными и клиентскими проверками.

Значение успешно сохраняется в `token_value_revisions`, а его техническая редакция увеличивается. Однако политика
журнала скрывает все созданные значения токенов, если сама тема создана в текущем черновике. Она не отличает служебное
начальное наполнение от последующего пользовательского изменения, поэтому до первой публикации журнал продолжает
показывать только создание темы.

Простое удаление фильтра небезопасно: относительно предыдущей опубликованной версии такое значение считается созданным,
и существующий откат удалит его вместо восстановления начального значения. Чтобы показывать пользовательское изменение
отдельно, нужно сохранить начальное значение новой темы как основание сравнения и отката, при этом не выводить само
служебное наполнение отдельными строками.

Дополнительно открытая панель журнала перечитывает данные только при открытии или смене контекста. Успешное
автосохранение токена не вызывает обновление уже открытого журнала, поэтому даже изменения существующей опубликованной
темы становятся видны только после повторного открытия панели.

Исправление сохраняет финальные начальные значения атомарно созданной темы в
`token_value_creation_baselines`. Это локальное исходное состояние границы создания, а не изменение глобальной версии
`BASELINE`, поэтому старые опубликованные версии не получают новую тему задним числом. Политика журнала скрывает
значения, пока они совпадают с исходными, и показывает последующее пользовательское изменение как `UPDATE`.
Типизированный обработчик отката восстанавливает исходные `palette_id` и `value`, не удаляя устойчивое значение.
Миграция заполняет исходное состояние существующих новых тем их текущими значениями, поскольку отделить уже
выполненные пользовательские изменения от начального наполнения задним числом невозможно. Открытая панель журнала
перечитывает данные после перехода автосохранения в подтверждённое состояние.

## 10. Одно изменение токена выглядит как много непонятных записей

Статус: исправлено в клиентском представлении и покрыто узкой проверкой.

Одно действие в редакторе пересчитало шесть зависимых токенов. Для каждого из них были атомарно
сохранены три устойчивые строки значений для Web, iOS и Android. Поэтому вычисляемый серверный журнал корректно
вернул 18 предметных строк. Прежний интерфейс показывал каждую из них как самостоятельное событие с типом
`token-value`, сырым идентификатором автора и без прежнего и нового значения.

Клиент теперь объединяет строки одного атомарного пакета по общим автору, времени и виду операции, а внутри объединяет
платформенные строки по токену, режиму и переходу значения. Один пакет показывается одной записью с деталями: именами
токенов, режимом, прежним и новым значениями и платформами. Имя автора разрешается из владельца и состава проекта;
если оно недоступно, остаётся краткий технический идентификатор. Объединение не меняет серверную модель: каждый `changeId` сохраняется
и откатывается отдельно.
