## Context

`frontend-kt` только что прошёл рефакторинг по ADR-0004/ADR-0005: бизнес-логика `dsbuilder` CLI вынесена в общие Kotlin Multiplatform модули `core-domain`, `core-network`, `core-auth`, `core-workspace`, `core-application` и feature-модули, специально для того, чтобы будущие клиенты (MCP-сервер, desktop, IDE-плагины) могли переиспользовать их вместо дублирования. IDE-плагин для Android Studio / IntelliJ IDEA — первый такой клиент.

Сегодня `core-auth` умеет резолвить только project access key (`ApiKeyResolver`, статичный ключ из `--api-key`/`DSBUILDER_API_KEY`) — модель, рассчитанная на CI и разработчиков самой дизайн-системы, привязанных к рабочей директории. ADR-0005 отдельно описывает «режим потребителя» — интерактивную авторизацию пользователя без привязки к `.sdds` рабочей директории, — но сознательно не фиксирует конкретный механизм. Это изменение реализует этот механизм впервые: OAuth Authorization Code + PKCE с loopback-редиректом, стандартный паттерн для нативных/десктопных клиентов (RFC 8252).

Бэкенд DS Builder уже использует Keycloak (realm `dsbuilder`) как identity provider, и уже есть публичный клиент `dsbuilder-api` (Authorization Code flow, PKCE-совместимый), которым пользуется веб-приложение. REST-поверхность для чтения токенов (`GET /api/projects`, `GET /api/projects/{id}/ds/tokens`, `GET /api/projects/{id}/ds/token-values`) уже существует, уже скоуплена на авторизованного актора (`requireActor()`) и уже публично проксируется через identity-gateway — новых бэкенд-эндпоинтов это изменение не добавляет.

Отдельно от DS Builder существует опубликованная в Maven Central Compose Multiplatform библиотека дизайн-системы `io.github.salute-developers:sdds-serv-compose` (таргетит среди прочего `jvm`), которую подключают приложения-потребители дизайн-системы. Она выбрана как UI-библиотека для самого плагина — независимо от того, какую дизайн-систему пользователь просматривает через плагин.

## Goals / Non-Goals

**Goals:**
- Дать разработчику-потребителю дизайн-системы возможность посмотреть токены DS Builder, не выходя из Android Studio / IntelliJ IDEA.
- Реализовать первую интерактивную пользовательскую авторизацию в `frontend-kt`, пригодную для переиспользования будущими клиентами (desktop, MCP runtime, запущенный из IDE).
- Встроить плагин в существующую модульную структуру `frontend-kt` без дублирования REST-клиентов, резолвинга контекста или доменных моделей.

**Non-Goals:**
- Генерация кода дизайн-системы внутри плагина — эта возможность уже реализована отдельно Gradle-плагином `io.github.salute-developers.design-system-builder` для команды, которая публикует библиотеку дизайн-системы, и не дублируется.
- Запись файлов, создание `.sdds` или изменение конфигурации в проекте пользователя.
- Просмотр компонентов (только токены в этой версии).
- Сверка отображаемых значений токенов с версией `sdds-serv-compose` (или другой библиотеки), реально подключённой в `build.gradle.kts` пользователя.
- Self-service запрос доступа к проекту, если пользователь ещё не приглашён участником.
- Интеграция с MCP-сервером (ADR-0004) — плагин обращается к REST API напрямую.

## Decisions

### Транспорт: прямой REST, без MCP

Плагин обращается к identity-gateway/db-service напрямую через REST, используя тот же `core-network`, что и CLI. MCP-сервер из ADR-0004 задуман как интерфейс для агентов (типизированные инструменты, машинно-читаемая диагностика), а не как транспорт для интерактивного UI. Добавление зависимости от ещё не реализованного MCP runtime увеличило бы объём этого изменения без выигрыша для read-only просмотра данных человеком.

**Альтернатива**: запускать локальный MCP-сервер из плагина (как предусмотрено ADR-0004 для будущих IDE-плагинов) и дергать `tokens_list`/`token_get`. Отклонено для этой версии — MCP-сервер ещё не реализован, а типизированный REST через `core-network` полностью покрывает read-only сценарий.

### Авторизация: OAuth Authorization Code + PKCE с loopback-редиректом, отдельный Keycloak-клиент

Плагин открывает системный браузер на `{gateway}/realms/dsbuilder/protocol/openid-connect/auth` (не на `/auth/login` — этот путь в текущей nginx-конфигурации gateway жёстко возвращает `404`), поднимает временный HTTP-listener на `127.0.0.1:{эфемерный порт}` для приёма redirect с `code`, и обменивает code на токены через уже существующий алиас `/auth/token`.

Для этого вводится новый публичный Keycloak-клиент `dsbuilder-studio-plugin`:
- `publicClient=true`, `standardFlowEnabled=true`, `directAccessGrantsEnabled=false` (без ROPC — плагин никогда не должен собирать логин/пароль сам);
- обязательный PKCE (`S256`);
- `redirectUris`, разрешающие loopback (`http://127.0.0.1:*`);
- тот же protocol mapper `oidc-audience-mapper` (`included.client.audience: dsbuilder-api`), что и у `dsbuilder-api`, — без него access token не пройдёт проверку `KeycloakJwtVerifier` на identity-gateway, которая сверяет единственное сконфигурированное значение `auth.keycloak.audience`.

Локально клиент заводится через realm-импорт (`dsbuilder-realm.json`, `/opt/keycloak/data/import/`). В проде клиенты Keycloak заводятся не realm-импортом, а идемпотентным скриптом `backend-kt/identity-gateway/keycloak/bootstrap-production-keycloak.sh` (выполняется через `kcadm.sh`/Keycloak Admin API при каждом старте прод-стека) — `dsbuilder-realm.prod.json` содержит только realm-level настройки и не перечисляет ни одного клиента, включая существующий `dsbuilder-api`. Поэтому `dsbuilder-studio-plugin` для прода добавляется вторым create-or-update блоком в этот скрипт, по образцу уже существующего блока для `dsbuilder-api`, а не правкой `dsbuilder-realm.prod.json`. В отличие от `dsbuilder-api`, чей `redirectUri`/`webOrigin` параметризован env-переменными (`OIDC_REDIRECT_URI`, `OIDC_WEB_ORIGIN`), потому что зависит от домена конкретного деплоя веб-приложения, loopback-адрес плагина от деплоя не зависит и может быть захардкожен в скрипте.

**Альтернатива 1 — переиспользовать существующий клиент `dsbuilder-api`**: отклонено, поскольку его `redirectUris` жёстко привязаны к портам dev-серверов веб-приложения (3000/3002/8080), а у него включён `directAccessGrantsEnabled` (ROPC) — нежелательный паттерн для нового клиента. Отдельный клиент также даёт независимый аудит и возможность отозвать доступ плагина, не трогая веб-клиент.

**Альтернатива 2 — Device Authorization Grant** (device code flow): не выбран для первой версии, поскольку loopback-редирект даёт более быстрый UX (не нужно вручную вводить код на отдельном экране) и является более распространённым паттерном для десктопных IDE-плагинов. Может быть пересмотрено, если loopback-редирект создаст проблемы в корпоративных сетевых окружениях.

### Хранение токена

Access token живёт только в памяти процесса плагина. Refresh token хранится через `PasswordSafe` IntelliJ Platform (использует системный keychain/credential manager хост-ОС) — не в файле конфигурации проекта и не в `.sdds`. При `401` от бэкенда плагин прозрачно обновляет access token через `grant_type=refresh_token`; при неудаче обновления — сбрасывает сессию и возвращает пользователя на экран логина.

### Модуль плагина живёт внутри `frontend-kt`, а не в отдельном репозитории

Новый модуль `frontend-kt/plugins/android-studio` добавляется в `frontend-kt/settings.gradle.kts` и зависит от `core-domain`, `core-network`, `core-auth`, `core-application` через обычные `project(...)`-зависимости.

**Альтернатива — отдельный Gradle-проект** (по образцу ранее существовавшего, ныне удалённого прототипа `plasma-android/sdds-studio-plugin`, который не входил в composite build `plasma-android` и был полностью независимым проектом): отклонено для этой версии, поскольку ни `core-domain`, ни `core-network`, ни `core-auth`, ни `core-application` сегодня не публикуются в Maven — отдельный репозиторий не смог бы получить их иначе, чем через хрупкий `includeBuild` с относительным путём к `frontend-kt`, что ломается при другой раскладке репозиториев на диске и в CI. Размещение внутри `frontend-kt` дословно соответствует целевой структуре, описанной в ADR-0004 (`frontend-kt/plugins/` — «будущие IDE-плагины или общие SDK для них»), и не требует настройки publishing pipeline для core-модулей.

Модуль — новый *тип* модуля в этом build: plain JVM + IntelliJ Platform Gradle Plugin, а не Kotlin Multiplatform. Ни один существующий `convention.*` в `frontend-kt/build-system/conventions` (все ориентированы на `convention.kotlin-multiplatform-module`) ему не подходит — вводится новый `convention.intellij-platform-module`.

### UI-библиотека плагина: `sdds-serv-compose`, а не generic uikit

Chrome плагина (кнопки, карточки, тулвindow-контент, тема) строится на `io.github.salute-developers:sdds-serv-compose` — готовой, полной, реально опубликованной Compose Multiplatform библиотеке (таргетит `jvm` в числе прочих платформ, что делает её встраиваемой в IntelliJ Platform через `ComposePanel`). Это отдельная, чисто техническая ось выбора UI-тулкита — она не ограничивает то, какие дизайн-системы плагин может **показывать**: данные любой дизайн-системы DS Builder рендерятся как обычные значения (цвет, текст, размер) внутри карточек, нарисованных `sdds-serv-compose`, без подключения отдельной Compose-библиотеки под каждую отображаемую дизайн-систему.

**Альтернатива — писать UI на голом IntelliJ Platform UI (Swing/Kotlin UI DSL)**: отклонена, поскольку не даёт визуальной согласованности с брендом DS Builder и требует вручную переносить токены (цвета, типографику, radius) в Swing-примитивы. Существование готовой, production-качества Compose Multiplatform библиотеки с `jvm`-таргетом делает более простым и целостным решением использовать её напрямую.

Технический риск embedding'а de-risked конкретным прецедентом: удалённый прототип `plasma-android/sdds-studio-plugin` (untracked в git, датирован 2026-08-02/03) успешно собирался как `.zip`-дистрибутив плагина (манифест: IntelliJ Platform Gradle Plugin 2.11.0, Android Studio build `AI-261.x`, Kotlin `2.2.10`) с полностью забандленным Compose Desktop/Skiko рантаймом внутри. Это не отменяет необходимость собственного spike перед реализацией, но подтверждает, что подход технически рабочий, а не только гипотетический.

### Версионный разрыв между DS Builder и зависимостью проекта — принят как известное ограничение

Плагин показывает состояние токенов "как сейчас в DS Builder", не пытаясь определить, какая версия `sdds-serv-compose` (или другой библиотеки дизайн-системы) реально подключена в `build.gradle.kts` открытого проекта. Автоматическая сверка версий потребовала бы парсинга чужого Gradle-графа — сложность, не оправданная для первой версии.

### `GET /ds/tokens` и `GET /ds/token-values` не были скоуплены по проекту — исправлено как часть этого change

При реализации use case'ов группы 7 обнаружилось, что `js/services/db-service/src/routes/api/tokens.ts` и `token-values.ts` читали таблицы без какой-либо фильтрации по дизайн-системе или проекту — `db.select().from(tokens)` возвращал строки всех дизайн-систем в базе, независимо от того, каким актором (project key или, в нашем случае, пользовательским Bearer JWT) пришёл запрос. Для сравнения, `design-systems.ts` уже применяет `designSystemScopeFilter(req)` — читает trusted-заголовок `X-Project-Id` от gateway (`auth_request /_auth_project` + `rewrite .../ds/tokens → /api/ds/tokens`, весь project-контекст идёт заголовком, не путём) и ограничивает выдачу дизайн-системами этого проекта плюс "базовыми" (`projectId IS NULL`).

Предпосылка исходного proposal.md («бэкенд-изменений для чтения не нужно») была основана на поверхностной сверке существования эндпоинтов на этапе exploration, не на чтении их реализации. Без исправления любой пользователь плагина увидел бы токены всех дизайн-систем DS Builder, а не только своего проекта — что противоречит project-scoped RBAC модели, которую описывает остальная система (ADR-0001).

**Решение**: применить тот же `designSystemScopeFilter` к `tokens.ts` (`GET /`, через `inArray(tokens.designSystemId, ...)`) и `token-values.ts` (`GET /`, через два вложенных `inArray` — `tokenValues.tokenId → tokens.id → tokens.designSystemId`). Маршруты, схема БД, OpenAPI-контракт не меняются — меняется только runtime-фильтрация внутри уже существующих обработчиков.

**Осознанно не в скоупе этого исправления**: `GET /:id`, `PATCH /:id`, `DELETE /:id` для `tokens`/`token-values` остаются без аналогичного скоупинга (позволяют enumeration по id за пределами своего проекта). Плагин их не вызывает — только `GET /` (list). Это pre-existing gap, отдельный от того, что нужно для read-only сценария этого change; расширять исправление на него значило бы выйти за рамки того, что требуется здесь.

## Risks / Trade-offs

- **[Риск] Конфликт версий Kotlin/Compose между плагином и хост-IDE — подтверждён и закрыт эмпирически.** IntelliJ Platform Gradle Plugin `2.18.1` тянет `kotlin-stdlib:2.4.0`, несовместимый с Kotlin `2.2.0` в `build-system/conventions`; версия `2.11.0` (как у старого прототипа) собирает пустой модуль, но её собственный код падает с `NoClassDefFoundError` при связке с `org.jetbrains.kotlin.plugin.compose` (compose-compiler). Рабочая версия — `2.17.0`. Целевая Android Studio закреплена как `2024.3.2.15` (build `243.*`) — build `261.x` из манифеста старого прототипа не резолвился ни в одном `defaultRepositories()`, точный маппинг build-number → version string для 261 не подтверждён и не требуется для этой версии.
- **[Риск] Плагин не показывает публичных/неприглашённых дизайн-систем.** В модели проектов DS Builder нет флага `visibility`/`isPublic` — пользователь должен быть заранее приглашён участником проекта (роль `viewer` и выше), иначе `GET /api/projects` вернёт пустой список. → **Митигация**: explicit empty state в UI с понятным объяснением, а не выглядящий как ошибка экран; изменение существующей invite-модели — вне рамок этого изменения.
- **[Риск] Расхождение отображаемых значений токенов с реально используемой версией библиотеки в проекте пользователя.** → **Митигация**: осознанно принято как ограничение v1 (см. Non-Goals); плагин явно не заявляет версионную точность.
- **[Риск] Loopback-редирект может быть заблокирован корпоративным firewall/VPN-политикой на некоторых машинах разработчиков.** → **Митигация**: если это станет проблемой на практике, можно добавить Device Authorization Grant как альтернативный флоу для того же клиента (не блокирует эту версию).
- **[Trade-off] Новый Gradle convention (`convention.intellij-platform-module`) увеличивает поверхность build-system вместо переиспользования существующих конвеншенов.** Осознанный компромисс: IntelliJ Platform Gradle Plugin принципиально не Kotlin Multiplatform, и попытка притянуть его под `convention.kotlin-multiplatform-module` была бы более хрупким решением, чем отдельный конвеншен.
- **[Риск] Отказ от Gradle-плагина `org.jetbrains.compose` (см. решение про Kotlin/Compose выше) означает, что платформенный native-рантайм Skiko не добавляется автоматически через `compose.desktop.currentOs` — подтверждено на практике.** При первом реальном запуске (`runIde`, не headless-проверка) клик по tool window ронял `ComposePanel` с `LibraryLoadException: Cannot find libskiko-macos-arm64.dylib.sha256` — заявленные `org.jetbrains.compose.*:*-desktop` зависимости тянут только API skiko, не native-бинарник. → **Митигация**: явные `runtimeOnly` на `org.jetbrains.skiko:skiko-awt-runtime-{macos-arm64,macos-x64,windows-x64,linux-x64}:0.9.4.2`, на все четыре основные платформы сразу, а не только под машину разработчика.
- **[Риск] `kotlinx.serialization`'s `Json` по умолчанию не прощает лишние поля — паттерн повторился трижды, в трёх разных клиентах.** Помимо `HttpProjectsClient`/`HttpDesignSystemDataClient` (см. группу 7 tasks.md), тот же баг обнаружился и в `KtorTokenExchangeClient` (`core-network`): реальный ответ `/auth/token` от Keycloak несёт `token_type`, `id_token`, `refresh_expires_in`, `scope`, `session_state` сверх ожидаемых `access_token`/`refresh_token`/`expires_in` — кнопка логина зависала после реального браузерного входа. → **Митигация**: `ignoreUnknownKeys=true` во всех местах, где парсится ответ backend'а; вывод на будущее — при заведении нового REST-клиента в этом кодбейзе сразу заводить `Json` с этим флагом, а не полагаться на дефолт.
- **[Риск] Очистка только локальной сессии плагина — не настоящий logout.** Подтверждено на практике (группа 9.6): `sessionResolver.clear()` не трогает SSO-cookie Keycloak в системном браузере, поэтому повторный вход после "выхода" молча получал новый code без формы логина. → **Митигация**: `LoginController.logout()` дополнительно открывает браузер на end-session endpoint Keycloak (`LogoutUrlBuilder`, тот же loopback-listener, что и вход) перед очисткой локальной сессии; локальная сессия чистится безусловно, даже если браузерный шаг не удался.
- **[Известный визуальный нюанс, принят как есть] У вкладок типов токенов (`TabsClip.Scroll`) остаётся небольшой, не до конца объяснённый отступ слева**, не совпадающий с остальными элементами экрана (группа 9.9). Расследовано декомпиляцией реального `uikit-compose` (`RegularRow`/`clipModifier`/`BaseTabs`) — исключены как причина `stretch`/`canStretch`/`stretchForScroll` и явные "кнопки-контролы" прокрутки (в `TabsClip.Scroll` их нет, это специфика только `ShowMore`). Точный источник не подтверждён (кандидат — `tabIndicator`/порядок применения `style { dimensions {...} }` override). Пользователь осознанно выбрал сохранить `TabsClip.Scroll` (поддержка прокрутки при большом числе типов токенов) вместо `TabsClip.None` (пиксель-идеальное выравнивание).

## Migration Plan

Изменение аддитивное — не переносит и не удаляет существующую функциональность CLI, project-key авторизацию или REST API. Специфичный порядок раскатки:

1. Завести Keycloak-клиента `dsbuilder-studio-plugin` в `dsbuilder-realm.json` (локальная разработка, realm-импорт) и вторым блоком в `bootstrap-production-keycloak.sh` (прод, Admin API при деплое) — независимо от кода плагина, можно проверить flow вручную (curl/Postman) на локальном контуре (`./setup-local.sh`), до того как плагин готов. Все проверки на этапе разработки — только на локальном контуре, не на staging/prod; прод-провижининг раскатывается обычным деплоем стека (сам скрипт в рамках этого изменения не исполняется против реального прод-Keycloak) и отдельно вручную не тестируется.
2. Добавить пользовательский OAuth-резолвер в `core-auth` и Bearer-поддержку в `core-network`, с тестами — не меняет поведение существующего `ApiKeyResolver`/`ProjectKey`-флоу.
3. Завести `convention.intellij-platform-module` и пустой `:plugins:android-studio`, подтвердить `runIde`/`buildPlugin` (spike из Risks).
4. Реализовать экран логина, затем read-only просмотр проектов/токенов поверх уже готового auth и REST-слоя.

Отката не требует специальной процедуры: плагин — новый, необязательный артефакт; в случае проблем достаточно не публиковать его сборку. Единственный компонент, требующий аккуратности при откате — Keycloak client `dsbuilder-studio-plugin`: его можно отключить (`enabled=false`) в realm-конфигурации без влияния на `dsbuilder-api` или существующие сессии пользователей.
