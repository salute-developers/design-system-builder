## Зачем

Проверки проекта в `ds-service` не гарантируют принадлежность UUID выбранной дизайн-системе: запрос из контекста A может прочитать или изменить сущность системы B того же проекта. Сейчас MCP предоставляет только чтение, но тот же REST-контракт небезопасен для будущих инструментов мутации и ошибочных запросов редактора.

## Что изменится

- **BREAKING**: принадлежащие дизайн-системе ресурсы публикуются под `/api/projects/{projectId}/design-systems/{designSystemId}/...`; прежние пути этих ресурсов удаляются, перенаправления мутаций не вводятся. Каталог дизайн-систем доступен под `/api/projects/{projectId}/design-systems`. Самостоятельный внутренний вход использует `/api/design-systems` для списка систем, `/api/design-systems/catalog/...` для глобальных ресурсов и `/api/design-systems/{designSystemId}/...` для системных ресурсов. Прежний префикс `/api/ds` полностью исключается из регистрации, OpenAPI и внутренней нормализации путей; алиасы не сохраняются.
- **BREAKING**: дублирующий `designSystemId` удаляется из входных DTO и query системных маршрутов; единственный источник ожидаемой системы — путь. Идентификаторы других адресуемых сущностей и поля ответов сохраняются. Создание самой дизайн-системы остаётся отдельной операцией каталога.
- Ожидаемая дизайн-система передаётся явно в `DsRequestContext`. Транзакционный адаптер применяет её к общим предикатам чтения и записи, включая администратора. Проверки разрешений и принадлежности проекту сохраняются.
- Ограничение распространяется на создание, списки, детали, связанные UUID, пакетные операции, импорт, предварительную проверку без сохранения (`dryRun`), публикацию, журнал, SSE и идемпотентные повторы.
- **BREAKING**: глобальные публичные ресурсы также переносятся под `/api/projects/{projectId}/design-systems/catalog/...`, но без ID конкретной системы (например, `/design-systems/catalog/components`). Прежние границы доступа сохраняются; административные пути не меняются.
- Совпадающие после переноса списки регистрируются однократно. Для токенов используется существующий `DesignSystemTokenSummaryResponse`, для тем — существующий `TenantResponse`: без нового объединённого DTO. Поля проверены по реальным клиентам; подробности — в `list-contracts.md`.
- Все собственные HTTP-клиенты, OpenAPI и манифест маршрутов обновляются вместе. Новые MCP-инструменты записи не добавляются.

## Возможности

### Новые возможности

- `design-system-request-scope`: сквозное ограничение операции ожидаемой дизайн-системой и полный реестр переноса маршрутов.

### Изменяемые возможности

- `design-system-model-api`: адреса предметных ресурсов, границы чтения и записи, разделение глобальных и системных данных, согласование конфликтующих прежних требований о стабильности URL.
- `multi-user-design-system-editing`: сохранение текущей идемпотентности с учётом системы из пути при сопоставлении команды.

## Влияние

- `backend-kt/ds-service`: `core`, четыре `feature-*`, `runtime`, OpenAPI и `contracts/route-manifest.json`; транзакции, разрешение версий, общие SQL-предикаты и отдельные входы создания/импорта/отката. Схема предметных сущностей и существующие миграции не переписываются.
- `backend-kt/app`: классификация публичных путей, доверенный контекст, кэширование тела, ограничения размера, OpenAPI-адаптация и контрактные проверки. Внутренний самостоятельный вход сервиса также требует систему для системных ресурсов.
- `frontend-kt`: HTTP-адаптеры `feature-ds`, `feature-theme`, `feature-components`, `feature-status`, общие MCP-чтения и Android Studio plugin; сигнатуры пользовательских MCP-инструментов и локальные форматы `.sdds` сохраняются.
- `js/apps/client`: построение URL, чтения редактора, мутации, публикация, SSE, кэши и тесты. `js/cli` генерирует из локальных файлов и не требует новой сетевой архитектуры.
- `documentation-service`: перевести внутреннее чтение принадлежности дизайн-системы и его тесты на `/api/design-systems/{id}`; остальные внутренние клиенты глобальных ресурсов также переводятся на `/api/design-systems/catalog/...`; `project-publisher` не получает новых обязанностей.
- Новые сервисы, модули, зависимости, учётные данные и параметры развёртывания не требуются. Подробности исследования и карта охвата находятся в `coverage.md`.
