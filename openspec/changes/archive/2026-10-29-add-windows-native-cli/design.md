# Design

## Контекст

См. [proposal.md](proposal.md). `:cli` и его зависимости объявляют JVM и macOS цели; `:mcp-server-core` дополнительно собирается для Node.js. Нативные реализации CLI существуют в `macosMain`, а общие `ProcessRequest` и `WorkspacePaths` принимают только пути с `/`. В `platform-web` поиск `npm` делит `PATH` по `:`, а `platform-android` ищет `gradlew`. При этом нужные прямые зависимости и основные зависимости MCP SDK опубликованы для `mingwX64` в используемых версиях.

## Цели и границы

- Собрать один `dsbuilder.exe`, в котором доступны CLI и `mcp serve`, без Java или Node.js у пользователя.
- Сохранить общие прикладные сценарии, формат сессии, имена MCP-инструментов и Unix-поведение.
- Проверять связывание на macOS; функциональную проверку на Windows x64 проводит тестировщик после передачи сборки.
- Не переносить локальный серверный `setup-local.sh` и iOS toolchain на Windows; Android Gradle и web-генератор сохраняют собственные требования к JDK и Node.js только при вызове соответствующих команд.

## Решения

### Граф целей и границы модулей

Добавить `mingwX64` в каждый модуль, от которого зависит `:cli`, включая `:mcp-server-core`; `:mcp-node` остаётся самостоятельной Node.js поставкой. Переиспользуемые реализации архивации документации и чтения ZIP на Okio перенести из `macosMain`/`posixMain` в общий нативный набор исходников, если их компиляция для Windows подтверждена. В `:cli` оставить только точку входа и платформенный composition root; предметные сценарии не дублировать. Для HTTP использовать Ktor WinHttp 3.3.0 в `mingwX64Main`, а MCP SDK оставить версии 0.10.0.

Объявление `mingwX64` в общих модулях делать явно или через существующий convention plugin без добавления MCP SDK и HTTP-движка в зависимости всех модулей. Это сохраняет правило минимальных зависимостей. Альтернатива в виде JVM-дистрибутива отклонена из-за требования установить Java; отдельный нативный MCP-процесс дублировал бы существующую команду `dsbuilder mcp serve`.

### Платформенный runtime Windows

Реализовать `defaultClientRuntime()` для Windows через существующие порты `ClientRuntime`: файловую систему, чтение окружения, WinHttp, `ProcessRunner`, `FileCredentialStore` и `PkcePlatform`. Для путей использовать системные операции Windows с поддержкой Unicode; преобразование к абсолютному пути и вычисление родителя централизовать на границе файловой системы. Общие модели `ProcessRequest`, `WorkspacePaths` и `DelegateInvocation` принимают абсолютные пути Unix, тома Windows и UNC, но отклоняют относительные и неполные пути вроде `C:folder`. Это изменение контракта, поэтому проверка путей не должна оставаться внутри macOS-адаптера.

Для исполняемых `.exe` процесс запускается напрямую. Сценарии `.cmd` и `.bat` запускаются через `cmd.exe` с заключением каждого аргумента в кавычки и рабочим каталогом без сборки команды из пользовательского текста. Аргументы с кавычками, символами подстановки `%`, `!`, `^` или управляющими символами отклоняются до запуска: их нельзя безопасно передать через общий контракт batch-файлов без проверки конкретного сценария на Windows. Оба режима `ProcessRunner` сохраняют наследуемый вывод либо захватывают stdout/stderr без взаимной блокировки. Windows-адаптер разрешает `npm.cmd` по `PATH` с разделителем `;` и `gradlew.bat` при подъёме по дереву каталогов. iOS-делегат и установщик не регистрируются в Windows composition root; запрос iOS-платформы получает явную ошибку о неподдерживаемой среде.

### Авторизация и локальная сессия

Windows `PkcePlatform` использует системный генератор случайных чисел, SHA-256, системный браузер и loopback listener на `127.0.0.1`. Общий сценарий сохраняет проверку `state`, путь callback и предел ожидания. `FileCredentialStore` сохраняет формат и имя файла по нормализованному API URL в домашнем каталоге пользователя, совпадающем с `os.homedir()` Node.js. На Windows адаптер ограничивает доступ к каталогу сессий текущим пользователем и администраторами, в том числе если каталог уже существует; временный файл наследует эти права. Блокировка файла создаётся эксклюзивно и совместима с `openSync(..., "wx")` Node.js. Замена файла выполняется атомарно в том же каталоге. Не использовать DPAPI: шифрование без согласованного ключевого механизма разорвало бы обмен сессией между нативным CLI и Node.js launcher.

### MCP stdio

Windows-адаптер подаёт в существующий `serveStdio` сырые байтовые потоки стандартного ввода и вывода через системные дескрипторы Windows. Он не пользуется текстовым режимом CRT, чтобы избежать замены `\n` на `\r\n` и повреждения JSON-RPC/UTF-8. Закрытие stdin завершает сессию и HTTP-клиент; stdout не используется для диагностики.

### Упаковка и проверка

Gradle-задача создаёт архив Windows x64 с `dsbuilder.exe`, инструкцией и сценарием установки PowerShell в пользовательский каталог. Локальный PowerShell-сценарий собирает тот же executable из исходников и вызывает общий установщик с путём к сборке. Существующие macOS и JVM архивы сохраняются. Сборка на macOS проверяет `mingwX64` граф, компиляцию и связывание. Общую логику путей, делегатов и авторизации покрывают тесты, запускаемые на macOS с подменёнными платформенными портами. Исполнение `.exe` и проверку системных Windows API выполняет тестировщик после передачи архива.

### Локальный Docker-контур Windows

`setup-local.ps1` работает на Windows-хосте и управляет Docker Desktop командами Compose. Override-файл заменяет только build context backend-сервисов: их обычные многостадийные Dockerfile собирают jars внутри Linux-контейнеров, поэтому для запуска контура не нужен JDK на хосте. Подготовка Keycloak выполняется PowerShell через Admin API. Существующие `bootstrap-base.sh`, `publish-compose-plugin.sh` и `seed-local-design-system.sh` запускаются внутри вспомогательного Linux-контейнера с JDK 17, Node.js, Python, Ruby и curl; контейнер видит рабочую копию как `/workspace` и обращается к Gateway через `host.docker.internal`. Контейнерные shell-скрипты и Compose-сервисы сохраняют прежнюю логику. Windows PowerShell лишь передаёт им пути, окружение и режимы `reset`/`down`.

Локальная установка CLI из исходников остаётся отдельной командой `install-local-cli.ps1`; ей нужен JDK для сборки, установленный executable Java не требует. Для запуска Docker-контура JDK и Node.js на Windows-хосте не требуются. Linux-контейнер bootstrap скачивает зависимости `js/cli`, если мета web-компонентов ещё не создана.

## Риски и компромиссы

- **[Риск]** `mingwX64` относится к третьему уровню поддержки Kotlin/Native. → Собирать на macOS, закреплять версии зависимостей и передать готовый архив тестировщику для проверки на Windows x64.
- **[Риск]** Разбор аргументов `.cmd`/`.bat` ошибочно обработает пробелы и метасимволы. → На macOS проверить формирование команды и отклонение опасных аргументов; тестировщику на Windows проверить запуск с пробелами и разрешёнными метасимволами, а также отсутствие выполнения внедрённой команды.
- **[Риск]** Windows ACL и атомарная замена отличаются от POSIX-операций. → Проверить права существующего и нового каталога сессий, совместимость блокировки с Node.js и сохранность сессии при одновременном обновлении.
- **[Риск]** Наличие опубликованных библиотек не гарантирует совместимость всего графа. → Первым шагом реализации собрать минимальную цель `mingwX64`; несовместимость фиксировать до разработки платформенных адаптеров.

## План проверки и выпуска

Локально на macOS: разрешить граф зависимостей, связать Windows executable, проверить состав архива, выполнить существующие JVM/macOS тесты и проверки качества `frontend-kt`. macOS не может исполнить этот `.exe` и подтвердить работу Win32 API, установщика или интеграции с MCP-клиентом. Проверка на Windows не блокирует завершение задач change: тестировщику передаётся архив и перечень сценариев — запуск без Java, установка без прав администратора, пути с пробелами и кириллицей, `auth login/status/logout`, одновременное обновление сессии с Node.js launcher, `mcp serve` (`initialize`, `tools/list`, `tools/call`, EOF и чистый stdout), `npm.cmd` и `gradlew.bat`. Результаты тестирования фиксируются отдельно; обнаруженные дефекты возвращаются в работу. Откат — удалить Windows-архив из следующего выпуска, не изменяя существующие архивы и серверные данные.
