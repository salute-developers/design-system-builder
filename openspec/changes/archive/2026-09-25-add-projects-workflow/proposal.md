## Why

Текущий веб-клиент открывает одну дизайн-систему и не предоставляет целостного сценария работы с проектами, несколькими дизайн-системами и темами. Из-за этого уже существующие API управления проектами и модель тем-тенантов недоступны пользователю, а редактор смешивает данные и черновики разных тем.

## What Changes

- Веб-клиент получает экраны списка, создания и просмотра проектов, а также настройки проекта и состава участников по ролям `viewer`, `editor`, `maintainer` и `owner`.
- Внутри проекта появляются экраны списка, создания, просмотра, настройки и полного удаления дизайн-систем.
- Тема становится пользовательским представлением tenant: темы можно создавать из профилей `Sber`, `Malachite`, `B2B` или `Custom`, просматривать и полностью удалять без отдельного статуса или версии.
- Карточка Theme получает динамическое превью Light/Dark из актуальных цветовых значений, а карточка дизайн-системы — мозаику из превью не более четырёх её тем; пустые и legacy-сущности получают выразительные детерминированные заглушки.
- `POST /tenants` атомарно создаёт tenant и полный набор начальных значений токенов выбранного профиля; создание дизайн-системы подготавливает общие определения токенов, необходимые всем её темам.
- Существующий редактор становится tenant-aware: выбранный `tenantId` участвует в маршруте, загрузке, черновиках и сохранении значений токенов, а данные соседних тем не изменяются.
- Добавляется пакетное атомарное сохранение значений токенов одного выбранного tenant, чтобы редактор не выполнял отдельный запрос для каждого значения.
- Локальные черновики нескольких tenant сохраняются независимо при переключении, а техническая ревизия редактирования предотвращает незаметную перезапись одного tenant из двух вкладок или пользовательских сессий.
- Модель версий остаётся на уровне дизайн-системы целиком; отдельное версионирование тем не вводится. Legacy-публикация npm-пакета не изменяется этим change.
- Интерфейс не показывает неподдерживаемые возможности: приглашения незарегистрированных пользователей, статус черновика темы, версию темы и архивирование дизайн-системы.

## Capabilities

### New Capabilities

- `web-projects-workflow`: пользовательские сценарии списка, создания, просмотра и настройки проектов, включая управление зарегистрированными участниками.
- `web-design-system-workflow`: пользовательские сценарии списка, создания, просмотра, настройки и полного удаления дизайн-систем внутри проекта, включая динамические обложки карточек.
- `theme-lifecycle`: создание, просмотр и удаление тем-тенантов с атомарной инициализацией значений токенов выбранного профиля и компактной проекцией цветов для превью.
- `tenant-aware-theme-editor`: открытие, загрузка, изоляция черновика и пакетное сохранение выбранной темы в существующем редакторе без изменения соседних тем и потери конкурентных изменений.

### Modified Capabilities

- `project-management`: ответы списка и карточки проекта получают `effectiveRole` — итоговую роль текущего пользователя в проекте, чтобы клиент не выполнял отдельный запрос участников для каждого проекта.

## Impact

- `js/apps/client`: маршрутизация по стабильным идентификаторам, новые экраны и диалоги из прототипа, клиенты Projects Service и `db-service`, tenant-aware состояние редактора и ключи локальных черновиков.
- `js/services/db-service`: расширение контрактов создания tenant и дизайн-системы, пакетное сохранение значений токенов tenant, техническая ревизия редактирования, компактные агрегаты превью, транзакционная инициализация данных и обновление OpenAPI. Проверки project scope и project role остаются вне этого изменения.
- `backend-kt/projects-service`: существующие API проектов, участников, поиска зарегистрированных пользователей и целевые роли используются без изменения модели; возможны только совместимые исправления выявленных контрактных расхождений.
- `frontend-kt`: не затрагивается.
- `js/services/db-service/src/db/schema.ts`, новая Drizzle-миграция и `js/docs/db-schema.dbml`: регистронезависимая уникальность нормализованного названия tenant внутри дизайн-системы; профиль темы хранится в расширенном типе существующего `colorConfig`.
- `js/apps/client` получает средства модульного и компонентного тестирования как зависимости разработки; новых производственных внешних зависимостей и изменений конфигурации не предполагается.
- Legacy-сценарий публикации npm-пакета, его generator/publisher, registry и token configuration не затрагиваются.
