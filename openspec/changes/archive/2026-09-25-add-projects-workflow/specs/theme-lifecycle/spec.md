## ADDED Requirements

### Requirement: Theme является tenant дизайн-системы

Система SHALL представлять каждую пользовательскую Theme одной записью tenant, принадлежащей ровно одной дизайн-системе.

#### Scenario: Тема возвращается как tenant DTO

- **WHEN** клиент запрашивает темы дизайн-системы
- **THEN** API MUST вернуть tenant DTO со стабильными `id`, `designSystemId`, `name`, необязательным `description` и `colorConfig`
- **THEN** DTO MUST NOT содержать отдельную версию или статус Draft темы

#### Scenario: Тема не имеет отдельной версии

- **WHEN** пользователь изменяет значения токенов темы
- **THEN** система MUST сохранять изменения в текущем tenant
- **THEN** система MUST NOT создавать версию темы

### Requirement: Tenant предоставляет компактное превью Theme

API SHALL возвращать пригодную для отрисовки карточки цветовую проекцию Theme без загрузки полного набора значений токенов.

#### Scenario: Превью построено по актуальным токенам

- **WHEN** tenant содержит разрешимые значения акцента, цвета на акценте и поверхностей Light и Dark
- **THEN** tenant DTO MUST содержать `preview.accentLight`, `preview.onAccentLight`, `preview.surfaceLight`, `preview.accentDark` и `preview.surfaceDark`
- **THEN** каждое поле MUST содержать нормализованный цвет, пригодный для CSS

#### Scenario: Значение связано с палитрой

- **WHEN** обязательный цвет tenant хранится через `paletteId` или ссылку на палитру
- **THEN** API MUST вернуть в `preview` разрешённый цвет, а не внутренний идентификатор или выражение ссылки

#### Scenario: Использован профиль

- **WHEN** обязательные значения токенов отсутствуют, но `colorConfig` содержит известный профиль
- **THEN** API MUST заполнить недостающие поля `preview` цветами этого профиля

#### Scenario: Использована резервная палитра

- **WHEN** legacy tenant не содержит ни разрешимых значений, ни известного профиля
- **THEN** API MUST детерминированно получить безопасную контрастную палитру из `tenantId`
- **THEN** повторные ответы для того же tenant MUST возвращать одинаковые резервные цвета

#### Scenario: Превью обновилось после сохранения

- **WHEN** пакетное сохранение изменяет один из цветов, участвующих в превью
- **THEN** следующий ответ tenant или списка дизайн-систем MUST содержать обновлённую проекцию

### Requirement: Пользователь создаёт тему из стартового профиля

API SHALL атомарно создавать tenant и начальные значения всех определённых в дизайн-системе токенов для режимов Light и Dark.

#### Scenario: Создан профиль Malachite по умолчанию

- **WHEN** Editor, Maintainer или Owner отправляет `POST /tenants` с уникальным названием и без явного профиля
- **THEN** API MUST использовать профиль `malachite`
- **THEN** API MUST вернуть созданный tenant только после создания полного набора начальных значений токенов

#### Scenario: Создан встроенный профиль

- **WHEN** запрос содержит профиль `sber`, `malachite` или `b2b`
- **THEN** API MUST сохранить выбранный профиль в `colorConfig`
- **THEN** API MUST инициализировать значения токенов согласно выбранному профилю для Light и Dark

#### Scenario: Создан профиль Custom

- **WHEN** запрос содержит профиль `custom` и четыре валидных цвета `primary`, `onPrimary`, `background` и `text` в формате `#[0-9A-Fa-f]{6}`
- **THEN** API MUST сохранить нормализованные параметры в `colorConfig`
- **THEN** API MUST сгенерировать согласованные начальные значения Light и Dark

#### Scenario: Создание темы откатилось

- **WHEN** хотя бы одно начальное значение токена не может быть создано
- **THEN** API MUST откатить tenant и все созданные в запросе значения
- **THEN** API MUST вернуть ошибку без частично созданной темы

### Requirement: Название темы валидируется внутри дизайн-системы

API и веб-клиент SHALL принимать название темы длиной не более 80 символов после нормализации пробелов и SHALL запрещать повтор внутри одной дизайн-системы без учёта регистра.

#### Scenario: Название нормализовано

- **WHEN** пользователь вводит название с крайними или последовательными пробелами
- **THEN** клиент MUST удалить крайние пробелы и схлопнуть последовательности пробелов перед отправкой
- **THEN** API MUST повторить нормализацию на доверенной стороне

#### Scenario: Название обязательно

- **WHEN** нормализованное название пусто
- **THEN** клиент MUST показать `Введите название Theme.`
- **THEN** API MUST отклонить отправленный напрямую запрос как `400 Bad Request`

#### Scenario: Название слишком длинное

- **WHEN** нормализованное название длиннее 80 символов
- **THEN** клиент MUST показать `Название Theme должно быть не длиннее 80 символов.`
- **THEN** API MUST отклонить отправленный напрямую запрос как `400 Bad Request`

#### Scenario: Название уже существует

- **WHEN** в этой дизайн-системе существует tenant с эквивалентным после нормализации и без учёта регистра названием
- **THEN** API MUST вернуть `409 Conflict`
- **THEN** клиент MUST показать `Theme с таким названием уже существует.`

### Requirement: Форма создания темы следует прототипу без несуществующего жизненного цикла

Веб-клиент SHALL реализовать одноэкранную форму с секциями основных параметров и внешнего вида, предварительным просмотром Light и Dark и профилями `Sber`, `Malachite`, `B2B`, `Custom`.

#### Scenario: Форма открыта

- **WHEN** Editor, Maintainer или Owner открывает создание темы
- **THEN** профиль Malachite MUST быть выбран по умолчанию
- **THEN** предварительный просмотр MUST отражать выбранный профиль и выбранный режим Light или Dark

#### Scenario: Выбран Custom

- **WHEN** пользователь выбирает профиль Custom
- **THEN** клиент MUST показать пресеты Neutral, Brand и Warm и четыре обязательных поля HEX
- **THEN** невалидный HEX MUST блокировать создание и иметь текстовую ошибку

#### Scenario: Создание выполнено

- **WHEN** API успешно создаёт tenant и начальные значения
- **THEN** клиент MUST открыть созданную тему в редакторе по `projectId`, `designSystemId` и `tenantId`
- **THEN** клиент MUST NOT показывать создание Draft или версии `0.1.0` темы

#### Scenario: Viewer открывает создание напрямую

- **WHEN** Viewer открывает маршрут создания темы
- **THEN** клиент MUST показать состояние отсутствия доступа
- **THEN** клиент MUST NOT отправлять запрос создания

### Requirement: Удаление темы соответствует ролевой политике

Система SHALL позволять полностью удалить tenant только пользователю с разрешением `tenants:delete`.

#### Scenario: Maintainer или Owner удаляет тему

- **WHEN** Maintainer или Owner подтверждает удаление темы
- **THEN** API MUST удалить tenant и принадлежащие ему значения токенов
- **THEN** клиент MUST удалить карточку темы из обзора дизайн-системы

#### Scenario: Editor не может удалить тему

- **WHEN** Editor просматривает карточку темы
- **THEN** клиент MUST NOT показывать действие удаления

#### Scenario: Viewer не может изменить тему

- **WHEN** Viewer просматривает карточку темы
- **THEN** клиент MUST NOT показывать действия переименования или удаления
