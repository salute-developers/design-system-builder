## Зачем

DS Builder нуждается в базовой аналитике веб-клиента и использования CLI/MCP: журналы API не показывают посещение разделов, локальную генерацию и результат команды целиком. Веб-счётчик и небольшой общий контракт Kotlin-клиентов с первой реализацией для Яндекс Метрики обеспечат прямую отправку без backend DS Builder.

## Что меняется

- Добавляются KMP-модули `core-analytics` с независимыми от поставщика интерфейсами и `analytics-metrica` с реализацией Measurement Protocol. Обязательное разбиение на `domain/application/data/di` не вводится.
- CLI регистрирует завершение конечной команды; MCP, запущенный через `dsbuilder mcp serve`, — завершение вызова инструмента. Автоматическое обнаружение MCP не считается продуктовой активностью.
- CLI/MCP используют общий отдельный от веба счётчик и разные токены. CI встраивает конфигурацию в распространяемый CLI; токены считаются извлекаемыми, OAuth-токены не поставляются.
- CLI и встроенный MCP используют один постоянный ID установки `dsbuilder`; режим различается именами событий, а не идентификаторами посетителя. Проверка возвращаемости после перерыва более 21 дня отложена до последующего наблюдения и не блокирует текущую реализацию.
- Предусмотрены ограниченная доставка, отключение аналитики и отсутствие влияния её ошибок на команды и MCP-протокол.
- Приём собственного `ClientID` и повторная идентификация остаются обязательными техническими проверками до выпуска реализации. Неоднозначность условий распространения `ms` принимается как известный риск; ответ поддержки Яндекса не является условием реализации, архивирования или выпуска.
- В React-вебе подключается стандартный счётчик Метрики с отдельным номером, просмотрами начального экрана и переходов SPA, нормализацией маршрутов и конфигурацией CI. Базовая активная аудитория определяется по уникальным посетителям за выбранный день/месяц; отдельные события DAU/MAU и собственные веб-цели не добавляются.
- Node.js MCP исключён из аналитики. Изменение его распространения и инструментирование Figma/Pixso/IDE-плагинов не входят в Change.

## Возможности

### Новые возможности

- `client-analytics-core`: общий контракт событий, контекста, жизненного цикла и отключённой реализации.
- `metrica-client-delivery`: прямой адаптер Метрики, идентификатор установки, ограниченная доставка и конфигурация через CI.
- `cli-mcp-analytics`: перечень и семантика событий конечных CLI-команд и MCP-инструментов, исключение Node.js MCP.
- `web-client-analytics`: стандартный веб-счётчик, просмотры разделов React SPA, изоляция окружений и базовые показатели аудитории.

### Изменяемые возможности

Нет. Новые спецификации дополняют существующие контракты CLI/MCP, не меняя их команды, результаты и протокол.

## Влияние

- `frontend-kt/`: новые модули, `settings.gradle.kts`, сборка и тесты; подключение в `:cli`; при необходимости нейтральная точка наблюдения в `:mcp-server-core`, без зависимости последнего от адаптера Метрики. Локальное состояние аналитики хранится вне `.sdds` и рабочих каталогов проектов.
- `.github/workflows/publish-cli-release.yml`: подстановка конфигурации сборки из переменных и секретов CI; реальные значения не попадают в Git и журналы сборки.
- `.github/workflows/deploy-front-apps-dev.yml` и `deploy-front-apps-prom.yml`: передача публичного номера веб-счётчика и признака включения через переменные окружения сборки, раздельно по стендам.
- Зависимости: существующие Kotlin/coroutines и Ktor в адаптере, без новых внешних SDK. `core-analytics` не зависит от Ktor, Метрики, `feature-*` или клиентов.
- `backend-kt/`: сервисы, публичные API, OpenAPI и база данных не меняются; приёмник телеметрии не создаётся.
- `js/apps/client`: асинхронное подключение JavaScript-счётчика, интеграция с React Router и `BASE_URL`, нормализация просмотров, конфигурация Vite, тесты и документация. Генератор `js/cli` не меняется. Веб использует стандартный JavaScript API, без подключения Kotlin/JS только ради счётчика.
- Архитектурные тесты, Strictacode и файлы агентского процесса не изменяются. Новые архитектурные контракты фиксируются в этом Change.
