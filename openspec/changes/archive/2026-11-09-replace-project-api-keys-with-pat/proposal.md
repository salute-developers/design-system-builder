# Замена проектных ключей персональными токенами

## Зачем

Проектные API keys действуют независимо от текущих прав создавшего их пользователя. Personal Access Token (PAT) позволит автоматизировать работу от имени пользователя, ограничивая каждый запрос одновременно выбранными scopes и актуальными правами пользователя в целевом проекте.

## Что меняется

- API управления располагается под `/api/settings/personal-access-tokens`; владелец всегда определяется по OAuth-сессии.
- Каталог scopes сохраняет точный набор прежних ключей; управление метаданными, архивом и участниками проекта через PAT запрещено.
- Добавляются персональные токены: название, RBAC scopes, срок действия, однократная выдача секрета, список и отзыв владельцем.
- На каждом запросе PAT проверяются токен, действительность аккаунта, доступ пользователя к проекту и пересечение scopes с актуальной ролью. Актуальная глобальная роль администратора сохраняет доступ к проектам без членства, но не обходит scopes PAT.
- Настройки пользователя открываются из меню аватара и повторяют структуру и оформление настроек дизайн-системы; единственный раздел — `Personal Access Token`. Управление токенами повторяет существующий интерфейс проектных ключей.
- **BREAKING**: проектные ключи, их API и интерфейс удаляются; существующие секреты сразу перестают работать без преобразования в PAT.
- **BREAKING**: CLI/MCP используют PAT через `--api-key` и `DSBUILDER_API_KEY`, передавая `Authorization: Bearer <PAT>`. Сохраняются --api-key, --api-key-env и DSBUILDER_API_KEY; удаляются только --project-key-env и проектные типы учётных данных.
- Интерактивный init и новые инструменты обнаружения CLI/MCP поддерживают PAT; оба режима init сохраняют auto, существующие принудительные настройки не переписываются.
- Выбор контекста через `--design-system` или локальную конфигурацию отделяется от авторизации. В режиме `auto` приоритет: явный PAT, PAT из окружения, OAuth-сессия. Отклонённый PAT не вызывает обновления OAuth-сессии или смены пользователя.

## Возможности

### Новые возможности

- `personal-access-tokens`: жизненный цикл, хранение и проверка персональных токенов, ограничения владельца и прав.
- `web-user-settings`: настройки пользователя, вход из меню аватара и управление PAT в существующем оформлении.

### Изменяемые возможности

- `project-access-keys`: удаление всех требований к проектным ключам.
- `project-authorization-policy`: отдельный контекст PAT и совместная проверка роли и scopes.
- `gateway-authorization`: различение PAT и OAuth, проверенный пользовательский контекст PAT и публичная граница новых маршрутов.
- `frontend-client-authentication`: выбор PAT, отдельный тип учётных данных и отсутствие обновления PAT через OAuth.
- `frontend-core-modules`: замена проектных типов учётных данных на PAT при сохранении модульных границ.
- `frontend-cli`: параметры init, status и Bearer-авторизация проектных команд.
- `frontend-mcp-server`: PAT из окружения, Bearer и публичные ошибки PAT_INVALID/BACKEND_UNAVAILABLE.
- `cli-ds`: единый выбор контекста и PAT/OAuth для загрузки темы и компонентов.
- `cli-themes`: PAT в загрузке темы, явные параметры и авторизация по ссылке.
- `frontend-projects-listing`: PAT/OAuth при обнаружении проектов и сохранение явной OAuth-стратегии IDE.
- `frontend-design-systems-listing`: PAT/OAuth для каталога систем до выбора контекста.
- `cli-core`: источники PAT, локальная конфигурация и независимость контекста от авторизации.

## Влияние

- `backend-kt/feature-user-settings`: новый модуль с моделью PAT, прикладными сценариями, портами хранения и актуальной личности владельца, Flyway-миграциями и пользовательским API; подключение к app через Gradle и DI. `projects-service/feature-projects` сохраняет членство и миграцию отзыва старых ключей. Переиспользуются генерация секрета, PBKDF2, проверки срока и отзыва.
- `backend-kt/identity-gateway/feature-auth`, `backend-kt/app`: распознавание PAT, внутрипроцессные адаптеры, пользовательские маршруты и очищение внешних заголовков.
- `authorization/policy.json`, JSON Schema и данные проверки соответствия: переименование каталога без расширения scopes.
- `backend-kt/authorization-core`, `ds-service`, `documentation-service`, `project-publisher`: каталог scopes, проверенный контекст, проверка прав и авторство действий во всех потребителях.
- `frontend-kt/core-*`, общие сценарии `feature-*`, `cli`, `mcp-server-core`, `mcp-node`: тип PAT, выбор учётных данных, параметры, конфигурация, ошибки и справка. Особые административные сценарии сохраняют OAuth/service account.
- `js/apps/client`: пользовательский API, экран настроек и перенос панели ключей; `js/cli` и примеры конфигурации проверяются на обращения к прежним ключам.
- Обновляются исходные OpenAPI `documentation.yaml`, проверки контрактов, документация и примеры окружения. Новые сервисы, порты и внешние библиотеки не требуются.
