## Context

Значения свойств записываются операциями `ds-service`:

- `POST` и `PATCH /variation-property-values`;
- `POST` и `PATCH /invariant-property-values`.

Маршрут разбирает тело как `JsonObject`. Затем `hasInvalidNull` отклоняет запрос, если хотя бы одно поле передано со значением `null`. Только после этого запрос декодируется в `UpdatePropertyValueRequest` / `CreateVariationPropertyValueRequest`.

`toCommand` переводит запрос в `PropertyValueRepository.ValueUpdate` с флагами `tokenIdPresent`, `valuePresent`, `alphaPresent`, `adjustmentPresent`. `ExposedPropertyValueRepository` по флагу берёт новое значение поля, включая `null`, а без флага оставляет прежнее. Кроме того, `value` сбрасывается, если у значения есть токен.

Клиент (`componentRepository.saveComponentMutation`) всегда отправляет `{ tokenId, value, adjustment }`, где неиспользуемые поля равны `null`.

## Goals / Non-Goals

**Goals:**
- Правки значений свойств из редактора сохраняются без изменения клиента.
- Пользователь может перевести значение с токена на сырое значение и обратно, а также снять корректировку.

**Non-Goals:**
- Изменение правил `null` на остальных маршрутах `ds-service`.
- Изменение формата тела запроса в клиенте.

## Decisions

### Явный `null` разрешается на сервере, а не убирается на клиенте

Для полей `tokenId`, `value`, `alpha`, `adjustment` проверка `hasInvalidNull` снимается на четырёх маршрутах: создание и изменение вариационного и инвариантного значения. Для `stateSetId` проверка остаётся.

- В `PATCH` поле со значением `null` считается переданным: `"tokenId" in payload` уже даёт `tokenIdPresent = true` с `tokenId = null`. Хранилище очищает поле.
- В `POST` `null` декодируется как отсутствие значения. Создание и так не различает «не передано» и `null`.

Альтернатива — удалять `null` из тела на клиенте. Отклонена, потому что тогда невозможно снять токен или корректировку. `PATCH` без поля оставляет прежнее значение, а `value` без снятого токена хранилище отбрасывает. Пришлось бы вводить отдельную операцию очистки, а хранилище уже умеет то, что нужно.

### Ошибочные типы по-прежнему отклоняются

Не-строка в поле или нераспознаваемый `tokenId` всё так же дают `400 invalid_body`: эта проверка выполняется в `json.decodeFromJsonElement` и `toCommand`.

## Risks / Trade-offs

- **[Случайная очистка]** Клиент, который передаёт `null` по ошибке, очистит поле. → Именно так клиент и задумывался: он всегда передаёт полное значение. Других клиентов этих маршрутов нет: CLI пишет через импорт конфигурации, а не через эти маршруты.
- **[Расхождение с остальными маршрутами]** Правило «`null` запрещён» перестаёт быть общим. → Исключение ограничено полями значения свойства и описано в спецификации.

## План проверки и развёртывания

- Тесты маршрутов в `feature-components`:
  - `PATCH` с `{ tokenId, value: null, adjustment: null }` обновляет токен;
  - `PATCH` с `{ tokenId: null, value: "48" }` переводит значение на сырое;
  - `POST` с `null`-полями создаёт значение;
  - `stateSetId: null` по-прежнему даёт `400`.
- `cd backend-kt && ./gradlew build` с `JAVA_TOOL_OPTIONS=-Dapi.version=1.44`.
- Ручная проверка на локальном стеке: правка цвета `Chip` в редакторе сохраняется и видна после перезагрузки.
- Бэкенд на стендах выкладывается вручную, после влития.
