## Контекст

Сейчас в `ds-service` DS-зависимыми уже являются стили (`styles.design_system_id`), оформления
(`appearances.design_system_id`), объявления осей оформления и их версионные ревизии. Не принадлежат
дизайн-системе только две таблицы: `variations (component_id, name, description)` и
`property_variations (property_id, variation_id)`. Оформление ссылается на общую запись оси через
`appearance_variations.variation_id`; для видимого имени оси в редакторе уже введён обходной путь
`display_name` (миграция `V12`). Запись `variations` не версионируется.

```mermaid
erDiagram
    COMPONENT ||--o{ VARIATION : "было: общий каталог"
    DESIGN_SYSTEM ||--o{ VARIATION : "станет: владеет"
    VARIATION ||--o{ STYLE : "значения"
    VARIATION ||--o{ APPEARANCE_VARIATION : "объявление"
    VARIATION ||--o{ PROPERTY_VARIATION : "связь со свойством"
```

## Цели / Вне целей

**Цели:** собственные оси у каждой дизайн-системы; изоляция записи, переименования и удаления оси;
безопасная миграция действующих данных.

**Вне целей:** отмена `display_name`; копирование осей между дизайн-системами через API.

## Решения

1. **Владелец оси — дизайн-система.** `variations.design_system_id uuid NOT NULL`, внешний ключ на
   `design_systems`, уникальность `(design_system_id, component_id, name)` вместо
   `(component_id, name)`, дополнительный `UNIQUE (id, design_system_id)`.
   Альтернатива — оставить общий каталог и хранить состав осей в оформлении: отклонена, потому что
   имя и описание оси, связи со свойствами и стили всё равно общие, а это и есть проблема.
2. **Ссылки проверяются составными ключами.** `appearance_variations`, `styles`,
   `component_reuse_configs` и `property_variations` ссылаются на ось через пару
   `(variation_id, design_system_id)`; для `property_variations` добавляется `design_system_id`,
   наследуемый от оси. Так база не допускает оформления одной системы с осью другой.
3. **Миграция размножает оси.** Для каждой существующей оси определяется множество дизайн-систем,
   которые её используют (через `styles`, `appearance_variations`, `component_reuse_configs`) или
   связаны с компонентом (`design_system_components`). Исходная запись переходит первой по порядку
   создания дизайн-системе, для остальных создаются копии с новыми `id`. На копии переносятся
   `property_variations` и все ссылки соответствующей дизайн-системы, включая ревизии
   (`appearance_variation_revisions`, значения осей и роли `root_variation_id`/
   `color_scheme_variation_id`). Ось без единой дизайн-системы-пользователя удаляется.
   Триггеры неизменяемости ревизий отключаются на время переноса, как в `V12`.
4. **Импорт и сиды.** `upsertAxes` и `ambiguousName` ищут ось по `(design_system_id, component_id,
   name)`; `component-seeds.json` загружается в дизайн-систему `base` без изменения формата файла.
5. **Запись оси версионируется по образцу стилей.** Таблица `variations` остаётся стабильной
   (`id`, `design_system_id`, `component_id`, `created_at`), а `name`, `description` и `deleted`
   переезжают в `variation_revisions` (`variation_id`, `design_system_version_id`,
   `version_sequence_number`, `name`, `description`, `deleted`). Текущие данные переносятся в ревизию
   исходной версии. Читатели получают значения через разрешённое представление
   `ResolvedRevisionTable` для версии чтения; в Exposed `VariationsTable` становится разрешённым
   представлением, а запись идёт в `StableVariationsTable` и `VariationRevisionsTable`. Уникальность
   имени оси `(design_system_id, component_id, name)` обеспечивается так же, как для стилей
   (`style_resolved_name_unique`): индексом на разрешённом состоянии, с проверкой в миграции целостности.
   В `ComponentDraftChangeHandlers` добавляется обработчик `variation`. Откат создания оси невозможен,
   пока на неё ссылаются живые стили или объявления: это обеспечивают отложенные составные внешние
   ключи, а журнал превращает нарушение в конфликт `409`. Строка оси, созданная в отброшенном черновике, не остаётся
   неиспользуемой: она исчезает вместе с черновиком.
   Альтернатива — оставить ось техническим ключом без ревизий: отклонена, потому что переименование
   и удаление оси при собственности дизайн-системы становятся изменениями её модели и обязаны попадать
   в журнал, публикацию и откат; иначе правка оси обходит черновик. `displayName` оформления
   сохраняется как версионируемая подпись оси внутри оформления.
6. **Все места записи оси переводятся на систему**: `ComponentConfigImporter.upsertAxes`,
   `AppearanceEditorAxisOperations.newVariation` (теперь создаёт ось и её ревизию в черновике), `AppearanceEditorConfigurationOperations`,
   `GeneratedDesignSystemComponentInitializer` и `ExposedComponentModelRepository`.
7. **Клиенты передают `designSystemId`.** `js/apps/client` строит `variationByName` по ответу
   `GET /components/{id}/variations`; при нескольких системах одноимённые оси перезаписали бы друг
   друга. Клиенты `js` и `frontend-kt` читают вариации с `?designSystemId=`, фильтр применяется на
   сервере. Это единственное изменение клиентов; редактор и генераторы не затрагиваются.
8. **API.** `POST /ds/variations` принимает `designSystemId`; `GET /ds/variations` и
   `GET /ds/components/{id}/variations` принимают необязательный `designSystemId`, ответ несёт
   `designSystemId`. Доступ проверяется по владению дизайн-системой проектом
   (`ComponentOwnership.readableDesignSystem/writableDesignSystem`), а не только по компоненту.
   Ограничение «`PATCH` имени только системному администратору» снимается.

## Риски / Компромиссы

- Право записи в ось определяется владением её дизайн-системы и не зависит от того, что тот же компонент
  подключён к системам других проектов (в отличие от прежних проверок записи компонента).
- Миграция удаляет оси компонентов, которые не использует ни одна дизайн-система (ни стили, ни объявления в
  оформлениях, ни reuse-конфигурации, ни роли осей) и компонент которых не подключён ни к одной системе.
  Такие оси возможны только после прямого `POST /ds/variations` для неподключённого компонента. Страховка:
  резервная копия БД перед выкатом и запрос, считающий такие оси (на проверенной локальной БД их 0).
- Составные ключи связывают ось с дизайн-системой, но не проверяют, что ось принадлежит тому же компоненту,
  что и ссылающаяся запись; так было и до изменения, проверку компонента делает прикладной слой.
- Связи `property_variations` остаются неверсионируемыми и пишутся напрямую, мимо черновика и журнала; в
  журнал входит сама ось, но не её связи со свойствами.
- Удаление оси по HTTP не открыто (маршрута `DELETE /ds/variations/{id}` нет); логика мягкого удаления в
  репозитории готова, но недостижима из API и в этом изменении не расширяется.
- Удаления дизайн-системы в прикладном коде нет, поэтому каскадное удаление осей отдельно не проверяется.
- Переименование оси проверяет совпадение с действующими именами других осей в оформлениях, где ось не
  переименована; полная проверка значений осей остаётся за редактором.
- Версионирование оси затрагивает разрешённое представление, триггеры неизменяемости ревизий,
  проверки целостности `V8` и обработчик черновика: ошибка в любом из них ломает все чтения
  `VariationsTable`. Риск снижается тем, что образец уже работает для `styles`, а интеграционные тесты
  целостности дополняются осью.
- Размножение осей увеличивает число строк в `variations` и `property_variations` примерно в число
  дизайн-систем на компонент; на текущих объёмах приемлемо.
- Если после миграции дизайн-системы разойдутся по именам осей, глобальное сопоставление «ось
  компонента в разных системах» пропадёт; экспорт и импорт между системами идут по именам и не
  затрагиваются.
- Ревизии неизменяемы: ошибка переноса ссылок исправима только новой миграцией, поэтому миграция
  проверяется интеграционным тестом на данных с несколькими дизайн-системами и ревизиями.
- Клиенты `frontend-kt` и `js/apps/client` читают `GET /components/{id}/variations` и
  `GET /variations`. Без параметра чтение совместимо по форме (массив с добавленным полем
  `designSystemId`), но неразличимо по системам; поэтому клиенты переводятся на `designSystemId`
  в этом же Change (решение 7). Сторонние клиенты без параметра увидят дубли имён осей.
  Вызовов `POST /ds/variations` в клиентах нет.

## План миграции

1. Применить `V14` (добавить столбец, размножить, проставить `NOT NULL`, пересоздать индексы и
   ключи); обновить отпечаток схемы и счётчики в проверках.
2. Развернуть `ds-service`; общий каталог после миграции больше не существует.
3. Откат: восстановление из резервной копии БД до применения `V14`; обратной миграции нет.

## Программное проектирование

```kotlin
data class ComponentVariationSummary(
    val id: UUID, val componentId: UUID, val designSystemId: UUID,
    val name: String, val description: String?,
)

internal object StableVariationsTable : Table("variations")         // id, design_system_id, component_id
internal object VariationRevisionsTable : Table("variation_revisions") // entityId, version, name, description, deleted
internal object VariationsTable : ResolvedRevisionTable(...)         // разрешённое чтение

interface ComponentModelRepository {
    data class VariationCreate(
        val designSystemId: UUID, val componentId: UUID, val name: String, val description: String?,
    )
    suspend fun listVariations(projectId: ProjectId, systemAdmin: Boolean, designSystemId: UUID?): List<ComponentVariationSummary>
    suspend fun listComponentVariations(projectId: ProjectId, systemAdmin: Boolean, componentId: UUID, designSystemId: UUID?): List<ComponentVariationSummary>
}
```

## Проверка на локальных данных

`setup-local.sh` засевает единственную дизайн-систему `base`, поэтому одной засеянной БД недостаточно
для размножения осей. Проверка идёт на данных, оставшихся от старой схемы: контур поднимается на
`origin/dev`, во вторую дизайн-систему добавляются те же компоненты, экспорты конфигураций
сохраняются, затем `ds-service` пересобирается с `V14` (без `--reset`, данные тома сохраняются), и
экспорты сравниваются.
