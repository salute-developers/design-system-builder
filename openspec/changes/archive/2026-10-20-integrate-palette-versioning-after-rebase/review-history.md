## Результаты валидации замечаний

### R1. Изменение тела повторяемого шага компонента — подтверждено

[Комментарий raininforest](https://github.com/salute-developers/design-system-builder/pull/109#discussion_r4334129563).
`componentRepository.ts:345` пересчитывает позицию по заново прочитанным значениям оси.
Если привязка уже сохранилась, а следующий шаг упал, повтор отправляет другую позицию
с прежним ключом. `IdempotentCreateExecutor` отклоняет несовпадение тела как
`IDEMPOTENCY_KEY_REUSED`. Нужно сохранять тело/результат шагов, в том числе для восстановления.
Статус: открыт, задача 6.2.

### R2. Очередь закрытой сессии — подтверждено с уточнением последствия

[Комментарий raininforest](https://github.com/salute-developers/design-system-builder/pull/109#discussion_r4334139777).
`ThemeEditorSession.ts:162` вызывает flush без остановки очереди. Повторы продолжаются,
а `send` не проверяет закрытие. Проверка предметных ревизий защищает от безусловной
перезаписи более свежего подтверждённого серверного значения; такую перезапись отдельно
не воспроизводили. Подтверждён другой опасный путь: старый `confirmed` проверяет только
свою карту поколений, затем удаляет общий локальный черновик и метаданные уже новой сессии
(`ThemeEditorSession.ts:503–510`, `designSystemDraft.ts:331–333`).
Статус: открыт, задача 6.3.

### R3. Общая строка черновика при SERIALIZABLE — подтверждено с оговоркой

[Комментарий vkaltyrin](https://github.com/salute-developers/design-system-builder/pull/109#discussion_r4334205267).
Финальная функция `bump_design_system_draft_revision` (`V7:2547`) обновляет общую строку.
`ExposedTransactionRunner` выполняет записи в `SERIALIZABLE`, но повторяет `40001`/`40P01`
до трёх попыток. Поэтому неизбежны конкуренция и лишние повторы, а не ошибка каждого
запроса пользователю. Частота окончательных отказов нагрузочным замером не подтверждена.
Выбран вариант 2; детализация — `review-followup-design.md`.
Статус: проектное решение подготовлено, реализация не начата; задачи 6.6–6.7.

### R4. Потеря ограничений уникальности — подтверждено

[Комментарий vkaltyrin](https://github.com/salute-developers/design-system-builder/pull/109#discussion_r4334205282).
`DROP COLUMN ... CASCADE` удаляет связанные ограничения, а индексы одной редакции на UUID
не защищают логические слоты разных UUID. Подтверждены потеря уникальности имени ДС,
компонентных значений одного слота и ряда позиций. Не все старые индексы потеряны:
ограничения неизменяемых отношений частично остаются, у палитры есть отдельный валидатор.
Статус: открыт, задачи 6.1 и 6.8.

### R5. Принадлежность state set компоненту — подтверждено

[Комментарий vkaltyrin](https://github.com/salute-developers/design-system-builder/pull/109#discussion_r4334205288).
`V7:1266–1268` удаляет `vpv/ipv/scm_state_set_coherent`. Проверки чтения связанных
объектов по отдельности не гарантируют одного компонента. Значению компонента A может
быть назначен доступный state set компонента B. FK проверяет существование, не этот инвариант.
Статус: открыт, задачи 6.1 и 6.8.

### R6. Миграция и её проверки — частично подтверждено

[Комментарий vkaltyrin](https://github.com/salute-developers/design-system-builder/pull/109#discussion_r4334205295).
Повторные определения функций и создание с удалением триггеров в одной V7 существуют;
самостоятельный функциональный дефект только этим не доказан. Одновременный перенос и
удаление столбцов соответствует последнему согласованному design интеграции, хотя более
ранний design описывал несколько миграций. Есть проверка количества перенесённых строк,
тесты заполненной схемы V6, палитры, ролей осей и компонентного экспорта. Формулировка
«почти без данных» слишком широкая. Реальный пробел — регрессионные сценарии потерянных
ограничений и межкомпонентной согласованности.
Решение: не переписывать уже применённую V7 ради косметической очистки; добавить новые
исправления следующей миграцией и расширить проверки. Автоматический repair/сброс не выполнять.
Статус: открыт в подтверждённой части, задача 6.8.

### R7. Конфликт имён токенов при отмене — подтверждено

[Комментарий vkaltyrin](https://github.com/salute-developers/design-system-builder/pull/109#discussion_r4334205303).
Общий `ExposedDraftChangeHandler.revert` удаляет редакцию черновика, восстанавливая
унаследованное состояние. Проверки уникальности итогового имени токена нет; индекс
`token_revisions_version_name_unique` действует в пределах одной версии, не разрешённого
состояния из нескольких границ. Возможны два активных одинаковых имени после отмены
удаления либо переименования. Клиентская карта имя → id скрывает одну запись.
Статус: открыт, задача 6.1.

### R8. Ложный отказ после успешной структурной операции — подтверждено

[Комментарий vkaltyrin](https://github.com/salute-developers/design-system-builder/pull/109#discussion_r4334205310).
`refreshStructure` ждёт все очереди до 30 секунд, палитра — до 8 секунд. Состояние `error`
другой очереди не считается завершением. Операция уже сохранена сервером, но обновление
не выполняется, а пользователь видит ошибку изменения и старое дерево/палитру.
Статус: открыт, задача 6.4.

### R9. Виртуализация большого журнала — подтверждено

[Комментарий neretin-trike](https://github.com/salute-developers/design-system-builder/pull/109#issuecomment-6310628462).
В `VersionJournalPages.tsx:510` и списке истории используются обычные `map`; все строки
попадают в DOM. Разбиение по параметрам и платформам увеличивает количество записей
намеренно. Причина именно показанного на скриншоте набора из тысяч изменений не установлена:
нужно проверить исходные данные, а не объявлять все эти записи ошибочными.
Статус: открыт, задача 6.5.

### R10. Много запросов и долгая загрузка — подтверждён путь избыточной работы

[Комментарий neretin-trike](https://github.com/salute-developers/design-system-builder/pull/109#issuecomment-6310696826).
`loadThemeEditor` загружает все связанные компоненты; `loadComponentData` отдельно
читает свойства, оси и стили каждой оси. Ограничитель параллельности и темпа запросов
не уменьшает их количество. При большом каталоге это даёт длительную загрузку.
Приведённая ревьюером минута и объём переданных данных в этой сессии не замерялись;
их нельзя выдавать за собственные измерения.
Статус: открыт, задачи 6.5 и 6.10.
