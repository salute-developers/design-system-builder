## Контекст

Архивы CLI уже доступны через GitHub Releases. Публичные адреса установщиков в S3 возвращают HTML,
а внешняя конфигурация nginx недоступна. Пользователь запросил перенести оба установщика в GitHub Releases.

## Решения

- Подготовленные `install.sh` и `install.ps1` становятся двумя дополнительными файлами полного комплекта
  GitHub Release. В них сохраняется встроенный адрес репозитория и выбор GitHub Latest либо явной версии.
- Новый выпуск остаётся черновиком до проверки архивов и точного совпадения скачанных установщиков
  с подготовленными из исходников выбранного тега. Workflow больше не использует AWS или S3.
- Для опубликованного выпуска сначала проверяются прежние архивы и метаданные. Затем добавляются
  только отсутствующие установщики без `--clobber`, и проверяется полный комплект. Существующие
  файлы не заменяются; ошибка либо несовпадение прерывает процесс. Latest при повторе не меняется.
- Старые S3-объекты и вспомогательный инструмент их загрузки не удаляются: изменение не должно
  затрагивать раздачу веб-клиента. В рабочем процессе выпуска S3 больше не участвует.

## Миграция и риски

Ссылки установки: `https://github.com/salute-developers/design-system-builder/releases/latest/download/install.sh`
и аналогичная ссылка `install.ps1`. Для закреплённого тега используются `/releases/download/cli-vX.Y.Z/`.
Старые ссылки Plasma не перенаправляются без доступа к nginx. При откате Latest следует выбирать
релиз, в который уже загружены оба установщика. Частичное добавление скриптов восстанавливается повтором.

## Проверка и выпуск

До PR: Python-тесты комплектности, восстановления черновика, добавления скриптов в опубликованный
релиз, сохранения архивов и Latest, отказа при несовпадении, FAST, независимое review и FULL.
После слияния: перенести релизный тег по отдельному запросу, выполнить workflow и проверить HTTP 200
и содержимое обоих `/releases/latest/download/install.*`. Публикация в GitHub не выполняется при создании PR.
