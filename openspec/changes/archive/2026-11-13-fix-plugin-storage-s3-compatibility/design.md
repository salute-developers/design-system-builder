## Контекст

Публикация плагина на DEV падает на записи файлов в SberCloud OBS (`obs.ru-moscow-1.hc.sbercloud.ru`, path-style).

Что уже проверено:
- пробная публикация проходит: хранилище настроено, авторизация публикатора работает;
- запись в этот бакет и префикс через Cyberduck работает, файлы доступны по адресу, значит ключ и права в порядке;
- регион исправлен на `ru-moscow-1`, это не помогло;
- выкладка клиента в тот же бакет работает через `s3cmd` с подписью V2.

ds-service пишет в S3 через AWS SDK 2.32.24 (`S3Client`, `UrlConnectionHttpClient`, подпись V4). Начиная с 2.30 SDK по умолчанию считает CRC32 для каждого `PutObject`: тело уходит в формате `aws-chunked`, а контрольная сумма — в завершающем заголовке (`x-amz-trailer`). Ошибку записи `PublishPluginBuildUseCase.upload` перехватывает и превращает в `503` без лога, поэтому точную причину сейчас не увидеть.

## Цели / Вне целей

**Цели:**
- запись файлов плагинов в S3-совместимые хранилища без расширений SDK, которые они не поддерживают;
- причина ошибки записи видна в логе ds-service.

**Вне целей:**
- клиент S3 `documentation-service`;
- подпись V2: SDK v2 её не поддерживает, а подпись V4 OBS принимает;
- изменение ответа публикации.

## Решения

### 1. Контрольные суммы — только там, где их требует операция

`S3Client` хранилища плагинов собирается с `requestChecksumCalculation(WHEN_REQUIRED)` и `responseChecksumValidation(WHEN_REQUIRED)`. Так SDK вёл себя до 2.30: `PutObject` уходит обычным телом с `Content-Length`, без `aws-chunked` и `x-amz-checksum-*`. Контрольная сумма остаётся у операций, где она обязательна по протоколу (например, `DeleteObjects`). Это рекомендация AWS для сторонних S3-совместимых хранилищ.

Альтернативы:
- **Понизить SDK до 2.29.** Отклонено: SDK общий для `documentation-service`, к тому же мы потеряли бы исправления.
- **Отдельная настройка окружением.** Отклонено: значение по умолчанию у SDK вредно для любого хранилища, кроме AWS, а хранилища плагинов на стендах и локально — не AWS.

Изменение относится к настройке клиента в `ds-service/runtime` (сборка инфраструктуры), слои `application` и `domain` не меняются.

### 2. Лог ошибки записи в хранилище

`S3PluginBuildStorage.putFile` перехватывает `SdkException`, пишет `WARN` с бакетом, ключом и сообщением SDK (вместе с исключением) и пробрасывает его дальше. Use case по-прежнему отвечает `503`. Лог пишется в слое `data`, рядом с вызовом S3: у use case нет бакета и ключа. В сообщениях SDK нет секретного ключа и подписи, есть код ошибки и ответ хранилища.

## Риски / Компромиссы

- **[Риск] Гипотеза не подтвердится.** Причина может оказаться в другом: например, OBS не принимает path-style для этого бакета, или прокси между стендом и OBS режет запросы. → Лог из решения 2 покажет точный ответ хранилища после первой же неудачной публикации. Проверка на DEV — внешняя задача до архивирования.
- **[Компромисс] Без контрольной суммы целостность записи проверяется только по `Content-MD5`/ETag хранилища.** Для статики плагина, которая публикуется заново целиком, этого достаточно.
