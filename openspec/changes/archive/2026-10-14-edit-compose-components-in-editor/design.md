## Context

Редактор получает компоненты одним запросом `component-configs` и строит меню по фиксированному
списку web-имён (`menuItems.ts`), сопоставляя их с конфигами по имени. Legacy-ответ уже содержит
`platformMappings.compose` для каждого свойства, а черновик preview берёт Compose-параметры именно
оттуда (`draft.ts`). Значит для Compose-компонента, свойства которого импортированы с
Compose-параметрами, payload собирается существующим кодом.

## Goals / Non-Goals

**Goals:** показать Compose-компоненты, отрисовать каждый плагином, сохранить прежнее поведение для
web и генератора.

**Non-Goals:** маппинг web→Compose; изменения Preview Protocol и плагина; редактор значений для
платформ кроме `web` и `compose`; отдельная модель «платформа дизайн-системы».

## Decisions

1. **Платформа — параметр запроса, а не отдельный endpoint.** Параметр необязателен и по умолчанию
   `web`: так генератор и текущий клиент не меняются. Это сознательное исключение из правила
   «платформа указывается явно» (`component-platform-model`), потому что endpoint legacy и его
   потребители заморожены; новый клиент платформу всегда передаёт.
2. **Идентичность компонента — `(platform, name)`.** Клиент хранит Compose-конфиги отдельным
   набором и ищет их в нём; меню строится для Compose из самих конфигов (список имён не
   фиксирован), без жёсткого каталога.
3. **Привязка выводится, а не хранится.** Имя Compose-компонента в API-мете равно `componentName`
   плагина (в `compose-preview-core-components` так и устроено), поэтому
   `componentId = storyId = name`. Если имени нет в манифесте, редактор открывается без preview и
   с диагностикой.
4. **Платформа — переключатель, а не группа меню.** Compose — не категория компонентов, а платформа,
   поэтому над списком стоит `SegmentButton` «Платформа», видимый только при нескольких платформах; список
   Compose раскладывается по группам явным соответствием имён (имена Compose частично отличаются от web:
   `BasicButton` и `Button`, `CheckBox` и `Checkbox`; есть собственные, например `AiAnswer`), с запасной группой «Other». Платформа определяется маршрутом
   (`compose-<Имя>`). Compose-компоненты видны только при заданном URL плагина и совместимом окружении, иначе клиент
   ведёт себя как сейчас.
5. **Локальный контур:** импорт меты и привязка выполняются через уже существующий admin-endpoint
   `import-api-meta` и API связей дизайн-системы; скрипт опционален и не меняет схему.

## Risks / Trade-offs

- Свежеимпортированные Compose-компоненты не имеют вариаций, стилей и значений: preview будет
  дефолтным, пока значения не заведены. Это данные, а не код; редактирование значений и их
  сохранение должны работать по тем же ручкам, что и web (проверяется в задаче 4).
- Один и тот же `name` у web и Compose: любой клиентский код, ключующийся по имени, требует
  аудита (меню, роутинг, сохранение, кэши).
- Токены темы хранятся по платформам `web|android|ios`; Compose использует `android`. Если у
  дизайн-системы нет `android`-значений, preview покажет диагностику `missing_token`.

## Open Questions

- Должны ли Compose-компоненты жить в той же дизайн-системе, что и web, или в отдельной? Предлагается
  та же: `design_system_components` уже позволяет, а платформа определяется компонентом.
- Достаточно ли `platform=compose` для редактора, или нужен отдельный раздел навигации верхнего
  уровня? Предлагается группа меню.

## Результаты проверки

Локальный контур: импорт меты (79 компонентов, 1275 свойств) и привязка к `base`. В редакторе
(Chrome-совместимый браузер, Vite) все 79 Compose-компонентов открываются через платформу Compose и
возвращают `success` без диагностик. Визуально проверены `BasicButton`, `Avatar`, `Switch`.

- Свежеимпортированные компоненты не имеют вариаций, стилей и значений, поэтому рисуются дефолтным
  стилем: например `Avatar` в тёмной теме почти не виден. Правка свойств не меняет результат, пока
  значения не заведены. Это данные, не код.
- Найден и исправлен цикл render: у компонента без story `useStory` отдавал новый пустой
  `storyArgs` на каждый render, и эффект `useComponentData` зацикливался (preview застревал в
  `rendering`). Теперь ссылка стабильна, есть регресс-тест.

### Импорт стилей и найденные дефекты клиента

Стили Compose-компонентов загружены командой `dsbuilder components push --platform compose` из
`plasma-android/tokens/sdds.serv.compose/build/theme-builder/components` (144 конфигурации: 143
созданы, 1 отклонена: в мете компонент называется `ModalBottomSheet`, в конфигурации `bottom-sheet`).
Конфигурации есть у 73 из 79 компонентов. После импорта вскрылись три дефекта клиента:

- `getPropList` падал на значении стиля, тип которого отсутствует среди свойств API выбранной
  вариации, и редактор показывал белый экран.
- Свойство типа `value` (имя константы enum, например `iconPlacement=start`) уходило в payload как
  ссылка на токен, а не как литерал. Из-за этого 22 компонента не рендерились.
- Токены `gradient` и `shadow` не попадали в черновик, хотя ассемблер их нормализует.

После исправлений 78 из 79 компонентов рендерятся без диагностик. Не рендерится `Switch`: его
конфигурация ссылается на токен `surface.on-dark.solid.default`, а в `base` он называется
`surface.on-dark.solid-default`. Это расхождение именования токенов web и Compose; `base` заведена
для web, и отчёт `push` перечисляет 33 неразрешённые ссылки на токены. Решается данными (дизайн-система
с Compose-токенами), а не клиентом.

### Сбой плагина

Исключение при layout/draw (воспроизведено: `Height = 900000000` у `BasicButton`) останавливает
Compose. Раньше плагин сообщал `success` до отрисовки, поэтому хост не знал о сбое, а превью залипало
на последнем кадре. Теперь успех приходит после отрисовки (change `confirm-preview-render` в
plasma-android), а хост по `render_crashed`, `plugin_crashed` или таймауту запроса перезагружает iframe.
Остановленный Compose не оживить иначе, чем перезагрузкой.

### Сочетания стилей и вложенные стили

Жалоба: `ButtonGroup` не стилизуется, `shape` не меняет скругления, компоненты с вложенными компонентами
выглядят неправильно. Причина — две не поддержанные клиентом части модели:

- `combinations`: значения свойств для сочетаний стилей разных вариаций. У `ButtonGroup` скругления и
  отступ лежат только в сочетаниях (`shape × size × gap`), у стилей `shape` собственных значений нет. 28
  компонентов, 436 сочетаний. Клиент их не читал.
- Ссылки на стили других компонентов (`component_style`, значение `basic-button.xxs.default`). `Props` отбрасывал
  такие свойства, поэтому вложенные стили не передавались вовсе. Формат: имя конфигурации целевого компонента и
  имена его стилей (по порядку вариаций, остальные берут значение по умолчанию).

Редактирование сочетаний и ссылок в панели не реализовано: они только читаются и участвуют в preview.

После изменений дополнительные компоненты стали упираться в токен `surface.on-dark.solid.default`
(`Cell`, `ComboBox`, `Select`, `SelectItem`, `Switch`): в `base` он называется `surface.on-dark.solid-default`.
Это то же расхождение имён токенов Compose и web, что и раньше; клиентом не решается.

`TextSkeleton` останавливает плагин (`IllegalStateException: Only Sp can convert to Px`): его конфигурация
не задаёт `textStyle`, а компонент считает высоту по `lineHeight`. Данные, не код; сбой обнаруживается и
показывается с причиной.

### Токены sdds-serv

Проверено сравнением, а не предположением: токены `base` совпадают с темой `sdds_serv` 0.10.0 (архив в
`theme-converter`) по всем типам и платформам, а 1517 цветов с HEX-значениями совпадают побайтно со значениями
Kotlin-модуля `sdds.serv.compose` (`ColorTokens.kt`). Отсутствуют только 72 `syntax.*`-цвета в обоих режимах; в
Kotlin-модуле их тоже нет. Импорт токенов ничего не меняет.

Расхождение другое: из 94 токенов, на которые ссылаются Compose-конфигурации, два записаны с точкой вместо
дефиса (`surface.on-dark.solid.default` вместо `solid-default`, `surface.default.transparent.tertiary` вместо
`transparent-tertiary`). Это ошибка в генерации конфигураций в plasma-android. Ассемблер находит токен по имени без
учёта разделителей, если такое имя единственное; неоднозначное имя токеном не считается.
