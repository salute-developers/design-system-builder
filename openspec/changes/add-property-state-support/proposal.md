## Зачем

Редактор компонентов разрешает добавить состояние только цветовому свойству, в имени которого нет `focus`. Это
эвристика: она не знает, что у Compose `DropZone.paddingStart` или `titleStyle` принимают значения по состояниям
(`StatefulValue`), а у многих цветовых свойств состояний на платформе нет. Из-за этого дизайнер либо не может задать
состояние, которое код компонента поддерживает, либо задаёт состояние, которое генерация молча проигнорирует.

Мета платформ вместе со знанием о генераторах говорит, в каких состояниях можно выразить значение свойства, но эти
сведения теряются в CLI и не доходят до модели `ds-service`. Признак нужно перенести из меты в глобальный слой
компонентов и сделать его источником правды для редактора и для проверки записи.

## Что меняется

- У свойства компонента появляется признак поддержки состояний `stateSupport`: список состояний, которые генератор
  платформы выражает для этого свойства, и флаг `combinations` — допустимы ли сочетания. Список хранится по
  идентификаторам состояний в пределах компонента (`property_supported_states`), флаг — в
  `properties.state_combinations`; у свойств, заведённых до изменения, признак не задан (`null`).
- Нормализаторы `dsbuilder components import-api` выводят признак по правилам платформы:
  - Compose — перегрузки `StatefulValue`/`InteractiveColor` и состояния, которые знает генератор;
  - View — тип свойства, состояния framework, `stateSets` и `stateValues`;
  - SwiftUI — типы `Stateful*` и поле `state`;
  - web — точный список состояний токенов, без сочетаний.

  Манифест передаёт признак полем `stateSupport` свойства.
- Импорт API-меты разрешает имена состояний в пределах компонента, записывает признак у новых свойств и обновляет его
  у существующих, как статус устаревания алиаса. Отчёт получает счётчик `stateSupportChanged` и список
  `unresolvedStates`. Манифест без поля (прежние версии CLI) признак не меняет.
- `ComponentPropertySummaryResponse` отдаёт `stateSupport`; `editor-bundle` дополнительно отдаёт `states` — общие
  состояния и состояния этого компонента с идентификаторами.
- Все операции записи значения отклоняют недопустимый набор состояний: `POST`/`PATCH` `invariant-property-values` и
  `variation-property-values` (автосохранение) и `PUT property-values`. Состояние, не поддерживаемое признаком,
  отклоняется кодом `422 states_not_supported`, состояние чужого компонента — кодом `422 state_not_in_component`.
  Свойство с незаданным признаком ограничивается только принадлежностью состояний компоненту. Импорт конфигураций,
  копирование конфигурации и удаление значений не ограничиваются.
- Билдер показывает кнопку «Добавить состояние» и строки состояний у свойства любого типа, в признаке которого есть
  состояния, с тем же контролом, что у базового значения. Меню предлагает ровно состояния из признака, а при запрете
  сочетаний даёт выбрать только одно. Клиент разрешает имена состояний и ищет наборы по идентификаторам в пределах
  компонента. Для свойства без признака сохраняется прежнее поведение (цвет без `focus` в имени,
  `hovered`/`pressed`/`focused`). Уже записанные недопустимые состояния видны только для чтения и удаляются.

## Возможности

### Новые возможности

- `component-property-state-support`: признак поддержки состояний свойства компонента (список и флаг сочетаний),
  его хранение, принадлежность состояний компоненту и правило допустимого набора.

### Изменяемые возможности

- `component-api-meta-import`: поле `stateSupport` манифеста, разрешение имён в пределах компонента, обновление
  признака импортом, `stateSupportChanged` и `unresolvedStates`.
- `cli-components`: вывод признака нормализаторами платформ, передача в манифест и печать отчёта.
- `component-editor-bundle-api`: `stateSupport` у свойств и список `states` в `editor-bundle`.
- `component-editor-operations`: проверка набора состояний на всех маршрутах записи значения, включая автосохранение.
- `component-editor-workbench`: состояния у свойств любого типа по признаку вместо цветовой эвристики, работа с
  состояниями по идентификаторам компонента.

## Влияние

- `backend-kt/ds-service`:
  - Flyway-миграция `V21`: столбец `properties.state_combinations` и таблица `property_supported_states`;
  - `PropertiesTable`, `ComponentPropertySummary`/`ComponentPropertySummaryResponse`;
  - импорт API-меты: `ImportApiMetaRequest`, `ImportApiMeta`, `ExposedApiMetaRepository`, `ImportApiMetaResponse`;
  - `editor-bundle`;
  - проверка набора `PropertyStateSetGuard` в записи invariant- и variation-значений и в
    `AppearanceEditorValueOperations`;
  - `openapi/documentation.yaml`, тесты.
- `frontend-kt/feature-components`: `ApiMetaProperty`, четыре нормализатора и списки состояний генераторов, сетевой формат
  `HttpApiMetaRemoteSource`, `ApiMetaImportReport` и печать отчёта в `:cli`, корпуса и тесты, `API_META_NORMALIZERS.md`,
  `cli/USAGE.md`.
- `js/apps/client`: DTO бандла и `ComponentAPI`, `StateBindingMenu`, `InspectorPropertyRow`, тип `PropState`,
  разрешение состояний и наборов в `componentRepository`, тесты.
  `js/cli` и `js/apps/preview-web-plugin` не меняются.
- Данные: после выкатки признак появляется у свойств только после повторного `import-api` по каждой платформе; до
  этого редактор работает по прежней эвристике.
