## Почему

Редактор DS Builder хранит незавершённые изменения в `localStorage`, поэтому сервер не является источником актуального
черновика, параллельная работа пользователей может незаметно перезаписывать данные, а опубликованные состояния нельзя
открыть через предметные API. Требуется единая серверная модель версий, которая сохраняет только фактические изменения,
поддерживает безопасное автосохранение и позволяет получить журнал отличий без копирования всей дизайн-системы.

## Что изменится

- `backend-kt/ds-service` станет владельцем общего серверного черновика и независимых опубликованных версий
  дизайн-системы.
- Предметные данные дизайн-системы будут храниться как устойчивые сущности и типизированные редакции, действующие с
  определённой временной границы; неизменившиеся строки при публикации копироваться не будут.
- Существующие изменяющие API получат технические редакции сущностей и полей, автоматическое объединение изменений
  разных полей и правило «последняя запись побеждает» для одного поля.
- Редактор будет автоматически сохранять изменения на сервере; `localStorage` останется только для неподтверждённых
  запросов и их технических данных.
- Появится вычисляемый журнал различий активного черновика или опубликованной версии относительно предыдущей
  опубликованной границы, а также единая операция отката чернового изменения.
- Публикация будет переводить общий черновик в неизменяемую версию с номером `major.minor.patch` и создавать следующий
  пустой черновик без копирования предметных данных.
- Предметные API чтения смогут возвращать состояние выбранной опубликованной версии для режима просмотра редакторов.
- Для небезопасных повторных запросов появится хранение результатов по ключу повторяемости.
- **BREAKING**: публичная группа `/api/ds/design-system-changes` и изменение либо удаление опубликованных версий через
  `PATCH` и `DELETE` будут удалены; контракт публикации перестанет принимать клиентские снимки и серверные поля статуса.
- Новые предметные операции токенов и компонентов, палитра, показ предупреждений о параллельной перезаписи и
  присутствие пользователей не входят в изменение.

## Возможности

### Новые возможности

- `design-system-version-history`: независимые временные границы, публикация и предметное чтение старых версий.
- `multi-user-design-system-editing`: серверное автосохранение и согласование параллельных изменений на уровне
  логической сущности и поля.
- `design-system-change-journal`: вычисляемый журнал отличий черновика и опубликованных версий с безопасным откатом.

### Изменяемые возможности

- `design-system-model-api`: предметное чтение токенов и компонентов получает выбор опубликованной версии и переносится
  на целевую модель `backend-kt/ds-service`.
- `tenant-aware-theme-editor`: локальные черновики и конфликт всего tenant заменяются серверным автосохранением и
  согласованием изменений отдельных логических значений.
- `theme-lifecycle`: создание, изменение и удаление tenant становятся изменениями общего черновика дизайн-системы без
  появления отдельной версии темы.

## Влияние

- **`backend-kt/ds-service`**: предметная модель, прикладные сценарии, хранилища PostgreSQL, миграции, транзакции,
  публикация, журнал, откат и публичный OpenAPI-контракт.
- **Веб-редактор в `js/`**: переход с хранения предметных данных в `localStorage` на серверное автосохранение, чтение
  журнала, откат, публикация и режим просмотра старой версии. Точный путь приложения определяется при реализации после
  проверки актуальной точки входа редактора.
- **API**: существующие изменяющие методы получают заголовок базовой редакции и метаданные результата; методы чтения —
  необязательный `versionId`; добавляются чтение журнала и откат изменения. Новые предметные команды не добавляются.
- **PostgreSQL**: `design_system_versions`, устойчивые предметные сущности, таблицы `*_revisions`,
  `entity_edit_states`, `entity_edit_paths` и `idempotent_requests`.
- **`frontend-kt`**: не изменяется, пока его CLI и MCP-сценарии продолжают читать актуальное состояние через
  совместимые предметные DTO.
- **Зависимости и развёртывание**: новые внешние библиотеки, службы, порты и переменные окружения не требуются.
