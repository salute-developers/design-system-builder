## ADDED Requirements

### Requirement: Изменение сохраняется в активный серверный черновик

Существующие предметные изменяющие API SHALL сохранять намеренно изменённые поля в активной версии `DRAFT` и SHALL
возвращать актуальное разрешённое состояние после транзакции.

#### Scenario: Пользователь изменяет одно поле

- **WHEN** уполномоченный пользователь отправляет предметный запрос с изменённым полем и `X-DS-Base-Revision`
- **THEN** API MUST создать или обновить предметную редакцию только соответствующей логической сущности
- **THEN** API MUST увеличить и вернуть её техническую редакцию
- **THEN** API MUST NOT копировать остальные сущности дизайн-системы

#### Scenario: Редактор сохраняет только значение токена

- **WHEN** пользователь изменил значение токена, но не менял его описание, имя или признак включения
- **THEN** клиент MUST NOT отправлять эти поля в `PATCH` определения токена
- **THEN** параллельное изменение определения другим пользователем MUST NOT быть перезаписано локальной копией

#### Scenario: Пользователь изменяет компонент во время сохранения

- **WHEN** во время выполняющегося автосохранения конфигурации компонента возникает более новое изменение
- **THEN** клиент MUST сохранить его следующим поколением той же последовательной очереди
- **THEN** ответ старого запроса MUST NOT удалить или заменить более новую ожидающую операцию

#### Scenario: Временная ошибка после частичного выполнения составной операции

- **WHEN** сервер выполнил часть шагов операции, но клиент получил временную ошибку и уже имеет более новое поколение
- **THEN** клиент MUST сначала повторить прежнее поколение с теми же ключами повторяемости
- **THEN** клиент MUST отправить новое поколение только после успешного завершения прежнего

#### Scenario: Освобождённое переименованием имя используется повторно

- **WHEN** пользователь переименовал токен и создаёт новый токен с прежним именем
- **THEN** клиент MUST дождаться завершения переименования перед созданием
- **THEN** новый токен MUST получить отдельную логическую идентичность и MUST NOT обновлять переименованный токен

#### Scenario: Значение снова равно опубликованному

- **WHEN** после записи предметное состояние сущности совпадает с состоянием на предыдущей опубликованной границе
- **THEN** система MUST удалить лишнюю предметную редакцию активного черновика
- **THEN** система MUST сохранить технический счётчик редактирования этой сущности

### Requirement: Параллельные изменения согласуются по изменяемому пути

Система SHALL отслеживать техническую редакцию логической сущности и последнюю редакцию каждого изменяемого пути.

#### Scenario: Пользователи изменяют разные поля одной сущности

- **WHEN** второй запрос основан на устаревшей редакции сущности, но его пути не менялись после этой редакции
- **THEN** API MUST объединить изменение с актуальным состоянием
- **THEN** API MUST вернуть успешный ответ без `409 Conflict`

#### Scenario: Пользователи изменяют одно поле

- **WHEN** второй запрос основан на устаревшей редакции и тот же путь уже был изменён
- **THEN** API MUST применить последнюю успешно зафиксированную запись
- **THEN** ответ MUST содержать машиночитаемое предупреждение с путём и актуальной редакцией
- **THEN** API MUST NOT требовать обязательного пользовательского диалога

#### Scenario: Изменяются разные логические токены темы

- **WHEN** пользователи параллельно изменяют разные комбинации `tenantId + tokenId + platform + mode`
- **THEN** изменения MUST иметь независимые технические редакции
- **THEN** одно изменение MUST NOT создавать конфликт для другого

#### Scenario: Изменяются разные ресурсы конфигурации одного компонента

- **WHEN** пользователи параллельно изменяют разные устойчивые строки appearance, style, property value, adjustment,
  combination, member или style reference одного компонента
- **THEN** каждый ресурс MUST иметь собственную техническую редакцию по его устойчивому `id`
- **THEN** система MUST NOT создавать общую ревизию или конфликт на весь компонент

### Requirement: Техническое состояние редактирования отделено от предметных данных

Система SHALL хранить счётчик сущности в `entity_edit_states`, а редакции путей — в `entity_edit_paths`, не используя
эти таблицы как журнал или хранилище предметных значений.

#### Scenario: Первая запись унаследованной сущности

- **WHEN** сущность существует в опубликованном состоянии, но ещё не изменялась в активном черновике
- **THEN** система MUST создать или заблокировать техническое состояние для этой сущности
- **THEN** система MUST записать предметное значение в таблицу редакций соответствующего модуля

#### Scenario: Один запрос меняет несколько сущностей

- **WHEN** предметная операция затрагивает несколько логических сущностей
- **THEN** система MUST блокировать их технические состояния в устойчивом порядке
- **THEN** все предметные и технические изменения MUST фиксироваться одной транзакцией

### Requirement: Независимые сущности не удерживают общую блокировку черновика

Обычная предметная запись SHALL согласовываться с публикацией на уровне дизайн-системы, но SHALL NOT удерживать
блокировку строки активного черновика на протяжении всей транзакции.

#### Scenario: Параллельно изменяются разные сущности

- **WHEN** две транзакции изменяют разные логические сущности одной дизайн-системы
- **THEN** обе транзакции MUST выполнять предметную работу параллельно
- **THEN** каждая транзакция MUST блокировать только техническое состояние своих сущностей
- **THEN** общая редакция черновика MUST увеличиться один раз для каждой успешно завершённой HTTP-транзакции

#### Scenario: Публикация пересекается с предметной записью

- **WHEN** публикация начинается одновременно с обычным изменением той же дизайн-системы
- **THEN** обычное изменение MUST удерживать разделяемую транзакционную блокировку дизайн-системы
- **THEN** публикация MUST получить исключительную блокировку того же ключа и создать границу только после завершения текущих изменений
- **THEN** запись, начавшаяся после исключительной блокировки, MUST применяться уже к следующему активному черновику

### Requirement: Уникальность проверяется для состояния черновика

Предметный модуль SHALL проверять уникальные значения среди сущностей, действующих на границе активного черновика.

#### Scenario: Два запроса создают одинаковое имя

- **WHEN** параллельные запросы пытаются создать одинаковый нормализованный уникальный ключ
- **THEN** система MUST последовательно обработать их под блокировкой этого ключа
- **THEN** только один запрос MUST завершиться созданием

#### Scenario: Старое значение удалено в черновике

- **WHEN** опубликованная сущность помечена удалённой в активном черновике
- **THEN** её прежний уникальный ключ MUST считаться свободным в черновом состоянии
- **THEN** пользователь MUST иметь возможность создать новую сущность с тем же значением ключа

### Requirement: Редактор хранит предметные данные на сервере

Веб-редактор SHALL автоматически отправлять изменения существующими предметными методами и SHALL NOT использовать
`localStorage` как источник подтверждённого состояния дизайн-системы.

#### Scenario: Автосохранение завершилось успешно

- **WHEN** сервер подтвердил предметное изменение
- **THEN** клиент MUST принять возвращённое состояние и техническую редакцию
- **THEN** клиент MUST удалить локальные сведения о подтверждённом запросе

#### Scenario: Запрос ещё не подтверждён

- **WHEN** сеть недоступна или ответ запроса ещё не получен
- **THEN** клиент MAY временно хранить тело запроса, ключ повторяемости и базовую редакцию в `localStorage`
- **THEN** клиент MUST NOT считать эти сведения подтверждённым серверным состоянием

#### Scenario: Новое изменение появляется во время сохранения

- **WHEN** запрос токена выполняется, а пользователь снова изменяет тот же токен
- **THEN** клиент MUST сохранить более новое поколение операции в устойчивой очереди
- **THEN** ответ старого запроса MUST NOT удалить более новое изменение
- **THEN** новое изменение MUST быть отправлено после подтверждения предыдущего с актуальными техническими редакциями

#### Scenario: Автосохранение временно недоступно

- **WHEN** запрос завершился сетевой ошибкой или ответом `5xx`
- **THEN** клиент MUST сохранить операцию в `localStorage` и повторить её с увеличивающейся задержкой
- **THEN** интерфейс MUST показывать ненавязчивое состояние сохранения без обязательного диалога

#### Scenario: У токена нет значения платформы

- **WHEN** изменяемый токен не содержит значения одной из поддерживаемых платформ
- **THEN** клиент MUST NOT включать отсутствующее значение в пакет
- **THEN** явное значение `null`, допустимое предметным типом, MUST NOT отбрасываться как отсутствующее

### Requirement: Небезопасные повторные запросы имеют устойчивый результат

API SHALL принимать ключ повторяемости для создания через `POST`, импорта, публикации и отката.

#### Scenario: Повторяется тот же запрос

- **WHEN** проект, ключ, операция и хэш тела совпадают с завершённым запросом
- **THEN** API MUST вернуть ранее сохранённые статус и тело ответа без повторного предметного изменения

#### Scenario: Ключ повторён с другим телом

- **WHEN** тот же проект и ключ используются с другим хэшем тела
- **THEN** API MUST отклонить повтор без выполнения предметной операции
