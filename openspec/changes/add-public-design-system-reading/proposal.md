# Публичное чтение дизайн-систем

## Зачем

Опубликованные дизайн-системы должны быть доступны по прямой ссылке в веб-клиенте, CLI и MCP без входа и членства в проекте. Сейчас обязательная авторизация и выбор черновика по умолчанию блокируют этот сценарий на сервере и в общих клиентских модулях.

## Что изменится

- У каждой пользовательской ДС появится доступность `private` или `public`; новые и существующие системы останутся приватными по умолчанию.
- Единые маршруты будут обслуживать участников по действующим правам, а гостей и пользователей вне проекта — только в пределах опубликованных версий публичной ДС. Каталоги проектов и ДС останутся защищёнными.
- Без селектора версии публичное чтение выберет последнюю опубликованную; участник с правом чтения черновика сохранит прежнее поведение. Ответ позволит закрепить фактическую версию в последующих запросах.
- CLI и MCP получат общий анонимный режим чтения. Гостевой `init` будет работать по ссылке либо двум явным ID без интерактивного выбора. Загрузки тем, компонентов и ДС будут согласованы по версии.
- В настройках под именем ДС появится «Доступность» с вариантами «Приватная» / «Публичная», пояснением и копированием прямой ссылки. Гостевой веб-просмотр не будет запускать редактор.
- Публичность не откроет проект, черновик, журнал изменений, SSE, команды записи, документацию или административные операции.

## Возможности

### Новые возможности

- `public-design-system-reading`: доступность ДС, адресное публичное чтение опубликованных данных, отзыв доступа и безопасные ответы.

### Изменяемые возможности

- `gateway-authorization`: проверенный контекст публичного чтения на существующих маршрутах.
- `design-system-model-api`: серверный выбор версии, совместимость component-config и авторизация предметного чтения.
- `design-system-version-history`: раздельные умолчания проектного и публичного чтения временных границ.
- `design-system-request-scope`: чтение необходимых глобальных определений только в контексте явно выбранной публичной ДС.
- `design-system-context-links`: необязательная версия ссылки и проверка доступа к самой ДС.
- `frontend-client-authentication`: анонимный режим только для допускающих его операций чтения.
- `cli-core`: общие разрешение контекста и HTTP-транспорт без обязательного входа.
- `frontend-cli`: явный гостевой init и проверка доступности ДС вместо обязательного чтения проекта.
- `cli-themes`: загрузка одной фактической версии без обязательных учётных данных.
- `cli-components`: публичный экспорт и web-адаптер одной версии.
- `cli-ds`: согласованная версия загрузки тем и компонентов.
- `frontend-mcp-server`: чтение и выбор версий по прямой ссылке без каталогов и входа.
- `web-design-system-workflow`: настройки доступности и гостевой просмотр.

## Влияние

- `backend-kt`: `app`, узкий сценарий проверки кандидата и различение недоступности JWT/JWKS в `identity-gateway/feature-auth`, `ds-service/core`, общие предикаты чтения `feature-components/data` и необходимые адаптеры предметных чтений `ds-service` (модель, новая Flyway-миграция, репозитории, транзакционный контекст, маршруты, DTO, OpenAPI и манифест). Публичный контекст остаётся внутри `ds-service`; `authorization-core` (типы principal, роли, scopes и вычислитель прав), модель/БД `projects-service` и исторические nginx-конфигурации не изменяются. Операции и точки интеграции перечислены в `read-operation-map.md`.
- `frontend-kt`: `core-auth`, `core-domain`, `core-application`, `core-network`, `core-workspace`, `feature-init`, `feature-status`, `feature-ds`, `feature-theme`, `feature-components`, `cli`, `mcp-server-core`, `mcp-node`; совместимость остальных потребителей общих контрактов проверяется сборкой.
- `js/apps/client`: маршрутизация, HTTP-клиент, кеш, загрузка ДС, гостевые страницы и настройки. `js/cli` сохраняет локальную генерацию; её совместимость проверяется существующими тестами.
- Новые сервисы, внешние зависимости, порты и обязательные переменные окружения не требуются. API URL клиентов по-прежнему задаётся независимо от ссылки через существующую конфигурацию.
