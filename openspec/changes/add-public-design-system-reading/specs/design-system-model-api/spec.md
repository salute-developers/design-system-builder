## MODIFIED Requirements

### Requirement: Gateway authorization for model read API

Публичный вход SHALL обслуживать единые маршруты через проектную авторизацию либо ограниченный контекст адресного публичного чтения. `ds-service` SHALL независимо проверять доступ, проект пути, ожидаемую систему и допустимость версии; глобальные чтения гостя требуют явного контекста публичной ДС.

#### Scenario: Существующий маршрут Gateway передаёт разрешённый запрос
- **WHEN** аутентифицированный клиент читает системный ресурс
- **THEN** публичный вход MUST проверить доступ к проекту и сформировать доверенный контекст, а сервис MUST проверить разрешение, принадлежность ресурса проекту и системе пути

#### Scenario: Поддельные заголовки
- **WHEN** клиент передаёт собственные заголовки доверенного контекста или ожидаемой системы
- **THEN** публичный вход MUST NOT принимать их как источник разрешений или замены ID системы пути

#### Scenario: Неверный проект
- **WHEN** проектный ключ не имеет доступа к проекту пути либо участник не имеет разрешения на операцию
- **THEN** запрос MUST быть отклонён до выполнения предметной операции

#### Scenario: Неавторизованный запрос отклоняется
- **WHEN** клиент без действительной проектной аутентификации вызывает чтение вне разрешённого адресного публичного доступа
- **THEN** публичный вход MUST отклонить запрос с `401` или `403`, а прямое обращение к `ds-service` с отсутствующим или противоречивым доверенным контекстом MUST быть отклонено
- **AND** сервис MUST NOT выводить доверенную проектную идентичность только из управляемых клиентом path или query


### Requirement: Совместимый серверный выбор номера версии

Чтения версионированной модели SHALL принимать version=draft либо точный major.minor.patch и сохранять versionId. Сервер SHALL разрешать номер внутри доступной DS ресурса через существующие связи и проверки доступа; без селектора публичное чтение выбирает последнюю опубликованную границу, проектное чтение с правом черновика — черновик. Чтение глобальной меты компонента SHALL сохранять прежний контракт без обещания снимка DS.

#### Scenario: Явная публикация

- **WHEN** клиент передаёт version существующей публикации
- **THEN** данные MUST соответствовать её временной границе без клиентского поиска UUID
- **THEN** неизвестная, чужая либо архивная snapshot-версия MUST вернуть NOT_FOUND без перехода на черновик

#### Scenario: Черновик и конфликт селекторов

- **WHEN** участник с правом чтения черновика не передал селекторы либо явно указал version=draft
- **THEN** сервер MUST читать текущий черновик
- **WHEN** переданы одновременно version и versionId вне совместимого проектного GET component-config либо повтор одного селектора
- **THEN** сервер MUST вернуть INVALID_QUERY

#### Scenario: Существующая авторизация

- **WHEN** ресурс читается по ID
- **THEN** сервер MUST переиспользовать проверки доступа и связей ресурса
- **THEN** запрос MUST NOT требовать нового обязательного designSystemId лишь для подтверждения локального контекста MCP

#### Scenario: Публичный выбор версии
- **WHEN** гость или пользователь вне проекта не передал селекторы
- **THEN** сервер MUST выбрать публикацию с наибольшим порядковым номером среди поддерживаемых опубликованных границ либо вернуть `404`
- **WHEN** такой субъект явно указал `draft`
- **THEN** сервер MUST вернуть `403` без подмены селектора


### Requirement: Метаданные фактического чтения вне тела

Расширенные чтения SHALL передавать безопасный X-DS-Read-Context в HTTP-заголовке, сохраняя прежние тела ответов. Контекст и данные MUST соответствовать одной транзакции; безопасное поле `accessMode` SHALL обозначать `project` либо `public`.

#### Scenario: Черновик изменяется конкурентно

- **WHEN** сервер возвращает данные черновика
- **THEN** заголовок MUST содержать designSystemId, version=draft, draftId и draftRevision фактического чтения
- **THEN** независимое изменение после чтения MUST NOT требовать expectedDraftRevision или приводить к DRAFT_CHANGED

#### Scenario: Публикация или история

- **WHEN** читается одна публикация
- **THEN** заголовок MUST содержать designSystemId, version и versionId
- **WHEN** читается история разных публикаций
- **THEN** контекст MUST NOT приписывать списку одну выбранную версию

#### Scenario: Прежний потребитель

- **WHEN** клиент игнорирует новые заголовки
- **THEN** он MUST получить прежний массив или объект без обёртки context/data
- **THEN** запрос MUST NOT требовать view, отдельного /page или предварительного read-context

#### Scenario: Безопасные заголовки доступны клиенту

- **WHEN** запрос проходит через Gateway
- **THEN** X-DS-Read-Context, X-DS-Page-Limit и X-DS-Next-Cursor MUST быть доступны через CORS
- **THEN** эти метаданные MUST NOT содержать учётные данные, внутренние URL или локальные пути

#### Scenario: Продолжение публичного чтения
- **WHEN** сервер разрешил отсутствующую версию в публикацию
- **THEN** `X-DS-Read-Context` MUST содержать фактические номер и `versionId`
- **THEN** последующий запрос с этим `versionId` MUST сохранять границу при появлении новой публикации, пока ДС публична

### Requirement: Предметное чтение поддерживает временную границу дизайн-системы

Методы чтения модели в `backend-kt/ds-service` SHALL принимать необязательный `versionId` для данных, принадлежащих
конкретной дизайн-системе. Без селекторов SHALL читаться черновик при проектном доступе с соответствующим правом либо последняя публикация при публичном доступе.

#### Scenario: Клиент читает актуальную модель

- **WHEN** участник с правом черновика вызывает список токенов, значения темы, конфигурацию оформления, варианты или стили без `version` и `versionId`
- **THEN** API MUST вернуть разрешённое состояние активного черновика
- **THEN** ответ MUST сохранять документированную предметную форму DTO

#### Scenario: Клиент читает опубликованную модель

- **WHEN** клиент вызывает поддерживаемый предметный метод с `versionId` опубликованной версии
- **THEN** API MUST вернуть разрешённое состояние на границе этой версии
- **THEN** API MUST применить проектные проверки прав либо проверку публичности, точной ДС и принадлежности ресурса

#### Scenario: Клиент передал недоступную версию

- **WHEN** версия отсутствует, принадлежит другой дизайн-системе либо недоступна выбранному режиму доступа
- **THEN** API MUST вернуть `404 Not Found`
- **THEN** ответ MUST NOT раскрывать наличие данных другого проекта

#### Scenario: Публичная граница по умолчанию
- **WHEN** публичное чтение не содержит селекторов
- **THEN** API MUST вернуть последнюю поддерживаемую публикацию без данных черновика либо `404`, если публикаций нет



#### Scenario: Первая разрешённая операция выбирает публикацию
- **WHEN** предметный запрос экспорта, списка тем или другого допустимого чтения первым разрешил публикацию
- **THEN** его ответ MUST содержать фактический `versionId` без обязательного предварительного чтения карточки ДС
- **THEN** чтение MUST NOT требовать дополнительных разрешений сверх разрешений самой операции

#### Scenario: Продолжение живого черновика
- **WHEN** участник получил `version=draft`, `draftId` и `draftRevision`
- **THEN** последующие чтения черновика MUST использовать `version=draft`, а не `versionId=<draftId>`
- **THEN** публикация между запросами MUST NOT превращать черновой ID в селектор публикации; следующий ответ MUST описывать фактически прочитанный активный черновик
- **THEN** независимые чтения черновика MUST NOT обещать неизменность его данных или требовать `expectedDraftRevision`


### Requirement: Совместимость перенесённого API

Каждый перенесённый маршрут SHALL сохранять наблюдаемый контракт прежнего `db-service`, зафиксированный в OpenAPI `ds-service`: имена и обязательность path/query/body полей, форму JSON, семантику `null` и отсутствующих полей, коды успешных ответов, предметные ошибки, порядок элементов там, где он стабилен, и транзакционные границы. Исключения, согласованные в `design-system-request-scope`: канонические системные/глобальные пути, удаление дублирующего `designSystemId` из входных HTTP DTO/query и единые списки токенов и тем. Эти изменения SHALL NOT трактоваться как нарушение совместимости переноса; остальные поля и предметная семантика SHALL сохраняться, кроме явно определённых ниже правил селекторов GET component-config.

#### Scenario: Сравнение чтения двух реализаций

- **WHEN** `ds-service` получает запрос чтения перенесённого маршрута
- **THEN** статус и JSON-ответ MUST соответствовать OpenAPI `ds-service`; второй реализации для сравнения нет

#### Scenario: Сравнение мутации двух реализаций

- **WHEN** допустимая мутация выполняется в `ds-service`
- **THEN** ответ и итоговое состояние предметных таблиц MUST соответствовать документированным транзакционным границам

#### Scenario: Версия в текущем component-config

- **WHEN** участник проекта вызывает `GET /component-config` с прежним параметром `version`
- **THEN** сервер MUST принять его как совместимый устаревший параметр без новой исторической семантики
- **THEN** при отсутствии `versionId` данные MUST соответствовать текущему черновику; при наличии `versionId` MUST использоваться эта публикация, а устаревший `version` MUST NOT создавать конфликт селекторов

#### Scenario: Компонентная конфигурация без устаревшего поля
- **WHEN** GET component-config передаёт остальные необходимые параметры `ds`, `component`, `appearance`, `platform`, но не передаёт `version`
- **THEN** сервер MUST принять запрос, в том числе с одним `versionId`
- **THEN** без селекторов участник с правом черновика MUST получить черновик, публичный читатель — последнюю публикацию либо `404`

#### Scenario: Селектор публичной компонентной конфигурации
- **WHEN** публичный GET component-config передаёт точный `version` либо `versionId`
- **THEN** сервер MUST использовать указанную публикацию; совместная передача селекторов MUST вернуть `400`
- **THEN** явный `version=draft` MUST вернуть `403`, даже если опубликованные данные существуют
- **THEN** неподдерживаемый номер версии MUST NOT трактоваться как устаревшая подсказка проектного клиента

### Requirement: Необязательное обогащение деталей компонента

Чтения свойств и зависимостей SHALL сохранять прежний глобальный контракт без `include`. Системное обогащение `include=platformParams` либо `include=reuseConfig` SHALL выполняться на системном пути. Чтение осей оформления SHALL сохранять существующие значения и значения по умолчанию.

#### Scenario: Детали запрошены
- **WHEN** клиент передал `include=platformParams` для системного `/components/{id}/properties` либо `include=reuseConfig` для системного `/components/{id}/deps`
- **THEN** сервер MUST собрать дополнительные данные только указанной системы и сохранить доступные метаданные родителей/детей

#### Scenario: Вариации уже доступны в первом Change
- **WHEN** клиент читает системный `GET /appearances/{id}/variations`
- **THEN** контракт MUST сохранить обязательный `appearanceId`, оси, значения и `defaultStyleId` без нового `include=values,defaults`

#### Scenario: Предметный контекст расширения
- **WHEN** системное расширение зависит от связи глобального ресурса с выбранной системой
- **THEN** сервер MUST проверить эту связь и принадлежность настроек системе пути
- **AND** старые проектные глобальные ID-чтения без расширения MUST NOT получить обязательный `designSystemId`; публичные чтения MUST явно задать ДС для проверки доступности и связи

#### Scenario: Платформы и формат сохранены
- **WHEN** клиент читает глобальные детали без `include`
- **THEN** сервер MUST вернуть прежние массивы/объекты без `context/data` и без преобразования платформ токенов, компонентов и документации

#### Scenario: Расширение на глобальном пути
- **WHEN** клиент передаёт `include=platformParams` либо `include=reuseConfig` на глобальный путь
- **THEN** сервер MUST вернуть `400`, не выполняя системное обогащение по query вместо пути; параметр `designSystemId` для ограничения связанных публичных определений MUST NOT считаться таким обогащением
