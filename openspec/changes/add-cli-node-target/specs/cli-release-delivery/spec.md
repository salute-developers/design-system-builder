## ADDED Requirements

### Requirement: Дополнительный Node.js-дистрибутив

Новые выпуски CLI SHALL дополнительно предоставлять `dsbuilder-cli-node.tgz` с npm-пакетом `@sddsjs/design-system-builder-cli`, командой `dsbuilder` и объявленным требованием Node.js 22+. Четыре существующих ZIP и установщики SHALL сохранять прежние имена и поведение.

#### Scenario: Версия и состав
- **WHEN** пакет собран для `cli-v1.2.3`
- **THEN** package.json и `dsbuilder --version` MUST сообщать `1.2.3`
- **THEN** пакет MUST содержать требуемые JS-файлы и объявлять все внешние зависимости без ссылок на локальные каталоги сборки
- **THEN** установка MUST NOT требовать Java/Kotlin, backend, credentials или запуска генератора

#### Scenario: Установка вне рабочей копии
- **WHEN** tarball устанавливается через npm в изолированный каталог вне Gradle build и исходного репозитория
- **THEN** установленный `dsbuilder` MUST выполнять help/version и обработку ошибки аргументов на Linux, macOS и Windows
- **THEN** одинаковая проверка MUST проходить на Node.js 22 и 24
- **THEN** пакет MUST NOT автоматически открывать браузер, устанавливать платформенные инструменты или принудительно заменять существующий launcher

#### Scenario: Проверка до публикации
- **WHEN** новый процесс выпуска готовит GitHub Release
- **THEN** tarball MUST присутствовать в полном комплекте и проверяться по SHA-256 вместе с существующими файлами до публикации и назначения Latest
- **THEN** SHA-256 MUST присутствовать в `SHA256SUMS` и необязательной записи `node` манифеста `release.json` со `schemaVersion: 1`
- **THEN** запись `node` MUST содержать `fileName`, `packageName`, `version`, `minNodeVersion` и `sha256`, совпадающие с проверенным пакетом
- **THEN** обязательность Node-файла MUST определяться отслеживаемым дескриптором в исходниках выбранного тега, а не наличием поля в скачанном манифесте
- **THEN** отсутствие либо повреждение Node-пакета нового выпуска MUST сохранять прежний Latest
- **THEN** новые npm-шаги текущего workflow MUST публиковать web-генератор, затем CLI до продвижения GitHub Release; исторические теги без дескриптора MUST сохранять прежний путь без npm-публикации

#### Scenario: Совместимость существующих выпусков и установщиков
- **WHEN** проверяется ранее опубликованный выпуск, в исходниках тега которого нет дескриптора Node-поставки
- **THEN** новый валидатор MUST применять прежний контракт комплекта без требования добавить tarball
- **THEN** повтор MUST NOT пересобирать выпуск, заменять файлы или менять Latest
- **WHEN** существующий сетевой установщик получает новые метаданные и контрольные суммы
- **THEN** он MUST продолжать выбирать и проверять прежний JVM/native ZIP без автоматического выбора Node.js

### Requirement: Публикация обоих npm-пакетов текущим workflow

Текущий `.github/workflows/publish-cli-release.yml` SHALL публиковать `@sddsjs/design-system-builder-generator` и `@sddsjs/design-system-builder-cli` отдельными шагами без нового workflow. Оба пакета SHALL происходить из выбранного стабильного CLI-тега; версия генератора SHALL браться из `js/cli/package.json`, версия CLI — из `CLI_RELEASE_TAG`.

#### Scenario: Автоматический и ручной запуск выпуска
- **WHEN** существующий workflow запущен по тегу `cli-v1.2.3` либо вручную для того же существующего тега
- **THEN** после успешных build/smoke и проверки GitHub draft он MUST публиковать сначала проверенный tarball генератора, затем проверенный tarball CLI
- **THEN** npm-публикация MUST использовать точные файлы, переданные из build, без повторной сборки или упаковки
- **THEN** GitHub Release MUST продвигаться только после подтверждения обеих npm-версий и проверки установки из registry
- **THEN** установленные пакеты MUST иметь публичный доступ; npm `latest` MUST NOT понижаться

#### Scenario: Версии и проверки до записи
- **WHEN** workflow подготавливает пакеты для публикации
- **THEN** он MUST явно выполнить typecheck, тесты, проверку состава и глобальной установки генератора, а также проверки CLI, до разрешения npm-записи
- **THEN** отсутствие релизного тега, несоответствие версии CLI тегу, несовпадение контрольной суммы или ошибка проверки MUST остановить публикацию
- **THEN** версия генератора MUST NOT автоматически меняться из-за номера CLI-релиза
- **THEN** workflow MUST NOT полагаться на запуск `prepublishOnly` при публикации готового tarball

#### Scenario: Авторизация
- **WHEN** шаг workflow публикует пакет в публичный npm registry
- **THEN** он MUST использовать `NODE_AUTH_TOKEN` из секрета `NPM_TOKEN` с правами публикации обоих пакетов в scope `@sddsjs`
- **THEN** отсутствие либо непригодность секрета MUST завершать npm-этап ошибкой до записи
- **THEN** секрет MUST NOT передаваться build, тестам/генераторам и проверкам установки или попадать в исходники, artifacts и логи

#### Scenario: Проверка состава
- **WHEN** проверяются tarball перед публикацией
- **THEN** CLI MUST содержать готовый JS, launcher, README, LICENSE и необходимые данные выполнения, а генератор — файлы по существующему контракту web-generator-package
- **THEN** тесты, результаты генерации, `.sdds`, `.env`, `.npmrc`, credentials и локальные кэши MUST отсутствовать
- **THEN** `packCliNodeNpm` MUST явно выполнить проверки перед упаковкой, не полагаясь на `prepublishOnly`

#### Scenario: Уже опубликованная версия
- **WHEN** целевая версия одного из пакетов уже существует в registry
- **THEN** workflow MUST сравнить `dist.integrity` с проверенным tarball и при совпадении успешно пропустить запись этого пакета, не меняя его npm-теги
- **THEN** при несовпадении содержимого workflow MUST завершиться ошибкой без перезаписи или удаления версии
- **THEN** ошибки сети, доступа и registry MUST NOT считаться отсутствием версии
- **WHEN** отсутствующая в registry версия ниже либо равна текущему `latest`
- **THEN** workflow MUST отклонить её публикацию с `latest` до записи

#### Scenario: Частичная публикация и повтор
- **WHEN** генератор опубликован, а публикация CLI или последующее продвижение GitHub не удались
- **THEN** workflow MUST завершиться ошибкой без удаления опубликованного npm-пакета и без продвижения GitHub draft/Latest
- **THEN** повтор MUST проверить опубликованный пакет по integrity и продолжить недостающую операцию
- **THEN** неоднозначный сетевой сбой MUST разрешаться проверкой версии/integrity, а не слепой перепубликацией
- **THEN** параллельные запуски выпуска MUST сериализоваться существующей группой concurrency без отмены начатой публикации

### Requirement: Глобальная установка опубликованного CLI

Публичный пакет SHALL устанавливаться через `npm install -g @sddsjs/design-system-builder-cli` и предоставлять команду `dsbuilder` на Linux, macOS и Windows при наличии Node.js 22+ и npm.

#### Scenario: Установка по имени и версии
- **WHEN** пользователь без npm-авторизации устанавливает пакет по имени в изолированный глобальный prefix
- **THEN** npm MUST получить публичную версию из `latest` и создать работоспособную команду `dsbuilder`
- **WHEN** пользователь устанавливает `@sddsjs/design-system-builder-cli@1.2.3`
- **THEN** установленный `dsbuilder --version` MUST сообщать `1.2.3`
- **THEN** установка MUST NOT требовать исходный репозиторий, Gradle, Java/Kotlin, backend или credentials

#### Scenario: Проверка до реального выпуска
- **WHEN** выполняются проверки реализации перед архивированием
- **THEN** порядок публикации обоих пакетов шагами workflow, отказ до записи при ошибке проверок, повтор/частичный сбой и установка по имени/версии MUST проверяться во временном тестовом npm registry без записи в публичный registry
- **THEN** отсутствие тестового registry или ошибка запуска MUST завершать проверку ошибкой, а не успешным пропуском
