## Context

Конфигурация компонента описывает оси (биндинги) и вариации. Вариация имеет идентификатор (`id`), по которому на
неё ссылаются в пакете, и биндинги (`name`/`value`), которые становятся осями и значениями осей в `ds-service`.
Для большинства компонентов идентификатор складывается из значений биндингов (`xs.clear`), но не для всех:
у `ai-input-icon-button-group` вариация `l.no-gap.default` имеет биндинги `size=l`, `gap=none`, `shape=default`;
у `notification-content` вариация `button-stretch` имеет биндинг `button-layout=stretch`; у `tab-bar-item-clear` вариация
`l.label` имеет `label-placement=bottom`; у `dropdown-empty-state` вариация `l.has-button` имеет булев биндинг.

Импортёр сохраняет исходный идентификатор в `authored_id`: у значения оси
(`AppearanceVariationValuesTable.authoredId`, если вариация состоит из одного биндинга) и у сочетания
(`AppearanceCombinationsTable.authoredId`, если вариация состоит из нескольких). Поэтому `underivable()` в отчёте
называет такие компоненты `underivableVariationIds`: имя нельзя вывести из значений.

`ComponentConfigImporter.resolveReferences` делит `reference` по точке, первый сегмент считает именем оформления,
а каждый следующий ищет в `effective` (действующие имена значений осей цели, в нижнем регистре) или
в `available` (имена стилей компонента). Если хоть один сегмент не найден, ссылка попадает в
`unresolvedComponentStyles`, а запись ссылки пропускается.

Проверка на реальных данных: из 408 различных строк `component_style` в `sdds_serv` 18 (23 вхождения в отчёте)
не разрешаются именами; с идентификаторами вариаций разрешаются все 408. Экспорт dev после полной загрузки содержит те
же идентификаторы вариаций, что и исходный пакет, то есть значения и сочетания с `authored_id` уже в базе.

## Goals / Non-Goals

**Goals:**
- Ссылки, написанные идентификаторами вариаций цели, разрешаются и записываются так же, как ссылки по именам.
- Ничего из того, что разрешалось раньше, не меняется: ни результат, ни отчёт.
- Не добавлять чтений к бюджету `optimize-component-config-import`.

**Non-Goals:**
- Менять формат пакета или конвертер.
- Писать в `reference` нормализованный вид: текст остаётся как в пакете.
- Вывод `authored_id` для компонентов, у которых его нет.

## Decisions

### Группы сегментов вместо подмены правила

Хвост ссылки (`parts.drop(1)`) разбивается на группы подряд идущих сегментов; группа допустима, если
1. это один сегмент, равный действующему имени значения оси цели или имени стиля компонента (прежнее правило), или
2. это один или несколько сегментов, соединённых точкой, равных `authored_id` значения или сочетания целевого
   оформления.

Ссылка разрешена, если существует разбиение без остатка. Каждая группа даёт стили: имя значения — один стиль;
`authored_id` значения — его стиль; `authored_id` сочетания — стили всех его участников. Итог — объединение стилей
групп без повторов, порядок следования сегментов.

Почему группы, а не «весь хвост как один идентификатор»: ссылки смешанные. `notification-content.button-stretch.default`
— это идентификатор вариации `button-stretch` и значение оси `view=default`; `tab-bar-item-clear.l.label.accent` —
сочетание `l.label` и значение `view=accent`. Правило «хвост целиком» их бы не покрыло.

Альтернативы:
- *Переписать идентификатор вариации в значения биндингов при чтении пакета.* Нужен вывод значений из идентификатора,
  а он как раз невыводим (`underivableVariationIds`); `authored_id` и есть записанное соответствие.
- *Исправить конвертер.* Правильно с точки зрения формата, но не лечит уже существующие пакеты и ссылки в других
  дизайн-системах; решается отдельно в `theme-converter`.

### Порядок и неоднозначность

- Сначала пробуется прежнее правило для всего хвоста; если оно разрешает ссылку, поведение прежнее
  (обратная совместимость и неизменность эталона).
- Новое разбиение включается, только если прежнее не покрыло хвост.
- Разбиение ищется поиском с возвратом с жадным выбором: на каждом шаге сначала самая длинная группа, при равной
  длине — имя значения раньше `authored_id`. Результат детерминирован: перебор идёт в порядке, зависящем от текста
  ссылки, а не от порядка строк в базе.
- `authored_id` сравнивается точно, без `trim` и без приведения регистра: это машинный идентификатор из пакета, а не
  отображаемое имя. Имена значений вариаций сравниваются как раньше (`trim().lowercase()`), имена стилей компонента
  точно.
- Если один `authored_id` есть и у значения, и у сочетания цели, выигрывает значение: позиции в разных таблицах
  несравнимы, а значение конкретнее. Внутри одной таблицы берётся первое по позиции (как для имён при совпадении, см.
  `optimize-component-config-import`: «берётся первая строка»). В корректном пакете такого не бывает: идентификаторы
  вариаций внутри конфигурации уникальны (проверено на 144 конфигурациях `sdds_serv`), а вариация либо одиночная, либо
  составная; правило нужно только для детерминизма на испорченных данных.

### Индекс идентификаторов читается один раз на цель

`ReferenceTarget` получает `authoredIds`: словарь `authored_id` → список стилей значения или сочетания. Строится одним
чтением значений вариаций (`EditorAxisValue.authoredId` уже есть в `AppearanceEditorModelReader.axes`) и одним
запросом с `JOIN` участников сочетаний (`AppearanceCombinationMembersTable`) с сочетаниями по `appearance_id` целевого
оформления, при первом обращении к цели, как и остальные поля `ReferenceTarget`. Готовый
`ComponentConfigBuilder.combinations()` не используется: он на каждый ключ сочетания делает `selectAll()` с
фильтром в Kotlin, то есть читает число строк, пропорциональное числу сочетаний в квадрате. Число запросов растёт с
числом различных целей, а не с числом ссылок, и число прочитанных строк на цель линейно по её размеру.

Чтения идут из таблиц представления; записи конфигураций целей к этому моменту сброшены (`flush` после
`resolveReferences` и перед ним уже есть), поэтому цели из того же запроса видны.

### Отчёт и запись

- `unresolvedComponentStyles` получает только те ссылки, для которых не нашлось разбиения.
- Запись ссылки (`writeReference`) и связи со стилями не меняются.
- `reference` пишется как в пакете.
- `dependencies()` (связь `REUSE`) использует только первый сегмент и не меняется.

## Risks / Trade-offs

- [Ложное совпадение: сегмент совпал с `authored_id` другой вариации] → прежнее правило проверяется первым, новое только
  для неразрешённых ссылок; такие ссылки раньше терялись целиком.
- [Экспорт и повторная загрузка: что пишет экспорт в `reference`] → круговой маршрут проверен тестом
  `an export of the imported package is imported back unchanged`: выгрузка после импорта загружается обратно без
  `created`/`updated`, ссылки и их стили остаются прежними.
- [Лишние чтения] → индекс строится лениво по цели и проверяется бюджет-тестом `ComponentConfigImportCostIntegrationTest`.
- [Ссылки, всё ещё неразрешённые] → остаётся информационный отчёт; причина теперь только в отсутствии цели или значения.

## Migration Plan

Миграций нет. Compose-пакеты загружались только в дизайн-систему `base` на dev; на проде и в других дизайн-системах
они не загружались, поэтому перезаливать больше нечего. После выката повторный `dsbuilder components push` с тем же пакетом создаёт недостающие ссылки
(`Updated` затронет только конфигурации-родители); пакет, ничего не потерявший раньше, остаётся прежним. Откат —
возврат предыдущего образа: созданные ссылки остаются валидными данными.
