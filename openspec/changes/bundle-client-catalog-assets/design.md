## Контекст

Клиент собирается Vite с `base`, взятым из `BASE_URL`. Deploy workflow стенда разработки передаёт
`BASE_URL=/dev/design-system-builder/client/`, прод — свой подпуть. Vite дописывает этот префикс только к ресурсам,
которые проходят через сборку (`import`, `url()` в CSS), и не трогает строковые пути в JSX.

Сейчас 10 картинок из `public/catalog/` используются в пяти компонентах через `src="/catalog/..."`. На стенде
`plasma.sberdevices.ru/catalog/icons/rail-colors.svg` отвечает `301` на HTML, а тот же файл по адресу
`/dev/design-system-builder/client/catalog/icons/rail-colors.svg` отдаётся с `200 image/svg+xml`. Картинки, уже
подключённые через `import` (`BrandPreview`), на стенде работают.

## Цели / Вне целей

**Цели:**
- Картинки каталога загружаются при любом `BASE_URL`.
- Сломанная ссылка на картинку становится ошибкой сборки, а не дефектом на стенде.

**Вне целей:**
- Смена способа публикации клиента и правка deploy workflow.
- Переработка `getBaseName()` и его ветки для `/pr/...`.
- Перенос иконок из `src/icons` и других картинок, уже подключённых через `import`.
- Замена иконок боковой панели на компоненты `@salutejs/sdds-icons`. Пять из них есть в пакете (`HistoryOutline`,
  `PlusOutline`, `TypographyOutline`, `ShapeOutline`, `FileStackOutline`), для «цветов» и «компонентов» соответствие не
  найдено. Решено отложить. Правило для новых иконок (брать из `sdds-icons`, сверять с макетом, при расхождении идти к
  дизайнеру) записано в `js/apps/client/README.md` и `js/CLAUDE.md`.

## Решения

### Подключать картинки через `import`, а не префиксовать строковые пути

Файлы переносятся в `js/apps/client/src/assets/catalog/` с сохранением структуры (`icons/` внутри), компоненты
импортируют их как модули:

```tsx
import railColorsIcon from '../../assets/catalog/icons/rail-colors.svg';

<img className="builder-rail-icon" src={railColorsIcon} alt="" />
```

Vite сам формирует итоговый адрес с учётом `base`, добавляет хеш содержимого в имя файла и падает при сборке, если
файла нет. Типы для импорта `.svg` и `.png` уже даёт `vite/client` из `tsconfig`.

Рассмотренная альтернатива — хелпер `publicAsset(path)`, который приклеивает `getBaseName()` к строковому пути и
оставляет файлы в `public/`. Изменений меньше, но защита работает только там, где о хелпере не забыли: новый
`src="/catalog/..."` снова сломает стенд, и ни сборка, ни тесты этого не заметят. Опечатка в пути тоже не ловится.

### Неиспользуемые файлы удалить

`project-cover-placeholder.svg`, `icons/rail-help.svg` и `icons/rail-notifications.svg` не упоминаются ни в коде, ни
в стилях. Переносить их в `src` бессмысленно: сборка не включает файлы без импорта. Если они понадобятся, их можно
вернуть из истории Git вместе с импортом.

### Тест проверяет импортированный адрес

`ProjectsWorkflow.test.tsx` ищет `img[src="/catalog/error-state.png"]`. Тест импортирует ту же картинку и сравнивает
`src` с импортированным значением, чтобы не зависеть от того, как Vitest формирует адрес ресурса.

## Риски / Компромиссы

- [Каталог `public/catalog/` исчезает из сборки, и внешняя ссылка на `/…/catalog/...` перестанет работать] → внешних
  потребителей у этих картинок нет: это внутренние иконки интерфейса, а адрес и так был нерабочим на стендах.
- [Небольшие SVG Vite может встроить в бандл как `data:`-адрес] → для `<img src>` это допустимо и не меняет
  отображение; порог встраивания не трогаем.

## План миграции

Изменение только клиентское. После выкладки на стенд разработки открыть клиент и убедиться, что иконки боковой панели и
заглушки пустых состояний отображаются, а в сетевых запросах нет обращений к `/catalog/...` от корня домена. Откат —
возврат коммита.
