ADR-0006 · Архитектурное предложение

Preview настоящих компонентов в DS Builder

Как отделить конфигурацию дизайн-системы от платформенного рендера и дать командам добавлять свои компоненты без релиза приложения DS Builder

Design System Builder2026
Проблема

Preview нельзя расширить без изменения самого DS Builder

Сегодня DS Builder показывает только заранее встроенные React stories. Пользователь не может подключить свой компонент, а поддержка новой платформы требует разработки и релиза со стороны SDDS Team.

Нужно отделить управление конфигурацией от платформенного кода, который отображает настоящий компонент.
Текущая архитектура ограничивает развитие preview2
Текущий подход

Сегодня preview вручную встроен в React-приложение DS Builder

1

Backend отдаёт настройки

Тема и конфигурация компонента приходят отдельными проекциями.

2

Клиент готовит CSS

React-приложение DS Builder преобразует настройки в CSS variables.

3

Mapper выбирает story

Компонент должен быть заранее зарегистрирован вручную.

4

React рисует preview

Локальная story получает args и отображается внутри приложения.

Конфигурация приходит из backend, а renderer живёт и выпускается вместе с приложением DS Builder.
Backend model → CSS → mapper → local story3
Что в нём хорошо

Текущий подход прост и эффективен в ограниченном масштабе

Низкий порог входа

  • Один runtime — React в браузере
  • Простая локальная отладка
  • Нет отдельной инфраструктуры плагинов

Предсказуемая поставка

  • Все renderer проверяются вместе с приложением DS Builder
  • Нет загрузки внешнего исполняемого кода
  • Хорошо подходит для фиксированного набора компонентов
Почему текущую реализацию не нужно считать ошибкой4

Ответственность

Границы владения становятся явными

DS Builder

Управляет контекстом и сессией

Собирает конфигурацию, выбирает совместимый модуль, запускает host и показывает результат.

SDDS Team

Поставляет общую платформу

Владеет контрактом, SDK, hosts, tooling и preview всех Core-компонентов.

Design-system teams

Владеют своими renderer

Разрабатывают, проверяют и публикуют preview-модули пользовательских компонентов.

Все участники работают через единый Preview Protocol и одинаковую модель публикации модулей
Общая инфраструктура централизована, продуктовый код остаётся у владельцев9
Что получаем

Новая модель снимает блокировки, но добавляет инфраструктуру

Преимущества

  • Настоящие компоненты каждой платформы
  • Новые компоненты без пересборки приложения DS Builder
  • Независимые релизы Core и design-system модулей
  • Одинаковая модель для встроенных и пользовательских компонентов

Недостатки и цена

  • Нужно создать SDK, hosts и сервис артефактов
  • Исполняемые модули требуют security и trust policy
  • Сложнее диагностика нескольких runtime
  • Каждая платформа должна поддерживать свой renderer
Гибкость достигается через явный контракт и платформенную ответственность10
