---
description: Аутентификация и авторизация
---

Система состоит из набора микросервисов, доступ к которым осуществляется через **API Gateway**. Для обеспечения безопасности используется механизм **JWT-аутентификации** и **RBAC-авторизации в контексте проекта**.

Клиенты взаимодействует только с Gateway. Микросервисы не выполняют проверку токена напрямую и не обращаются к сервису проектов для определения ролей.

Для работы механизма аутентификации и авторизации необходим следующий минимальный набор сервисов:
- Auth service - сервис аутентификации
- Projects service - сервис управления проектами и ролями пользователей
- Gateway - API шлюз - точка входа в систему

Авторизация осуществляется на основе ролей пользователя в конкретном проекте.
## Auth service.

Отвечает за аутентификацию пользователей с использованием протокола OAuth2. Можно выделить следующий минимальный набор функций:
- login пользователя
- Выдача и проверка Access Token
- Хранение пользователей
- Назначение глобальных ролей - ролей, действующих на всю систему и не ограниченных проектом.

Требования к JWT токену:
- Содержит userId
- Содержит глобальную роль (например, system_admin, user)

## Gateway
Шлюз - главная точка входа в систему, Nginx. Все клиенты должны общаться с системой через этот сервис. Минимальный набор функций:
- Проксирует запросы к различным сервисам
- Делегирует проверку токена в auth service
- Извлекает роль пользователя в проекте и формирует нужные заголовки

Требования к шлюзу:
- Маршрутизация. Сервисы, требующие авторизации на уровне проекта, должны быть под URL с projectId
- Rate limit
- Мониторинг и логирование
- Безопасность - аутентификация и авторизация через сервис Auth

## Projects service

Отвечает за хранение информации о проектах. Можно выделить следующий минимальный набор функций:
- Хранение метаданных проекта
- Хранение членов проекта с их ролями
- Механизм проверки роли пользователя внутри проекта - должен быть доступен только для gateway

Gateway обращается к Project Service только через **internal API**.

## Процесс обработки типового запроса к системе

### 1. Пользователь отправляет запрос

```
POST /projects/{projectId}/design-system/{dsId}/tenants
Authorization: Bearer <JWT>
```

### 2. Проверка токена (аутентификация)
Gateway отправляет токен на проверку в Auth Service.
Auth Service выполняет:
- проверку подписи токена
- проверку срока действия
- проверку issuer
- проверку audience

Если токен невалидный, Gateway возвращает:
```
401 Unauthorized
```

### 3. Извлечение идентификатора пользователя
Если токен валиден, Gateway извлекает из него: `userId = sub`
Также Gateway извлекает из URL: `projectId`

## 4. Получение роли пользователя
Gateway определяет роль пользователя в проекте.

- Gateway делает запрос в ProjectService (к internal api).
- Project Service возвращает роль пользователя.
### 5. Наполнение запроса заголовками
Gateway добавляет в запрос служебные заголовки:
```
X-User-Id
X-Project-Id
X-Project-Role
```
После этого Gateway проксирует запрос в целевой API-сервис.

### 6. Проверка разрешений (авторизация)
API-сервис выполняет проверку разрешений, согласно общим правилам и доменной логики сервиса.
Проверка основана на соответствии: role → permissions
Например,
Для изменения значения токена сервис Tokens должен проверить, что у роли в заголовке запроса X-Project-Role есть соответствующий permission tokens:write.

### 7. Принятие решения
#### Если разрешения нет
Сервис возвращает:
```
403 Forbidden
```
#### Если разрешение есть
Сервис выполняет бизнес-логику и возвращает результат.
