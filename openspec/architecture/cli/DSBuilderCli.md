# DS Builder CLI

`dsbuilder` — CLI для локальной синхронизации артефактов дизайн-системы из бэкенда DS Builder в рабочий проект. CLI запускается локально или в CI, читает локальный контекст проекта, делает авторизованные запросы в бэкенд и записывает результат в `.sdds`.

## Назначение CLI

CLI нужен для повторяемых сценариев работы с дизайн-системой:

- инициализировать локальный проект командой `dsbuilder init`;
- проверить доступ к настроенному проекту и дизайн-системе командой `dsbuilder status`;
- загрузить тенанты, палитру, токены и значения токенов командой `dsbuilder theme fetch`;
- управлять локальными псевдонимами тенантов командой `dsbuilder theme alias`.

CLI работает в контексте конкретного проекта DS Builder и дизайн-системы. Этот контекст хранится локально в `.sdds/config.json`, а не передается заново в каждую команду.

## Общий процесс запуска

Типовой запуск команды, которой нужен бэкенд, выглядит так:

```text
Разработчик / CI
  │
  ▼
dsbuilder <command>
  │
  ├─► ищет ближайший .sdds/config.json вверх от текущей директории
  │
  ├─► читает projectId, designSystemId и ссылку на учетные данные
  │
  ├─► получает проектный API-ключ из источника среды выполнения
  │
  ├─► делает HTTP-запросы к DS Builder API
  │     Authorization: ProjectKey <api-key>
  │
  └─► пишет или обновляет локальные файлы в .sdds
```

Команда `init` является исключением: она не требует существующего `.sdds/config.json`, потому что сама создает этот файл в текущей директории.

## Директория `.sdds`

`.sdds` — локальная директория с контекстом проекта и загруженными артефактами дизайн-системы. Она создается в корне проекта, где пользователь запускает `dsbuilder init`.

CLI ищет `.sdds/config.json` от текущей директории вверх по дереву. Поэтому команды можно запускать не только из корня проекта, но и из вложенных директорий: будет использован ближайший родительский `.sdds/config.json`.

Текущая структура:

```text
.sdds/
  config.json
  tenants/
    palette.json
    <tenant-directory>/
      meta.json
      android/
        android_<token-type>.json
      ios/
        ios_<token-type>.json
      web/
        web_<token-type>.json
```

### Зачем нужна `.sdds`

`.sdds` отделяет сгенерированные артефакты дизайн-системы от исходного кода приложения и задает стабильный контракт между DS Builder CLI и потребителями токенов в проекте.

Директория нужна для четырех задач:

- хранить локальный контекст проекта без секретов;
- держать загруженную палитру и файлы тем рядом с проектом;
- сделать результат `theme fetch` детерминированным и пригодным для проверки изменений;
- позволить инструментам проекта читать дизайн-токены из фиксированного места.

CLI считает файлы внутри `.sdds/tenants` сгенерированным результатом. При повторном `theme fetch` он удаляет известные ранее сгенерированные файлы тенанта и платформы, затем записывает актуальный результат заново. Локальные псевдонимы тенантов сохраняются в `config.json`.

## `config.json`

`.sdds/config.json` — локальная конфигурация проекта. Она связывает рабочую директорию с проектом DS Builder и дизайн-системой.

Примерная структура:

```json
{
  "projectId": "project-123",
  "designSystemId": "ds-456",
  "credential": {
    "type": "env",
    "name": "DSBUILDER_API_KEY"
  },
  "tenants": [],
  "palettePath": null
}
```

Назначение полей:

| Поле | Назначение |
| --- | --- |
| `projectId` | Идентификатор проекта DS Builder. Используется во всех проектных маршрутах бэкенда. |
| `designSystemId` | Идентификатор дизайн-системы внутри проекта. Используется для загрузки тенантов и токенов. |
| `credential` | Ссылка на источник API-ключа в среде выполнения. Секрет не хранится в конфигурации. |
| `tenants` | Локальные метаданные загруженных тенантов: `id`, `name`, `directoryPath`, `alias` и временные метки. |
| `palettePath` | Относительный путь до загруженного `palette.json`. |

Конфигурация не должна содержать API-ключ в открытом виде, приватные URL, токены доступа или другие секреты. Это позволяет безопасно хранить `.sdds/config.json` в репозитории, если продуктовая политика проекта разрешает коммитить сгенерированные метаданные дизайн-системы.

## Инициализация проекта

`dsbuilder init --project-id <id> --design-system-id <id>` создает `.sdds/config.json`.

Во время `init` CLI:

1. Берет текущую директорию как корень целевого проекта.
2. Создает директорию `.sdds`, если ее еще нет.
3. Создает `.sdds/config.json`.
4. Записывает `projectId`, `designSystemId` и ссылку на учетные данные.
5. Не перезаписывает существующую конфигурацию молча.

По умолчанию ссылка на учетные данные указывает на env-переменную `DSBUILDER_API_KEY`. Пользователь может указать другое имя env-переменной через `--api-key-env`.

## Загрузка темы

`dsbuilder theme fetch` синхронизирует локальные артефакты тем с бэкендом.

Последовательность работы:

1. CLI находит ближайший `.sdds/config.json`.
2. Из конфигурации получает `projectId`, `designSystemId` и имя env-переменной с API-ключом.
3. Получает API-ключ из источника среды выполнения.
4. Загружает удаленные данные:
   - тенанты;
   - токены;
   - палитру;
   - значения токенов для каждого тенанта.
5. Проверяет, что для каждого включенного токена есть значение в каждом тенанте.
6. Строит локальный план записи.
7. Записывает:
   - `tenants/palette.json`;
   - `tenants/<tenant>/meta.json`;
   - файлы платформ для `android`, `ios`, `web`.
8. Обновляет `tenants` и `palettePath` в `.sdds/config.json`, сохраняя существующие локальные псевдонимы.

Имена директорий тенантов нормализуются, чтобы получались стабильные и безопасные для файловой системы пути. Значения токенов группируются по платформе и типу. Если значение токена имеет `mode`, режим добавляется как префикс к имени токена в сгенерированном JSON.

## Псевдонимы тенантов

Псевдоним тенанта — локальное имя тенанта, удобное для CLI-команд и инструментов-потребителей. Псевдоним хранится только в `.sdds/config.json` и не отправляется в бэкенд.

Команды:

```text
dsbuilder theme alias list
dsbuilder theme alias set --tenant-id <tenant-id> --alias <alias>
dsbuilder theme alias unset <alias>
```

При повторной загрузке тем CLI сопоставляет псевдонимы по `tenant.id` и переносит их в обновленную конфигурацию.

## Авторизация

CLI использует проектный API-ключ. Это отдельный участник для автоматизации, CI и локальных интеграций, описанный в `ADR-0001`.

Ключ не хранится в `.sdds/config.json`. Конфигурация хранит только ссылку на env-переменную:

```json
{
  "credential": {
    "type": "env",
    "name": "DSBUILDER_API_KEY"
  }
}
```

Разрешение API-ключа выполняется при каждом запуске команды в таком порядке:

1. Значение `--api-key`, если оно явно передано для текущего запуска.
2. Env-переменная, указанная в `.sdds/config.json`.
3. Env-переменная `DSBUILDER_API_KEY`.

Если ключ не найден, CLI завершает команду с пользовательской ошибкой и не делает запрос в бэкенд.

Для запросов в бэкенд CLI добавляет HTTP-заголовок:

```http
Authorization: ProjectKey <api-key>
```

Бэкенд/Gateway проверяет проектный ключ, определяет контекст проекта и разрешения ключа. CLI не вычисляет RBAC локально: он только передает ключ и идентификаторы проекта и дизайн-системы. Решение `401`, `403` или успешный доступ принимает бэкенд.

Обработка типовых ответов:

| HTTP-статус | CLI-сообщение |
| --- | --- |
| `401 Unauthorized` | API-ключ отсутствует или невалиден. |
| `403 Forbidden` | API-ключ не имеет доступа к проекту. |
| `404 Not Found` | Проект или ресурс не найден. |
| Другой non-2xx | Бэкенд вернул ошибку с HTTP-статусом. |

## Маршруты бэкенда

Для `theme fetch` CLI использует проектные маршруты:

```text
GET /api/projects/{projectId}/ds/design-systems/{designSystemId}/tenants
GET /api/projects/{projectId}/ds/design-systems/{designSystemId}/tokens
GET /api/projects/{projectId}/ds/palette
GET /api/projects/{projectId}/ds/tenants/{tenantId}/token-values
```

Все запросы идут с `Authorization: ProjectKey <api-key>`.

## Границы ответственности

CLI отвечает за:

- локальный контекст проекта;
- разрешение учетных данных в среде выполнения;
- загрузку удаленных данных дизайн-системы;
- преобразование удаленных данных в структуру `.sdds`;
- детерминированную локальную запись и сохранение псевдонимов.

Бэкенд отвечает за:

- выпуск, хранение хеша и отзыв проектных API-ключей;
- проверку проектного ключа;
- проверку проектных разрешений;
- валидацию существования проекта, дизайн-системы, тенантов и токенов;
- отдачу канонических данных дизайн-системы.

`.sdds` не является источником истины для DS Builder. Источник истины находится в бэкенде; `.sdds` — локальный снимок, пригодный для использования приложением, ревью и повторяемых сценариев сборки.
