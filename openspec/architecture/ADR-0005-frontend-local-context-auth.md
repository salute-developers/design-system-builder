# ADR-0005: Локальный контекст и авторизация клиентской части DS Builder

## Статус
* На ревью.

## Контекст

`frontend-kt` должен обслуживать несколько типов клиентов:

- терминальный CLI;
- desktop-приложение;
- IDE-плагины;
- среду выполнения MCP, описанную в [ADR-0004: MCP сервер клиентской части DS Builder](./ADR-0004-dsbuilder-cli-mcp.md);
- будущие клиентские приложения.

Эти клиенты должны понимать, с какой дизайн-системой они работают, какую версию и платформу использовать, какие права
есть у пользователя или автоматизированного участника и где хранить локальные настройки. Раньше CLI-модель была проще:
команда искала
`<workspace>/.sdds/config.json`, брала оттуда `projectId`, `designSystemId` и ссылку на проектный ключ. Такая модель
подходит для сценариев, привязанных к рабочей директории, но не покрывает все случаи.

Проблемный сценарий потребителя:

```text
Пользователь подключил библиотеку дизайн-системы как зависимость приложения.
Он хочет использовать IDE-плагин и MCP-инструменты для подсказок, документации и ссылок на код.
Он не развивает саму дизайн-систему и не хочет, чтобы плагин молча создавал .sdds в проекте приложения.
```

Определять дизайн-систему по зависимостям проекта как основной механизм нельзя. Это хрупко из-за соглашений об именовании
в registry, catalog-файлов версий, BOM, транзитивных зависимостей, composite build, локальных репозиториев и проектов с
несколькими дизайн-системами.

## Решение

Нужно отделить локальный контекст проекта от пользовательского профиля и интерактивного выбора дизайн-системы.

Ключевое решение:

> `<workspace>/.sdds` является источником контекста для сценариев CLI, генерации и CI, привязанных к рабочей директории,
> но не является обязательным контрактом для сценариев потребителя. IDE-плагин, desktop и MCP должны получать контекст через
> общий `ContextResolver`, который поддерживает локальную `.sdds`, глобальную пользовательскую `~/.sdds`, настройки
> запускающего приложения и явный выбор авторизованного пользователя.

### Два уровня `.sdds`

#### Локальная `.sdds` проекта

```text
<workspace>/.sdds/
  config.json
  tenants/
  docs/
  generated/
```

Локальная `.sdds` проекта используется, когда рабочая директория действительно связана с DS Builder:

- разработка кодовой библиотеки дизайн-системы;
- `dsbuilder init`;
- `dsbuilder theme fetch`;
- `dsbuilder docs generate`;
- `dsbuilder docs publish`;
- CI;
- воспроизводимые локальные артефакты.

В локальной `.sdds` проекта можно хранить:

- `projectId`;
- `designSystemId`;
- ссылку на источник учетных данных, но не секрет;
- локальные сгенерированные артефакты;
- результат синхронизации тем;
- временные файлы сборки документации;
- локальную привязку рабочей директории к DS Builder.

IDE-плагин или среда выполнения MCP не должны автоматически создавать `<workspace>/.sdds` в проекте потребителя без явного
действия пользователя. Создание локальной `.sdds` проекта должно быть результатом команды или подтвержденного UI-сценария.

#### Глобальная пользовательская `.sdds`

```text
~/.sdds/
  config.json
  profiles/
  contexts/
  cache/
    documentation/
    tokens/
    components/
  credentials/
    keychain-ref.json
```

Глобальная пользовательская `.sdds` используется для пользовательского окружения:

- настройки CLI, desktop и IDE-плагинов;
- список окружений бэкенда;
- выбранные пользователем проекты и дизайн-системы;
- последние выбранные `projectId`, `designSystemId`, `version`, `platform`;
- кэш документации, токенов, компонентов и CodeBinding;
- ссылки на учетные данные в keychain, хранилище учетных данных или другом безопасном хранилище.

Глобальная пользовательская `.sdds` не должна быть источником сгенерированных проектных артефактов, которые должны жить в
рабочей директории и участвовать в локальной сборке или ревью.

### Режимы работы

#### Режим с привязкой к рабочей директории

Подходит для владельцев и разработчиков дизайн-системы, CI и сценариев генерации:

```text
<workspace>/.sdds/config.json
  -> projectId
  -> designSystemId
  -> ссылка на учетные данные
  -> сгенерированные артефакты
```

Основные учетные данные - проектный ключ доступа. Он подходит для автоматизации, CI и повторяемых команд. Проектный ключ
не является пользователем и проверяется бэкендом/gateway согласно
[ADR-0001: Auth, Projects и project-scoped RBAC](./ADR-0001-auth-projects-rbac.md).

#### Режим потребителя дизайн-системы

Подходит для пользователя дизайн-системы, который подключил библиотеку как зависимость и хочет использовать IDE-плагин,
desktop или MCP:

```text
авторизация пользователя
  -> список доступных проектов и дизайн-систем
  -> явный выбор projectId/designSystemId/version/platform
  -> сохранение выбора в настройках запускающего приложения или ~/.sdds
  -> MCP-инструменты работают с выбранным контекстом
```

В этом режиме локальная `.sdds` проекта не обязательна. Пользователь выбирает дизайн-систему явно из доступных ему в
DS Builder проектов. Выбор можно сохранить:

- в настройках рабочей директории IDE;
- в настройках desktop-приложения;
- в `~/.sdds/contexts`;
- в пользовательском профиле клиентского приложения.

### Авторизация

Нужно поддерживать два класса учетных данных.

#### Проектный ключ

Проектный ключ доступа используется для:

- CI;
- автоматизации;
- CLI-сценариев, привязанных к рабочей директории;
- сценариев генерации и публикации, где пользователь явно настроил проектный ключ.

Ключ не хранится в локальной `.sdds` проекта в открытом виде. Конфигурация хранит только ссылку на источник:

```json
{
  "credential": {
    "type": "env",
    "name": "DSBUILDER_API_KEY"
  }
}
```

#### Авторизация пользователя

Интерактивные клиенты должны поддерживать пользовательскую авторизацию:

- desktop;
- IDE-плагины;
- интерактивный CLI;
- среду выполнения MCP, запущенную из запускающего приложения.

ADR не фиксирует конкретный способ авторизации пользователя. Это может быть OAuth/OIDC через браузер, device code flow,
SSO или другой утвержденный способ. Не нужно фиксировать контракт как “логин и пароль”, потому что это привяжет
архитектуру к одному механизму входа.

Авторизация пользователя нужна, чтобы клиент мог:

- получить список доступных пользователю проектов;
- получить список доступных дизайн-систем;
- выбрать версию и платформу;
- выполнять инструменты только для чтения без проектного ключа;
- выполнять операции записи/публикации в рамках прав пользователя, если такие операции разрешены.

Среда выполнения MCP не должна сама реализовывать отдельную модель авторизации. Она получает учетные данные от
запускающего приложения или общего механизма учетных данных.

### Разрешение контекста

Общий `ContextResolver` должен поддерживать несколько источников контекста.

Базовый приоритет для интерактивных потребительских сценариев:

```text
1. Явный контекст от запускающего приложения или входных данных инструмента
2. Выбор авторизованного пользователя
   projectId + designSystemId + version + platform
3. Локальный <workspace>/.sdds/config.json
4. Настройки рабочей директории запускающего приложения
5. Глобальный пользовательский ~/.sdds/config.json или ~/.sdds/contexts
6. Требуется ручной выбор
```

Для сценариев с привязкой к рабочей директории, например `dsbuilder docs generate`, `dsbuilder docs publish` и CI, после
явно переданного контекста основным источником является локальный `<workspace>/.sdds/config.json`. Это нужно, чтобы
команды владельцев дизайн-системы были воспроизводимыми и не зависели от последнего выбора пользователя в IDE, desktop
или глобальной `~/.sdds`.

Пояснения:

- явный контекст нужен для MCP-инструментов, desktop и IDE, когда запускающее приложение уже знает активную дизайн-систему;
- выбор авторизованного пользователя является основным сценарием потребителя;
- локальная `.sdds` проекта остается основным сценарием с привязкой к рабочей директории;
- настройки запускающего приложения позволяют IDE-плагину хранить выбор на уровне рабочей директории без создания `.sdds`;
- глобальная пользовательская `.sdds` позволяет переиспользовать выбор между проектами и клиентами;
- если контекст не найден, клиент должен попросить пользователя выбрать проект, дизайн-систему, версию и платформу.

Определение дизайн-системы по зависимостям проекта не является источником истины. Клиент может использовать зависимости
только как подсказку для выбора платформы или версии, но финальный контекст должен задаваться явно пользователем,
настройками запускающего приложения, `.sdds` или профилем авторизованного пользователя на бэкенде.

### Платформа

Платформа должна быть частью активного контекста:

```text
projectId
designSystemId
version
platform
```

Основной источник платформы - явный выбор пользователя или запускающего приложения.

IDE может предлагать платформу как подсказку:

- Android Studio может предложить `android-compose` или `android-view`;
- IntelliJ в web-проекте может предложить `react`;
- desktop может предложить последнюю выбранную платформу;
- если уверенности нет, клиент не должен угадывать.

Проект может использовать несколько платформ или несколько дизайн-систем. Поэтому MCP-инструменты должны принимать
`platform` явно или использовать активную платформу из разрешенного контекста.

### Хранение учетных данных

Правила:

- секреты не хранятся в `<workspace>/.sdds/config.json`;
- глобальная пользовательская `~/.sdds` может хранить только ссылки на учетные данные, но не обязательно сами секреты;
- предпочтительное место для пользовательских токенов - системный keychain, хранилище учетных данных или безопасное
  хранилище запускающего приложения;
- проектный ключ для CI может приходить из переменных окружения;
- среда выполнения MCP не должна логировать учетные данные и не должна отдавать их агенту через инструменты.

### Диагностика

Если контекст не найден:

```json
{
  "code": "CONTEXT_NOT_FOUND",
  "message": "Не выбран проект, дизайн-система, версия и платформа."
}
```

Если требуется интерактивная авторизация:

```json
{
  "code": "AUTH_REQUIRED",
  "message": "Требуется авторизация пользователя в DS Builder."
}
```

Если локальная `.sdds` проекта отсутствует в проекте потребителя, это не ошибка само по себе. Ошибкой является только
отсутствие любого пригодного контекста.

## Последствия

- `.sdds` перестает быть единственным способом определить контекст DS Builder.
- Проекты потребителей не загрязняются `.sdds` без явного действия пользователя.
- IDE-плагины и desktop могут работать через авторизацию пользователя и явный выбор дизайн-системы.
- CLI и CI сохраняют проектный ключ и локальную `.sdds` проекта для воспроизводимых сценариев с привязкой к рабочей
  директории.
- Среда выполнения MCP получает контекст и учетные данные от общего прикладного слоя клиентской части, а не решает их
  самостоятельно.
- Определение по зависимостям не используется как источник истины.

## Открытые вопросы

- Какой сценарий авторизации пользователя выбрать первым для CLI/desktop/IDE: OAuth/OIDC через браузер, device code flow
  или другой вариант?
- Где хранить глобальную пользовательскую конфигурацию на разных ОС: строго `~/.sdds` или системная директория
  конфигурации?
- Нужно ли синхронизировать выбранные контексты между desktop, IDE-плагином и CLI через пользовательский профиль на
  бэкенде?
- Какие права нужны пользовательским токенам и проектным ключам для MCP-инструментов только для чтения, генерации и
  публикации?
