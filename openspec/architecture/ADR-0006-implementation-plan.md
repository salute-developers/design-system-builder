# План реализации preview Compose-компонентов

Документ дополняет [ADR-0006](./ADR-0006-components-preview.md). ADR фиксирует целевую архитектуру, а здесь записан порядок работ по отдельным изменениям OpenSpec. Список живой: при выполнении или пересмотре изменения обновляйте его статус.

## Цель первого релиза

Показывать в клиенте DS Builder на сайте настоящие Compose-компоненты, собранные в Wasm-плагин, для всего набора Core-компонентов.

Preview строится для **текущего состояния** дизайн-системы: клиент загружает модель из базы (`themeEditorRepository.load`), поверх неё накладываются несохранённые правки редактора, и результат передаётся плагину. Это работает одинаково при редактировании и при простом просмотре: отдельный режим редактирования для preview не нужен.

Preview выпущенных версий дизайн-системы в первый релиз не входит (см. «Отложенное»).

## Что уже есть (прототип)

| Часть | Репозиторий | Состояние |

| `@Story` для Core-компонентов (около 74) | plasma-android, `uikit-compose-fixtures` | Есть |

Ветки прототипа перебазированы локально: `feature/compose-preview` на `feature/ds-service` и `feature/preview-compose` на `develop`. Новые рабочие ветки: `feature/compose-preview-web` в обоих репозиториях.

| № | Изменение | Репозиторий | Статус | Зависит от |

| 1 | `ship-compose-preview-on-web` | оба | Не начато | — |

### 1. `ship-compose-preview-on-web`

- Перенести прототип на новые ветки.
- Собрать плагин и прогнать тесты и браузерную проверку клиента на перебазированных ветках (после перебазирования не запускались).
- Клиент загружает плагин во время работы по адресу из переменной сборки (плагин не входит в сборку клиента и не линкуется с ним); в README описано, как собрать и раздать архив, локально есть готовый скрипт.
- Проверка manifest, включение Compose-preview только при заданном адресе, возврат к React-preview при сбоях.
- CI/CD, хранилище и инфраструктура не меняются: доставка на DEV и PROM отложена.
- Убрать дубли `.agents/skills/openspec-*`, добавленные прототипом.

### 2. `preview-payload-v2`

Расширить контракт под реальные данные компонентов:

- градиенты и alpha цвета;
- типы состояний и кастомные состояния компонентов (например, `Checked`, `Indeterminate`);
- вложенные стили компонентов (`dependencies`);
- shadow и icon;
- единый владелец JSON Schema вместо трёх копий (`backend-kt/preview/contract`, `plasma-android/.../preview-contract`, копия в клиенте).

Менять контракт лучше до первого релиза, пока им никто не пользуется.

### 3. `universal-compose-registry`

- Добавить `componentId` в `@Story` и стабильный `key` в `@StoryProperty`.
- Сделать публичный type-erased реестр в `sandbox-ksp`.
- KSP-генератор фабрик стилей по `uikit-compose-api-meta.json`: на каждый Style-класс сейчас нужна ручная фабрика (для BasicButton это 104 строки).
- Правила выбора перегрузки билдера описать как спецификацию. Код мапперов Theme Builder перенести нельзя, он порождает исходный текст. Правила: приоритет `StatefulValue`, затем `InteractiveColor`, затем обычный тип; для градиента только перегрузки с `Brush`.
- Дифференциальный тест: для одного конфига сравнивать выбор Theme Builder и сгенерированной фабрики, иначе preview расходится с генерируемым кодом.
- Мета подключается как Gradle-зависимость, а не копией файла.
- Начать со спайка на компонентах: BasicButton, CheckBox, TextField, Avatar (перегрузки `Brush` и `StatefulValue`), Tabs (вложенные стили).

### 4. Расширение набора Core-компонентов

Из 79 компонентов в мете 27 содержат только простые типы и значения-перечисления:

| Фаза | Что покрывает | Требует |
| --- | --- | --- |
| A | Простые компоненты (около 27) | изменения 3 |
| B | Компоненты с кастомными состояниями (20) | изменения 2 |
| C | Компоненты с вложенными стилями (48) | изменения 2, рекурсия в фабриках |
| D | Компоненты с icon и shadow | ресурсы и shadow-токены |

## Принятые решения

- Assembler остаётся в клиенте на TypeScript. Он принимает чистый JSON `ComponentPreviewDraft` и не зависит от контроллеров клиента.
- Один плагин на платформу содержит запись на каждый компонент; клиент и assembler про конкретные компоненты ничего не знают.
- Preview строится только для текущего состояния. Серверная часть (`ds-service`, `db-service`) в рамках первого релиза не меняется.

## Отложенное

### Preview выпущенных версий

Решено не делать в первом релизе: нужного продукта «версии» пока нет. В клиенте нет выбора версии из базы, поле `version` в адресе страницы — просто метка `'0.1.0'`, а таблица `design_system_versions.snapshot` содержит только имена токенов и компонентов и нигде не заполняется полноценно. Параметр `version` в `GET /component-config` принимается, но игнорируется.

Если потребуется, нужно сначала выбрать, как хранить прошлое состояние. Рассмотренные варианты:

- **Снимок (JSON) в `design_system_versions.snapshot`.** Нормализованная копия модели с `schemaVersion`, строится на сервере в одной транзакции, неизменяемость обеспечивается триггером в базе. Растёт одна таблица на одну строку за версию. Самая рискованная часть — разнобой формы значений в `token_values.value` (одно и то же поле шрифта встречается под разными именами), поэтому нужна нормализация с явными ошибками.
- **Копия строк (клон дизайн-системы).** Не подходит: около 20 таблиц с перекладыванием ключей, имя дизайн-системы уникально, клон остаётся изменяемым, а общий слой компонентов (`components`, `properties`, `states` и др.) не копируется и продолжает меняться при каждом импорте меты Plasma. Версия «изменяется задним числом».
- **Журнал изменений** (`design_system_changes`): не проверялось, что в нём достаточно данных для восстановления состояния.
- **Пакет, выпускаемый `project-publisher`.** Не проверялось, содержит ли он пригодные для preview данные. Если да, замороженная копия уже существует и снимок не нужен.

Прорабатывавшийся вариант снимка (proposal, design, спецификации и задачи change `snapshot-design-system-version`) остался в истории git, коммит `0d55e554`, ветка `feature/compose-preview-web`.

Перед возвратом к теме нужно ответить на вопросы продукта: что такое «версия» для пользователей, кто и как её создаёт, и нужно ли смотреть прошлые версии в preview.

### Доставка плагина на сайт (DEV и PROM)

Не входит в первое изменение: его цель PoC, связывать сборки клиента и плагина и менять CI/CD не нужно. Что выяснено и решено, чтобы не терять при возврате к теме:

- Клиент деплоится как статика в S3 (`deploy-front-apps-dev.yml`, `deploy-front-apps-prom.yml`, `s3cmd sync --delete-removed --no-mime-magic`). Поэтому плагин нельзя класть в каталог клиента: деплой удалял бы его, и это связало бы релизы клиента и `plasma-android`.
- Плагин выкладывается в соседний каталог бакета по версионированному неизменяемому пути (`.../compose-preview/{версия}/`). Адрес версии задаётся переменной репозитория GitHub для каждого окружения и передаётся шагу сборки клиента. Откат — смена переменной и пересборка клиента.
- Принято: выкладка вручную командой `s3cmd`, автоматизация отдельным изменением.
- `--no-mime-magic` определяет тип содержимого по расширению: корректный `application/wasm` для `.wasm` нужно проверять в каждом окружении до включения для пользователей. Также нужны проверки CORS и кеширования версионированного пути.
- Принято для первого выпуска: плагин в том же бакете и под тем же именем хоста, что клиент. Клиент и плагин тогда на одном источнике, и код плагина способен читать `localStorage` с access- и refresh-токенами (`api/tokenStore.ts`). Допустимо при условиях: плагин собирает только SDDS, сторонние плагины запрещены, право записи в каталог плагина ограничено. Отдельное имя хоста для плагина обязательно до поддержки пользовательских или сторонних плагинов.
- Какое имя хоста стоит перед бакетом в DEV и PROM, из репозитория не видно; это нужно выяснить у того, кто настраивал домен.

### Другое

- Внешнее требование собрать плагин под `js`, а не под `wasmJs`: не принято, решение отложено, первый выпуск строится под `wasmJs`. Подробности и найденные ограничения записаны в `design.md` изменения `ship-compose-preview-on-web`. ADR-0006 закрепляет только `wasmJs`, при смене цели его потребуется обновить.

- Preview вне браузерного клиента (CLI, MCP, скриншоты в CI). Сборка payload сегодня происходит в клиенте на TypeScript, а CLI и MCP написаны на Kotlin. Это не связано со снимками. Кроме payload потребуется хост, способный выполнить Wasm-плагин (например, headless-браузер). Варианты: Node-процесс с assembler, порт на Kotlin, серверный assembler. Откладывается до появления реального потребителя.
- `GET /component-config`: сделать параметр `version` осмысленным. Клиенты сегодня передают в него произвольную метку, поэтому смена семантики их сломает.
- Замерить размер Wasm-бандла и время холодного старта; предусмотреть запасной вариант на React-preview для браузеров без WasmGC.
- Обновить ADR-0006:
  - закрыть открытый вопрос о платформе значений токенов для Compose (`android` против `compose`; в прототипе обойдено явным `themeValuePlatform`);
  - отметить расхождения с прототипом: assembler в клиенте, собственный формат manifest, расположение `preview-contract` в plasma-android;
  - уточнить, что единица работы на компонент — фабрика стиля по мете билдера, а не регистрация story.
- Вне первого релиза: серверный assembler, Preview Artifact Service и `PreviewPluginResolver`, десктопный клиент, плагины для React, Android и iOS.
