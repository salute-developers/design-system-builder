# design-system-request-scope Specification

## Purpose
Ограничить чтения и мутации системных сущностей выбранной дизайн-системой из пути запроса, сохраняя проектные разрешения, глобальный каталог, историю и идемпотентные повторы.

## Requirements
### Requirement: Системный ресурс имеет обязательную границу запроса

API SHALL публиковать принадлежащие дизайн-системе ресурсы под `/api/projects/{projectId}/design-systems/{designSystemId}` и применять ожидаемую систему ко всем чтениям и мутациям. Ограничение SHALL дополнять существующие проектные разрешения, в том числе для администратора. Самостоятельный внутренний вход SHALL применять ту же границу под `/api/design-systems/{designSystemId}`.

#### Scenario: UUID другой системы доступного проекта
- **WHEN** путь указывает систему A, а UUID токена, темы, конфигурации или другой системной сущности принадлежит B того же проекта
- **THEN** API MUST вернуть `404` без данных B и без изменения состояния

#### Scenario: Администратор передал чужой системе UUID
- **WHEN** администратор вызывает системный маршрут A с UUID ресурса B
- **THEN** API MUST вернуть `404`, сохранив ограничение A

#### Scenario: Неверный идентификатор системы
- **WHEN** системный путь содержит некорректный UUID системы
- **THEN** API MUST вернуть `400`, не выполняя запрос в области всего проекта

#### Scenario: Создание сущности не дублирует систему
- **WHEN** клиент создаёт сущность по системному пути и передаёт допустимые данные без `designSystemId` в теле
- **THEN** API MUST использовать систему пути и MUST NOT требовать её дублирования

#### Scenario: Входной контракт системной операции
- **WHEN** клиент формирует запрос создания, изменения, импорта, выгрузки, публикации либо другой системной операции
- **THEN** входной DTO и query-контракт MUST NOT содержать дублирующий `designSystemId`; клиент MUST передать систему в пути
- **AND** `designSystemId` ответов и внутренние идентификаторы application-команд MUST сохраняться там, где они нужны существующей модели

#### Scenario: Неизвестное поле не меняет систему
- **WHEN** запрос содержит устаревшее поле `designSystemId` в теле
- **THEN** сервер MUST применить действующую политику неизвестных JSON-полей и MUST NOT использовать это поле для выбора или переопределения системы пути

#### Scenario: Создаётся сама дизайн-система
- **WHEN** клиент вызывает `POST /api/projects/{projectId}/design-systems`
- **THEN** API MUST создавать новую систему в проекте без требования ID уже существующей системы

#### Scenario: Система глобально доступна только на чтение
- **WHEN** участник читает глобально доступную систему или пытается изменить её
- **THEN** API MUST сохранить существующие разрешения чтения и запрет записи; системный путь не расширяет права

### Requirement: Списки и временные границы ограничены системой

API SHALL ограничивать списки, счётчики, связанные сущности, разрешённые значения и метаданные одной ожидаемой системой до формирования ответа. Версия и курсор SHALL проверяться относительно той же системы. Допустимый пустой список SHALL отличаться от отсутствия доступа к самой системе.

#### Scenario: Два черновика в одном проекте
- **WHEN** клиент читает список A, а в проекте также существует B
- **THEN** DTO, сводки и метаданные ответа MUST содержать только системные данные A

#### Scenario: Чужая опубликованная версия
- **WHEN** запрос к A содержит `versionId` или курсор B
- **THEN** API MUST отклонить запрос существующей ошибкой неверного курсора либо `404` для чужой версии без подстановки другого черновика

#### Scenario: Система отсутствует и элементов нет
- **WHEN** клиент читает пустой список неизвестной или недоступной системы
- **THEN** API MUST вернуть `404`, а не успешный пустой список

### Requirement: Пакет не выходит за границу системы

Любая пакетная команда SHALL проверять все адресованные системные элементы и ссылки. Нарушение границы SHALL откатывать всю операцию, включая устойчивые строки, редакции, журнал, результаты повторяемости и уведомления. Чужие элементы MUST NOT молча исключаться из успешного пакета.

#### Scenario: Значения темы смешивают системы
- **WHEN** сохранение значений темы A или создание темы с начальными значениями содержит токен B
- **THEN** API MUST отклонить пакет без сохранения темы или любого значения пакета

#### Scenario: Порядок или комбинация содержит чужой элемент
- **WHEN** порядок осей/значений/состояний либо пакет членов комбинации A адресует системный UUID B
- **THEN** API MUST отклонить команду и сохранить исходное состояние целиком

#### Scenario: Переименование или удаление затрагивает зависимости
- **WHEN** в A переименовывается или удаляется группа, семейство токенов либо конфигурация с зависимыми ссылками
- **THEN** API MUST изменять только принадлежащие A предметные редакции; ссылки и редакции B MUST остаться прежними

#### Scenario: Пустой пакет недоступной системы
- **WHEN** клиент отправляет пустую пакетную команду в недоступную систему
- **THEN** API MUST проверить доступ к системе и MUST NOT вернуть успех вследствие отсутствия элементов

### Requirement: Импорт и предварительная проверка имеют одну границу

Импорт конфигураций, выгрузка, web-адаптер, пакет редактора и чтение конфигурации по имени SHALL ограничиваться системой пути. `dryRun` SHALL применять те же проверки и контекст транзакции, что сохранение, с обязательным откатом. Существующая семантика переносимых идентификаторов файла и предметных отчётов импорта SHALL сохраняться.

#### Scenario: Импорт в A содержит системную ссылку B
- **WHEN** сохраняемый импорт или `dryRun` в A пытается адресовать серверную системную сущность B
- **THEN** API MUST отклонить нарушение границы без сохранения каких-либо изменений этого запроса

#### Scenario: Предварительная проверка глобальных последствий
- **WHEN** допустимый `dryRun` создаёт промежуточные подключения, зависимости или наборы состояний
- **THEN** после ответа MUST отсутствовать все созданные этим запросом изменения, включая глобальные служебные последствия импорта

#### Scenario: Имя не совпадает с системой пути
- **WHEN** чтение или импорт по пути A передаёт имя системы B как параметр выбора
- **THEN** API MUST отклонить несовпадение и MUST NOT выбирать B вместо A

#### Scenario: Импорт переносимой конфигурации
- **WHEN** допустимый импорт использует имена и переносимые идентификаторы исходного файла
- **THEN** API MUST сохранить текущие правила разрешения этих идентификаторов внутри целевой системы, не выдавая их за UUID ресурсов другой системы

### Requirement: Публикация журнал и события сохраняют границу

Публикация, чтение и откат журнала, поток SSE SHALL использовать ожидаемую систему. Проверки SHALL выполняться и для специализированной публикационной транзакции, и при повторном чтении курсора SSE.

#### Scenario: Черновик другой системы
- **WHEN** публикация по пути A содержит `draftId` системы B
- **THEN** API MUST отклонить команду без публикации и изменения любой системы

#### Scenario: Пакетный откат смешивает изменения
- **WHEN** запрос отката A содержит `changeId` из A и B
- **THEN** API MUST отклонить пакет без отката изменения A или B

#### Scenario: События другой системы
- **WHEN** клиент подписан на A, а изменяется B
- **THEN** поток MUST NOT выдавать событие B или метаданные его черновика

### Requirement: Транзакционный контекст не теряется и не переносится между операциями

Контекстные транзакции чтения, записи, отката и публикации SHALL устанавливать ожидаемую систему для своей операции. Установка контекста SHALL NOT требовать существования системы: совпавший идемпотентный повтор SHALL возвращаться до проверки существования, а новое предметное выполнение и чтение SHALL проверять доступность системы до обращения к её данным. Глобальные операции SHALL явно очищать эту границу. Повтор транзакции SHALL повторно устанавливать её. Проверки только в HTTP или только при блокировке MUST NOT считаться достаточными.

#### Scenario: Соединение повторно используется
- **WHEN** одно соединение последовательно обслуживает A, глобальную операцию и B
- **THEN** каждая операция MUST иметь только свою границу, независимо от предыдущего commit или rollback

#### Scenario: Повтор после конфликта транзакций
- **WHEN** адаптер повторяет транзакцию A после ошибки конкурентного выполнения
- **THEN** повтор MUST применить ту же ожидаемую систему A

### Requirement: Глобальные определения сохраняют самостоятельный контракт

Глобальный каталог компонентов, свойств, платформенных параметров, зависимостей компонентов, состояний, наборов состояний, палитры и плагинов SHALL использовать публичный префикс `/api/projects/{projectId}/design-systems/catalog` без ID системы, сохраняя прежние правила доступа. Настройки переиспользования, оси, стили и значения свойств SHALL оставаться системными. Обогащение глобального компонента системными настройками SHALL обслуживаться системным маршрутом.

#### Scenario: Чтение глобального определения
- **WHEN** клиент читает глобальный компонент или свойство без системного обогащения
- **THEN** API MUST использовать новый адрес под `catalog` без ID системы и сохранить прежнюю доступность независимо от предшествующего системного запроса

#### Scenario: Обогащение свойств или зависимостей
- **WHEN** клиент запрашивает `include=platformParams` либо `include=reuseConfig`
- **THEN** клиент MUST использовать путь `/api/projects/{projectId}/design-systems/{designSystemId}/components/{componentId}/properties` либо `/deps`; прежний глобальный путь MUST отклонить системные параметры с `400`

### Requirement: Перенос адресов однозначен и синхронен

Сервер, OpenAPI, манифест и собственные HTTP-клиенты SHALL использовать одну карту маршрутов. Все прежние системные ссылки в требованиях остальных возможностей SHALL интерпретироваться через приведённые ниже правила переноса; их DTO и предметные правила сохраняются, кроме явно изменённых требований. Удалённые ранее методы SHALL NOT восстанавливаться из устаревшего манифеста.

| Прежний остаток после `/api/projects/{projectId}/ds` | Новый адрес |
|---|---|
| `/design-systems` | `/api/projects/{projectId}/design-systems` |
| `/design-systems/{id}` и его вложенные ресурсы | `/api/projects/{projectId}/design-systems/{designSystemId}` с прежним вложенным остатком |
| `/design-system-versions`, `/design-system-versions/{id}`, `/design-system-versions/by-design-system/{designSystemId}` | Системные `/versions`, `/versions/{id}`, `/versions` соответственно |
| `/tokens`, `/token-values`, `/tenants`, `/token-groups` и их вложенные ресурсы | Тот же остаток под системным корнем |
| `/design-system-components`, `/component-reuse-configs`, `/variations`, `/property-variations`, `/styles` и вложенные ресурсы | Тот же остаток под системным корнем |
| `/appearances`, `/appearance-variations`, `/appearance-variation-values` и вложенные ресурсы | Тот же остаток под системным корнем |
| `/variation-property-values`, `/invariant-property-values`, обе категории `*-platform-param-adjustments`, `/style-combinations`, `/style-combination-members` | Тот же остаток под системным корнем |
| `/component-config` и вложенные операции | Тот же остаток под системным корнем |
| `/components/{id}/variations` | Системный `/components/{componentId}/variations` |
| Вложенный `/by-design-system/{designSystemId}` у стилей/инвариантов | Удаляется, система уже присутствует в корне |
| Глобальные компоненты/свойства/зависимости/состояния/наборы/палитра/плагины | `/api/projects/{projectId}/design-systems/catalog/...` без ID системы; системное обогащение — по отдельному системному пути |

#### Scenario: Старый системный маршрут
- **WHEN** клиент обращается к прежнему системному пути, включая мутацию
- **THEN** сервер MUST вернуть `404`, без перенаправления или определения системы по UUID ресурса

#### Scenario: Совпавшие списки
- **WHEN** после переноса обычный и сводный список получают один адрес
- **THEN** сервер MUST зарегистрировать один обработчик; токены MUST использовать существующий `DesignSystemTokenSummaryResponse`, темы — существующий `TenantResponse`, без нового объединённого DTO; фильтры, граница версии и необязательная пагинация MUST сохраняться

#### Scenario: Собственные клиенты и MCP
- **WHEN** веб-клиент, CLI, MCP или Android Studio plugin читает либо изменяет системный ресурс
- **THEN** его HTTP-адаптер MUST передать выбранную систему в пути и MUST NOT повторять запрос через старый путь при ошибке
- **AND** изменение MUST NOT добавлять новые MCP-инструменты записи или менять локальный формат `.sdds`

#### Scenario: Согласованность регистрации и контракта
- **WHEN** контрактные проверки перечисляют зарегистрированные публичные и внутренние методы/пути
- **THEN** они MUST совпасть с OpenAPI и манифестом с учётом глобальных/административных входов, без двойных обработчиков

### Requirement: Списковые DTO сохраняют используемые клиентами поля

Список токенов SHALL возвращать все поля существующего `DesignSystemTokenSummaryResponse` с прежними типами и nullability, включая `groupId`, `position`, `publishedIn`, `createdAt`, `updatedAt`. Список тем SHALL возвращать существующий `TenantResponse`, включая полный `colorConfig`, `preview`, `editRevision` и даты. Детали и мутации SHALL сохранять свои существующие DTO без расширения ради списка.

#### Scenario: Размещение и публикация токена
- **WHEN** веб-клиент получает список токенов
- **THEN** поля `groupId`, `position` и `publishedIn` MUST позволять восстановить порядок/группы и предупреждения опубликованного токена без отдельных запросов

#### Scenario: Загрузка Kotlin-клиентом
- **WHEN** CLI декодирует списки токенов и тем
- **THEN** ответ MUST содержать прежние обязательные декодируемые поля, включая даты, без изменения локальных форматов; дополнительные поля MUST NOT требовать нового декодера

#### Scenario: Карточка темы и профиль
- **WHEN** клиент читает список тем системы
- **THEN** каждый элемент MUST содержать `colorConfig` с сохранённым профилем и прочими существующими параметрами, а также пять CSS-цветов preview по существующей политике tenant
- **AND** клиент MUST NOT запрашивать отдельно каждую тему ради карточки

#### Scenario: Редакция списка не используется для сохранения
- **WHEN** пользователь открывает редактирование после загрузки или кэширования списка тем
- **THEN** клиент MUST получить необходимые актуальные редакции через существующее предметное чтение, не подменяя их `editRevision` из списка

#### Scenario: Обогащение только выбранной страницы
- **WHEN** список тем ограничен системой, фильтром или страницей
- **THEN** вычисление preview и редакций MUST ограничиваться выбранными элементами после ограничения выборки и MUST NOT расширять ответ данными других систем

### Requirement: Внутренние предметные пути не содержат префикс ds

Самостоятельный вход `ds-service` SHALL публиковать каталог по `/api/design-systems`, глобальные ресурсы — по `/api/design-systems/catalog/{resource}`, карточку и системные ресурсы — по `/api/design-systems/{designSystemId}` и вложенным путям. Административные операции SHALL использовать `/api/admin/...`. Все внутренние клиенты, включая проверку принадлежности `documentation-service`, SHALL использовать канонический контракт. Регистрация маршрутов, OpenAPI, манифест и внутренняя нормализация SHALL NOT использовать префикс `/api/ds` или резервное преобразование в него.

#### Scenario: Внутренняя проверка принадлежности
- **WHEN** `documentation-service` проверяет систему по `/api/design-systems/{id}`
- **THEN** сервис MUST применить существующую проверку принадлежности проекту и вернуть прежний DTO карточки

#### Scenario: Прежний внутренний префикс
- **WHEN** клиент вызывает `/api/ds` либо любой вложенный системный, глобальный или административный путь
- **THEN** сервис MUST вернуть `404`, без алиаса, перенаправления или резервной обработки

#### Scenario: Внутренний глобальный каталог
- **WHEN** внутренний клиент вызывает `/api/design-systems/catalog/components` либо `/api/design-systems/catalog/palette`
- **THEN** сервис MUST обслужить глобальный ресурс с прежними разрешениями и DTO, не интерпретируя статический сегмент как ID системы

#### Scenario: Канонические ключи контракта
- **WHEN** приложение нормализует публичный путь для поиска контракта или политик
- **THEN** оно MUST использовать канонический внутренний путь `/api/design-systems/...` либо `/api/admin/...`, без промежуточного `/api/ds`

### Requirement: Глобальные ресурсы выделены в ветку catalog

Глобальные публичные ресурсы SHALL использовать `/api/projects/{projectId}/design-systems/catalog/{resource}` без ID конкретной системы. Системные ресурсы SHALL использовать `/api/projects/{projectId}/design-systems/{designSystemId}/{resource}`. Статический сегмент `catalog` SHALL NOT интерпретироваться как UUID системы; внутренний вход SHALL использовать симметричную ветку `/api/design-systems/catalog/{resource}`.

#### Scenario: Глобальный каталог компонентов
- **WHEN** клиент вызывает `GET /api/projects/{projectId}/design-systems/catalog/components`
- **THEN** API MUST вернуть глобальный каталог с прежними проектными разрешениями, не требуя ID конкретной системы

#### Scenario: Компоненты выбранной системы
- **WHEN** клиент вызывает `GET /api/projects/{projectId}/design-systems/{designSystemId}/components`
- **THEN** API MUST вернуть компоненты указанной системы с проверкой её доступности

#### Scenario: Приоритет ветки catalog
- **WHEN** клиент обращается к зарегистрированному глобальному ресурсу под `/design-systems/catalog/...` через публичный либо внутренний вход
- **THEN** маршрутизация MUST выбрать глобальный обработчик, не разбирая `catalog` как UUID системы и не устанавливая ожидаемую систему

#### Scenario: Прежний публичный глобальный префикс
- **WHEN** клиент вызывает перенесённый глобальный ресурс по `/api/projects/{projectId}/ds/...`
- **THEN** сервер MUST вернуть `404` без резервной обработки по прежнему пути

#### Scenario: Нет параллельного глобального пути без catalog
- **WHEN** клиент запрашивает глобальный каталог компонентов через прежний корень `/design-systems/components` вместо `/design-systems/catalog/components`
- **THEN** сервер MUST NOT обслуживать его как глобальный каталог; новые глобальные обработчики MUST регистрироваться только под `catalog`
