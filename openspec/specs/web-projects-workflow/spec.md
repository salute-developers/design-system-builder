## Requirements
### Requirement: Пользователь видит доступные проекты

Веб-клиент SHALL показывать вошедшему пользователю проекты, возвращённые `GET /projects`, и SHALL использовать `effectiveRole` каждого проекта для доступных действий.

#### Scenario: Список проектов загружен

- **WHEN** вошедший пользователь открывает начальный экран
- **THEN** клиент MUST показать карточки доступных ему проектов с названием и количеством нетехнических дизайн-систем
- **THEN** клиент MUST показать архивные проекты отдельной секцией ниже активных
- **THEN** клиент MUST NOT показывать описание и статус active в метаданных карточки
- **THEN** клиент MUST открывать проект по стабильному `projectId`

#### Scenario: У пользователя нет проектов

- **WHEN** `GET /projects` возвращает пустой список
- **THEN** клиент MUST показать пустое состояние с действием создания проекта

#### Scenario: Список проектов не загрузился

- **WHEN** запрос списка проектов завершается ошибкой
- **THEN** клиент MUST показать состояние ошибки и действие повторной загрузки

### Requirement: Пользователь создаёт проект

Веб-клиент SHALL позволять вошедшему пользователю создать проект с обязательным названием и необязательным описанием.

#### Scenario: Проект успешно создан

- **WHEN** пользователь отправляет валидную форму создания проекта
- **THEN** клиент MUST вызвать `POST /projects`
- **THEN** клиент MUST открыть обзор созданного проекта по возвращённому `projectId`

#### Scenario: Название проекта не заполнено

- **WHEN** пользователь отправляет форму с пустым после удаления крайних пробелов названием
- **THEN** клиент MUST показать ошибку обязательного поля
- **THEN** клиент MUST NOT отправлять запрос создания

#### Scenario: Создание проекта отменено

- **WHEN** пользователь выбирает отмену
- **THEN** клиент MUST вернуться к списку проектов без создания проекта

#### Scenario: Создание проекта не содержит приглашений

- **WHEN** пользователь открывает форму создания проекта
- **THEN** клиент MUST NOT показывать ввод приглашений незарегистрированных пользователей

### Requirement: Действия проекта соответствуют итоговой роли

Веб-клиент SHALL показывать действия согласно разрешениям целевых ролей `viewer`, `editor`, `maintainer` и `owner`.

#### Scenario: Viewer или Editor открывает проект

- **WHEN** пользователь с `effectiveRole` `viewer` или `editor` открывает проект
- **THEN** клиент MUST позволить просматривать проект и его дизайн-системы
- **THEN** клиент MUST NOT показывать действия изменения метаданных проекта, управления участниками или создания дизайн-системы

#### Scenario: Maintainer управляет проектом

- **WHEN** пользователь с `effectiveRole` `maintainer` открывает проект
- **THEN** клиент MUST показать изменение метаданных, управление участниками и управление дизайн-системами
- **THEN** клиент MUST NOT показывать архивирование или восстановление проекта

#### Scenario: Owner управляет жизненным циклом проекта

- **WHEN** пользователь с `effectiveRole` `owner` открывает проект
- **THEN** клиент MUST показать все действия Maintainer и архивирование либо восстановление проекта

#### Scenario: Прямой переход к недоступному действию

- **WHEN** роль пользователя не разрешает действие, но пользователь открывает его маршрут напрямую
- **THEN** клиент MUST показать состояние отсутствия доступа
- **THEN** клиент MUST NOT отправлять изменяющий запрос

### Requirement: Maintainer и Owner управляют зарегистрированными участниками

Веб-клиент SHALL позволять Maintainer и Owner просматривать участников, искать и добавлять зарегистрированного пользователя по имени, username или адресу электронной почты, менять роль и удалять участника через Projects Service.

#### Scenario: Пользователь ищет зарегистрированного участника

- **WHEN** Maintainer или Owner вводит не менее двух символов имени, username или электронной почты
- **THEN** клиент MUST запросить список совпадающих зарегистрированных пользователей
- **THEN** клиент MUST показать результаты выпадающим списком с именем, username и электронной почтой
- **THEN** клиент MUST позволить выбрать найденного пользователя без создания ожидающего приглашения

#### Scenario: Зарегистрированный пользователь добавлен

- **WHEN** Maintainer или Owner выбирает зарегистрированного пользователя и роль `viewer`, `editor` или `maintainer`
- **THEN** клиент MUST отправить запрос добавления участника
- **THEN** клиент MUST обновить список участников после успеха

#### Scenario: Пользователь не зарегистрирован

- **WHEN** Projects Service сообщает, что пользователь с указанным username или адресом не найден
- **THEN** клиент MUST показать понятную ошибку
- **THEN** клиент MUST NOT создавать ожидающее приглашение

#### Scenario: Недопустимая роль Owner

- **WHEN** Maintainer или Owner выбирает роль нового либо существующего участника
- **THEN** клиент MUST предлагать только `viewer`, `editor` и `maintainer`

#### Scenario: Участник удалён

- **WHEN** Maintainer или Owner подтверждает удаление участника
- **THEN** клиент MUST удалить membership через Projects Service
- **THEN** клиент MUST сохранить Owner проекта вне списка изменяемых membership

### Requirement: Настройки проекта отражают состояние API

Веб-клиент SHALL позволять уполномоченному пользователю обновлять название и описание проекта, а Owner — архивировать и восстанавливать проект.

#### Scenario: Метаданные проекта сохранены

- **WHEN** Maintainer или Owner отправляет валидные название и описание
- **THEN** клиент MUST вызвать `PATCH /projects/{projectId}`
- **THEN** клиент MUST отобразить сохранённые данные из ответа

#### Scenario: Owner архивирует проект

- **WHEN** Owner подтверждает архивирование активного проекта
- **THEN** клиент MUST вызвать `POST /projects/{projectId}/archive`
- **THEN** клиент MUST показать проект как архивный и отключить изменяющие действия, кроме восстановления

#### Scenario: Owner восстанавливает проект

- **WHEN** Owner восстанавливает архивный проект
- **THEN** клиент MUST вызвать `POST /projects/{projectId}/restore`
- **THEN** клиент MUST снова разрешить действия согласно `effectiveRole`
