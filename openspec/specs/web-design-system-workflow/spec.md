## Requirements
### Requirement: Проект показывает свои дизайн-системы

Веб-клиент SHALL показывать дизайн-системы выбранного проекта и количество тем каждой системы без отдельного запроса для каждой карточки.

#### Scenario: Список дизайн-систем загружен

- **WHEN** пользователь открывает обзор проекта
- **THEN** клиент MUST запросить дизайн-системы выбранного `projectId`
- **THEN** каждая запись ответа MUST содержать стабильный `designSystemId`, `tenantCount` и не более четырёх элементов `themePreviews`
- **THEN** клиент MUST показать название и количество тем и открыть систему по `designSystemId`

#### Scenario: В проекте нет дизайн-систем

- **WHEN** список дизайн-систем пуст
- **THEN** клиент MUST показать пустое состояние
- **THEN** клиент MUST показать действие создания только пользователю с разрешением `design-systems:write`

#### Scenario: Дизайн-система содержит темы

- **WHEN** `themePreviews` содержит от одной до четырёх тем
- **THEN** клиент MUST построить обложку дизайн-системы как мозаику 2×2 в порядке элементов ответа
- **THEN** заполненная плитка MUST показывать название Theme и её акцентный цвет
- **THEN** незанятые плитки MUST иметь нейтральное оформление прототипа

#### Scenario: Дизайн-система не содержит тем

- **WHEN** `tenantCount` равен нулю
- **THEN** клиент MUST показать выразительную заглушку из элементов токенов, типографики и компонентов в стиле прототипа

#### Scenario: Обложка строится без дополнительных запросов

- **WHEN** клиент отображает список дизайн-систем проекта
- **THEN** `tenantCount` и `themePreviews` MUST быть получены тем же запросом списка
- **THEN** клиент MUST NOT выполнять отдельный запрос tenant или значений токенов для каждой карточки дизайн-системы

### Requirement: Maintainer и Owner создают дизайн-систему

Веб-клиент SHALL позволять пользователю с разрешением `design-systems:write` создать дизайн-систему внутри текущего проекта.

#### Scenario: Дизайн-система успешно создана

- **WHEN** Maintainer или Owner отправляет непустое название
- **THEN** клиент MUST вызвать `POST /design-systems` с текущим `projectId`
- **THEN** API MUST атомарно создать дизайн-систему и общий набор определений токенов, необходимый для создания её тем
- **THEN** клиент MUST открыть обзор созданной дизайн-системы

#### Scenario: Создание недоступно Viewer и Editor

- **WHEN** Viewer или Editor открывает маршрут создания напрямую
- **THEN** клиент MUST показать состояние отсутствия доступа
- **THEN** клиент MUST NOT отправлять запрос создания

#### Scenario: Инициализация дизайн-системы завершилась ошибкой

- **WHEN** создание общего набора определений токенов завершается ошибкой
- **THEN** API MUST откатить создание дизайн-системы
- **THEN** клиент MUST остаться на форме и показать ошибку

### Requirement: Обзор дизайн-системы показывает темы

Веб-клиент SHALL показывать темы-тенанты выбранной дизайн-системы без статуса черновика и без версии темы.

#### Scenario: Темы загружены

- **WHEN** пользователь открывает обзор дизайн-системы
- **THEN** клиент MUST запросить `GET /design-systems/{designSystemId}/tenants`
- **THEN** каждый tenant DTO MUST содержать компактный `preview` с цветами акцента, цвета на акценте и поверхностей Light и Dark
- **THEN** клиент MUST показать название, визуальный профиль и динамическое превью каждой темы
- **THEN** клиент MUST открывать тему по `tenantId`

#### Scenario: Theme имеет полные данные превью

- **WHEN** `preview` содержит актуальные цвета Theme
- **THEN** клиент MUST построить мини-интерфейс с панелями Light и Dark в стиле прототипа
- **THEN** цвета акцента, элементов на акценте и поверхностей MUST соответствовать `preview`

#### Scenario: Legacy Theme не имеет полных данных превью

- **WHEN** актуальные значения обязательных цветов не могут быть разрешены
- **THEN** API MUST сформировать `preview` из профиля и `colorConfig`, если это возможно
- **THEN** при отсутствии и этих данных API MUST вернуть детерминированную резервную палитру, зависящую от `tenantId`
- **THEN** клиент MUST показать полноценную обложку без сломанного изображения или пустой области

#### Scenario: У дизайн-системы нет тем

- **WHEN** список tenant пуст
- **THEN** клиент MUST показать пустое состояние
- **THEN** клиент MUST показать действие создания пользователю с разрешением `tenants:write`

#### Scenario: Несуществующие свойства не показаны

- **WHEN** клиент отображает карточку темы
- **THEN** клиент MUST NOT показывать версию темы или статус Draft

### Requirement: Maintainer и Owner управляют дизайн-системой

Веб-клиент SHALL позволять пользователю с разрешениями `design-systems:write` и `design-systems:delete` изменять, переносить и полностью удалять дизайн-систему.

#### Scenario: Дизайн-система переименована

- **WHEN** Maintainer или Owner сохраняет валидное новое название
- **THEN** клиент MUST вызвать `PATCH /design-systems/{designSystemId}`
- **THEN** существующие маршруты MUST оставаться действительными, поскольку используют `designSystemId`

#### Scenario: Дизайн-система перенесена

- **WHEN** Maintainer или Owner выбирает другой проект, в котором имеет разрешение `design-systems:write`, и подтверждает перенос
- **THEN** API MUST изменить `projectId` дизайн-системы вместе со всеми её темами, определениями токенов, значениями, компонентными настройками и версиями
- **THEN** клиент MUST открыть дизайн-систему в целевом проекте

#### Scenario: Нет доступного целевого проекта

- **WHEN** у пользователя нет другого проекта с разрешением `design-systems:write`
- **THEN** клиент MUST отключить перенос и объяснить причину

#### Scenario: Дизайн-система полностью удалена

- **WHEN** Maintainer или Owner вводит точное название и подтверждает удаление
- **THEN** клиент MUST вызвать `DELETE /design-systems/{designSystemId}`
- **THEN** API MUST полностью удалить дизайн-систему и принадлежащие ей данные
- **THEN** клиент MUST вернуться к обзору проекта

#### Scenario: Архивирование дизайн-системы не предлагается

- **WHEN** пользователь открывает настройки дизайн-системы
- **THEN** клиент MUST NOT показывать архивирование или восстановление дизайн-системы
