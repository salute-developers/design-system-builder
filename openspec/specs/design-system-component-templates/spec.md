# design-system-component-templates Specification

## Purpose
Добавление web-компонентов в дизайн-систему из шаблонов `ds-service`: список шаблонов и раскладка шаблона с зависимостями в черновик через существующую ручку связей.
## Requirements
### Requirement: Список шаблонов компонентов

`GET /api/projects/{projectId}/design-systems/catalog/component-templates` SHALL возвращать web-компоненты, для которых в `ds-service` есть шаблон: `componentId`, `name`, `platform` и `dependsOn` — идентификаторы компонентов, от которых он зависит по шаблону. Ручка MUST быть доступна читателям компонентов проекта и MUST NOT раскрывать компоненты, которых нет в глобальном каталоге.

#### Scenario: Шаблон с зависимостью

- **WHEN** в шаблонах есть AvatarGroup, зависящий от Avatar
- **THEN** запись AvatarGroup MUST содержать идентификатор Avatar в `dependsOn`.

### Requirement: Добавление компонента из шаблона

`POST /api/projects/{projectId}/design-systems/{designSystemId}/design-system-components` с телом `{ componentId, fromTemplate: true }` SHALL в одной транзакции текущего черновика добавить компонент в дизайн-систему.

#### Scenario: Условия выполнения — Добавление компонента из шаблона

- **WHEN** пользователь добавляет компонент из шаблона
- **THEN** Если у компонента уже есть конфигурация в дизайн-системе, сервис MUST только восстановить связь, сохранив конфигурацию.
- **AND** Иначе сервис MUST создать связь и конфигурацию из шаблона.
- **AND** Если у конфигурации из шаблона нет вариации `view`, сервис MUST добавить вариацию `view` со значением `default` по умолчанию в конце осей.
- **AND** Отсутствующие в дизайн-системе компоненты, от которых он зависит по шаблону, MUST добавляться так же.
- **AND** Без `fromTemplate` ручка MUST вести себя как раньше: создавать или восстанавливать связь.
- **AND** Ручка MUST требовать право записи компонентов дизайн-системы, MUST поддерживать `Idempotency-Key` и MUST отвечать ошибкой, если у компонента без конфигурации нет шаблона или в дизайн-системе нет нужных шаблону метаданных или токенов; в этом случае ничего не меняется.


#### Scenario: Новый компонент

- **WHEN** пользователь добавляет Card в дизайн-систему без Card
- **THEN** в дизайн-системе MUST появиться связь Card и его оформления, вариации и стили из шаблона, а изменение MUST быть видно в журнале черновика.

#### Scenario: Добавление с зависимостью

- **WHEN** пользователь добавляет AvatarGroup, а Avatar в дизайн-системе нет
- **THEN** в дизайн-системе MUST появиться и AvatarGroup, и Avatar.

#### Scenario: Скрытый компонент

- **WHEN** у компонента есть конфигурация, но нет связи
- **THEN** сервис MUST восстановить связь и MUST NOT менять конфигурацию.

#### Scenario: Компонент уже в составе

- **WHEN** компонент уже связан с дизайн-системой
- **THEN** сервис MUST вернуть успешный ответ и MUST NOT менять его конфигурацию.

#### Scenario: Не хватает токенов

- **WHEN** шаблону нужен токен, которого нет в дизайн-системе
- **THEN** сервис MUST ответить `422` со списком недостающего и MUST NOT ничего записать.

#### Scenario: Откат добавления

- **WHEN** пользователь откатывает добавление в журнале до публикации
- **THEN** компонент MUST пропасть из дизайн-системы.

#### Scenario: Шаблон без view

- **WHEN** пользователь добавляет Heading, в шаблоне которого нет вариации `view`
- **THEN** у конфигурации Heading MUST появиться вариация `view` со значением `default` последней осью

### Requirement: Создание дизайн-системы не меняется

Создание дизайн-системы SHALL по-прежнему раскладывать все шаблоны в базовую версию тем же кодом раскладки, что и добавление одного компонента.

#### Scenario: Новая дизайн-система

- **WHEN** создаётся дизайн-система на полных метаданных
- **THEN** она MUST получить все компоненты из шаблонов, как до изменения.

### Requirement: Вариация view у существующих конфигураций

`ds-service` SHALL один раз после обновления добавить вариацию `view` со значением `default` по умолчанию в конце осей каждой конфигурации черновика, у которой её нет. Опубликованные версии MUST NOT меняться. Повторный запуск MUST NOT менять данные и журнал.

#### Scenario: Конфигурация без view

- **WHEN** у конфигурации Heading в черновике нет вариации `view`, и `ds-service` запускается после обновления
- **THEN** у неё MUST появиться вариация `view` со значением `default`, значения свойств MUST NOT измениться

#### Scenario: Повторный запуск

- **WHEN** миграция уже выполнена, и `ds-service` перезапускается
- **THEN** данные и журнал черновиков MUST NOT измениться

### Requirement: Вариация view при импорте конфигурации

Если у импортируемой конфигурации компонента нет вариации `view`, `ds-service` SHALL добавить вариацию `view` со значением `default` по умолчанию последней — после всех вариаций пакета, включая вариации, заданные только в `targets`.

#### Scenario: Вариация только в targets

- **WHEN** импортируется пакет с объявленной вариацией `size` и вариацией `gap`, заданной только в `targets`
- **THEN** вариации конфигурации MUST идти в порядке `size`, `gap`, `view`

#### Scenario: Повторный импорт

- **WHEN** пакет, импортированный этой версией, импортируется повторно
- **THEN** порядок вариаций и данные конфигурации MUST NOT измениться
