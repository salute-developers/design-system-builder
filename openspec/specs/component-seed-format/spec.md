# component-seed-format Specification

## Purpose
Определяет формат prod-сидов компонентов `db-service`: папка на компонент, описание данными без идентификаторов, единый формат для сида, выгрузки из базы и импорта из plasma, частичный пересев одного компонента и объявление зависимостей компонентов по именам.

## Requirements

### Requirement: Component seed is a directory without identifiers

Prod-сид компонента SHALL лежать в папке `seeds/prod/components/<имя>/`, где `<имя>` — имя компонента с
первой буквой в нижнем регистре, и описывать компонент данными без идентификаторов базы. Ссылки между
свойством, вариацией, стилем и токеном темы SHALL задаваться именами; идентификаторы раздаёт сидер.

#### Scenario: Папка описывает компонент целиком

- **WHEN** папка компонента экспортирует `seed`
- **THEN** сид MUST содержать имя компонента, свойства, вариации со стилями и хотя бы один appearance
- **THEN** каждый appearance MUST нести значения по стилям `values[вариация][стиль]`, инварианты и сочетания стилей
- **THEN** ни одно поле сида MUST NOT содержать идентификатор строки базы

#### Scenario: Реестра компонентов нет

- **WHEN** в `seeds/prod/components/` появляется новая папка с экспортом `seed`
- **THEN** сидер MUST подхватить её без правки какого-либо списка
- **THEN** удаление папки MUST убирать компонент из сида без правки других файлов

#### Scenario: Папка без экспорта seed отклоняется

- **WHEN** папка в `seeds/prod/components/` не экспортирует `seed`
- **THEN** сид MUST завершиться детерминированной ошибкой, называющей папку

#### Scenario: Ссылка на неизвестное имя отклоняется

- **WHEN** значение ссылается на свойство, стиль или токен, которого нет в сиде компонента или в токенах базовой ДС
- **THEN** сидер MUST завершиться ошибкой, называющей компонент и имя
- **THEN** сидер MUST NOT записать частичные данные этого компонента

### Requirement: One format for seeding, export and import

Сид в базу, выгрузка из базы и импорт из plasma SHALL читать и писать один и тот же формат папки
компонента, так что выгруженный компонент можно засеять обратно без ручных правок.

#### Scenario: Выгрузка перезаписывает папку целиком

- **WHEN** запущена выгрузка компонента из базы
- **THEN** папка компонента MUST быть переписана по состоянию базы целиком
- **THEN** результат MUST быть валидным сидом, который сидер принимает без изменений

#### Scenario: Круговой прогон сохраняет данные

- **WHEN** компонент засеян на пустую базу, выгружен и засеян снова
- **THEN** второй сид MUST дать тот же набор свойств, вариаций, стилей, значений, инвариантов и поправок по именам
- **THEN** сверка MUST идти по именам, а не по идентификаторам

#### Scenario: Платформа проставляется сидером

- **WHEN** сид записывает appearance или свойство
- **THEN** колонка `platform` MUST получить значение `web`
- **THEN** сид папки компонента MUST NOT содержать это поле явно

### Requirement: Partial reseed of one component

Сид SHALL принимать имя одного компонента и пересевать только его, не трогая данные остальных
компонентов и других дизайн-систем.

#### Scenario: Пересев одного компонента

- **WHEN** сид запущен с параметром `--component=<X>`
- **THEN** данные дизайн-системы (стили, значения, инварианты, поправки, сочетания) этого компонента в базовой ДС MUST быть удалены и записаны заново
- **THEN** данные других компонентов MUST остаться без изменений
- **THEN** глобальные строки компонента (компонент, вариации, свойства) MUST обновляться, а не дублироваться

#### Scenario: Неизвестное имя компонента

- **WHEN** параметр `--component` называет компонент, папки которого нет
- **THEN** сид MUST завершиться ошибкой со списком доступных компонентов
- **THEN** база MUST остаться без изменений

#### Scenario: Компонент заводится только в базовой ДС

- **WHEN** сид записывает данные компонента
- **THEN** стили и значения MUST принадлежать базовой дизайн-системе
- **THEN** сид MUST NOT копировать компонент в другие дизайн-системы

### Requirement: Appearance-scoped variations in seeds

Сид компонента SHALL допускать несколько appearance с общими свойствами и вариациями, но своим
составом вариаций, порядком, дефолтами, значениями и инвариантами.

#### Scenario: Состав вариаций по appearance

- **WHEN** appearance перечисляет `variations`
- **THEN** объявление вариаций этого appearance MUST содержать ровно перечисленные вариации в указанном порядке
- **WHEN** appearance не перечисляет `variations`
- **THEN** он MUST получить все вариации компонента в порядке их объявления

#### Scenario: Дефолт принадлежит appearance

- **WHEN** два appearance задают разные `defaults` для одной вариации
- **THEN** оба дефолта MUST быть записаны на объявления соответствующих appearance
- **THEN** вариация без записи в `defaults` MUST остаться без дефолта

#### Scenario: Значения принадлежат appearance

- **WHEN** два appearance задают разные значения одного свойства для одного стиля
- **THEN** оба значения MUST быть записаны со ссылкой на свой appearance

### Requirement: Component dependencies are declared by name

Зависимости компонентов SHALL объявляться одним списком пар `(родитель, дочерний, тип, порядок)`,
где компоненты заданы именами, а тип — `compose` или `reuse`.

#### Scenario: Пара с отсутствующим компонентом пропускается

- **WHEN** один из компонентов пары ещё не засеян
- **THEN** пара MUST быть пропущена без ошибки
- **THEN** после сида недостающего компонента повторный сид зависимостей MUST записать пару

#### Scenario: Повторный сид не дублирует связи

- **WHEN** пара уже есть в базе
- **THEN** повторный сид MUST оставить одну строку
