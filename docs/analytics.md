# Аналитика клиентов DS Builder

Веб-клиент использует стандартный JavaScript SDK Яндекс Метрики. Kotlin CLI и
встроенный `dsbuilder mcp serve` отправляют POST Measurement Protocol напрямую в
`https://mc.yandex.ru/collect`. Backend DS Builder не участвует. Node.js MCP
(`mcp-node`) аналитику не подключает.

## Что передаётся

CLI/MCP: один случайный положительный 63-битный ID установки (десятичная строка),
время, название разрешённой операции, результат (`success`, `failure`, `cancelled`),
версия, семейство ОС и версия схемы. Имя цели:
`<cli|mcp>_<операция с заменой пробелов и дефисов на _>_<результат>`.
Длительность и категория ошибки есть в нейтральном событии клиента, но первая
версия адаптера не передаёт их в Метрику. Средняя длительность в отчётах не обещается.
Аргументы, пути, содержимое проектов, тексты ошибок, backend URL и credentials
не передаются. Справка, версия, группы и ошибки до начала конечной команды не
считаются операциями. MCP discovery и неизвестные инструменты не учитываются.

Перед первой целью процесса и после 30 минут без операций MCP отправляется
технический просмотр `<BASE_URL>/analytics/<cli|mcp>/activity`. Тайм-аут визита в
счётчике нужно установить в 30 минут. Цель отправляется только после успешного
приёма просмотра. Нет повторов при неоднозначном тайм-ауте, дисковой очереди или
гарантии доставки. Очередь — 128 событий, тайм-аут запроса — 1 секунда, ожидание
при выходе — до 1500 мс. События старше 12 часов отбрасываются.

Веб: просмотры устойчивых экранов, начальный экран, SPA-переходы и Back/Forward,
с `client_type=web`. Динамические части URL заменяются `:projectId`,
`:designSystemId`, `:tenantId`, `:componentName`; query/hash исключаются, заголовки
фиксированы по каталогу. Редиректы считаются по конечному экрану. Загрузка SDK
отложена до удаления параметров авторизации. Очередь до загрузки — 32 просмотра,
при переполнении удаляется старый; отказ скрипта очищает очередь без повтора.
Вебвизор, карта кликов, переходы по ссылкам, автодействия и собственные цели
выключены. Базовые технические данные браузера, cookies и сети собирает сам SDK;
проверка всех его запросов на тестовой сборке обязательна перед выпуском.

Получатель данных — Яндекс Метрика. В её интерфейсе тоже нужно отключить
автоматические цели, Вебвизор, карты кликов и сбор дополнительных данных; не
включать Яндекс Тег Менеджер или advanced matching для этих счётчиков.

## Идентификация и отключение

Один ID хранится в `~/.dsbuilder/analytics/installation-id` (формат `1:<cid>`) под
межпроцессной блокировкой. CLI и MCP читают один файл. Обновление, смена проекта,
вход/выход и длительный перерыв ID не меняют. Повреждённое или недоступное
состояние отключает аналитику запуска без создания временной идентичности.
Удаление файла сбрасывает идентификацию; отдельные домашние каталоги ОС и
устройства считаются отдельными установками. Установка не равна человеку или
аккаунту, а общий визит может содержать оба `client_type`: режимы нужно различать
по префиксам целей, а не делить визиты только по параметру.

`DSBUILDER_ANALYTICS_DISABLED=1` **или** `DO_NOT_TRACK=1` отключает аналитику до
доступа к аналитическим файлам и сети. Обычная сборка без встроенной конфигурации
также использует `NoOpAnalytics`. Тесты/установочные smoke checks запускаются с
отключением. Эти переменные не отключают веб: веб включается только при сборке.

## Настройка сборок и счётчиков

Для CLI/MCP создать два счётчика: DEV и PROM (production), отдельные от обоих
веб-счётчиков. В каждом включить Measurement Protocol и создать два разных токена:
для CLI и встроенного MCP. Итого четыре счётчика, четыре токена.

В GitHub → Settings → Secrets and variables → Actions нужны только
production-настройки CLI/MCP (суффикс `PROM`). Repository variables:

| Переменная | Значение |
| --- | --- |
| `DSBUILDER_ANALYTICS_ENABLED_PROM` | `false` до проверки production, затем `true` |
| `DSBUILDER_METRICA_COUNTER_ID_PROM` | Номер CLI/MCP PROM, только цифры без ведущих нулей |
| `DSBUILDER_METRICA_BASE_URL_PROM` | `https://plasma.sberdevices.ru/design-system-builder` |

Repository secrets:

| Секрет | Значение |
| --- | --- |
| `DSBUILDER_METRICA_CLI_TOKEN_PROM` | Токен CLI из счётчика CLI/MCP PROM |
| `DSBUILDER_METRICA_MCP_TOKEN_PROM` | Другой токен из того же PROM-счётчика |

`publish-cli-release.yml` использует только PROM-настройки и сохраняет существующий
процесс выпуска по тегу `cli-v*`. Он отображает их в общие входы Gradle без
суффикса. Автотесты и установочные smoke checks выполняются с
`DSBUILDER_ANALYTICS_DISABLED=1` независимо от конфигурации в бинарнике.

DEV-версия CLI/MCP собирается локально. DEV-переменные и DEV-секреты CLI/MCP в
GitHub не нужны. Старые Repository variables/secrets CLI/MCP без суффикса или
с суффиксом `_DEV` workflow не читают; после переноса production-значений их
можно удалить. Все четыре счётчика должны различаться. CI проверяет изоляцию
трёх известных ему счётчиков: веб DEV, веб PROM и CLI/MCP PROM. При локальной
сборке нужно самостоятельно выбрать отдельный тестовый CLI/MCP-счётчик.

Пример локальной сборки в **Bash** из `frontend-kt` (номер заменить своим;
токены вводятся в скрытых приглашениях и не записываются в команду):

```bash
export DSBUILDER_ANALYTICS_ENABLED=true
export DSBUILDER_METRICA_COUNTER_ID=123456789
export DSBUILDER_METRICA_BASE_URL=https://plasma.sberdevices.ru/dev/design-system-builder
read -r -s -p 'CLI test token: ' DSBUILDER_METRICA_CLI_TOKEN
printf '\n'
read -r -s -p 'MCP test token: ' DSBUILDER_METRICA_MCP_TOKEN
printf '\n'
export DSBUILDER_METRICA_CLI_TOKEN DSBUILDER_METRICA_MCP_TOKEN
DSBUILDER_ANALYTICS_DISABLED=1 ./gradlew :cli:jvmTest :cli:packageJvmCli
```

Архив: `cli/build/distributions/dsbuilder-cli-jvm.zip`. Для native-дистрибутивов
использовать `:cli:packageMacosArm64Cli`, `:cli:packageMacosX64Cli` или
`:cli:packageWindowsX64Cli` на поддерживаемом хосте. Встроенный MCP уже входит в CLI.
Отключение в команде выше действует на время сборки и тестов; при обычном запуске
собранный бинарник использует тестовый счётчик. Параметры аналитики встраиваются
при сборке, изменение окружения уже собранного приложения их не заменяет.
Базовый адрес указывается без `/analytics`: клиент добавляет этот сегмент сам.
Для последующих обычных сборок установить `DSBUILDER_ANALYTICS_ENABLED=false`
или убрать экспортированные параметры. Без флага аналитика отключена по умолчанию.

Неполная включённая конфигурация или совпадающие токены ломают сборку. Значения
генерируются только в `cli/build/generated/analytics`, меняются при изменении
входных переменных, не печатаются и не передаются дочерним генераторам. Для
инвалидации в Gradle inputs записываются SHA-256 отпечатки. Для сборки
дистрибутивов OAuth не требуется; он нужен только административной задаче ниже.
Получить полный актуальный список целей без токенов и сетевых обращений:

```bash
cd frontend-kt
./gradlew -q :cli:analyticsGoals
```

Создать эти цели как «JavaScript-событие» в счётчике до включения клиентов —
вручную или скриптом ниже.
`core-analytics` содержит только общие интерфейсы/значения/NoOp, без Метрики и HTTP.
`analytics-metrica` содержит преобразование и доставку, а клиенты выбирают
реализацию через интерфейс `Analytics`. Feature-модули аналитику не подключают.

Веб CI: `VITE_METRICA_ENABLED_DEV`/`VITE_METRICA_ENABLED_PROM` (по умолчанию false)
и `VITE_METRICA_COUNTER_ID_DEV`/`VITE_METRICA_COUNTER_ID_PROM`. При сборке они
переходят в `VITE_METRICA_ENABLED`/`VITE_METRICA_COUNTER_ID`. DEV включать только
на тестовом счётчике, отличном от PROM и CLI/MCP. Локальная разработка/тесты по
умолчанию не загружают SDK. Веб не содержит Measurement Protocol токенов.

Для локального Docker-стека из корня репозитория:

```bash
VITE_METRICA_ENABLED=true VITE_METRICA_COUNTER_ID=123456789 ./setup-local.sh
```

Номер заменить своим веб-счётчиком DEV. Compose передаёт эти две переменные в
контейнер Vite; API и авторизация настроены стандартным setup. Клиент доступен
на `http://localhost:3002`. Без флага Метрика отключена по умолчанию.

## Автоматическое создание целей CLI/MCP

Gradle-задача `:cli:syncAnalyticsGoals` на Kotlin получает каталог напрямую из
кода CLI/MCP и создаёт недостающие цели одним пакетным PUT. Python и файловый
экспорт не нужны. В тело изменения счётчика передаются `counter.id`,
`counter.goals_remove=0` и полный массив `counter.goals`: все существующие цели
с их ID и полями плюс недостающие определения без ID. PUT заменяет массив;
передавать только новые цели нельзя. Существующие объекты пересылаются без изменений,
остальные настройки счётчика в запрос не включаются. После записи задача
повторно читает цели и проверяет весь каталог и сохранность старых целей/ID.
Совпадение определяется по типу `action` и единственному условию `exact`, а не
по названию. Переименованные цели не дублируются; существующие цели не изменяются
и не удаляются. Конфликт имени или превышение лимита 200 целей останавливает
план до первой записи. Одновременные локальные запуски одного счётчика не поддерживаются.
Административный код компилируется отдельно и не входит в CLI/MCP-дистрибутивы.

### Получение OAuth-токена

Это отдельный административный токен. Два токена Measurement Protocol из CI
для управления целями не подходят. Для release-workflow добавь Repository secret
**`METRICA_OAUTH_TOKEN_PROM`**. Он передаётся только шагу синхронизации целей и
не встраивается в CLI/MCP.

1. Войди в Яндекс под аккаунтом с правом редактирования нужного счётчика.
2. Открой [создание OAuth-приложения](https://oauth.yandex.ru/client/new).
3. Выбери вариант **«Для доступа к API или отладки»**, укажи название, например
   `DS Builder — настройка Метрики`, и контактную почту.
4. В доступах к данным добавь **`metrika:read`** (чтение списка целей) и
   **`metrika:write`** (создание целей). Для аккаунта организации с porg-логином
   также добавь `passport:business`.
5. Создай приложение и скопируй его **ClientID**. Это идентификатор OAuth-приложения,
   он не связан с ClientID посетителя в аналитике.
6. Открой в браузере адрес, заменив `APPLICATION_ID` на этот ClientID:
   `https://oauth.yandex.ru/authorize?response_type=token&client_id=APPLICATION_ID`.
7. Подтверди доступ и скопируй выданный OAuth-токен для скрытого ввода при запуске
   задачи. Его не нужно передавать в чат, записывать в репозиторий или аргументы.

Порядок и права описаны в [документации авторизации API Метрики](https://yandex.ru/dev/metrika/ru/intro/authorization).

### Локальный запуск

Из `frontend-kt` в **Bash** (Java 17): сначала подготовить административную
компиляцию без OAuth, затем скрыто ввести токен и проверить план. Вместо
`123456789` указать номер CLI/MCP-счётчика, не веб-счётчика.

```bash
./gradlew :cli:prepareAnalyticsGoals
read -r -s -p 'Metrica OAuth token: ' METRICA_OAUTH_TOKEN
printf '\n'
METRICA_OAUTH_TOKEN="$METRICA_OAUTH_TOKEN" ./gradlew --no-daemon --no-configuration-cache --no-build-cache :cli:syncAnalyticsGoals -PmetricaCounterId=123456789 -PmetricaDryRun=true
```

После проверки плана выполнить создание, затем убрать локальную переменную:

```bash
METRICA_OAUTH_TOKEN="$METRICA_OAUTH_TOKEN" ./gradlew --no-daemon --no-configuration-cache --no-build-cache :cli:syncAnalyticsGoals -PmetricaCounterId=123456789
unset METRICA_OAUTH_TOKEN
```

`-PmetricaDryRun=true` — режим просмотра плана с чтением API. Gradle `--dry-run`
показывает только граф задач и не заменяет эту проверку. Для тестового счётчика
повторить запуск с его номером. Каталог всегда берётся из текущего исходного кода.

### Запуск в CI

В `publish-cli-release.yml` после сборки и smoke-проверок выполняется отдельное
задание `analytics-goals`. Оно проверяет исходники выпускаемого тега,
компилирует административную задачу без OAuth, затем синхронизирует цели перед
публикацией. Только шаг синхронизации получает:

- `METRICA_OAUTH_TOKEN` из Repository secret **`METRICA_OAUTH_TOKEN_PROM`**;
- публичный номер счётчика из `DSBUILDER_METRICA_COUNTER_ID_PROM`.

Если `DSBUILDER_ANALYTICS_ENABLED_PROM` отсутствует или не равен `true`, задание
успешно пропускает синхронизацию без OAuth и запросов Метрики. При включённой
аналитике отсутствующий токен или ошибка синхронизации блокирует публикацию.
OAuth не доступен шагам сборки дистрибутивов, тестирования и публикации. Встраивание
аналитики в административном задании отключено; MP-токены ему не нужны.

При успешной записи и проверке выводится `Batch verified: created=N, catalog=M,
preserved=K`. При повторном запуске ожидается `missing=0`, без запросов записи.
Dry-run также выполняет только GET и показывает `Would create ...`.

После тайм-аута или ошибки часть целей уже могла появиться. Повтор PUT
автоматически не выполняется; следующий запуск читает актуальное состояние и
передаёт полный список: актуальные цели с их ID плюс недостающие определения. При неполном результате или изменении
старой цели проверка завершится ошибкой и остановит публикацию в CI. Сообщение
разделяет `missing`, `removed` и `changed`, перечисляет идентификаторы каталога и
числовые ID целей, без сырых объектов или значений полей.

Предыдущая версия пакетной задачи ошибочно отправляла только недостающие цели.
Если после неё часть целей исчезла, исправленная версия сохранит текущие активные
ID и создаст недостающие цели заново. Ранее удалённые ID эта задача автоматически
не восстанавливает.

Диагностика различает тайм-аут, сетевой сбой, неверный JSON и отсутствие полей.
HTTP 401 обычно означает недействительный OAuth, 403 — недостаточные права,
429 — превышение квоты. Исходные тексты исключений и тело ответа не выводятся.
Полный ответ PUT не нужен: результат подтверждается отдельным GET.
Методы: [список целей](https://yandex.ru/dev/metrika/ru/management/openapi/goal/goals),
[пакетное изменение счётчика](https://yandex.ru/dev/metrika/ru/management/openapi/counter/editCounter).

Проверка без запросов к Яндексу: `./gradlew :cli:analyticsAdminTest` из `frontend-kt`.

## Как читать показатели

Веб DAU — уникальные посетители с просмотром за день; MAU — уникальные за
календарный месяц **в часовом поясе счётчика**. MAU не получается суммированием
DAU, а последние 30 дней — другой период, чем календарный месяц. Это активность
по просмотру, а не по успешному редактированию. События `daily_active` и
`monthly_active` не отправляются. Cookies, блокировщики, разные устройства и
потеря доставки ограничивают точность. Веб и CLI/MCP не объединяются в людей.

## Проверки перед выпуском и принятые ограничения

Нужны доказательства из отчётов/Logs API тестового счётчика: новый собственный
`cid` без веб-визита, общая установка CLI/MCP при разных токенах, новый визит
того же посетителя после тайм-аута и другой посетитель для другого ID. HTTP 200
сам по себе это не доказывает. Проверить упакованные дистрибутивы
локально на JVM/macOS/Windows и все запросы веб-SDK, включая технические и рефереры.
Без доступа к счётчику эти проверки остаются невыполненными.

Поведение возвращаемости после перерыва более 21 дня — отложенное наблюдение,
не причина локально менять ID. Долгосрочное узнавание посетителя пока не доказано.
Ключи в бинарнике считаются извлекаемыми. Подделка событий возможна; счётчик
не является аудитом действий. Отзыв токена канала отключает старые версии.
Неоднозначность условий распространения `ms` принята как известный риск, а не
разрешение Яндекса; ответ поддержки не является условием выпуска.
