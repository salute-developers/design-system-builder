# Генерация iOS: с чего начать

Короткая инструкция для тех, кто хочет сгенерировать iOS-тему и документацию через `dsbuilder`.
Подробный справочник по всем командам — в [USAGE.md](./USAGE.md).

## В работе участвуют два CLI

| Кто | Что делает | Откуда берётся |
|---|---|---|
| `dsbuilder` | Общий CLI дизайн-системы: выгружает токены в `.sdds`, решает, какая платформа нужна, и зовёт платформенный инструмент | этот репозиторий |
| `dsbuilder-ios` | Swift CLI: превращает `.sdds` в Swift-код темы и собирает дерево документации | репозиторий [plasma-ios](https://github.com/salute-developers/plasma-ios) |

Вы вызываете только `dsbuilder`. Он сам запускает `dsbuilder-ios`, показывая перед запуском,
какой платформой и каким toolchain'ом будет сделана работа.

## Быстрый старт

```bash
# 1. один раз поставить iOS-инструмент
dsbuilder toolchain install ios

# 2. убедиться, что он на месте
dsbuilder toolchain doctor

# 3. сгенерировать тему из .sdds текущего проекта
dsbuilder theme generate

# 4. собрать пакет документации
dsbuilder docs generate
```

Шаги 3 и 4 запускаются из папки проекта — той, внутри которой лежит `.sdds/config.json`.
Установке проект не нужен: она кладёт инструмент в домашнюю папку и работает в любом каталоге.

### Откуда берётся платформа

Из `platforms` в `.sdds/config.json`. Если там `["swiftui"]`, ничего указывать не надо.
Если платформ несколько или их нет вовсе, назовите платформу явно:

```bash
dsbuilder theme generate --platform swiftui
```

### Как передать аргументы самому Swift CLI

Всё после `--` уходит в `dsbuilder-ios` без изменений:

```bash
dsbuilder theme generate -- --scheme sdds_serv
```

## Когда вызывать `toolchain install`

Вызывайте:

- **первый раз на машине** — инструмента ещё нет;
- **когда вышел новый релиз plasma-ios** и нужны свежие компоненты или исправления;
- **на новом агенте CI** — там домашняя папка каждый раз чистая.

Не нужно вызывать:

- перед каждой генерацией — установленный инструмент никуда не девается;
- если вы собираете `dsbuilder-ios` из исходников сами (см. «Своя сборка» ниже).

Что делает команда:

```bash
dsbuilder toolchain install ios                          # последний релиз
dsbuilder toolchain install ios --version release-01-09-2026   # конкретный релиз
```

Инструмент кладётся в `~/.dsbuilder/toolchains/ios/<версия>`, а симлинк `current`
переставляется на неё. Прежние версии остаются на диске — откатиться можно повторной
установкой нужного тега. После установки ни `--tool`, ни переменные окружения не нужны:
`doctor` и генерация находят инструмент сами.

Если установка сорвалась (нет сети, битый архив), прежняя версия остаётся рабочей:
`current` переключается только после успешной распаковки.

## Откуда берётся релиз Swift CLI

Из GitHub Releases репозитория `salute-developers/plasma-ios`. В релизе много ассетов
(xcframework'и, темы, исходники); `dsbuilder` берёт один — **`dsbuilder-ios-cli-<тег>.zip`**.
Внутри архива лежат:

- `dsbuilder-ios` — сам бинарь;
- `ios-api-meta.json` — описание API стилей компонентов, без него генерация не знает,
  какие свойства есть у Appearance. Файл должен лежать рядом с бинарём, поэтому архив
  распаковывается целиком, а не «вытаскивается один бинарник».

Сам архив собирается в plasma-ios скриптом `scripts/release/build_release.sh` и публикуется
вместе с остальными ассетами релиза. Теги релизов — даты вида `release-01-09-2026`,
поэтому «последний» определяет GitHub, а не сортировка имён.

### Без доступа к GitHub

Скачайте архив заранее (или возьмите у коллеги) и поставьте его локально:

```bash
dsbuilder toolchain install ios --from ~/Downloads/dsbuilder-ios-cli-release-01-09-2026.zip
```

`--from` принимает и путь, и URL, и в GitHub при этом не ходит.

### Своя сборка

Если вы правите Swift CLI и хотите проверить сборку из исходников, установка не нужна —
укажите бинарь напрямую:

```bash
dsbuilder theme generate --tool ~/plasma-ios/DesignSystemBuilder/.build/release/dsbuilder-ios
```

То же значение можно задать переменной `DSBUILDER_IOS_TOOL`, чтобы не повторять флаг.
Порядок поиска инструмента: `--tool` → `DSBUILDER_IOS_TOOL` → установленный `current` → `PATH`.

## Если что-то пошло не так

Начните с `dsbuilder toolchain doctor` — он ничего не генерирует, только проверяет инструмент
и печатает его путь и версию. Ненулевой код возврата означает, что инструмент непригоден.

| Сообщение | Что это значит |
|---|---|
| `dsbuilder-ios was not found. Checked: …` | Инструмент не установлен — выполните `toolchain install ios` |
| `dsbuilder-ios was not found at <путь>, the path given by --tool` | Путь в `--tool` неверный: опечатка или бинарь не собран |
| `Release <тег> … has no dsbuilder-ios-cli asset` | В этом релизе нет архива с инструментом — возьмите другой тег через `--version` или поставьте архив через `--from` |
| `No platform toolchain is registered for 'compose'` | Выбрана платформа, которую этот клиент не обслуживает; для iOS нужна `swiftui` |
| `Toolchain 'ios' does not support components generation` | На iOS вариации компонентов генерируются вместе с темой — используйте `theme generate` |

### Две детали, о которые легко споткнуться

1. `docs generate` читает метаданные (`config-info-ios.json`, `config-info-tokens-ios.json`)
   из `.sdds` проекта — туда их кладёт `theme generate`. Если тему сгенерировать
   с `--output` в другую папку, метаданные уедут вместе с ней, и сборка документации
   пожалуется на отсутствующий вход. Порядок «`theme generate` без `--output`, затем
   `docs generate`» работает всегда.
2. Генерация темы идёт по схеме компонентов. Без явной `--scheme` берётся схема из конфигурации
   проекта, и если для неё нет комплектов компонентов, часть из них будет пропущена
   с предупреждением `no corresponding scheme found`.
