# Настройки пользователя

Модуль работает внутри backend app, владеет персональными токенами и не зависит от проектов.

API: GET/POST `/api/settings/personal-access-tokens`, DELETE `/{id}`, GET `/scopes`.
Управление требует пользовательскую OAuth-сессию. Секрет выдаётся только при создании;
Новые секреты хранятся как SHA-256, проверка прежних PBKDF2-хешей сохранена. Внутренний API проверки возвращает владельца, scopes и актуальную
глобальную роль. Отзыв и срок проверяются на каждом запросе; сведения аккаунта Keycloak кешируются не более 30 секунд.

Миграции PAT и отзыва старых ключей выполняются после инициализации базы проектов,
до readiness монолита. Используется отдельная история `user_settings_schema_history`.
База и identity-провайдер берутся из существующей конфигурации проектов.
Требуются разрешения Keycloak на чтение пользователей и их эффективных realm-ролей.

Клиенты передают PAT как Bearer через прежние --api-key / DSBUILDER_API_KEY.
PAT не обновляется через OAuth и не переключает клиента на другую сессию при отказе.

## Обновление ранее запущенной feature/pat

V2 отзывает ключи только при наличии прежней таблицы. На новой базе она не создаётся.

Если на тестовой базе уже применена прежняя V2, Flyway сообщит о несовпадении checksum.
Перед обновлением остановите backend и сохраните резервную копию базы проектов.
Проверьте, что единственное расхождение истории — checksum версии 2 и что прежние ключи отозваны.
Оператор может явно выполнить Flyway repair для этой базы с таблицей истории
`user_settings_schema_history` и обоими актуальными locations
`classpath:dsbuilder/user-settings/migrations` и `classpath:dsbuilder/projects/pat-migrations`.
Используйте ресурсы из новой сборки, затем выполните validate и migrate и запустите backend.
При других расхождениях сначала выясните их причину. Автоматического repair при старте нет.
