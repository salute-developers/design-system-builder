# Проверка чтений темы и журнала

## Область влияния

| Изменяемый участок | Потребители | Проверка регрессий |
| --- | --- | --- |
| `ResolvedSubjectRows` через `ThemeRevisionQueries` | Темы, значения всех типов, цвета, палитра, размеры, типографика; вспомогательные чтения записи и инициализации | Исторические HTTP-чтения, начальные значения, palette/gradient/size/typography, публикация и отмена |
| `ResolvedSubjectRows` через `ExposedTokenRepository` | Каталог определений, проверки имени, чтения до/после записи | EditorSectionReads, VersionedRead, TokenGroup, ColorToken, журнал |
| `AggregateTokensTable` | Публичные фильтры и страницы определений токенов; остальные агрегатные проекции не меняются | EditorSectionReads, VersionedRead, фильтры и курсоры каталога |
| `ExposedDraftChangeHandler` | Все типизированные обработчики тем, токенов, компонентов и дизайн-систем; describe/visit/hasChanges/describeEntity | CompactJournal, VersionedJournalPublication, проверки компонентов и палитры |
| `tenantEditRevisions` и preview | Список и карточка темы, ответы изменения метаданных и значений | TenantInitialValues, EditorSectionReads, KeyedThemeMutations |
| Условное раскрытие палитры размеров | GET размеров; мутации сохраняют прежнюю проверку ссылок | SizeTokenUseCase, SizeTokenHttp, VersionedPalette |
| SQL использования размеров | Использование компонентами, вычисляемые радиусы, поиск текстовых ссылок при переименовании | SizeTokenHttp: удаление компонента, переименование, опубликованная граница, поправки платформ |

Общий `latestRevision` не изменён. Поиск кандидатов использует предметные ревизии, а не технический журнал редакций. Политики исходных значений новой темы, производного типа и зависимых компонентных записей остаются действующими. Стабильные поля, переданные обработчикам, одинаковы в обоих состояниях: их изменение не используется как самостоятельный источник отличий.

Переиспользование результатов разрешено только в read-only-транзакции и сбрасывается при установке доверенного контекста. В транзакциях записи каждый вызов читает актуальное состояние повторно. Все условия удаления и типа применяются после выбора последней ревизии.

В общем `token-values` хранимые значения читаются до снимка палитры. Уже загруженный полный набор может дать подмножества цветов и теней; промах кеша не вызывает полную загрузку ради узкой операции. Одинаковые UUID-фильтры упорядочиваются перед построением ключа. В `queryPerformance` сценарий общего `token-values` дополнительно проверяет по pg_stat_statements, что выполнена одна выборка значений; для исходного dev эта проверка отключается флагом `performanceLegacy` вместе с исходной схемой. При сравнении со снимком первого этапа используются сохранённые исходники и тестовый набор самого первого этапа, а индексы V18 сохраняются в обоих вариантах.

Второй этап сравнивает сохранённый первый этап и новый кандидат на одной копии данных. Для итоговой серии используются одинаковые настройки и оба порядка запусков A–B–B–A, 10 прогревов и 20 измерений на сценарий в каждом порядке. Объединяются все 40 измерений каждого варианта без отбора быстрых запросов. Серверный `http_request`, получение тела и разбор JSON измерительным клиентом учитываются отдельно. Планы и JFR снимаются отдельными проходами и не подменяют временную серию. Результаты, включая разброс отдельных серий и оставшуюся задержку цветового revert, приведены в `RESULTS.md`.

## Цветовой откат и обновление клиента

Третий этап цветового отката использует отдельные исполняемые варианты и одинаковые настройки
диагностики. Изменяются только синтетические значения семейства, журнал перед сценарием должен
быть пустым. На каждый вариант — пять прогревов и двадцать повторов; после каждого отката
сравниваются все значения темы без технических редакций и проверяется пустой журнал.
Длительность команды берётся из `http_request` по correlation ID; число SQL и JDBC — из
`ds_transaction`. Планы одного запроса собираются отдельным проходом. На клиенте отдельно
проверяются восстановленное значение, отметки журнала и цепочка последующих HTTP-чтений.
Результаты и ограничения сравнения приведены в разделе третьего этапа `RESULTS.md`.

## Изолированное сравнение форм SQL

```bash
python3 performance/compare_queries.py --output build/query-plans
```

Команда запускает собственный временный контейнер `postgres:17-alpine`, создаёт 134 400 значений в 14 системах/темах, по 9 600 в выбранной теме, с исходными и будущими ревизиями. Идентификаторы токенов моделируют 1 700 определений на систему; это сравнение формы SQL, а не полной схемы или HTTP. Проверяется эквивалентность результатов через EXCEPT ALL, затем выполняются прогрев и 20 измерений каждого варианта. Для журнала проверяются 0, 3 и 9 изменений. Планы и отчёт сохраняются по указанному пути. Контейнер удаляется после завершения; другие контейнеры не затрагиваются. Ошибка Docker или PostgreSQL завершает команду неуспешно.

## Полный HTTP-набор

Из `backend-kt/ds-service`:

```bash
DOCKER_HOST=unix:///Users/aamalyshev/.docker/run/docker.sock \
JAVA_TOOL_OPTIONS=-Dapi.version=1.44 \
./gradlew :runtime:queryPerformance -PperformanceOutput=/tmp/ds-query-current.json
```

Путь socket и параметр API относятся к текущему Docker Desktop; в другом окружении используются его настройки. Задача не входит в обычный `test`. Она требует реальный PostgreSQL 17 через Testcontainers, мигрирует схему, включает pg_stat_statements только в своём контейнере, создаёт 14 тем через API, добавляет 500 определений и их платформенные значения через SQL и публикует две версии. Обязательные размеры проверяются; отсутствие Docker или расширения не считается успехом. Измеряются чтение темы, все определения, все значения, палитра, размеры, журнал/сводка с 0/3/9 изменениями и 20 команд отмены после прогрева. Число SQL получаем по разности calls собственной БД, исключая диагностическое чтение статистики. Результаты — длительность HTTP в тестовом сервере, а не время браузерного рендера.

Для сравнения на точно одинаковых данных исходная серия использует экспорт синтетической фикстуры:

```bash
# Оптимизированная версия: создать данные и экспортировать снимок до измерений.
./gradlew :runtime:queryPerformance -PperformanceOutput=/tmp/ds-query-current.json \
  -PperformanceFixtureExport=/tmp/ds-query-fixture.dump
# Исходная dev с тем же тестовым набором и PostgreSQL 17:
./gradlew :runtime:queryPerformance -PperformanceOutput=/tmp/ds-query-baseline.json \
  -PperformanceFixtureImport=/tmp/ds-query-fixture.dump -PperformanceLegacy=true
```

Импорт выполняется только в собственной временной БД Testcontainers. Флаг `performanceLegacy` удаляет из восстановленного снимка три индекса V18 и её запись истории миграций, чтобы исходная версия измерялась с исходной схемой. Предметные данные не меняются. Сравниваются также отпечатки нормализованных HTTP-ответов: порядок верхнего массива записей с id не учитывается, время changedAt новых команд исключается; порядок вложенных массивов сохраняется, кроме неупорядоченной коллекции привязок palette.tokens, сравниваемой по tokenId. Полное сравнение палитры подтвердило, что различается только порядок этих 1 634 привязок; их состав и остальные поля совпадают. Порядок публичной выдачи и заголовки дополнительно проверяют контрактные тесты.

Для исходной серии используйте исходники `dev` до изменения и тот же тестовый набор с PostgreSQL 17 и pg_stat_statements. Не переносите новые production-классы или миграцию V18 в исходную серию. Серии запускаются последовательно, с одинаковыми ресурсами Docker и без параллельной нагрузки. Проверка отчётов:

```bash
python3 performance/compare_reports.py --baseline /tmp/ds-query-baseline.json \
  --current /tmp/ds-query-current.json --output build/query-performance/comparison.json
```

Порог уменьшения медианы на 30 процентов относится к чтениям данных темы и журнала; каталог определений измеряется отдельно. Ограничение ухудшения p95 действует и для каталога. Отсутствующие серии, различие отпечатков или нарушение порогов завершают команду ошибкой. Для итоговой приёмки нужны обе серии и проверка порогов из design.md. Планы реального dev, проверки инспектора в браузере и задержки под конкурирующей нагрузкой выполняются отдельно.

## Диагностика транзакции

`DS_QUERY_DIAGNOSTICS=true` включает событие `ds_transaction`: correlationId, режим, номер попытки, число SQL, sqlMs, connectionMs, commitMs и totalMs. По умолчанию диагностика выключена. SQL и параметры не выводятся. commitMs измеряется хуками до и после COMMIT, включая отложенные ограничения; totalMs фиксируется после возвращения транзакции. sqlMs — время JDBC-выполнений, не включает полное преобразование результата в DTO. Ошибки и повторы дают отдельные события попыток. При подключённом пуле события также содержат poolBefore и poolConnected: active, idle, pending, total до и после получения соединения. Снимки не атомарны и не доказывают причину ожидания сами по себе. Новых публичных маршрутов для них нет. Блокировки внутри SQL включены в время SQL; для их детализации нужны wait events PostgreSQL.

## Миграция

После rebase на актуальную dev индекс значений темы принадлежит уже выпущенной V18; новая V19 добавляет только индексы кандидатов журнала для определений и значений. Результаты предыдущих этапов ниже относятся к состоянию до rebase, где эти индексы создавались общей V18. Индексы поиска последней ревизии уже существуют и не дублируются. На большой production-БД обычное создание индексов требует окна обслуживания: блокируется запись. Код совместим с прежними индексами; при откате приложения новые индексы можно оставить.

## Приёмка сохранения и клиентской сверки

Набор этого Change использует неизменный синтетический снимок не менее 6600 цветовых
значений. Исходная версия должна содержать production-код актуального `dev`; копируются
только одинаковые измерительные файлы `Performance*.kt`, `ThemeQueryPerformanceTest.kt`
и регистрация задачи `queryPerformance`. Не включайте `performanceLegacy` для актуального
`dev`: его индексы и история Flyway уже входят в исходную схему.

`performanceScenario=color-save` измеряет запись 36 адресов. `addressed-revert` отдельно
измеряет серверную команду 72 адресов и последовательные HTTP-чтения, но не клиентскую
очередь. Для фактического кода клиентской сверки:

1. Соберите оба клиента (требуется установленный `esbuild` из зависимостей клиента):

   ```bash
   node performance/build_editor_acceptance.cjs \
     /path/to/current/js/apps/client /path/to/baseline /tmp/editor-acceptance
   ```

2. Запустите один изолированный сервер с импортом того же снимка:

   ```bash
   DOCKER_HOST=unix:///path/to/docker.sock JAVA_TOOL_OPTIONS=-Dapi.version=1.44 \
   ./gradlew :runtime:queryPerformance -PperformanceNetty=true \
     -PperformanceFixtureImport=/tmp/theme-opt-fixture.dump \
     -PperformanceScenario=client-server -PperformanceOutput=/tmp/editor-current-server.json
   ```

3. В другом терминале после создания JSON с портом и идентификаторами выполните:

   ```bash
   node performance/measure_editor_acceptance.cjs current \
     /tmp/editor-current-server.json /tmp/editor-current-result.json \
     /tmp/editor-acceptance/editor-accept-current.cjs
   ```

Повторите последовательно для `baseline` на другом временном сервере и той же фикстуре.
Измеряются 20 повторов после трёх прогревов: откат 72 адресов, сводка/отметки и настоящие
`EditorSectionData`/`readEditor` (полная сверка dev, адресная — текущая версия). Подготовка
изменений, применение их подтверждений к состоянию клиента и проверка восстановления
всех значений БД и снимка редактора находятся за границами таймера. Исходный клиент
инвалидирует `theme-tokens` с адресами изменений, как `ThemeEditorSession.refreshChanges`,
а не всю оболочку. Для сравнения снимков сортируется только копия `meta.tokens`
по типу и имени: runtime сам сортирует эти метаданные, остальные массивы сохраняются;
дубликаты и все поля продолжают сравниваться.
Скрипт создаёт файл `.stop` рядом с JSON сервера; ручной выход — создать тот же файл.
Сервер ограничен общим таймаутом теста. Сценарий предназначен только для временной
синтетической БД, не для действующих стендов.

Границы проверки: Node HTTP без React render, браузерного gzip и gateway authentication.
Адаптер направляет проектные маршруты во внутренний DS API с тестовыми trusted-заголовками;
аутентификация, проектный DTO и стили заменены тестовыми адаптерами. Логика чтения,
очередь, преобразование ответов и слияние раздела берутся из исходников соответствующего
клиента. Это не заменяет отдельную ручную браузерную проверку очереди и проверки прав.

Чтения проверяются в обоих порядках (dev → текущая → текущая → dev), по 20 запросов каждой
серии после прогрева. Для итоговой медианы объединяются все 40 исходных замеров каждого
варианта, без выбора быстрых серий. `samplesMs` сохраняются в JSON, нормализованные
отпечатки сравниваются для всех маршрутов. Цели берутся из design активного Change;
старый `compare_reports.py` содержит пороги предыдущего Change и не заменяет его критерии.
