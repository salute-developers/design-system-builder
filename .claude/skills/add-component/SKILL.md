Добавление компонента идёт по одному сценарию: инструмент импорта делает предсказуемую часть, ты читаешь его отчёт, принимаешь решения по спорным пунктам и доводишь компонент до превью и пакета. Не пропускай шаги проверки: каждый из них ловил реальные ошибки на TextField.

## Источники

Клон plasma лежит в `~/Documents/work/plasma` (переопределяется `--plasma=` или `PLASMA_DIR`). Перед первым компонентом сессии проверь, что версия `packages/plasma-new-hope/package.json` совпадает по мажору токенов с `@salutejs/plasma-new-hope` в `js/services/generator/package-lock.json`: между версиями меняются ключи токенов.

| Что | Откуда |
|---|---|
| API компонента | `packages/plasma-new-hope/src/components/<X>/<X>.tokens.ts`, объект `tokens` |
| Конфиг оформления | `packages/sdds-serv/src/components/<X>/<X>.config.ts(x)` |
| Аргументы стори | `utils/plasma-sb-utils/src/components/<X>/meta.ts`, иначе `packages/plasma-new-hope/src/examples/components/<X>/<X>.stories.tsx` |
| Имена токенов темы | `js/services/db-service/src/db/seeds/prod/tokens.ts` |
| Значения токенов формы | `js/services/db-service/src/db/seeds/prod/token_values/shape.ts` |

Если токены лежат не в `<X>.tokens.ts` (Tabs, Segment, Typography собраны из подкомпонентов), передай `--tokens=` и `--config=` явно и заводи подкомпоненты как отдельные компоненты. База про нюансы генератора не знает: имена экспортов ядра, если они не `<x>Tokens` / `<x>Config`, и форма обёртки (`castToProps` у Modal, Popup, Tooltip) лежат в манифесте `js/services/generator/app/templates/<X>/component.json`, инструмент пишет его сам; клиент держит зеркало для токенов в `controllers/componentPreview/coreTokens.ts` (Tabs, TabItem, IconTabItem → `tabsTokens`), при новом компоненте с чужим объектом токенов добавь его туда руками. Если у компонента нет объекта токенов вовсе, в модель он не ложится: скажи об этом и остановись.

## Компоненты с несколькими appearance (прецедент Tabs)

В ядре Tabs один компонент, но `orientation` переключает базовый конфиг (`horizontalTabsConfig` / `verticalTabsConfig`), у него дочерние элементы `TabItem` и `IconTabItem`, и все три делят объект токенов `tabsTokens`. В модели это два appearance одного компонента, `horizontal` и `vertical`:

- **Токены, вариации и стили общие** для всех appearance компонента (`variations`, `styles` в ДС).
- **Состав вариаций, их порядок и дефолты — свои у каждого appearance** (`appearance_variations`): у вертикальных Tabs нет `pilled`, дефолт `view` у горизонтальных `filled`, у вертикальных `divider`.
- **Значения и инварианты — свои** (`variation_property_values.appearance_id`, `invariant_property_values.appearance_id`).
- **Проп, по которому обёртка выбирает appearance**, — в манифесте генератора: `appearances: { prop: 'orientation', default: 'horizontal' }`. Имя appearance равно значению пропа, базовый конфиг ядра — `<appearance><X>Config`.
- **Дочерние компоненты** — `component_deps` типа `compose`: в сгенерированном пакете они лежат в папке родителя, с корня экспортируется только родитель.

В сидах это `appearances: [{ name, variations?, defaults?, values, invariants? }]` в `index.ts` компонента и файл `values.<имя>.ts` на каждый appearance (у единственного `default` — просто `values.ts`).

Импорт: `npm run component:import -- --component=Tabs --dir=<sdds>/components/Tabs --tokens=<core>/components/Tabs/tokens.ts [--root=orientation]`. Подпапки папки — appearance, файл `<Appearance><Element>.config.ts` — конфиг элемента в этом appearance; элемент с именем `--component` становится родителем, остальные — дочерними. Инструмент объединяет свойства по всем appearance (тип должен совпадать, шаблон один на свойство) и пишет манифест с `appearances`.

Генератор раскладывает такой компонент как sdds-serv: `Tabs/horizontal/HorizontalTabs.config.ts`, `Tabs/vertical/...`, обёртки `Tabs.tsx`, `TabItem.tsx` с выбором конфига по пропу и пробросом ref, дополнительные файлы из `generator/app/templates/<Component>/` (`TabsController.tsx`).

Стори выбирает базовый конфиг ядра по аргументу стори `orientation` (это не вариация), как обёртка, и рендерит контейнер с элементами.

**Второй вид: один конфиг ядра и выбор пропом `appearance`** (Range: `Range.config.ts` и `Range.clear.config.ts`, обёртка sdds-serv через `createConditionalComponent`). Инструмент видит `createConditionalComponent(` в обёртке и пишет в манифест `appearances: { conditional: true }`; генератор собирает такую же обёртку из тех appearance, что есть в ДС (`<X>.config.ts` для `default`, `<X>.<имя>.config.ts` для остальных). Плоские соседние конфиги инструмент пока не импортирует (только `--dir` с подпапками): у Range заведён только `default`, `appearance="clear"` в пакете не типизируется, а в рантайме ядро откатывается к `default`.

**Клиент** пока показывает и сохраняет первый appearance (`configs[0]`, у Tabs — `horizontal`); остальные appearance сохранение не трогает. Переключателя appearance в интерфейсе нет.

## Шаги

1. **Сухой прогон.** `cd js/services/db-service && npm run component:import -- --component=<X>`. Прочитай отчёт целиком.
2. **Реши спорные пункты.** Раздел «ТРЕБУЕТ РЕШЕНИЯ» обязателен к ответу: неизвестные токены темы задаются через `--alias=<ident>=<token.name>`, соседний конфиг (`X.clear.config.ts`) как второй appearance заводится только через `--dir`, разные значения одного свойства в disabled и readOnly требуют выбора. «ПРИБЛИЖЕНИЯ» и «ПРОПУЩЕНО» просто перечисли пользователю в итоге. Правила ниже.
3. **Применить.** Тот же вызов с `--apply`: инструмент пишет папку `js/services/db-service/src/db/seeds/prod/components/<имя>/` целиком (`index.ts`, `properties.ts`, `variations.ts`, `values.ts`), реестра нет — папки находятся сами. Если импорт нужно повторить после правок (алиас токена, исправление инструмента, обновление ядра), сначала сними папку: `npm run component:import -- --component=<X> --remove --apply`, затем импортируй заново. Прогони `tsc` в контейнере: `docker exec db-service-dev sh -c "cd /home/node/app && npx tsc --noEmit -p ."`.
4. **Сид в базу.** `docker exec db-service-dev npm run db:seed:prod -- --component=<X>`. Сид чистит только этот компонент и только в базовой ДС. Компонент заводится в `base` и больше никуда: в чужие ДС его не копируют — там свои наборы токенов, и лишняя копия расходится с базой при следующем сиде.
5. **Клиент.** Стори `js/apps/client/src/stories/<X>.story.tsx` по образцу `TextField.story.tsx`. Переносить все стори из `packages/sdds-serv/src/components/<X>/<X>.stories.tsx` (Default, Custom*, Vertical и т.д.), а не только Default: `XStories = [XDefault, XCustom]`, имена как в sdds-serv, но первая стори всегда называется `Default`: `useStory` выбирает её по имени, и без неё редактор уходит в бесконечный цикл обновлений (Popup в sdds-serv называет её PopupDemo). Стори строятся: `component(mergeConfig(<x>Config as any, {}))`, аргументы из storybook-подсказки отчёта. Зарегистрируй в `stories/index.ts` и `hooks/useStory.ts`, включи `disabled: false` в `utils/menuItems.ts`. Проверь `npx tsc -b` в `js/apps/client`.
6. **Проверка генератором.** `POST http://localhost:3005/generate-download` с `{"packageName":"base","packageVersion":"0.1.0","exportType":"tgz"}`; в архиве должен быть `styled-components/es/<X>/<X>.config.js`, в логах `ds-builder-generator-dev` не должно быть `SyntaxError`. Legacy-выдача: `GET http://localhost:3008/api/ds/legacy/design-systems/base/component-configs` с заголовком `X-System-Admin: true`.
7. **Итог пользователю.** Что импортировано, какие решения принял сам, что приближено, что пропущено, что осталось.

## Правила модели

- Имя web-параметра свойства равно ключу объекта токенов ядра. Клиент и генератор берут по нему CSS-переменную из `<x>Tokens`; чужое имя даст пустое превью и сломанную сборку пакета. Если объект токенов или базовый конфиг ядра называются иначе (`tabsTokens`, `lineSkeletonConfig`), база об этом не знает: имена лежат в манифесте генератора `templates/<X>/component.json` (`coreTokensExport`, `coreConfigExport`), инструмент импорта читает их из `index.ts` папки компонента ядра и пишет в манифест сам; клиент держит зеркало для токенов в карте `coreTokensByComponent` в `controllers/componentPreview/coreTokens.ts`, её правь руками. Сиды идентификаторов не содержат: ссылки идут именами, id раздаёт сидер.
- Шесть токенов шрифта одной группы становятся одним свойством `typography` с именем `<prefix>Style` и значением вида `body.l.normal`. Если `FontWeight` взят из жирного варианта (`bodyLBold.fontWeight`), группа получает жирный токен `body.l.bold`; идентификаторы `h1…h6` это `header.h*`, `dspl*` это `display.*`. Отдельный `fontWeightSelected` без остальных пяти частей не выражается и пропускается.
- Многозначное CSS-значение (`padding: a b`, `inset`) выражается одним шаблоном web-параметра на свойство, где `$1` получает число стиля. Если меняется больше одного числа, шаблон точен для размера по умолчанию, остальные размеры получают его литералы. Это известное ограничение модели, не ошибка импорта.
- Вариации `disabled` и `readOnly` не вариации: их токены уходят в инварианты, как `disableAlpha` у Button. Состояния в клиенте только `hovered` и `pressed`.
- Аргументы стори не должны совпадать с именами вариаций компонента: превью рендерится только если такой аргумент указывает на стиль. Вариации без дефолта (`hintView`, `hintSize`) в панели вариаций не показываются. Defaults: сначала блок `defaults` конфига темы; для вариаций без значения подставляется `defaults` из `*Config` ядра, если такой стиль есть в теме.
- Радиус сначала сверяется с токенами формы: значение ядра ищется среди web-значений `round.*` из `token_values/shape.ts`. Совпали все значения свойства — заводи `shape` со ссылкой на токен; хотя бы одно не совпало — всё свойство уходит в `dimension`, потому что `shape` без токена темы не выражается. Инструмент делает это сам и пишет исход в отчёт; при ручном разборе проверяй в том же порядке и не начинай с `dimension`.
- Значения `auto`, `100%`, `fit-content`, `pointer`, `url(...)`, transition заводятся свойствами типа `value`: строка уходит в CSS как есть, в превью применяется, в панели свойств пока не редактируется. Одиночные числа типизируются по всем значениям ключа: `0` рядом с `0.25rem` это `dimension`, а не `float`.
- Колонка `platform` (`web | compose | ios`) есть у `appearances` и `properties`. Сидер (`seeds/prod/component-seed.ts`) проставляет `web` сам, в папке компонента её писать не нужно. Legacy-роут и веб-сохранение работают только со строками `platform = 'web'`; нативные appearances (`NULL`) им не видны и не затираются.
- `mergeConfig` ядра заменяет вариации целиком, поэтому частичный перенос конфига недопустим: непрописанный токен не подхватится из ядра.

## Прецеденты первой партии базовых компонентов (сентябрь 2026)

- **Пустой компонент**: в sdds-serv есть обёртка, но конфига темы нет (Image, AvatarGroup) или он без стилей (Price, `view: {}`). Инструмент определяет это сам и заводит только строку компонента, связь с ДС и appearance; генератор для компонента без свойств пишет обёртку `mergeConfig(xConfig)` без локального конфига. Стори собирается через `component(mergeConfig(xConfig as any))`. Если компонента нет в `sdds-serv/src/index.ts` (PaginationDots), заводить его не нужно.
- **Сиды лежат по компонентам**: `seeds/prod/components/<имя>/` описывает компонент данными без идентификаторов — свойства с web-параметрами и вариациями, вариации со стилями и дефолтами, значения по `values[вариация][стиль]`, инварианты, сочетания стилей. Ссылки идут именами (`prop`, `token`, стиль), их разрешает общий сидер. Раньше данные лежали по таблицам в файлах на десятки тысяч строк и правились регулярками по заголовкам — оттуда были поломки соседних компонентов при `--remove`.
- **Ошибка сборки пакета** видна теперь в логе генератора («Package build failed»). Если пусто, выгрузи `exportType: zip`, распакуй в `/home/node/app/result-debug` контейнера генератора, `chmod +x scripts/*.sh` и запусти `npm run build` там.
- **Смешанные значения одного ключа** (`avatarSize: 2rem` рядом с `100%`, `borderRadius: 0.5rem` рядом с `50%`): инструмент сам переводит всё свойство в `value` и пишет об этом в «ПРИБЛИЖЕНИЯ». Стиль удалять нельзя: `mergeConfig` ядра подменяет `variations` целиком. На крайний случай есть `--skip-style=<вариация>.<стиль>`.
- **Реэкспорты `index.ts`** (подкомпоненты, `xClasses`, `xTokens`, провайдеры и типы из `@salutejs/plasma-new-hope/styled-components`, а также локальный `XProps = ComponentProps<typeof X>`): инструмент читает `index.ts` sdds-serv и пишет `reexports: { runtime, types, localTypes }` в манифест. Для уже заведённого компонента манифест пересобирается без сидов: `npm run component:import -- --component=X --manifest --apply`. Имена из других локальных файлов и чужих пакетов в манифест не попадают и поднимаются в отчёт; у Skeleton список правлен руками (ядро не экспортирует LineSkeleton/TextSkeleton).
- **Вложенный компонент в стори берётся из `relatedComponents`, а не собирается из голого ядра.** Превью само собирает связанные компоненты (`component_deps`, любой тип связи) с конфигом темы ДС и отдаёт их готовыми:

  ```tsx
  render: function Story({ relatedComponents, ...args }: any) {
      const { Button } = relatedComponents;
  ```

  Собственные вариации вложенного (`view="clear"`, `size`) работают только так: на сцену превью кладутся значения переменных для выбранных в панели вариаций, и голый компонент ядра всегда получает дефолтный вид. Симптомы, если забыть: белые кнопки вместо прозрачных, неменяющийся размер, белый крестик на белом фоне, StepItem без кружков и линии.

  Рядом с каждым компонентом лежит его конфиг под ключом `<Имя>Config`: он нужен провайдерам ядра (`NotificationsProvider config={...}`) и компонентам с фабричным конфигом (Steps: `stepsConfig(StepItem)` — такой компонент превью собрать не может, стори строит его сама из `StepsConfig` и `StepItemConfig`). Механизм: `createThemeConfig` в `controllers/componentPreview/themeConfig.ts`, рантайм-аналог того, что генератор пишет в `<X>.config.ts`.

- **`args` не разливается в компонент целиком**: служебный проп попадёт в DOM. Разбирай (`const { itemsCount, ...rest } = args`) и передавай `rest`.
- **Кнопка-триггер в сцене не ставится в левый верхний угол**: там переключатель историй. Отступ сверху не меньше `3.25rem`.
- **Повторяющийся ключ внутри стиля**: сначала общая часть (вставка), потом переопределение своим цветом. В CSS побеждает последнее значение, инструмент теперь так и делает. Симптом, если пропустить: все значения вариации выглядят одинаково, переключение вариации ничего не меняет. Проверяй запросом: значения свойства по стилям одной вариации не должны совпадать все разом.
- **Флаг хранится как в ядре: один стиль `true`, без дефолта.** Конфиг sdds-serv описывает у флага только включённое состояние (`pilled: { true }`), выключенное — отсутствие ключа в `defaults`. Стиль `false` не заводится ни инструментом, ни руками: `PropsType` ядра типизирует проп как `boolean` только при ключах вариации ровно `'true'`, с ключом `false` тип становится `'true' | 'false'`, и `<Tabs pilled>` в чужом приложении не компилируется (у TabItem ошибка выглядит как «обязательный `orientation`», потому что подходит только вертикальная ветка). Панель показывает флаг (`Variation.isFlag()`) переключателем: включён — аргумент равен id стиля `true`, выключен — аргумента нет; «по умолчанию» у `true` ставится и снимается через меню стиля. Парный пустой стиль инструмент заводит только у ориентации (`orientation: { vertical }` → `horizontal`), потому что там второй вариант — настоящий конфиг ядра. Под корнем (`orientation`) вариация без значений ни под одним корнем (`truncate` у TabItem) генератор кладёт в конфиг каждого корня, иначе исчез бы её проп.
- **Радиус-«капсула»** (`1000px`, `9999px`) в конфигах — это токен `round.circle`, инструмент считает таким любой радиус от 500px; не заводи его числом в `dimension`.
- **Ссылки на токены ядра внутри значений** (`var(${accordionTokens.accordionItemPaddingVertical}) var(...)`, `0.063rem solid ${surfaceSolidTertiary}`) инструмент переводит в имена CSS-переменных и заводит свойство типом `value` (в панели не редактируется, в пакет и превью уходит как есть). Не раскладывай такое свойство на числа по размерам руками: у Accordion `accordionItemPadding` так потерял вертикальный отступ и обнуление горизонтального в `clear`.
- **`--remove` удаляет только папку названного компонента.** Дочерние компоненты (Counter у SegmentGroup, StepItem у Steps) и связи в `component_deps.ts` не трогаются: связи заданы именами и пропускаются, пока компонента нет, поэтому после повторного импорта продолжают работать без ручного восстановления.
- **Стори дочернего компонента показывает один элемент**, а не весь родитель: свойства самого элемента так видны лучше. Родитель остаётся контейнером (сам элемент не позиционируется), его вид берётся нейтральным. Количество соседей выносится аргументом со значением 1 по умолчанию. Вариации, выбранные в панели на странице элемента (`view`, `size`, `pilled`), уходят элементу, а не родителю. Если стили вариации различаются в основном у выбранного состояния (сегмент, таб), элемент выбирается сразу (`defaultSelected`), иначе переключение вида ничего не меняет на глаз. На странице родителя вид элемента — аргумент стори (`segmentItemView`, как в сторибуке), значение по умолчанию берётся из стори sdds-serv, а не из `defaults` темы.
- **Интерактивность в стори**: компонент с выбором (Steps, Tabs, Segment) хранит состояние в стори и меняет его в обработчике ядра (`onChange` у Steps переключает `active`/`completed`). Без этого превью выглядит статичным.
- **Фрагменты-вставки в конфиге** (`${baseItemView}`, `${accentConfig}` у Steps: строковая константа, которую подставляют в несколько стилей) инструмент не разбирает и пропускает молча. Симптом: у части стилей нет значений, компонент в превью прозрачный. Раскрывай их руками при импорте и сверяй число свойств с числом ключей `tokens.` в конфиге (`grep -o "tokens\.[a-zA-Z]*" <X>.config.ts | sort -u | wc -l`).
- **Объект токенов ядра под подкомпонент может не существовать**: у StepItem, SegmentGroup, Body ядро экспортирует только общий `stepsTokens`, `segmentTokens`, `typographyTokens`. Кроме манифеста генератора, добавь компонент в карту `controllers/componentPreview/coreTokens.ts` клиента, иначе превью вычислит имена переменных неверно и компонент останется без стилей.
- **Подкомпоненты в одной папке sdds-serv** (Segment → SegmentGroup/SegmentItem, Steps → StepItem, Typography → Body/Dspl/Heading/Text): каждый заводится отдельным компонентом с `--dir-name=<папка> --config=<файл> --tokens=<файл>`; общий объект токенов уходит в манифест. Несколько конфигов в одном файле (Typography `configL…`) склеиваются в одну вариация, дефолт задаётся `--default=size=m`.
- **Соседи без конфига темы в той же обёртке** (ToolbarDivider, DrawerContent/Header/Footer) инструмент пишет в `siblings` манифеста, генератор кладёт им пустые обёртки рядом.
- **Обёртка, которую нельзя вывести из данных** (Toast с HOC, Notification с провайдером, Steps с фабрикой конфига `stepsConfig(StepItem)`): файл `templates/<X>/<X>.tsx` подменяет сгенерированную обёртку, её локальные экспорты попадают в `reexports.local`. Прочие файлы в `templates/<X>/` (BodySizes.tsx с BodyL…BodyXXS) экспортируются из index.ts через `export *`.
- **`intersections` в конфиге** (Steps: значения на пересечении view × itemView) не переносятся: таблица `style_combinations` есть, но инструмент их не заводит и клиент не показывает. В отчёте это «ПРОПУЩЕНО».
- **Дженерик-обёртка** (Select, Combobox, Dropdown: `fixedForwardRef`, тип элемента списка): инструмент читает `propsType`, `itemType`, `refElement` из `<X>.tsx` sdds-serv в `generic` манифеста, генератор пишет `.tsx` с `DistributiveOmit`/`DistributivePick` и списком вариаций из конфига. Типы из корня `@salutejs/plasma-new-hope` (`SelectItemOption`) уходят в `reexports.coreTypes`.
- **Шрифтовые группы с разнобоем имён** (`fontFamily` рядом с `fontLetterSpacing` у Select, нет `itemFontWeight` у Dropdown) инструмент склеивает сам; `${bodyL.fontWeight}` внутри значения переписывается в `var(--plasma-typo-body-l-font-weight)`.
- **Компонент, собранный или поправленный в интерфейсе билдера, закрепляется в сидах выгрузкой**: `docker exec db-service-dev npm run db:seed-generate:prod -- --component=<X>` переписывает его папку по состоянию базы (без `--component` — все компоненты `base`). Проверка любых правок сидера и формата — полный сид на пустую базу и сверка с эталонной выгрузкой по именам, а не по идентификаторам.
- **Cast-обёртка** (`component(...) as ForwardRefExoticComponent<XProps & RefAttributes<HTMLDivElement>>` у Tooltip, Modal, Popup): инструмент читает приведение из `<X>.tsx` sdds-serv и пишет `castToProps` в манифест; генератор берёт тип из `@salutejs/plasma-new-hope/styled-components`, не из локального index.ts. Modal и Popup в стори позиционируй через `frame={ref}` на контейнер внутри сцены превью, иначе портал в body уводит их из-под переменных темы.
- **Вариация без дефолта** ни в теме, ни в `defaults` ядра (Pagination `type`): инструмент берёт стиль `default`, если он есть, и пишет об этом в «СПРАВКА». Без такого стиля вариация остаётся без дефолта и в панели превью появляется только после выбора в списке вариаций.
- **Стили с пометкой deprecated** (`// deprecated` или JSDoc `@deprecated` перед стилем в конфиге sdds-serv, как `view.primary` у Progress) инструмент не переносит и пишет в «ПРОПУЩЕНО». Решение пользователя: устаревшим стилям в ДС делать нечего.
- **Литералы цвета** (`#F3A912`, `rgba(...)`) заводятся как значение цвета без токена, генератор и клиент отдают их в CSS как есть.
- **Тени** `${shadowDownHardM}` из sdds-themes сопоставляются токену `down.hard.m` автоматически.
- **Составные значения с идентификаторами темы** (`color-mix(in srgb, ${textPrimary}, …)`, `calc(var(${tokens.x}) …)`) переписываются: идентификаторы темы в CSS-переменные, локальный алиас `tokens` в настоящее имя экспорта ядра. Иначе linaria падает на сборке пакета.
- **Ключи, которых нет в ядре `latest`** (Rating `iconSizeLarge` на ветке `dev` plasma) уходят в «ПРОПУЩЕНО»: это дрейф версий, а не ошибка.
- **Описание компонента** берётся из JSDoc над `export const <X>` в обёртке sdds-serv.
- **Стори с дочерними компонентами** (ButtonGroup, ChipGroup, TextFieldGroup, Popover, Sheet) собирают детей из ядра тем же `component(mergeConfig(childConfig as any, {}))`. Чтобы ребёнок в превью получил свою тему, заведи связь `reuse` в `seeds/prod/component_deps.ts` (родитель → ребёнок) и бери ребёнка из `relatedComponents` (см. выше): переменные на сцену для `reuse` не кладутся, ребёнок получает полный конфиг темы, и разные view/size у детей в одной стори работают.

## Когда не использовать инструмент

У компонента нет объекта токенов ядра (тогда он в модель не ложится, см. «Источники»), или конфиг написан не в форме `variations: { axis: { style: css\`...\` } }`. Тогда разбирай руками по тем же правилам и создавай папку `seeds/prod/components/<имя>/` в том же формате, что пишет инструмент (образец — `textField/`); типы формата описаны в `seeds/prod/component-seed.ts`.
