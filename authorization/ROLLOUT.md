# Развёртывание политики авторизации

## Совместимость и миграция ключей

В этом релизе доступ Documentation Service для ключей проекта становится явным. Существующие ключи не изменяются: Owner
или Maintainer должен перевыпустить их с минимально необходимыми областями доступа:

- `documentation:read` — для клиентов публикаций, навигации, страниц, привязок, ресурсов, поиска и `kb/fetch`;
- `documentation:write` — для клиентов, загружающих пакеты документации;
- обе области — только если одна и та же автоматизация читает и загружает документацию.

Нужно провести инвентаризацию активных учётных данных CLI/MCP вне системы контроля версий, создать заменяющие ключи,
обновить используемое хранилище секретов, проверить новые ключи и затем отозвать старые. Нельзя автоматически добавлять
области доступа к документации в существующие строки базы данных.

## Порядок развёртывания

1. Развернуть Projects Service с версией политики `2026-09-22.2` и проверить, что он принимает обе области доступа к
   документации.
2. Перевыпустить и развернуть затронутые учётные данные CLI/MCP с минимально необходимыми правами.
3. Развернуть Documentation Service и проверить, что в его журнале указаны те же версия политики и SHA-256, что и у
   Projects Service.
4. Проверить Viewer, Editor, Owner, `system_admin`, ключ только для чтения, ключ для записи, ключ без областей доступа к
   документации и ресурс чужого проекта.

Оба образа для рабочей среды содержат `/app/authorization/policy.json` и по умолчанию задают
`PROJECT_AUTHORIZATION_POLICY_PATH` на этот файл, доступный только для чтения. Локальные JAR со всеми зависимостями
используют ту же политику, встроенную модулем `authorization-core`; переменная окружения с внешним путём переопределяет
встроенный файл. Отсутствие или некорректность настроенного файла прерывает запуск, поэтому проверка готовности остаётся
отрицательной, а переход на разрешающую политику не выполняется.

## Откат

Сначала следует откатить Documentation Service. Новые области доступа останутся допустимыми непрозрачными значениями для
старых потребителей, а откат данных не потребуется. Projects Service и каноническую политику можно оставить
развёрнутыми. Заменяющие ключи следует отзывать только при намеренном возврате старых учётных данных.
